# 仓库知识树：约定

这里是 NarraFork 仓库自己的知识：按主题组织，描述**当前代码实际怎么工作**。它跟代码一起放在仓库里、一起提交、一起评审、一起合并：某个提交上的知识，描述的就是这个提交上的代码。

## 放什么，不放什么

放：
- 一块功能是干什么的、边界在哪。
- 代码实际遵守的规则和约束（不变量、上限、顺序、失败时怎么办），以及在哪里能看到它们被执行。
- 关键入口：从哪个文件、哪个函数开始读。
- 和其他部分的关系。

不放：
- 进行中的任务、计划、谁在做什么。这些在会话和团队工作项里，不在这里。
- 过程：怎么调查出来的、试过什么。
- 从 `docs/` 或代码注释里抄来的说法。见下一节。

## 事实从哪来

**只以代码为准**：函数实现、表结构、路由、测试。

- `docs/` 下很多文件已经过时，代码注释也可能偏颇或过时。它们只能当线索：读到一个说法，要回到实现和测试里核实；核实不了就不写。
- 测试是好证据：一条规则有测试守着，说明它是真的。
- 写不确定的东西时明说「未核实」，不要把推测写成事实。

## 结构

- 目录就是层次。有下级的节点是一个目录加 `index.md`；叶子节点是一个 `.md` 文件。
- 顶层按主题分，不照搬代码目录。顶层只由人或整理者调整。
- 每个文件开头是这样的头部：

```yaml
---
id: narrator.messages        # 稳定 ID：文件移动、改名时不变，链接用它
title: 消息存储
summary: 一行话说清这个节点讲什么
anchors:                     # 这个节点依据的代码（文件、目录或 glob），必须真实存在
  - server/services/narrator-messages.ts
status: stub                 # stub（待填）/ draft（已填，未复核）/ verified（复核过）
verified_at: null            # 最近一次按代码核对时的提交
---
```

## 正文

叶子节点按这几段写，没有内容的段可以省略：

```markdown
# 标题

一两句话：这是什么、为什么存在。

## 关键规则
- 规则（`文件:函数` 或 `文件:行`）

## 从哪读起
- `文件`：它负责什么

## 相关
- [其他节点](相对路径)
```

有下级的节点（`index.md`）写这一块的整体：由哪几部分组成、它们怎么配合，然后列出下级。

篇幅：第一版每个叶子 15–40 行。宁可短而准确，也不要长而含糊。

## 什么时候更新

- 代码改动合并前，在同一个 PR 里更新受影响的节点：锚点覆盖到改动路径的节点要核对一遍。
- 新功能需要新节点时，加在最合适的主题下；放不进现有主题，就提出来，不要随手加顶层。
- 节点和代码不一致时，以代码为准改节点，并更新 `verified_at`。
