# 仓库知识树：约定

这里是 NarraFork 仓库自己的知识：按主题组织，描述**当前代码实际怎么工作**。它跟代码一起放在仓库里、一起提交、一起评审、一起合并：某个提交上的知识，描述的就是这个提交上的代码。

## 放什么，不放什么

放：
- 一块功能是干什么的、边界在哪。
- 代码实际遵守的规则和约束（不变量、上限、顺序、失败时怎么办），以及在哪里能看到它们被执行。
- 关键入口：从哪个文件、哪个函数开始读。
- 和其他部分的关系。

不放：
- 进行中的任务、计划、谁在做什么。这些在会话和团队工作项里，不在这里。
- 过程：怎么调查出来的、试过什么。
- 从 `docs/` 或代码注释里抄来的说法。见下一节。

## 事实从哪来

**只以代码为准**：函数实现、表结构、路由、测试。

- `docs/` 下很多文件已经过时，代码注释也可能偏颇或过时。它们只能当线索：读到一个说法，要回到实现和测试里核实；核实不了就不写。
- 测试是好证据：一条规则有测试守着，说明它是真的。
- 写不确定的东西时明说「未核实」，不要把推测写成事实。
- 常量名、函数名和注释都不算核实：要追到值或函数实际被用到的地方。几次搜索能查清的，查清再写，不要先标「未核实」。
- 有分支的规则（错误码、接收人集合、存储层、启用条件）每个分支单独写一行，不要压成一句「分别……」。抽查发现，压缩分支是出错最多的地方。

## 结构

- 目录就是层次。有下级的节点是一个目录加 `index.md`；叶子节点是一个 `.md` 文件。
- 顶层按主题分，不照搬代码目录。顶层只由人或整理者调整。
- 每个文件开头是这样的头部：

```yaml
---
id: narrator.messages        # 稳定 ID：文件移动、改名时不变，链接用它
title: 消息存储
summary: 一行话说清这个节点讲什么
anchors:                     # 这个节点依据的代码：文件、小目录或 glob，必须真实存在
  - server/services/narrator-messages.ts
keywords:                    # 别人会拿来搜的词：界面上的叫法、路由、设置键、错误码、表名、工具名
  - 消息分页
  - narrator_message_refs
status: stub                 # stub（待填）/ draft（已填，未独立复核）/ verified（已独立复核）
verified_at: null            # 内容最近一次对照代码写成或核对时依据的提交
---
```

状态含义：
- `stub`：只有头部，待填。
- `draft`：依据代码写成，但没有经过独立复核。
- `verified`：由独立的复核者对照代码检查过。

`verified_at` 记的是内容最近一次对照代码写成或核对时依据的提交；它不等于状态是 `verified`。

### 锚点

锚点决定两件事：改某个文件时能不能找到这个节点，以及代码变了这个节点会不会被标成过期。所以：

- 锚点指向节点里的说法实际依据的文件。功能节点要锚住它的整条纵线：服务、路由、校验器、共享类型、前端组件和 API 客户端，不只是服务端。
- 一个锚点匹配的源文件不超过 40 个（`check` 会报）。太宽的锚点会让节点在任何改动后都显示过期，也会让按路径查找总落到它身上。
- 总览节点（`index.md`）只锚入口文件，不锚整个目录。
- 一个大文件被很多节点共用时，可以写成 `path#符号名` 说明依据的是哪个函数；目前按文件判断过期，符号只是提示。

### 关键词

`keywords` 写别人会拿来搜的词：界面上的中文叫法、英文标识符、路由（`/api/...`）、设置键、错误码、表名、工具名。正文里已经有的标题词不用重复。

## 正文

叶子节点按这几段写，没有内容的段可以省略：

```markdown
# 标题

一两句话：这是什么、为什么存在。

## 关键规则
- 规则（`文件:函数` 或 `文件:行`）

## 从哪读起
- `文件`：它负责什么

## 改它时
- 改这一块时必须一起改的地方、会拦你的守卫测试（只写代码里查得到的）

## 相关
- [其他节点](相对路径)
```

「改它时」写给要动这块代码的人：加一个同类东西要改哪几处（例如加一个工具：注册表、权限分类、测试），哪些守卫测试会失败，哪些不变量不能破。只写从代码和测试里查得到的。

有下级的节点（`index.md`）写这一块的整体：由哪几部分组成、它们怎么配合，然后列出下级。

篇幅：第一版每个叶子 15–40 行。宁可短而准确，也不要长而含糊。

## 改功能时怎么用

工具：`bun scripts/knowledge.ts`。

1. **动手前定位**：`find <词…|路径>`。词可以是界面叫法、标识符、错误码；路径可以是要改的文件或目录。顺着结果读节点和它的「改它时」，再按锚点读代码。跨好几块的改动先看[核心流程](flows/index.md)。结果前标「过期」的节点，说明它的代码在它之后改过，读时以代码为准。
2. **改完、合并前**：`affected [基线]`（默认 `origin/main`）列出这次改动碰到锚点的节点，在同一个 PR 里逐个核对并更新，更新 `verified_at`。它还会列出没有任何节点覆盖的改动文件：要么给合适的节点加锚点，要么新建节点。
3. **提交前**：`check` 检查头部、ID、锚点、链接和下级列表，必须通过。

## 怎么保持新鲜

- **过期按 git 判断**：一个节点在它最后一次提交之后，只要有提交改了它的锚点，就算过期（`stale` 列出全部）。节点和代码在同一个提交里一起改，就不算过期。这个判断只看 git，任何分支、任何 worktree 都一样。
- **覆盖率**：`coverage` 给出有节点锚定的源文件比例和缺口最大的目录，用来发现没有节点的功能。
- 新功能需要新节点时，加在最合适的主题下；放不进现有主题，就提出来，不要随手加顶层。
- 节点和代码不一致时，以代码为准改节点。
