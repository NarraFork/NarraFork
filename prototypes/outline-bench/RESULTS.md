# 大纲 P0 性能基准：结果

对应 `docs/OUTLINE_KNOWLEDGE-DESIGN.md` §2.5、§3.2、§5.3、§7.1、§7.2 和 D10。代码和复现方法见 [README.md](./README.md)，每次运行的原始数字在 `results/*.json`（含 EXPLAIN 计划）。

## 0. 结论速览

**基准一：按时间点读取。能保持视口级延迟，但表要加一个冗余列，索引要选对。**

- 推荐：版本行上冗余 `page_id`，建 `(page_id, from_seq, to_seq)` 索引（下称 B2/B3）。页@T（约 1850 个存活块、含正文）在 1.1 M 版本行上：SQLite p50 4.6–4.9 ms / p95 8.1–8.3 ms，PostgreSQL p50 5.6–6.1 ms / p95 10.4–10.5 ms。500 块视口 p95 约 9–10 ms。
- 历史变长到 30 个版本/块（330 万行，最热的页 15 万个版本）：页@T p95 仍是 10.9 ms（SQLite）/ 10.2 ms（PG）；视口 p95 11.3 / 8.7 ms。增长大致线性，斜率很小（p50 3.1 → 4.6 → 7.3 ms 对应 3 → 10 → 30 版本/块）。
- 只靠 `parent_id` 递归还原（A）整页比 B 慢 3.5–5 倍（p50 18–29 ms，A1 的 p95 58 ms），时间轴框选慢 1–3 个数量级（40–50 ms 对 0.01–3 ms），冷读 228 ms。但"取前 500 块"这一件事 A 做得和 B 一样快（5 ms），而且不随页大小变。
- 满足 §7.2 的上限：视口 500 块、整页 2000 块、提交列表 200 条/页、单个提交增量，全部在主线程可接受的范围内（热缓存 p95 ≤ 11 ms；5000 个提交的框选约 1100 条事件，p95 18–26 ms）。1 万块的页整页读取 p95 31–42 ms，应该放到只读 db-worker，或者用"先读结构、再读正文"的两步法（p95 15–20 ms）。
- 冷读（操作系统缓存清空，真正读盘）慢一个数量级：B 的整页 p50 38–50 ms，p95 65–125 ms；A 的整页 p50 约 225 ms。这是首次打开很老的时间点的代价，之后的拖动走增量，不受影响。

**基准二：db-worker 里暴力扫描向量。常驻内存 + int8 量化 + WebAssembly SIMD 就够到百万级；每次从 SQLite 读只适合十万级候选。**

- 常驻 worker 内存，int8，wasm SIMD 内核，1024 维，100 万向量：目标空间占 10%（连续存放）p50 25 ms / p95 46 ms，空间标签/id 列表（物理上不连续）p95 71 ms，整个矩阵扫一遍 p50 230 ms / p95 268 ms。768 维约快 1/4。
- 同样的数据，纯 JS 内核慢 3–4 倍（10% 过滤 p95 152 ms，全量 p95 1066 ms），float32 比 int8 在 wasm 里慢 2.4 倍且内存 4 倍（100 万 × 1024 维 = 4.1 GB，加载时峰值 8 GB）。
- 200 ms 预算下"候选数"上限（按 100 万向量处的 p95 线性外推）：常驻 wasm int8 约 28–76 万（取决于是否连续和维度），常驻 JS 约 12–20 万，每次从 SQLite 重读约 2–12 万（取决于表设计）。
- 设计文档 §7.1 的 `outline_embeddings` 表（按 `(model_id, content_hash)` 存，空间要靠和块表 join）是最慢的读法：总量 20 万向量（10% 过滤，2 万个候选）p95 就到 174–234 ms，已经逼近或超过预算。向量要另存一张按 `(space_id, chunk_no)` 打包的表。
- int8 对 float32 的召回：@10 约 0.98、@50 约 0.99；对 int8 的前 200 名用 float32 重排后是 1.000。

**什么时候必须换扩展**：见 §3.4。简单说：单次查询的候选数超过 50–70 万（int8、1024 维、wasm），或者常驻内存超过 1–2 GB 不可接受，或者要在 PG 里直接做库内检索时。注意 sqlite-vec 目前也是暴力扫描（据我所知，没有 ANN 索引，未在本机验证），换它本身不会带来量级提升；真正突破暴力扫描上限的是 pgvector 的 HNSW。

**对设计文档的修改建议**：见 §4。

| id | 21 字符 nanoid 文本，和仓库一致 |
| 页成员表（C 方案用） | 137,021 行 |

数据规模对应用户要求的 "50 页 × 2000 块 = 10 万块、约 100 万版本、约 20 万提交"（实际 11 万块 / 110 万 / 19.5 万，多出来的是那一页 1 万块的大页，用来回答 §11 第 6 条超长页）。

### 2.2 比较的设计

| 编号 | 做法 | `outline_block_versions` 上的索引 |
|---|---|---|
| A1 | 只靠 `parent_id`，在时刻 T 递归还原子树 | `(parent_id, from_seq)`，过滤 `to_seq IS NULL OR to_seq > T` |
| A2 | 同上 | `(parent_id, from_seq, to_max)`，`to_max` 是 `to_seq` 的 NOT NULL 哨兵版本 |
| B1 | 版本行冗余 `page_id`，按页过滤 | `(page_id, from_seq)` |
| B2 | 同上 | `(page_id, from_seq, to_seq)`，`to_seq` 保持 NULL 表示当前版本 |
| B3 | 同上 | `(page_id, from_seq, to_max)` |
| B4 | 同上，仅 PG | GiST `(page_id, int8range(from_seq, to_seq))`（btree_gist） |
| B5 | 同上，结构与正文分两步 | 覆盖索引 `(page_id, from_seq, to_max)`+`INCLUDE(deleted, block_id, parent_id, order_key)`（SQLite 里是同样列的复合索引）；先只读结构，再按需读 500 块正文 |
| C | 版本行不冗余 `page_id`，另建 `outline_page_members(page_id, block_id, from_seq, to_seq)` 区间表 | 成员表 `(page_id, from_seq, to_max)` |

所有设计都有主键 `(block_id, from_seq)` 和 `(commit_id)`，提交表有 `(space_id, seq)` 唯一索引。

### 2.3 结果（热缓存，p50 / p95，毫秒）

**Q2：某一时刻整页（2000 块页，约 1850 个存活块，含正文）**

| 设计 | SQLite | PostgreSQL |
|---|---|---|
| A1 parent 递归 | 22.3 / 58.0 | 29.1 / 58.3 |
| A2 parent 递归（覆盖过滤） | 18.0 / 23.8 | 21.4 / 31.0 |
| B1 `(page_id, from_seq)` | 5.8 / 23.1 | 8.1 / 27.0 |
| **B2 `(page_id, from_seq, to_seq)`** | **4.9 / 8.3** | **5.6 / 10.4** |
| **B3 `(page_id, from_seq, to_max)`** | **4.6 / 8.1** | **6.1 / 10.5** |
| B4 GiST 区间（PG） | - | 7.6 / 12.5 |
| B5 覆盖结构索引（读全列） | 5.1 / 9.3 | 4.3 / 8.4 |
| C 页成员表 | 12.3 / 16.9 | 12.2 / 18.2 |

1 万块的页：

| 设计 | SQLite | PostgreSQL |
|---|---|---|
| A1 / A2 | 125 / 193；98.8 / 121 | 133 / 178；110 / 151 |
| B1 / B2 / B3 | 27.1 / 41.5；21.1 / 27.3；22.5 / 31.2 | 33.5 / 54.4；28.9 / 42.8；26.4 / 37.8 |
| B5 | 25.3 / 36.2 | 17.4 / 25.5 |
| C | 62.2 / 80.1 | 61.0 / 87.3 |

要点：

- 关键是把结束边界放进索引（B2/B3 对 B1）：B1 要回表判断 `to_seq`，p95 差 3 倍。NULL 和哨兵没有区别（B2 对 B3：SQLite 4.9 对 4.6 ms，PG 5.6 对 6.1 ms），所以设计里 `to_seq` 保持 NULL 表示当前版本即可，不必改成哨兵。
- PG 的 GiST 区间索引没有比 btree 好（7.6 对 6.1 ms），建索引慢 20 多倍（110 万行上 27.8 s 对 1.1–1.3 s），体积 3 倍，写入更慢（200 块提交 87 对 59 ms）。不值得。
- PG 里 B3 的服务器端执行只有 1.2 ms（EXPLAIN ANALYZE），客户端测得 6.1 ms：其余是把 1850 行 × 约 400 字节正文传回来并解码。去掉正文列，p50 降到 3.2 ms；只读结构（B5，索引内扫描）1.7 ms。说明 PG 上的成本主要在行物化，不在查询。
- A 方案每个节点一次索引探测，加上热点块的几百个版本都要扫，波动大（A1 p95 是 p50 的 2.6 倍）。
- C 方案（页成员区间表）整页比 B 慢 2–2.7 倍：要对每个成员块再做一次按 `(block_id, from_seq)` 的反向探测。它的好处是跨页移动不用重写后代版本，见 §2.5。

视口（B3，读整页取 500）：SQLite 3.4 / 5.9 → 5.7 / 9.1 → 7.7 / 11.3，PG 3.7 / 5.8 → 5.9 / 10.2 → 5.6 / 8.7。

时刻的位置（早/中/晚）影响很小：B3 SQLite 10 版本/块，页@T p50 3.6 / 5.0 / 6.0 ms。PG 在 30 版本/块档比 10 版本/块还略快，是执行计划和噪声的缘故，不要读成"变长反而更快"。页版本行数最多的那页（15 万行）也包含在这些样本里。

粗略外推：B3 的成本约等于页的版本行数（索引扫描 + 过滤），斜率约 0.13 ms 每增加 1 个"版本/块"（30 版本/块以内）。到平均 100 版本/块，页@T 预计 p95 在 25–30 ms 量级（外推，没测）。

| 设计 / 查询 | SQLite 冷 p50 / p95 | PG 冷 p50 / p95 | 同一查询再跑一次（SQLite，热） |
|---|---|---|---|
| B3 页@T | 49.6 / 123 | 38.4 / 65.0 | 4.7 / 7.7 |
| B3 视口 500 | 43.2 / 73.6 | 42.0 / 66.9 | 5.5 / 9.8 |
| B5 只读结构 | 4.5 / 12.3 | 5.8 / 19.0 | 1.4 / 3.2 |
| B5 两步视口 | 63.4 / 86.3 | 50.9 / 70.4 | 6.4 / 12.4 |
| A2 页@T | 228 / 339 | 223 / 271 | 21.7 / 32.6 |
| A2 视口 500（递归停在 500 行） | 70.9 / 120 | 50.7 / 65.7 | 4.5 / 8.5 |
| C 页@T | 138 / 227 | 132 / 173 | 10.0 / 14.8 |

冷读慢是因为每个存活块的行散落在不同的页上（版本行按时间顺序追加，一页的存活块来自整个历史），要读上千个随机块；这台虚拟机上约 30 µs 一个。"只读结构"走覆盖索引、物理上连续，所以冷读也只要 4–6 ms，可以先把大纲结构画出来，正文再补。B5 的两步法冷读反而比一次读完更慢（500 次按主键的随机读），不适合冷读。

**SQLite 大缓存对照**（2 GB 缓存 + 4 GB mmap，其余相同）：A2 页@T 12.3 / 17.1，B3 3.7 / 7.7，B5 4.2 / 7.1，C 8.1 / 11.9；1 万块页 B3 17.7 / 25.8。也就是说默认的 16 MiB 缓存下 B3 的热读大约慢 25%。

SQLite 单块提交约 0.08 ms（WAL + synchronous=NORMAL，不 fsync）；PG 单块提交约 1 ms，由 WAL fsync 主导，各索引集差别在噪声内（见下）。200 块提交在 PG 里是 1000 条语句的往返，真实实现应该批量插入，这里的绝对值偏高，只看相对：GiST 最贵。SQLite 里 A 的 `parent_id` 索引在 200 块提交上比 `page_id` 索引慢 1.5–3.5 倍（推测：新条目散落在随机的叶子页上，而 `page_id` 前缀只有 51 个取值，写入集中在末尾；没有进一步验证）。PG 单块提交里 C 和 B1/B2 的 p95 出现 4–7 ms，语句相同，来源不明，按噪声处理。

### 2.4 结论

**是否满足 §7.2 的上限**

| §7.2 项 | 结果 |
|---|---|
| 按时间点读取，单个视口 500 块 | 满足。B2/B3 热缓存 p95 9–10 ms（SQLite / PG），30 版本/块下 11 / 9 ms；冷缓存 p95 约 70 ms |
| `OutlineRead` 单次 2000 块 | 满足。整页 p95 8–10 ms（热）；冷 65–125 ms |
| 时间轴提交列表，每页 200 条，游标分页 | 满足。p95 ≤ 2.2 ms（含按页过滤） |
| 单个提交的增量下发 | 满足。相邻提交的增量 p95 ≤ 0.3 ms；5000 个提交的框选（约 1100 条事件，含正文）p95 18–26 ms |
| 单页块数 1 万 | 可以存、可以读，但整页@T p95 31–42 ms（热）、冷读未测。超过主线程"小而快"的界线，要放到 db-worker 或分批 |

**推荐的表设计和索引**

- 版本行冗余 `page_id`（B 方案）。要同时遵守两条写入不变量：删除子树时给每个后代写墓碑（否则按页过滤会看到被删子树里的孤儿）；跨页移动子树时给每个后代写新版本（本数据集里这类行占 0.4%，4614 / 1,100,015）。
- 索引：主键 `(block_id, from_seq)`；`(page_id, from_seq, to_seq)`（页@T、增量、按页的提交列表都用它）；`(commit_id)`（撤销、提交详情）。`to_seq` 保持 NULL。
- 加 `change_flags` 列。
- `order_key` 在 PG 里必须用二进制排序（`COLLATE "C"`），否则本地化排序会和 JS 的字符串比较不一致。
- 页的当前态表 `outline_blocks` 也要 `page_id` 和 `(page_id)` 索引，否则"现在"的整页读取也只能递归。
- 不要：只有 `(page_id, from_seq)`（p95 差 3 倍）；GiST；`outline_page_members`（慢 2.5 倍，只在跨页移动非常频繁时才值得）。

**A 方案还有用的地方**：只要"从这个块往下取前 500 块"，A2 递归在 500 行处停止，成本是 3–5 ms 且不随页大小变化（1 万块页也是 3.5 ms）。但它需要再建一个 `(parent_id, from_seq, to_max)` 索引，整页、框选、冷读都差很多。P1 不需要，页内聚焦子树从整页结果在内存里截取（2000 块以内）就够；1 万块的页可以考虑 B5 两步法。

### 2.5 注意事项和局限

- 版本行里每个版本存全文。同一个块反复"只移动、不改内容"也会复制正文。把正文按 `content_hash` 拆成独立表可以让版本行很小，但读时多一次 join；没有测。
- B 方案的本页时间轴看不到"块被移到别页"：移走那一刻的新版本属于别页。要么给 `outline_page_members` 式的成员区间（C），要么在写跨页移动时在原页补一条标记。没有实现，也没有测。
- 数据集里最热的块有 1637 个版本（30 版本/块档 5.6 万个），页热度也不均匀，所以 p95 已经包含热页。真实的热点分布可能更尖。
- 冷读数字来自这台虚拟机的磁盘（每行约 30 µs），NVMe 笔记本会更快，网络盘会更慢。
- 没有测并发写入时的读取，没有测 SQLite 的 WAL 检查点对读的影响，没有测 FTS 并存时的缓存挤占。
- Windows / macOS 上 `bun:sqlite` 的行为（系统自带 SQLite、mmap 实现）没测。

## 3. 基准二：db-worker 里暴力扫描向量

### 3.1 设置

- Bun Worker。向量合成：聚类中心 + 噪声，L2 归一化，所以内积就是余弦。10 个空间，第 i 个块属于空间 i % 10，所以目标空间正好占 10%。top-K = 50。
- 规模 5 万 / 20 万 / 100 万，维度 768 / 1024，int8（对称量化，每向量一个 float32 缩放）对 float32。
- 常驻：整个矩阵在一个 `WebAssembly.Memory` 里，JS 内核和 wasm SIMD 内核扫同一份字节。过滤有四种：连续区间（按空间聚在一起存放）、逐向量空间标签、id 列表、不过滤（100%）。后三种对应"向量在内存里是按到达顺序散着放的"。
- 每次从 SQLite 读：worker 里开只读连接，每个查询读候选向量并在 JS 里打分。三种表：`r2`（`WITHOUT ROWID`，主键 `(space_id, block_id)`，一向量一行）；`r3`（按 `(space_id, chunk_no)` 打包，512 个向量一行）；`r1`（设计文档的样子：`blocks(space_id, content_hash)` join `embeddings(model_id, content_hash, vector_blob)`）。
- wasm 内核：`kernels.c`（clang 18，`-msimd128`，5 KB），int8 用 `i16x8.extmul` + `i32x4.extadd_pairwise`，float32 用 `f32x4`。每次查询 100 个，前 3 个预热；慢的配置在 20 秒预算内至少 12 个。JS 和 wasm 内核的结果逐查询比对，全部一致。
- 延迟是主线程发出请求到收到结果的往返，包含 postMessage；worker 内部的扫描时间比往返只少 0.2–0.3 ms。

### 3.3 观察

1. wasm SIMD 对 int8 的加速是 3.5–6 倍（20 万 × 768：区间扫描 3.6 对 14 ms，全量 36 对 144 ms）；对 float32 只有约 2 倍，因为 float32 已经被内存带宽卡住。JS 里 int8 比 float32 没有明显更快（JS 没有 SIMD），只省内存。
2. 向量在内存里是否按空间连续存放很重要：int8 下标签/id 列表的方式比连续区间慢 2.3–3 倍（20 万 × 768：10 对 3.6 ms；float32 只慢 1.2–1.3 倍），推测是每个候选都是一次缓存/TLB 未命中，没有用 perf 验证。工程上把向量按 `(空间, 页)` 排序存放，新写入的先放在末尾的小段，后台合并。
3. 每次从 SQLite 读的代价主要在"取行"而不是打分。设计原样的 join（r1）比聚簇表（r2）慢 2–4 倍，比打包表（r3）慢 4.5–7 倍；r1 要为每个候选做一次随机的主键探测。打包表是最快的读法（100 万 × 1024 int8 只读 59 ms）。
4. 内存：100 万 × 1024 维的 int8 是 1.0 GB，float32 是 4.1 GB。float32 不适合常驻。

### 3.4 回答：多大规模以内暴力扫描够用

按 p95 ≤ 200 ms（§7.2），**候选数**（过滤之后真正要打分的向量数）从 100 万向量处的实测线性外推：

| 方式 | 1024 维 int8 | 768 维 int8 | 1024 维 float32 |
|---|---|---|---|
| 常驻 + wasm，连续区间 | 43 万 | 76 万 | 25 万 |
| 常驻 + wasm，散放（标签 / id 列表） | 28 万 | 30 万 | 20 万 |
| 常驻 + wasm，整个矩阵（不过滤） | 75 万 | 100 万 | 31 万 |
| 常驻 + 纯 JS，连续区间 | 13 万 | 20 万 | 13 万 |
| 每次从 SQLite 读，r3 打包 | 9.5 万 | 12 万 | 4 万（按 20 万外推） |
| 每次从 SQLite 读，r2 聚簇行 | 5 万 | 8 万 | 3 万 |
| 每次从 SQLite 读，r1 设计原样 | 2 万 | 2 万 | 2 万 |

目标空间占 10% 时，"总向量数"是候选数的 10 倍：常驻 wasm int8 对应总量 280–300 万（散放）、430–760 万（连续），也就是说 **100 万向量在 10% 过滤下 p95 是 46–71 ms（1024 维），余量 3–4 倍**。不过滤的全库搜索（100%）在 100 万 × 1024 维时 p95 268 ms，已经超预算，上限约 75 万。

建议的阈值（写进 D10 的"门槛"）：

- 初版：向量存成打包表，worker 常驻 int8 矩阵，wasm 内核（附 JS 回退）。单个模型总量到 **约 100 万向量、候选数 ≤ 30 万** 都够用。
- **必须换扩展**的信号，满足任一：
  1. 单次查询的候选数稳定超过 **50–70 万**（int8、wasm），或没有 wasm 时超过 **10–15 万**。
  2. 常驻内存不能接受：100 万 × 1024 维 int8 要 1.0–1.2 GB，float32 要 4.1 GB（加载峰值再翻倍）。
  3. 需要不过滤的全库搜索且规模超过 **约 75 万**。
  4. 向量要在 PG 里直接参与 SQL 过滤和 join（本次没有测 PG 路径）。
- 换哪个：sqlite-vec 据我所知目前也是全量扫描，需要先实测再决定它是否带来量级提升；pgvector 的 HNSW / IVFFlat 是真正的近似检索，但只在 PG 后端可用，召回会低于暴力扫描，需要接口层统一 `OutlineSearch` 的向量召回。

## 4. 对设计文档的修改建议

按章节：

**§2.5 历史**："按时间点读取直接按区间查询"改写为：版本行带 `page_id`，按时间点读取一页是 `WHERE page_id=? AND from_seq<=T AND (to_seq IS NULL OR to_seq>T)`，由索引 `(page_id, from_seq, to_seq)` 支撑。块在页内的子树，从整页结果在内存里截取。

**§3.2 时间轴**："按视口分批读取，每批最多 500 块"保留，补一句实现：读整页（≤2000 块）后在内存里按树序切批；拖动时用相邻提交的增量（版本行上的 `change_flags` 直接给出增/改/移/删，不需要和上一个版本比较）。

**§5.3 向量存储 / D10**：
- 把"在 db-worker 里先按空间过滤，再暴力扫描"补全为：向量存在**打包表**里，按 `(model_id, space_id, chunk_no)` 打包（每行约 512 个向量，含块 id 和缩放），worker 启动时加载成 int8 矩阵常驻，按 `(空间, 页)` 连续存放；用 wasm SIMD 内核（`prototypes/outline-bench/vector/kernels.c`，5 KB），不支持时回退 JS。
- `outline_embeddings(model_id, content_hash, …)` 保留为按内容去重的缓存，但**不要在查询路径上 join 它**（总量 20 万向量、10% 过滤时 p95 已是 174–234 ms，100 万（int8）时 885–1041 ms）。
- 门槛写成 §3.4 那张表：候选数 50–70 万（wasm int8）或 10–15 万（纯 JS）、常驻内存 1–2 GB、不过滤全库搜索 75 万。
- 精度：int8 召回约 0.98；需要更高就 int8 取前 200 再用 float32 重排（召回 1.000，要保留 float32 副本或从原文重新计算，没有测这部分成本）。
- 加载峰值是稳态的两倍，需要分批加载。

**§7.1 表**：
- `outline_block_versions` 加 `page_id`（页根块 id，冗余）和 `change_flags`（创建/内容/移动/删除/恢复/任务/换页的位）。
- 写下两条不变量：删除子树给每个后代写墓碑；跨页移动子树给每个后代写新版本（`page_id` 变）。
- 索引：`PRIMARY KEY (block_id, from_seq)`、`(page_id, from_seq, to_seq)`、`(commit_id)`。`to_seq` 继续用 NULL。
- `order_key` 在 PG 里声明 `COLLATE "C"`。
- `outline_blocks`（当前态）也加 `page_id` 和 `(page_id)` 索引。
- 提交表：`UNIQUE (space_id, seq)`，按会话过滤的时间轴再加 `(space_id, narrator_id, seq)`。
- 不需要 `outline_page_members`。

**§7.2 上限**：
- "按时间点读取，单个视口 500 块"保留，补验收口径：热缓存 p95 ≤ 15 ms（SQLite / PG），冷缓存 p95 ≤ 150 ms。
- 新增一行：同一时间点整页读取，≤2000 块可以在主线程；超过（最多 1 万块）必须走 db-worker 或"先结构后正文"。
- "单次向量扫描 200 ms"保留，但标明按**候选数**计，不是总向量数。

**§11 第 6 条超长页**：数据回答了一半。1 万块的页在时间轴上整页@T 是 31–42 ms（热）、两步法 15–20 ms，不需要因为性能把页拆小；占位节点是否够用仍是界面问题。

**§10 / §12**：P0 四项验证里，本次完成了"按时间点读取"和"向量扫描"两项；风险表"按时间点读取的性能"可以改写为"已验证：B 方案下 30 版本/块仍在视口级延迟内，超过 100 版本/块再考虑页检查点"。

## 5. 没测到的
