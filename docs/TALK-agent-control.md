# 深度掌控 Agent 行为 — NarraFork 实战课堂讲稿（60 分钟）

受众：用过 Claude Code / Codex / Cursor 的研发人员。
形式：讲解 + 真机演示，全部演示在 NarraFork 里做。

## 给讲者的三条纪律

1. 不讲其他工具的具体操作和版本号。我们没有一手验证过那些内容，讲错了会反噬可信度。被问到就直说「这个我没实测过，不替它们下结论」。
2. 每幕结束看一眼表。超了先砍演示时长，绝不砍「什么时候该用」的判断力部分，那是听众带得走的东西。
3. 任何演示卡住，不现场 debug。统一话术：「这是我本地的开发分支，跑的是未发布代码，我直接讲它背后的机制。」

## 第 0 幕 开场（5 分钟）

大家手里都有 Claude Code、Codex 或者 Cursor。所以今天我不讲怎么用 agent 写代码，这件事在座的都会。

我想讲一个更窄的问题：当 agent 跑偏的时候，你手里有什么？

三个场景。

聊了两小时，上下文满了自动压缩，压缩完你反复强调的约束没了，接下来它开始违反那条约束。

派个子任务去调研，三分钟里它在读一堆无关文件，你说不上话。

长对话里试了个方案，十几轮后发现不行，想回到第 5 轮换个方向，又不想丢掉前面五轮攒的上下文。

（举手环节，等一下）

这三件事的共同点是：模型没问题，是模型外面那层壳没给你抓手。这层壳叫控制面。模型是引擎，控制面决定你对引擎有多少话语权。

今天用我们自己做的 NarraFork 讲这个。先用一分钟说它是什么。

NarraFork 是我们做的 agent 协作平台。一台服务器部署，多人多端同时用，浏览器和手机都能访问，装了 PWA 可以当本地应用用。长会话不卡：消息列表用 pretext 做文本测量，配合虚拟列表，几万条消息滚动不掉帧。窄屏和触屏做了专门处理，右键菜单在移动端是滑动手势，多选、分叉、压缩这些操作手机上都能做。上下文管理是它的重点，今天前三幕都在讲这个。worktree 是图形化管理的，多分支并行开发不用碰命令行。

每一部分我都会先讲什么时候该用，再演示具体怎么做。判断力的部分比操作的部分重要：操作记不住可以查文档，什么时候该用查不到。

## 第 1 幕 压缩（13 分钟）

### 1.1 为什么值得认真对待（2 分钟）

上下文满了，工具会把前面的对话压成一份摘要。从这一刻起，这份摘要就是后续所有推理的事实基础，没有机制会去复核它。

摘要漏了一句关键约束，后面每一轮都在错的前提上推理。它不报错，你只会看到它开始做一些莫名其妙的决定。

所以压缩不是省 token 的性能问题，是正确性问题。

### 1.2 什么时候该自己压（4 分钟）

不要等系统自动压。自动触发的时机是最差的时机：上下文最满、最乱，你可能正调着一个没解决的问题。你比系统清楚哪些信息可以丢。

该压的时刻有四个。

刚做完一件事，要开始一个不相关的新任务。这是最优时机。

刚跑完一轮长输出的工具调用，比如几百行测试日志。那坨东西现在是噪音。

上下文用了五六成，而你知道后面路还长。别等八成时自动触发，那时候你没有选择权了。

一次探索失败了。十几轮弯路只需要留下一句「A 方案不可行，因为 X」。

不该压的时刻有三个。

正在调试一个没解决的问题。你还不知道哪个细节关键，压缩会把它当噪音丢掉。

刚压过一次又想压。多次压缩累积失真，正确动作是开新会话、把结论手写进去。

上下文里有你要逐字引用的东西，比如一份规格。压缩会改写它。

一句话总结：把主动压缩当 git commit 用，在一个逻辑单元完成时做，带一句说明。

### 1.3 演示（5 分钟）

1. 打开长对话叙述者。在中间一条消息右键，选「压缩到此」。
   说：锚点是任意一条消息，包括一次工具调用。

2. 压缩过程中指出实时字符数。
   说：能看到摘要模型正在产出多少字符，不是一个转圈的黑盒。

3. 压缩完成后，点击压缩卡片，弹出摘要全文。
   说：这是模型生成的摘要。现在它就是这个会话唯一的历史依据。

4. 点编辑，手动加一行：`约束：不要修改 foo() 的函数签名`。保存。
   说：保存的瞬间，摘要字段更新、上游会话缓存作废。下一轮请求里，模型看到的就是我刚写的这句话。

5. 再打开卡片，点「撤回压缩」。历史全部回来。
   说：被压缩的消息从来没被删过，只是被挡在模型视野外面。撤回就是把这个遮挡去掉，所以不可能失败。

6. 多选中间几条消息（Ctrl/Cmd 加点击），选「压缩选中消息」。
   说：只压中间这一段，前后的原文都保留。适合处理「这两百行日志是噪音，但它前后的对话都有用」。点「查看原文」能看到被压掉的内容：对模型隐藏，不等于对人销毁。

7. 提一句：压缩用的模型在设置里单独配，不跟随当前会话的模型。压缩失败可以重试，重试时能换模型。

### 1.4 被问到的备用答案

- 压缩提示词能自定义吗？不能，目前是内置的。这是已知缺口，承认。
- 自动压缩和手动压缩是一条路径吗？是，自动压缩就是系统替你选了锚点，走的是同一份代码。
- 上下文超过摘要模型的窗口怎么办？切块级联压缩，每块的摘要作为下一块的输入。

## 第 2 幕 分叉与回退（12 分钟）

### 2.1 先分清两个动作（2 分钟）

走错路了想退回去，是回退。想试另一条路但不想丢掉现在这条，是分叉。

用回退去做分叉是最常见的浪费：你销毁了一条已经建好的上下文，而重建它比你以为的贵。

### 2.2 什么时候分叉、什么时候回退（4 分钟）

先问一个问题：现在这条线的上下文还有价值吗？跑偏了、被污染了，就没有，回退或者开新会话。

还有价值，再问：要不要同时保留两条路做对比？要，分叉。确定新方向更好，回退，不留垃圾分支。

该分叉的时刻。做技术方案对比，同一起点分两条线各自跑完再比。试高风险大改，分叉出去试，不行丢掉。上下文很贵，聊了几十轮攒下来的，重建要很久。想问一个跑题的问题，分叉出去问完丢掉。

该回退的时刻。明确知道新方向更好，旧的没有保留价值。代码写坏了但推理是对的，只回退代码。上下文被污染了，只回退对话。

有一个常见的错误做法：跑偏了，追加提示词纠正，还不对，再追加。每次追加都在往上下文里堆矛盾信息，模型要自己判断哪个是最终意图。我的经验标准：追加纠正超过两次还没对，停下来，回退或分叉。

### 2.3 演示（4 分钟）

1. 在长对话中间一条消息右键，选「从此处分叉」，打开新叙述者。
   说：前面的上下文全在，原会话一条消息都没动。

2. 在新线里发一句话跑起来，然后切回原叙述者。
   说：两条线各自向前，共享同一批消息。

3. 在一条用户消息上右键，指出同样能分叉。
   说：能从自己说的话那里分叉很重要。「我上一句问错了，想换个问法，但保留前面的上下文」是最常见的需求。

4. 多选几条不连续的消息，选「为这些消息分叉」。
   说：不是从某点切，是把这几条挑出来组成一个干净的新会话。适合把一次长调研里有用的几条结论捞出来。

5. 指出「回退到此处」可选是否连同工作区文件改动一起回退。
   说：推理对了但代码写坏了，就只回退代码，保留对话。

### 2.4 一句底层解释（1 分钟，有人问原理再讲）

分叉便宜的原因是消息内容全局只存一份，「谁的第几条消息」是另一张表里的指针。分叉只复制指针。

这件事的实际意义不是省存储，是让你敢分叉。如果每次分叉都贵，「保留失败路径做对比」这个工作方式就永远不会形成。成本决定习惯。

## 第 3 幕 子任务（13 分钟）

### 3.1 症状（2 分钟）

派一个子任务出去调研，三分钟里它在读一堆无关文件。等它跑完再否定结论，代价是那几分钟白烧了，它已经建立的正确部分也一起丢了。

方向错误是子任务最常见的失败模式。不是能力不够，是它猜错了你想要什么，而你给的任务描述总是不完整的。关键问题不是怎么让它一次猜对，是怎么在它猜错时便宜地纠正。

### 3.2 五个手段怎么选（4 分钟）

按侵入性从轻到重。

看着不动，它方向对，只是慢。发消息排队，补充一个它不知道的信息，它跑完这轮自己看。发消息插队，方向不对，要马上改，打断当前一轮。接管，需要来回几轮才能掰正，你自己坐进去带；接管本身不打断当前一轮，它只把结论的归属改成你。中断重派，任务定义错了，丢掉全部已建立的上下文。

选哪个，先问它错在哪一层。缺一个事实，发消息补充，别中断。方向偏了但任务没错，插队纠偏。要来回澄清，接管。任务定义错了，中断重派。

最常见的误判是把「缺一个事实」当「任务错了」处理：它只是不知道某个文件在哪，你却把它整个停掉重派。反过来也常见：任务定义错了却不停发消息纠偏，上下文里堆满矛盾指令。我的经验标准：纠偏两次它还在偏，问题不在它，在你的任务描述。停下来重派，并且改写任务描述，不要用同一段描述再派一次。

再往前一步：什么时候该派子任务。该派的：要读很多文件才能得到一个小结论；需要并行的独立任务；高风险探索。不该派的：任务描述比它要做的事还长；需要频繁来回确认的事；你自己都不确定要什么。一句话：子任务适合输入小、过程大、输出小的任务。

### 3.3 演示（5 分钟）

1. 展开子任务卡片，指着逐条活动记录。
   说：每一次工具调用都在这儿，Read 哪个文件、Grep 什么模式。不是进度条，是逐条记录。我现在就知道它在往哪找。

2. 点「打开完整会话」。
   说：这是一个完整的会话页面，它的全部消息和上下文用量都在。

3. 让一个子任务跑起来，点「接管」。
   说：注意它没有被打断，这一轮照样跑完。接管声明的是「结论归我」，不是「立刻停手」。跑完之后它不再把结果交上去，而是停下来等我。父 agent 那边的调用保持阻塞，它不知道我插进来了。想让它立刻停手是另一个按钮：中断，而且接管期间的中断是软的，不会结束接管。

4. 直接给它发消息纠正方向，等它跑一轮。

5. 点「停止接管」。
   说：控制权交还，我刚才的成果作为结果回到父 agent 手里。父 agent 收到的是一个被我修正过的结论。

6. 补一句权限：子任务要批权限时，请求出现在父会话的卡片里，父页面直接批复。待批请求不会超时自动拒绝，去吃个午饭回来，任务还活着。

### 3.4 反思机制（2 分钟）

有一组功能叫反思。它解决的问题是：agent 无人值守跑的时候，有些决定没人可问，但不能直接放行。

触发点主要在 bypassPermissions 模式下。平时有人的会话里，危险操作会弹审批等人点。没人看的会话里没有人可点，反思就是这条审批路径的替代：操作暂停，起一个嵌套的反思循环，带着完整的对话上下文，只允许调两个决策工具——确认或取消。它看完危险分级（严重度、后果、更安全的替代方案）之后做出判断，确认就继续执行，取消就不执行。

一个细节：反思循环只许调决策工具，别的工具一律拒绝。它判断不了的时候——比如模型超时、重试耗尽——操作不会执行。失败方向是关死的，不是放行。人随时可以中止反思、把决定权拿回来。

同样的结构用在另外三个地方。

计划模式退出前，反思循环先查一遍计划：具体吗、可执行吗、有没有明显漏洞。不过就打回去，附上修改意见。

标记了「务必完成」的任务被改动时，反思循环问一个问题：这次修改是否违背了用户真正要求的东西。这里有个真实教训值得讲。早期版本的提示词问的是「证据够不够」，结果有一次会话卡了一个半小时：3067 个测试全部通过，反思循环连续五次驳回，理由分别是还缺基准测试、还缺这样那样的证据。每次驳回单独看都合理，合在一起是个死循环——因为那个任务的写法本身就没有可判定的完成条件。现在提示词改成问意图，不问证据是否完备，并且允许把没有完成条件的任务改写成有完成条件的。

agent 向你提问而你没在时，可以由摘要模型根据对话内容代答。这个功能默认关闭，需要手动开启，而且只在无人值守（bypassPermissions）模式下生效。开启后默认等五分钟，你开始作答的那一刻倒计时就取消。

### 3.5 被问到的备用答案

- 接管为什么不是中断重派？中断重派丢掉全部上下文，接管保留。接管也不打断当前一轮：它只是把「这一轮的结论交给谁」改成交给你，所以实现上比中断难。
- 能不能不打断地问它在想什么？能，有个只读追问手段，从历史快照里生成回答，子任务本人完全无感知。
- 子任务能直接问我吗？不能，必须经父 agent 转达。并发的多个子任务各自抢用户注意力会互相干扰。

## 第 4 幕 团队讨论与并行开发（12 分钟）

### 4.1 症状（2 分钟）

你看着 agent 干了一件事，想跟同事说「这个方案有问题」。说在哪？

说在 agent 对话框里，这句话就变成了给 agent 的指令，它会响应甚至照着改。说在群聊里，脱离了上下文，同事得问你说的哪一步。说在 PR 评论里，那是代码评审，不是过程讨论，而且要等代码写完。

目前各家的协作都收敛到同一个形状：各自跑 agent，产出 PR，在 PR 上评审。协作发生在 PR 层，不在过程层。你和 agent 的两小时对话，同事看到的是最后那个 PR。中间丢掉的是「为什么这么做」：PR 里有代码，没有那两小时里被否掉的三个方案。

### 4.2 讨论室演示（4 分钟）

1. 工具栏点「讨论」图标（带未读角标），面板在时间线旁边打开。
   说：它和 agent 时间线并排。人在这里说话，agent 看不到。这不是过滤，是两套数据之间没有通道。

2. 发一条消息：「这个方案的错误处理不对」。

3. 切到 agent 的对话，指出它完全不知道刚才那句话。

4. 回讨论室，选中那条消息，点「发给叙述者」。指着输入框里出现的引用块。
   说：带作者、带时间戳、引用块包起来。它进的是输入框，不是直接发送，我还能在发之前改。带署名是必须的：几个人争论的内容不带名字转给 agent，它会以为是一个人的自相矛盾。

5. 演示「摘要后发送」：选中多条，弹出「确认摘要」，指出这里也能改。
   说：这和第 1 幕的编辑摘要是同一个立场：AI 生成的东西，人在它生效之前有一次编辑机会。

6. 直说缺口：没有 @提及，讨论不能锚定到时间线的具体某条消息，不进全文搜索；讨论室消息不进站内通知中心，只有未读角标。

### 4.3 并行开发与叙事线（4 分钟）

十个需求同时跑，让任务并行起来不难。难的是另一半：各自进展到哪了，谁和谁有关系，最后怎么收拢。

我们的做法是章节：一个章节等于一个 worktree、一个分支、一个 agent 会话。项目主页是一张图，每个节点对应一个真实 worktree，每条边对应一次真实的 fork 或合并。这张图和 git 状态是同一份数据，不是可视化装饰。你休眠一个节点，对应的 worktree 就真的被移除了，分支保留。

演示（1.5 分钟）：打开故事图，指节点和边。右键一个节点休眠，指出 worktree 消失、分支还在。套索多选两三个节点，指出批量合并入口。合并遇冲突会停下来等你决定。

没做完的直说（1 分钟）：章节之间的依赖关系表达不了（用户拖拽创建 dependency 边的能力已移除）。把多个方案组织成对比实验的探索组只有数据库表没有功能。commit 和对话的关联只在 split/fork 路径接通。所以这张图现在是历史的自动可视化，还不是组织并行工作的工作台。这是我们最不完整的地方，而它恰好是这个隐喻承诺要解决的问题。

## 第 5 幕 收尾（5 分钟）

### 5.1 带走这张表（2 分钟）

| 情况 | 动作 |
|---|---|
| 一个阶段做完了，要换任务 | 主动压缩，别等自动触发 |
| 刚跑完一坨长输出的工具调用 | 把那一段压掉 |
| 上下文过半，后面路还长 | 现在压 |
| 一次探索失败了 | 压成一句结论 |
| 正在调试没解决的问题 | 不要压 |
| 刚压过又想压 | 开新会话 |
| 想试另一条路但要留住现在这条 | 分叉 |
| 确定新方向更好，旧的没用了 | 回退 |
| 推理对了但代码写坏了 | 只回退代码 |
| 上下文被污染了 | 只回退对话 |
| 追加纠正两次还不对 | 停手，回退或分叉 |
| 子任务缺一个事实 | 发消息补充，别中断 |
| 子任务方向偏了 | 插队发消息 |
| 要来回几轮才能掰正 | 接管 |
| 任务定义本身错了 | 中断重派，并改写任务描述 |
| agent 要执行危险操作 | 让它先反思，说不通就停在那 |
| 想跟同事讨论 agent 正在做的事 | 去讨论室，别在对话框里说 |
| 讨论出结论了 | 选中转发，别复制粘贴 |
| 多个需求并行 | 图上 fork 章节各自跑 |
| 并行做完了 | 图上批量合并 |

两条元规则。把主动压缩当 git commit：逻辑单元完成时做，带一句说明。纠偏两次不成就换手段。

### 5.2 一个工程教训（1.5 分钟）

刚才讲的那些缺口有个共同的模式：声明了，校验器接受了，但没有写入者。依赖关系边的用户拖拽创建能力已整体移除。探索组的界面文案存在但没有任何创建代码。commit 关联只在 split/fork 路径写入，用户 git 提交的调用点不传关联。

还有一个已删掉的例子最能说明问题。曾经有一个 frozen 章节状态，声明了、校验器接受、没有代码路径写它。按它过滤会静默返回全部章节，因为没有一行是 frozen，过滤条件等于没写。

这个模式不报错。类型系统满意、测试满意，每一层单独看都自洽，只有端到端跑一遍真实场景才会发现功能不存在。

一个字段不算完成，直到它有真实的写入者和真实的读取者。只做一半就合并，那半个功能会以「看起来能用」的形态留在代码库里，比完全没有更糟，因为下一个人会以为它能用。

### 5.3 Q&A 引导（1.5 分钟）

如果没人提问，用这几个启动：

「这些控制手段是不是把复杂度推给用户了？」默认路径和别的工具一样：自动压缩、派子任务等结果。这些是出问题时的逃生门，区别在于有和没有，不在于每天用不用。自动压缩走的就是手动压缩那条代码路径，所以那条路径被天天验证。

「多人同时操作一个会话会怎样？」没有并发编辑保护。是「同看加轮流开」，权限批准先到先得，第二个点允许的人会静默无效。这是真缺口。

「讨论室为什么不让 AI 也看到？」因为「能看到」和「会响应」在 LLM 里是同一件事。讨论一旦进入上下文，你和同事的每句话都会影响它下一步，包括你们还在争论、尚未定论的话。转发是一个决定：决定这段讨论现在是给 agent 的输入了。

「其他工具也有这些能力吗？」部分有，而且近几个月变化很快。我没有系统实测过各家现状，不替它们下结论。建议自己用 `--help` 和斜杠命令补全查，列出来的东西一定存在。

## 附录 C NarraFork 现状速查（被问到现状时用）

成熟可用：压缩全套（任意锚点、区段、编辑、撤回、换模型重试），任意位置分叉，子任务可观测与四种干预手段，侧边讨论室，权限模型，worktree 隔离与生命周期，合并的失败路径与批量合并重启恢复。

明确缺口：压缩提示词不可自定义；多人协作无并发编辑保护；依赖关系、探索组、commit 关联（手动 git 路径）未做；讨论室无 @提及、无法锚定时间线、不进搜索；AI 解冲突无 diff 审核界面；叙事线停在「历史的可视化」。
