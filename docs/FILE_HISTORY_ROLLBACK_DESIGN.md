# 全实例文件版本与会话回退设计

状态：**主体已实现**（提交 `a78b5166` 起）。本文为设计基线；设计符号与实现名对照：`InstanceFileWriter` → `LocalFileChangeRuntime`（`server/services/file-change-runtime.ts`），`FileRestoreService` → `file-change-local-restore.ts` + revert 服务簇。§10–12 的改造/验收清单反映目标态，实施进度见 `evidenceVersion=2` 与相关服务。

## 1. 决策与约束

核心只有一句话：**可控写入线性记账，符合条件的 Bash 捕获差量，回退恢复已保存版本，不确定项明确跳过。**

1. 所有会话、子代理及设备的 Edit/Write 共用全实例日志顺序；成功写入必须有可恢复的原始内容。同一文件串行，不同文件不必互相等待。
2. 只有短时、边界明确、整个捕获窗口没有其他 Bash 重叠的 Bash，才生成可回退的快照差量。
3. 长时、并发、边界不明的 Bash 只产生缺口提示，不取消其他记录的回退资格。
4. 恢复某个文件的历史版本，可以覆盖其他会话在该文件上的后续修改；一次预览讲清影响，由用户确认。
5. 回退是新的写入，不倒拨日志、不删除旧文件版本、不自动重放其他 Agent 的操作。
6. 一个文件回退入口，不增加“严格/宽松”“工作区/归因”两套恢复模式。

**不做的事：**按作者从交错修改中抽取补丁、默认三方合并、证明所有外部进程没有写入、回放历史 Bash、构建跨设备分布式事务。

授权与路径访问控制继续有效；“文件内容有后续变化”则是覆盖提示，不是访问拒绝理由。

## 2. 核心结构：三个职责，不再叠加证明系统

```text
Edit / Write / 内置编辑器 / 文件恢复
                 │
          InstanceFileWriter
       全局序号 + 按文件短写入队列 + 原始版本日志
                 │
          设备文件执行适配器

Bash ── BashCaptureWindow ── 成功：差量进入同一日志
                          └─ 不符合条件：记录跳过原因

会话中的恢复动作 ── FileRestoreService
                   选择记录 → 每文件目标版本 → 预览 → 新写入
```

- **InstanceFileWriter**：只负责分配全局序号、按文件排队、保存原始内容、实际写入及登记结果。
- **BashCaptureWindow**：只负责判断本次捕获窗口是否成立，不决定其他操作能否回退。
- **FileRestoreService**：只负责把历史选择转换成文件目标版本，以及组织确认和执行。

原始对象存储、设备寻址、认证、消息 COW 和事件总线复用现有实现。归因统计可以继续存在，但不再决定用户有没有恢复权。

为支持委派范围，`file_change_operations` 另外保存一个轻量的 `executionSegmentId`。执行段记录实际触发它的 tool-call / 输入投递，以及直接父执行段；这是来源索引，不是文件证据图。每个文件操作仍只有一个所属执行段，选择时沿直接父子关系向下展开并按 operationId 去重。

## 3. 数据模型

### 3.1 复用现有记录，不创建另一套文件历史库

| 数据 | 作用 | 改造方向 |
|---|---|---|
| `file_change_operations` | 谁发起了什么操作 | 增加全实例 `journalSeq`、明确的操作类别和 Bash 捕获结果 |
| `file_change_effects` | 某文件的一次版本变化 | 保存 before/after；按新文件身份和全局序号索引 |
| `file_change_blobs` | 去重后的原始内容 | 复用，不把文件全文塞进消息或 SQLite 行 |
| `revert_operations` / `revert_operation_files` | 一次恢复请求及逐文件结果 | 复用分组、确认和结果记录，不另建事务框架 |

在现有 [server/db/schema.ts](../server/db/schema.ts) 上演进；旧记录保留兼容读取，新语义使用独立协议版本。

全局序号用一个新增的单行 `file_history_clock` 分配：在登记操作的短数据库事务内递增并取得序号，再插入操作。保留现有文本操作 ID 和外键，避免为换主键重写整套引用。

- 序号持久化，重启不回拨；允许空号。
- 不使用消息 seq、时间戳、随机 ID 或作用域 revision 代替全局顺序。
- 旧记录的 `journalSeq` 留空，不按时间戳伪造过去的全实例执行顺序。

### 3.2 文件身份表示“设备上的路径”，不是“某会话的文件”

```text
fileKey = 设备身份 + 设备路径语义下的规范路径 + 对象角色
```

- 不包含 narratorId、cwd 或因选择根目录不同而变化的 scopeId。
- 同一设备、同一规范路径，从不同会话或 cwd 访问，进入同一版本链。
- 不同设备上同名路径不能合并；设备重连不拆链，更换实际设备应使用新设备身份。
- 不用 inode 作为文件版本链主键：替换写入本身就可能更换 inode。
- 权限校验仍依据当前请求的真实目标，不从历史记录继承权限。

现有 [server/services/file-change-identity.ts](../server/services/file-change-identity.ts) 中工作区归属信息保留用于展示和寻址，不再切分文件版本链。

### 3.3 一个文件效果保存什么

```text
FileVersion {
  operationId,
  journalSeq,
  fileKey,
  before: FileState,
  after: FileState,
  restoreTarget?: { effectId, side: before | after }
}

FileState = 不存在 | 原始文件内容引用及必要模式 | 链接对象状态
```

- before 是执行前实际读取的字节；不是模型输入，也不是第一次访问该文件时的原文。
- Edit/Write 的 after 是后端实际成功写入的字节。并发 Bash 在稍后再次修改文件，不改写这个已保存版本。
- 创建文件的 before 为“不存在”；恢复该状态意味着删除这个文件。
- Bash 重命名先按路径的删除和新增表达，无需额外引入重命名依赖图。
- 编码、换行、二进制和已有链接处理语义沿用文件后端；不能为了恢复方便把所有文件变成 UTF-8 文本。
- `attributionGrade` 等旧字段可继续服务统计，但不能作为 v3 文件版本的可恢复开关。

按 `(fileKey, journalSeq)` 建索引即可查最新版本和后续修改，不另建一套版本 HEAD 状态表。记录可恢复与工具业务执行成功是两件事，例如 Bash 非零退出但边界内确实改了文件，仍应保存版本。

## 4. Edit/Write：先有恢复材料，再发生写入

全局序号覆盖所有操作；实际读改写窗口只在同一文件内串行，不覆盖模型请求、权限等待、交互确认和完整工具生命周期。

```text
1. 取得写入队列位置，核对目标设备与权限。
2. 读取真实 before，生成本次实际写入字节。
3. 持久化 before、拟写入内容和操作记录，分配 journalSeq。
4. 执行实际文件写入。
5. 登记实际结果，完成版本记录，释放队列。
```

主要复用 [server/services/file-change-runtime.ts](../server/services/file-change-runtime.ts) 的原始字节保存和先记意图再执行流程，替换其按 workspace 排队及 Bash 连带降级语义。

### 正常写入的保证

- 多个 Edit/Write 从同一个实例入口分配全局序号；同一文件按文件队列串行，不同文件可以并行，不再有主/子代理、本地/远程的旁路。
- 内置编辑器及其他平台可控文件写入也必须进入相同协调点；只有处于同一 Bash 捕获根的写入才需要暂时让出该捕获窗口。
- after 已知但后来被别的操作覆盖，历史版本仍可恢复。
- 记录或原始内容保存失败时，本次受控写入不能先执行再悄悄降为“不可回退”。
- 已开始写入后异常，保留 before 和执行状态；不能因为缺少最终工具消息就丢掉恢复材料。

### 远程接入只补必要能力

远程沿用同一套服务器版本存储，新增的仅是设备侧幂等文件写入能力，不是第二套历史库：

1. 服务器在该文件的写入队列内从实际设备读取原始 before，先把 before、拟写入内容和带 `operationId + journalSeq` 的操作持久化到服务器内容存储；其他文件不等待。
2. 向执行器提交目标、预期 before 和拟写入字节。执行器在实际写入入口检查 before 是否仍一致；不一致则明确返回“未执行”，重新读取后形成新的写入尝试，不能用失真的 before 给一次成功写入记账。
3. 执行器先持久登记该请求，再执行文件 IO，最后持久保存可按 operationId 查询的结果。不能只依赖连接内存中的 RPC 请求表。重复请求返回原结果，不重复写入。
4. 结果由服务器收录后可以回收设备上的详细回执；设备保留已受理序号水位，已回收的旧请求只能返回“结果已过期”，不能当作新写入执行。

before 的原始内容在发送写入前已位于服务器，因此设备写完即断线或执行器重启，也不会丢掉该操作的恢复材料。这一步的 before 校验是保证本次写入记录真实，不是要求历史恢复目标必须等于当前文件。

正常队列持有到实际执行结束，而非持有到 HTTP 超时。响应丢失后查询原 operationId：仍在执行则等待该设备，终态存在则收录；若结果查无记录，但已确认旧执行结束，则以“执行结果未知”结束核实，不重放旧写入、不按当前 hash 伪造成功。before 仍可作为明确恢复目标，设备后续写入恢复派发。

核实期间不继续向该设备派发后续受控写入，无关设备可继续；未知请求保留序号位置，不冒充已完成的 after 版本。这里保证的是文件版本的逻辑顺序，不声称网络分区下还能证明所有设备的物理写入绝不同时发生。设备离线只影响它当前的文件 IO，不形成实例级历史恢复禁令。

## 5. Bash：短捕获窗口，不是全实例 Shell 串行器

### 5.1 影子 tree 的边界

工具执行热路径中，Edit/Write 不再捕获整棵 tree；Bash 使用前后 tree 获取所覆盖文件的真实差量。

- tree 根目录取实际执行工作区的已解析根，范围与忽略策略在预览中可见。
- 差量展开为新增、修改、删除文件的 before/after，进入同一文件日志。
- 原始版本引用落入统一内容存储后，不再依赖影子仓库永远保留该 tree。
- Bash 回退按这些文件恢复，不 checkout 整棵旧 tree。
- Git tree 未覆盖的内容，例如忽略文件、空目录、仓库外文件和外部系统副作用，不承诺由该 Bash 快照恢复。Edit/Write 则不因 gitignore 而丢失逐文件记录。

章节 fork/merge 等结构性快照继续复用 [server/services/worktree-tree-snapshot.ts](../server/services/worktree-tree-snapshot.ts)，不与日常会话恢复资格绑定。既有结构性快照事务的 commit/finalize/discard 约定保持不变。

### 5.2 唯一判据是实际窗口

实例维护一个轻量的 Bash 活动集合，覆盖全部会话、子代理、前后台及设备；记录真实执行和捕获期间的重叠，不解析命令字符串来证明没有写入。

```text
登记 Bash 活动
  ├─ 已有其他 Bash / 后台执行 / 不支持捕获 → 直接记录 skip，正常执行命令
  └─ 尝试取得短窗口
       → before tree
       → 执行并确认结束
       → after tree
       → 固定前后 tree 及操作序号
       → 成立则异步归档文件版本，否则 skip
```

短窗口暂时占用捕获根范围内的文件写入锁。**其他 Bash 不等待这个窗口串行执行**：一旦第二个 Bash 进入，就使重叠候选失效；不会为了提高快照成功率而串行整个实例的命令。捕获根之外的 Edit/Write 不受影响。

判定覆盖 before 捕获开始到 after 捕获结束，不能只在命令开始和结束各检查一次活动数量。窗口中曾发生重叠，就不能因为另一个 Bash 已经退出而重新变成“独占”。

### 5.3 只设一个短窗口预算

采用一个覆盖“捕获排队、before 捕获、命令执行和 after 捕获”的有界预算，具体数值由真实工作区性能验收确定；它是内部常量，不新增一组用户配置，也不把任意秒数写成产品行为。

- 超时、出现重叠或捕获失败时，立即取消候选资格，并释放写入窗口；命令按自身超时策略继续，不为快照杀死用户命令。命令始终由原执行路径启动一次，捕获取消信号不能取消或重新派发命令。
- 取消后尚未结束的只读扫描即使后来产出 tree，也不能补称为之前的精确边界。
- 文件差量展开、内容归档在固定 after tree 后可移出写入队列；操作保存其预留的序号，并保留前后 tree 的临时引用直到归档结束，不能提前被 GC。
- 归档未完成时显示“记录处理中”。若此时生成回退预览，该操作明确列为“本次暂不恢复”；用户可以等待后刷新，也可以在同一次确认中接受跳过。它不是永久 capture skip，不禁用其他文件。
- after tree 必须属于执行驱动的结束流程，不能来自工具消息的“已启动”返回或稍后的消息事件钩子。
- 不能确认后台后代作业结束的命令不生成可逆条目；普通退出码只说明前台进程状态。

长时、重叠或结束未知的 Bash 保存起止信息及原因，而非一个虚假的“无变化”版本。未结束活动只影响新的 Bash 是否符合捕获条件，不影响 Edit/Write 记账或已有版本恢复。

### 5.4 跳过原因保持少量、可理解

| 原因 | 告知用户 |
|---|---|
| `concurrent` | 捕获期间与其他 Bash 重叠 |
| `long_running` | 超过短快照窗口 |
| `background_or_unknown_end` | 后台执行或无法确认执行结束 |
| `capture_unavailable` | 无可用捕获范围、快照失败或后端暂不支持 |

原因只解释本次 Bash，不生成 workspace quarantine 或永久禁用开关。

## 6. 回退语义：会话决定选哪些记录，全局版本链决定恢复什么

### 6.1 从选择得到逐文件目标

消息只承担记录定位，不承担文件状态证明。纯文本、Read、控制工具和系统消息不要求存在文件变更日志。

对会话回退所选的操作集合 `S`：

1. 通过来源关联查到这些操作及应包含的子代理文件记录。
2. 将不确定 Bash 和正在归档的 Bash 分别说明并列入本次跳过列表，不能当作无文件变化；从 `S` 排除这些已明确告知的操作，得到本次实际恢复集合 `R`。
3. 对每个已知受影响文件，找到 `R` 中最早那条文件效果，以它的 **before** 为目标。
4. 查询同文件此后的全局版本，列出其他会话和用户的后续修改；不因作者不同而过滤。
5. 读取当前实际文件状态，生成“当前 → 目标”的预览，并固定本次纳入与跳过的操作、目标原始内容引用。

后到的 Bash 归档不能自动扩张已确认计划，也不能在执行时重新查询 `S` 改写目标。例如 Bash 100 把 v0 改成 v1，但尚在归档，Edit 101 已把 v1 改成 v2：预览必须明确跳过 100，才可以用 v1 作为本次目标；若用户要连 100 一起恢复，归档后刷新预览，目标才是 v0。不能把前一种计划说成完整恢复了两次操作。

同一文件只生成一个目标和一次恢复，不逐步撤销中间每个 patch。不要求所有中间 after、无关操作回执和其他文件快照都存在；目标原始内容可读即可。受控写入执行结果未知但 before 已保存时，也能明确选择该 before；不能把未知的 after 列为已完成版本。

若最早选中效果的目标内容真的缺失，该文件明确显示不可执行；不能悄悄改成某个较晚的可用版本。其他文件继续准备。没有原始内容与“归因不排他”不是同一类问题。

### 6.2 交错编辑的确定结果

```text
100  A  f.ts  v0 → v1
101  B  f.ts  v1 → v2
102  A  f.ts  v2 → v3
103  B  f.ts  v3 → v4
```

A 回退 102，目标为 v2：B 的 101 自然保留，B 的 103 会被覆盖。A 回退 100 及其后自己选中的修改，目标为 v0，预览相应显示 f.ts 的后续影响。

确认后追加：

```text
104  用户恢复  f.ts  v4 → v5，v5 的内容来自 v2
```

不删除 102/103，不倒拨全局序号，不修改 B 的会话历史。B 在其他文件上的修改不在本次文件集合中，不受影响。

### 6.3 不确定 Bash 不能形成回退屏障

```text
201  Edit a.ts                    有记录
202  Bash                        因并发跳过
203  Write b.ts                   有记录
204  Bash                        短窗口快照可用，修改 c.ts
```

恢复这个区间时，a.ts、b.ts、c.ts 各自恢复到选中区间内的目标版本，并报告 202 未撤销。

**跳过 Bash 不是承诺保留它的所有结果。** 如果 202 也改过 a.ts，恢复 a.ts 的旧版本可能覆盖这部分内容；预览展示当前差异并说明这一点，用户仍可确认。不得通过默认三方合并或新增“内容冲突”开关再次禁止恢复。

### 6.4 子代理调用属于回退选择，而不是另一套恢复机制

**主代理选中了某次委派调用，就纳入这次调用产生的子代理文件操作；有下级委派时递归展开，之后仍走同一个逐文件版本恢复流程。**

```text
主代理的选中范围
  ├─ Edit a.ts                       seq 301
  └─ Agent 调用 C
       ├─ 子代理 Write b.ts           seq 302
       └─ 下级 Agent 调用 D
            └─ Edit a.ts              seq 303
```

选择 C，得到 302、303：b.ts 回到 302 的 before，a.ts 回到 303 的 before。若主代理同时选中 301，则 a.ts 的目标改为 301 的 before；不是先回退子代理、再用主代理另一份快照覆盖一遍。

#### 用实际调用来源展开，不按子代理名称或整段会话猜

- 文件操作保留实际执行者和所属执行段；执行段通过已有任务/run/输入投递记录关联到发起它的调用记录主键及实际尝试，不依靠模型输出的 toolUseId、别名或结果文本猜来源。
- 首次 Agent/Task 调用属于它触发的执行段；后续 Send、恢复或重试若触发新任务，要关联到那一次实际输入及执行段。新输入被消费后的工具批次切换来源，已派发工具保留原关联。若同一批消费多条委派输入，保留实际来源集合，选中任一来源即纳入该批次并提示共同来源，不靠最后一条输入覆盖其他来源。
- 同一子代理可以被多次使用：只选中启动调用 C，不意味着选中该子代理以后通过调用 E 执行的全部任务。E 的同文件后续修改按覆盖影响展示，E 在其他文件上的独立修改不扩大本次恢复范围。
- 查询只需沿已持久化的委派/执行段关联向下展开，按 operationId 去重；不建立另一套证据图或复制父子快照。需要补齐的是缺失的执行段来源字段与索引，不是所有工具的无副作用证明。
- 子代理从父会话继承或共享的历史文件记录不属于这次新调用；不能因为它们出现在子代理上下文里就再次选入。
- Await、查看结果、只读 ContextAsk 本身不产生新委派：仅选中这些等待/查看消息，不撤销发生在范围外的原始调用。后台子代理属于发起它的调用，不按完成通知出现在哪条消息里归属。
- 调用失败、取消或缺少最终回复，不抹去已记录的 Edit/Write。旧数据缺少某条委派关联时，只报告该来源的覆盖缺口，不能使整个主代理回退不可用。

现有 [server/services/subagent-runner.ts](../server/services/subagent-runner.ts) 已记录初始 `originToolCallId`；[server/services/subagent-resume.ts](../server/services/subagent-resume.ts) 和 [server/services/agent-communication.ts](../server/services/agent-communication.ts) 的继续执行/输入投递需要补齐每次执行段关联。不能沿用当前选择器“找到子代理后选择它的全部历史”的语义。

#### 仍在运行的子代理：只撤销选中的委派，不冻结整个团队

当动作包含主代理消息回退时，确认框一次说明将撤销哪些仍在运行的委派。用户确认前只预览，不因打开弹窗就停止任务。

确认后先沿既有中断机制关闭这些执行段及其下级委派的新工作入口：未开始的受控写入取消，已开始的短写入登记结果；然后核对最终文件目标。若停止前新增了操作、文件或下级委派，更新受影响的预览再确认，不能静默扩张旧计划，也不能遗漏后就声称整次调用已经恢复。

- 不停止同一子代理中属于其他未选中调用的新执行段，也不停止其他会话或无关子代理。
- 子代理中长时/无法确认结束的 Bash 仍按已有规则跳过并提示，不要求所有进程都结束才允许恢复已知文件。不可立即访问的远程项按逐文件结果处理。
- 仅恢复文件而不撤销消息/调用时，不默认中断子代理；提示它仍可能继续修改文件，并使用普通文件版本变化通知。
- 已撤销执行段的迟到回复或自动续跑不能重新接回已裁剪的主代理调用；复用任务取消和输入投递状态处理，不为此创建全实例隔离状态。

#### 子代理历史与预览

预览在文件行里显示实际修改者和委派来源，例如“主代理 → 子代理 B → b.ts”，但仍按文件合并成一个恢复目标，不增加“同时回退子代理”开关。子代理中的 Bash 缺口也在同一个跳过列表里显示来源。

主代理消息裁剪不等于删除整个子代理会话：撤下被选中的调用呈现/引用，保留子代理执行记录及文件日志供追查和再次恢复。若子代理以后被单独继续使用，以新的输入执行段开始，并获知当前文件版本；不能自动重新执行已撤销的任务。

## 7. 预览、执行与会话处理

### 7.1 只保留现有 preview → apply 形状

复用路由和确认框，不新增平行入口。预览结果分为：

```text
files[]   { fileKey, target, expectedHeadSeq, expectedCurrentState,
            laterChangesSummary, executable, reason? }
skipped[] { sourceOperationId, reason, knownScope? }
summary   { selectedFileCount, skippedOperationCount, affectedOtherSessions }
```

- 一次确认汇总全部覆盖影响和 Bash 缺口，不逐工具弹窗。
- 文件列表按需分页；用户不必滚动加载每一页才能确认，服务器负责保存完整目标清单。
- 用户可以取消某个文件的勾选；提交集合必须是该预览文件集合的子集。
- 保留 `planId + planHash` 绑定已确认的清单，但 hash 不再承担“所有历史证据完整”的证明。
- 主按钮按情况显示“恢复 3 个文件（跳过 1 次 Bash）”，不统一变为“文件回退不可用”。
- 没有可执行文件时明确显示零项；若该动作还包含消息处理，用户仍可选择只处理消息。

### 7.2 执行就是普通的受控写入

每个已选文件通过 InstanceFileWriter 执行：

1. 在队列内重新检查该文件的最新日志序号及当前实际内容是否仍与预览一致。
2. 保存恢复前的当前原始状态。
3. 写入预览中指定的目标，追加新的文件版本，并记录恢复目标引用。
4. 保存逐文件结果，发布版本变化事件。

**只检查本文件的变化，不拿实例最新序号、其他会话消息更新或整个 workspace revision 使计划失效。**

预览后文件又改变时，该行返回“需要刷新”，其他未变文件可以执行；用户看到更新后的差异再确认该行。预览时当前内容本来就与历史 after 不同，不属于这种过期条件，不能因此拒绝。

活跃 Bash 不构成通用执行禁令。它可能在恢复后再次改写文件，界面对此作明确提示；系统不自动终止它，也不通过反复扫描等待“整个世界稳定”才报告本次写入完成。

### 7.3 多文件采用逐文件结果，不做跨设备原子承诺

一次恢复请求是文件写入的分组，不是全实例文件系统事务：

- 每个成功恢复的文件都已有新版本，可再次撤销。
- 某文件 IO 失败、设备离线或预览过期，只影响该项；返回已完成、失败、待刷新和跳过清单。
- 已开始但结果不确定的单个文件，沿用现有 capture-then-compensate 处理该文件；不把其他已成功文件自动写回去，避免补偿覆盖期间的新修改。
- 重试只执行尚未完成的项；已完成项不因为 HTTP 重试而再次覆盖文件。
- 用户要撤销本次恢复，仍使用同一个文件版本恢复机制；不存在另一套 redo 引擎。

这条决策只取消“一个候选缺口就让全批次不可用”的前置门槛，不取消已开始文件写入的逐文件补偿；章节 fork/merge 的结构性快照事务和现有 commit/finalize/discard 出口不在此次替换范围内。

### 7.4 会话历史最后处理

若用户选择的是“会话与文件一起回退”：

- 沿用当前会话的中断和消息写入协调，不冻结其他会话。
- 所有用户选定的可执行文件完成后，才按原选择裁剪当前会话历史；已告知的 Bash skip 不阻断消息处理。
- 有实际执行失败或待刷新项时，先保留会话历史并显示部分结果。用户可以重试，或明确选择保留现状、仅完成消息处理。
- 消息处理失败时，已产生的文件恢复版本仍保留并准确报告；不自动再次改写工作区来假装全局原子性。
- 原始版本日志独立于消息引用，不能随消息删除而级联丢失。

其他会话只收到文件版本变化通知，不被裁剪。事件使相关读缓存失效；已基于旧读取结果排队的写入在执行点重验该文件版本，提示重新读取，而非静默覆盖。本会话自己的成功写入结果推进其已知版本，不能要求连续 Edit 之间机械地插入 Read。首次 Write 没有历史读取基线时沿用正常写入行为，不强制所有写入先 Read。

## 8. 只保留必要约束

| 保留 | 解决的实际问题 |
|---|---|
| 现有设备、路径、用户授权 | 不允许恢复越权文件 |
| 修改前保存原始内容 | 保证存在可恢复版本 |
| 执行时核对本文件的预览基线 | 不把用户未见过的新修改静默覆盖 |
| operationId 与逐文件结果去重 | 防止响应丢失或重复点击引发重复执行 |
| 有界 IO、分页、取消与空间预算 | 防止主线程、队列及存储失控 |

以下做法明确删除或退出新回退的决定链：

- 任一工具无 journal 就要求整段 `evidenceComplete=false` 并拒绝。
- 仅因 Bash 活动而取消 Edit/Write 的恢复能力。
- 为了恢复一个已知 before，校验整段历史每个中间对象和回执。
- `unknownFiles === 0`、所有 attribution 都 measured 等全局完美覆盖要求。
- 多层相同的 scope/fence/manifest proof 互相证明后才允许恢复。
- 归因失败后的持久 workspace quarantine、历史欠账导致的永久禁用。
- 将当前文件漂移解释成无法恢复，或者强制三方合并成功。
- 强制用户加载/阅读所有分页、重复确认相同覆盖提示。
- 普通 Edit/Write 前后的全工作区 tree 扫描。
- 为追求全局原子性建立跨设备事务和自动全批次反向写入。

## 9. 性能、取消与存储

1. SQLite 只保存有索引的元数据，序号分配与登记使用短事务；内容读取、哈希、tree 和文件 IO 在事务外完成。
2. Edit/Write 只处理本文件，不扫描工作区。文件大小和原始内容存储预算复用现有 `FILE_CHANGE_LIMITS`，不再叠加一组“证明预算”。
3. 历史查询和后续修改列表走游标分页；同文件多个选中操作直接定位最早目标，不累计读取全部中间内容。
4. Bash 采用单一有界捕获窗口；固定 tree 后的差量归档使用后台有界任务。扫描输入、路径数、输出字节、子进程超时沿用现有捕获预算，超过时该 Bash 标记 skip。
5. 多文件恢复按文件推进，不把所有文件内容载入 JS 堆，也不把全批次历史查询放进全局写入锁。沿用现有文件、计划及队列的大小上限，超出单批容量时分页分批执行，不把巨大前缀冒充完整结果。
6. 取消停止尚未开始的项；已经实际开始的短写入先登记终态，不把网络取消当作“没有写过”。所有已完成项可在该恢复请求中查询。
7. 慢日志只记录操作类型、耗时、文件/字节数量和跳过原因，不复制文件正文。
8. 仍被保留版本引用的内容不得被默认 TTL 静默清理。空间不足在新写入前告知；用户显式清理历史时，清楚说明哪些版本将不可再恢复。正文去重、孤立对象回收继续复用现有存储能力。

## 11. 实施顺序与完成边界

1. **统一版本基础**：时钟、文件身份、逐文件日志和所有 Edit/Write/编辑器入口；覆盖本地、Windows、远程。用跨会话同文件测试证明顺序和原始内容正确。
2. **版本恢复闭环**：新目标选择、单文件普通写入恢复、跨会话覆盖预览、逐项结果和恢复后的新版本。先让 Edit/Write 在包含任意 Bash 的历史里可用。
3. **Bash 窗口**：全实例活动跟踪、短窗口 tree 差量、后台归档和四类 skip；不扩张为 Shell 副作用分析器。
4. **会话动作收敛**：所有现有单文件、块级、会话回退和编辑重生成的文件恢复部分都走同一服务；消息裁剪保持独立而明确的结果。
5. **删除旧门禁**：移除不再使用的归因逆算、重复证明和旧热路径捕获；完成旧记录兼容与存储验证后结束迁移。

数据库变更只修改 schema 并通过 `bun run db:generate` 生成迁移；本设计阶段不生成或执行迁移，不修改现有用户业务代码，不重启承载会话的服务。

## 12. 验收矩阵

以下是实施验收要求，不表示当前实现已经通过。

| 场景 | 必须得到的结果 |
|---|---|
| 两会话同时 Edit 同一文件 | 有序、连续的真实 before/after 链；不存在最后覆盖而漏记的一次成功写入 |
| 同文件从不同 cwd、父子目录或规范路径别名访问 | 同一设备上归入同一版本链，不按 workspace 分裂 |
| A/B/A/B 交错编辑，A 回退后一次修改 | 精确得到目标 v2；预览说明 B 的后一次修改会被覆盖 |
| 回退自身 | 新增操作，不删除旧版本；能恢复回退前的当前内容 |
| 文件创建、二进制、非 UTF-8、被 gitignore 忽略的 Edit/Write | 恢复原始状态；创建前不存在的文件可恢复为不存在 |
| 本地、Windows、远程成功 Edit/Write | 使用同一顺序及恢复契约，不把兼容旁路当作完成 |
| 独占短 Bash 使用 sed 修改多个文件 | 捕获前后差量，恢复这些文件，不 checkout 其他文件 |
| Bash 窗口内第二个 Bash 短暂进入后退出 | 重叠候选仍 skip，不因结束时只剩一个进程而误判 |
| Bash 长时、后台或与另一 Bash 重叠 | 解释 skip；不长时间持有写入队列，不取消 Edit/Write 历史恢复 |
| Edit 只是在队列等待 Bash 结束 | 随后成功写入的版本正常可恢复，不被等待时间污染 |
| Bash 非零退出但已改文件且捕获成立 | 记录真实差量，不能用退出码推断没有文件修改 |
| before/after 捕获超时后后台扫描终于完成 | 不能补称旧边界有效；之后的新捕获可正常尝试 |
| 较早 Bash 尚在归档、较晚 Edit 已完成，二者一并被选中 | 等待后刷新，或明确跳过 Bash 再确定目标；晚到归档不改变已确认目标 |
| 远程写入后断线、执行器重启或回执被清理 | 写前原文已在服务器；按 ID 对账，不重放旧请求；确认旧执行结束后未知结果不永久锁住设备 |
| 本会话连续 Edit、没有其他来源改写文件 | 自身结果推进基线，不强制每次重新 Read |
| 选中区间中间有不确定 Bash | 其他已知文件目标正常生成并可执行，跳过项可见 |
| 主代理消息范围包含 Agent/Task 调用及子代理 Write/Edit | 沿实际调用来源递归纳入子代理及下级子代理的文件记录，按文件版本合并 |
| 子代理被多次 Send/恢复，主代理只选中第一次调用 | 只纳入选中执行段；后续调用单独展示影响，不按子代理 ID 选中全部历史 |
| 子代理上下文继承了父代理旧消息 | 不重复纳入继承的旧文件记录，只纳入本次委派执行段产生的记录 |
| 子代理调用仍在运行且被选中 | 用户确认后只停止该调用及下级新工作，不停止其他会话；新产生的文件先刷新预览 |
| 子代理中的 Bash 被跳过 | 仅跳过该 Bash，并显示来源链；主代理和子代理其他已知 Edit/Write 仍可回退 |
| 子代理迟到回复、重试或取消 | 不重新接回已裁剪调用；已有文件版本日志保留且仍可单独恢复 |
| 未知 Bash 也改过待恢复文件 | 展示当前到目标的覆盖差异，允许用户确认，不强制合并 |
| 预览后只有无关文件或别的会话消息变化 | 原文件计划仍可执行 |
| 预览后本文件变化，包括相同内容的新版本 | 该行刷新；其他行可执行，不使用旧确认覆盖新版本 |
| 某设备离线或单文件 IO 失败 | 逐项报告，其他文件完成；已完成项不自动被反向写回 |
| 响应丢失、重复点击、重试部分结果 | 根据请求及文件结果去重，不重复覆盖已完成项 |
| 恢复时另一个会话持有旧读取结果 | 收到文件变化通知；基于旧版本的排队写入在执行点重验 |
| 文件已恢复但消息裁剪失败 | 文件新版本可见可撤销，消息保留，准确报告部分结果 |
| 纯文本/只读/系统消息或旧记录缺口 | 不要求凭空生成文件证据，不连带禁用新版本恢复 |
| 多页文件清单、较大历史、空间不足或取消 | 有界读取与准确进度，不要求全量正文入堆，不静默漏项或先写后丢历史 |

最终验收标准：**用户能预测将恢复哪些文件、覆盖哪些后续版本、跳过哪些 Bash；系统按已确认的目标执行，而不是在后台替用户重新裁决这次回退是否值得允许。**
