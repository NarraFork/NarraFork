# 大纲系统 P2 实施计划：替换 spec://，落地任务与多 agent 协作

依据：`docs/OUTLINE_KNOWLEDGE-DESIGN.md`（下称设计）§2.2、§2.6、§3.3、§3.4、§4.1–§4.6、§4.8、§8.1，决策 D25–D27、D31；调研见大纲 `p/1dPpT682`（spec 任务的读者、写者和要保留的行为，Q48–Q52 已由负责人采纳建议）。P1a 的实施计划是 `docs/OUTLINE_IMPLEMENTATION-PLAN.md`，本文沿用它的约定（`outline.enabled` 开关、两种方言、主线程规则、浏览器测试写法）。

## 1. 范围

**P2 的完成标准**（设计 §10）：spec 相关的表和代码退役；一个团队任务能从委派走到完成。

**做**
- 任务：复选框四态、指派、前置、截止；开始即领取（原子）、租约与领取代数；等待由前置和未回答的提问推出。
- 人建任务、`/goal`、锁定与待确认；`Ask` 与收件箱；汇报。
- 续跑改造（D27a–c）、内置视图注入（当前任务、行为边界、compact 上下文，D27e），去掉每 15 次工具调用的任务提醒。
- 计划模式改成计划树；委派即任务，子代理报告与运行记录挂回；唤醒、团队动态、重叠提示、可领取池。
- 事实视图里的「进行中」标记；任务看板。
- 旧 spec 导入（含被吞内容的离线排查）、插件兼容命令（D27d）、旧消息卡片只读化；最后退役 spec 的表、路由、服务、前端组件和 `spec://` 工具路由。

**不在 P2**
- 检索的 embedding、rerank，依据（运行记录挂接、代码锚点），整理队列与「下层已变」：P3。P2 里任务完成时的工具返回照原型给出「要整理的内容和做法」，由原会话整理；整理队列和兜底整理 agent 在 P3。
- 知识库迁移、Bot 写入待确认：P4。
- 多工作区（设计 §4.6 工作区部分，R22、R24）：建议单独成一条线，放在 P2 之后（§9 第 4 问）。关注范围在 P2 只做系统推断的默认值，给团队动态用；`Agent` 工具的 `focus`、`workspaces` 参数随多工作区一起做。
- 跨空间就地编辑、universal 视图（D36 第二、三步）。D36 第一步（agent 跨空间读和总览）作为独立的小线，排在 P1b 之后（§7 PR 0）。

## 3. 切换方式

spec 和大纲任务在一段时间里并存，按会话切换，避免一次性切换打断正在跑的会话。

- 会话上记一个任务后端：`spec` 或 `outline`。`outline.enabled` 打开后，新建的根会话用 `outline`；已有会话保持 `spec`，直到导入（PR 12）把它转过来。子代理跟随根会话。
- 续跑、注入、中断守卫、状态栏、compact 都经一个按后端分派的「任务源」接口读任务，两个后端各一个实现。PR 5 先把现有 spec 读取收进这个接口，行为不变，后续 PR 再加大纲实现。
- `spec://` 的工具路由在 `outline` 会话里不可用（返回提示改用 `OutlineEdit`）；`spec` 会话里照旧。
- 导入后旧会话切到 `outline`；退役（PR 13）在导入跑完、一个发布周期没有回退之后做。

## 4. 存储

在 `server/db/schema.ts` 加，按规范流程生成两种方言的迁移（设计 §7.1 已列出 P2 的列和表）：

| 表或列 | 用途 |
|---|---|
| `outline_blocks.task_json` 扩展 | 现有 `status`、`assignee`、`depends`、`due` 之外加 `manager`（建任务的人或会话）、`humanCreated`、`lock`（锁定人、代确认的 agent、锁定时的版本）、`claimable` |
| `outline_task_claims` | `task_block_id, holder_narrator_id, epoch, task_version_at_claim, claimed_at, expires_at`：领取与租约；`epoch` 是领取代数，迟到的结果按它识别 |
| `outline_pending` | `id, space_id, kind, ops_json, base_json, requested_by, decider_json, status, created_at, decided_at`：待确认 |
| `outline_blocks.in_process` | 派生缓存：块是不是过程（任务和它下面的块、会话空间）。移动子树、改复选框时批量维护，给事实视图、「进行中」标记和检索过滤用 |
| `outline_commits.kind` 加 `confirm` | 确认生效的提交，时间轴上单独标出 |
| 会话上的任务后端 | §3 的 `spec` / `outline` |

- 领取在写入路径里原子完成：`[ ]` 改 `[/]` 的那次提交里，插入或接管 `outline_task_claims` 的行，已有未过期的别人的领取就整次拒绝并说出是谁。
- 租约随会话运行自动续；会话结束或长时间无响应由后台 job 让租约到期，任务回到 `[ ]`，自动记一条「上一位执行者的租约到期」。
- 等待（等前置、等人）不存，读的时候推出来：前置任务未完成，或任务下有未回答的 `Ask`。

## 5. agent 侧

- **工具**：`OutlineEdit` 改成核心工具（现在是可选工具配例程 `outline_edit`）。新增 `Ask`（问题、选项、建议和理由，挂在当前任务下，回答回来时唤醒）。`Agent` 工具加 `task` 参数：传任务地址，子代理说明由任务树按预算渲染。
- **系统提示**：`outline` 会话里，用设计 §0 的三条约定替换 Dynamic Spec 说明（现在在 `server/services/narrator-prompt.ts`、`server/lib/prompts/system-reminders.ts`）。
- **写入返回**：勾完成时返回要整理的笔记和做法（原型的 `settle`）；转待确认时说明交给谁、哪些任务因此要等；领取被拒时说明是谁在做。
- **内置视图注入**（设计 §4.2）：「当前任务」（进行中、等待中、下一个，有字符预算，只在变化时注入）；「行为边界」（D27e 的三个时机）；compact 时注入「未完成的任务和本会话的关键决定」。去掉每 15 次工具调用的任务摘要、任务为空时的催促。
- **续跑**（设计 §4.8）：候选从数据库查：本会话领取的任务和会话空间里的任务，待办或进行中，前置都完成，下面没有未回答的提问，执行人不是人。没有进行中的就把第一个候选提为进行中（大纲里这一步就是一次领取）。续跑提示照旧只点名一条、写明是系统发的、给四种结局；停滞规则、用户中断后抑制一次、中断守卫照旧。
- **计划模式**：`EnterPlanMode` 后在大纲里写计划树；`ExitPlanMode` 提交计划根，人看到和上一版的 diff，选退回、按草稿执行或锁定后执行（可指定代确认的 agent）。计划模式下写任务不受限制。现在的计划审查改成在计划上留意见，不阻塞。`.narrafork/plans/` 在 `outline` 会话里不再使用。
- **子代理**：默认不拿大纲工具（R16）。结束时报告原文按 markdown 语法转成子块挂到它的任务下，运行记录的引用一并记下（依据的挂接在 P3）。派它的会话记摘要、提问、遗留。结果带领取代数，租约转手后才到的记为迟到结果，不能完成任务。

## 6. 人侧

- **任务看板**：过程这一维的内置视图，按执行人和状态分组，能指派、转交、重开；替代会话 dock 里的 Spec 任务面板。状态栏的当前任务改从任务源读。
- **`/goal` 和界面加任务**：建人建任务，管理者是人，执行者是本会话，默认锁定；首轮即使续跑是 off 也启动，计划模式下不启动，按正文去重，留卡片（调研 `p/UMvz9lIu` 列的行为都保留）。
- **用户在界面改任务要通知 agent**：agent 工作中就作为插话送达（现在 `server/routes/spec.ts` 的做法）。
- **收件箱**：在 human attention（`shared/human-attention.ts`）上加 `outline_decision`（待确认、问你的问题）和 `outline_digest`（汇报、代你确认的摘要）。同一个块下的几条提问算一件事，可以一次回答，全部采纳建议是一键。
- **事实视图的「进行中」**：事实块上挂着未完成的任务或提问、或者有等确认的改动时显示，点开列出是哪些。P1a 的事实视图已经隐去过程，P2 补这个标记。
- **汇报**（设计 §3.4）：从提交 diff 生成：新增或改写的事实、完成的任务、在等你的事，每项带链接。

## 8. 取舍

1. **按会话切换，不一次切换**（§3）。代价是有一段时间两套任务源并存，续跑和注入要经接口分派；换来正在跑的会话不被打断，导入可以分批、可回退。
2. **等待不存，读时推导**。续跑候选和看板每次要多查前置和未回答的提问，都走索引、有上限；换来 agent 不用维护受阻状态（D27b）。
3. **任务反思的删除时机**。D26 要求先补齐四个缺口，其中「依据带结果、晚于最后一次相关改动、能确定性校验的由系统校验」要用到 P3 的运行记录挂接。建议：P2 里 `outline` 会话不接任务反思，spec 会话照旧；反思和它的表随 PR 13 或 P3 依据就位后删除，以缺口补齐为准。
4. **整理在 P2 只做「原会话整理」这一条路**：勾完成时工具返回给出内容和做法；队列、兜底整理 agent、「下层已变」在 P3。
5. **插件**：团队插件的源码不在仓库里。兼容期内旧命令按正文比对转换，按正文去重照旧；新命令发布后通知插件作者，旧命令在 PR 13 之后一个版本下线。

## 9. 要负责人拍板的问题

1. **Q14 团队任务树放哪**。建议：会话自己的工作（自己的计划、`/goal`、派给自己子代理的任务）放会话空间，子代理本来就用根会话的空间（D31）；要交给别的根会话或别人一起做的任务，放项目空间的「任务」页。会话空间里的任务要交出去时，系统复制到项目空间并记出处，不让用户每次选。理由：按「谁要看」决定，和读权限一致；会话空间对其他会话不可见，团队任务放那里别人领不到。
2. **Q15 可领取池的策略**。建议首版只做设计里的两样：管理者指派（默认），加一个项目级开关「空闲成员自动领取可领取的任务」（默认关）。优先级、技能匹配、配额等策略等有了使用数据再加。
3. **Q16 agent 在场信息怎么显示**。建议：agent 不显示光标和逐字输入（它本来就按提交整块写入）；页面上只在它领取的任务旁显示一个小标记，页头显示「N 个 agent 在这页的任务上工作」，点开列出；它写入的块短暂高亮一次。人的在场照 PR8 不变。
4. **多工作区放在哪**。建议从 P2 拆出，单独做一条线排在 P2 之后：它涉及设备授权、执行策略和项目归属（D21），和替换 spec:// 互不依赖，放进 P2 会拖长退役。

## 10. 测试

- 任务语义和领取：两种方言的契约测试，加并发领取的随机测试。
- 续跑和注入：现有 `turn-continuation-decisions`、`narrator-session` 的测试在 spec 实现上照过；大纲实现另写同一组场景。
- 端到端：每个里程碑一个 `*.browser.test.ts`（看板、`/goal`、确认、收件箱）和一个服务端端到端（委派 → 子代理 → 挂回 → 完成 → 通知）。
- 导入：用真实形态的 spec 数据（含受保护任务、blocked、行为边界、插件写入）做导入前后的对照。
- CI 守卫：事务原子性守卫（`server/db/transaction-atomicity-contract.test.ts`，文件名不带 guard，推送前要显式跑）、方言清单守卫、vlist 隔离守卫。

## 11. 风险

- **续跑行为变化**：默认 protectedOnly 下改看人建任务，迁移时受保护任务必须一一对应成人建任务，否则会话会停跑或多跑。PR 12 的对照测试专门覆盖。
- **注入时机**：去掉 15 次提醒后，长回合里模型看不到任务进展。靠「当前任务」在变化时注入和 compact 上下文兜住，PR 4 要在长回合场景里验证。
- **插件不可同步验证**：只能按宿主侧接口做兼容，兼容期靠旧命令的转换测试。
- **主线程**：导入、被吞内容排查、租约到期扫描都放后台 job，有上限和超时。
