# 深度掌控 Agent 行为

NarraFork 实战课堂讲义，2026 年。

这份文档讲一件事：agent 跑偏的时候，你能做什么。

不讲怎么写提示词，不讲模型能力。讲的是 agent 工具在模型之外给你的抓手：回退、压缩、干预、协作。业内管这一层叫控制面。模型是引擎，控制面决定你对引擎有多少话语权。

下面分五块：压缩、分叉与回退、子任务干预、团队讨论、并行开发。每块先讲什么时候该用，再讲 NarraFork 里具体怎么做。

NarraFork 是我们自己在做的 agent 协作平台，文档里所有操作以它为准。简单说几个它的特点：一台服务器部署，多人多端同时用，浏览器和手机都能访问；长会话不卡，消息列表用 pretext 做文本测量、配合虚拟列表，几万条消息滚动不掉帧；窄屏和触屏做了专门处理，桌面上的右键菜单在移动端是滑动手势；上下文管理和图形化的 worktree 管理是它的重点，这份文档主要讲这两块。

## 一、压缩

### 为什么压缩值得认真对待

上下文满了，工具会把前面的对话压成一份摘要。从这一刻起，这份摘要就是后续所有推理的事实基础，没有机制会去复核它。

摘要漏了一句关键约束，后面每一轮都在错的前提上推理。它不报错，你只会看到 agent 开始做一些莫名其妙的决定。

所以压缩不是省 token 的性能问题，是正确性问题。

### 什么时候该自己压

不要等系统自动压。自动触发的时机是最差的时机：上下文最满、最乱，你可能正调着一个没解决的问题。你比系统清楚哪些信息可以丢。

该压的时刻：

- 刚做完一件事，要开始一个不相关的新任务。这是最优时机。
- 刚跑完一轮长输出的工具调用，比如几百行测试日志。那坨东西现在是噪音。
- 上下文用了五六成，而你知道后面路还长。别等八成时自动触发。
- 一次探索失败了。十几轮弯路只需要留下一句「A 方案不可行，因为 X」。

不该压的时刻：

- 正在调试一个没解决的问题。你还不知道哪个细节关键，压缩会把它当噪音丢掉。
- 刚压过一次又想压。多次压缩累积失真，正确动作是开新会话、把结论手写进去。
- 上下文里有你要逐字引用的东西，比如一份规格。压缩会改写它。

把主动压缩当 git commit 用：在一个逻辑单元完成时做，带一句说明。

### NarraFork 里怎么做

压缩在消息级别操作。右键任意一条消息，选「压缩到此」，这条之前的对话被压成摘要，之后的原样保留。

也可以多选中间几条消息，选「压缩选中消息」，只压那一段，前后原文都保留。

压缩完成后，点那张压缩卡片能打开摘要全文。可以直接改。改完保存，下一轮请求里模型看到的就是你写的内容。

摘要压错了可以整个撤回：打开卡片，点「撤回压缩」，历史全部回来。压缩失败可以重试，重试时可以换模型。压缩用的模型在设置里单独配置，不跟随当前会话的模型。

撤回之所以可靠，是因为压缩没有删数据。被压缩的消息只是被挡在模型视野外，撤回就是把这个遮挡去掉。

## 二、分叉和回退

### 先分清两个动作

走错路了想退回去，是回退。想试另一条路但不想丢掉现在这条，是分叉。

用回退去做分叉是最常见的浪费：你销毁了一条已经建好的上下文，而重建它比你以为的贵。

### 什么时候分叉，什么时候回退

先问一个问题：现在这条线的上下文还有价值吗？跑偏了、被污染了，就没有，回退或者开新会话。

还有价值，再问：要不要同时保留两条路做对比？要，分叉。确定新方向更好，回退，不留垃圾分支。

该分叉的时刻：

- 做技术方案对比。同一个起点分两条线，各自跑完再比。
- 试一个高风险的大改。分叉出去试，不行丢掉分支，主线不动。
- 上下文很贵。聊了几十轮攒下来的上下文，重建要很久。
- 想问一个跑题的问题。分叉出去问，问完丢掉，主线不受污染。

该回退的时刻：

- 明确知道新方向更好，旧的没有保留价值。
- 代码写坏了但推理是对的。只回退代码，保留对话。
- 上下文被污染了。只回退对话。

有一个常见的错误做法：跑偏了，追加提示词纠正，还不对，再追加。每次追加都在往上下文里堆矛盾信息，模型要自己判断哪个是最终意图。我的经验标准：追加纠正超过两次还没对，停下来，回退或分叉。

### NarraFork 里怎么做

右键任意一条消息，选「从此处分叉」。新会话带着这之前的全部上下文，原会话不动。可以从你自己的消息分叉，也可以从一次工具调用分叉。

多选几条不连续的消息，选「为这些消息分叉」，把这几条挑出来组成一个干净的新会话。适合把一次长调研里有用的几条结论捞出来。

右键选「回退到此处」是回退，可选是否连同工作区的文件改动一起回退。

分叉在这套实现里很便宜：消息内容全局只存一份，分叉只复制指针。你可以放心多分叉，「保留失败路径做对比」才会成为习惯。

## 三、子任务

### 方向错了怎么便宜地纠正

派一个子任务出去调研，三分钟里它在读一堆无关文件。等它跑完再否定结论，代价是那几分钟白烧了，它已经建立的正确部分也一起丢了。

方向错误是子任务最常见的失败模式。不是能力不够，是它猜错了你想要什么，而你给的任务描述总是不完整的。关键问题不是怎么让它一次猜对，是怎么在它猜错时便宜地纠正。

### 五个手段怎么选

按侵入性从轻到重：

1. 看着不动。它方向对，只是慢。
2. 发消息，排队。补充一个它不知道的信息，它跑完这轮自己看。
3. 发消息，插队。方向不对，要马上改，打断当前一轮。
4. 接管。需要来回几轮才能掰正，你自己坐进去带。
5. 中断重派。任务定义错了，丢掉全部已建立的上下文。

选哪个，先问它错在哪一层。缺一个事实，发消息补充，别中断。方向偏了但任务没错，插队纠偏。要来回澄清，接管。任务定义错了，中断重派。

最常见的误判是把第一种当第五种处理：它只是不知道一个事实，你却把它整个停掉重派。反过来也常见：任务定义错了却不停发消息纠偏，上下文里堆满矛盾指令，它越来越糊。我的经验标准：纠偏两次它还在偏，问题不在它，在你的任务描述。停下来重派，并且改写任务描述，不要用同一段描述再派一次。

再往前一步：什么时候该派子任务。该派的：要读很多文件才能得到一个小结论，比如调研、找 bug 根因；需要并行的独立任务；高风险探索。不该派的：任务描述比它要做的事还长，说明这事需要你的上下文；需要频繁来回确认的事；你自己都不确定要什么。子任务适合输入小、过程大、输出小的任务。

### NarraFork 里怎么做

子任务的每一次工具调用都在卡片里逐条列出，`Read · xxx.ts`、`Grep · pattern`。点卡片上的「打开完整会话」，能进入这个子任务的完整页面，看到它的全部消息和上下文用量。

纠偏用 Send：默认排队，加 doInterrupt 插队。还有一个只读的 ContextAsk，问它「你现在判断是什么、读了哪些文件」，它本人不知道这件事发生过，回答是从它的历史快照里生成的。

点「接管」，它当前这一轮不会被打断，继续跑完；跑完之后不再把结果交给父 agent，而是停下来等你。父 agent 那边的调用保持阻塞，不知道你插进来了。想让它立刻停手是另一件事，用「中断」按钮（接管期间的中断是软的，不会结束接管）。掰正之后点「停止接管」，你的成果作为结果回到父 agent 手里。

子任务跑着要批权限时，请求会出现在父会话的卡片里，你在父页面直接批复，不用跳过去。待批的请求不会超时自动拒绝，去吃个午饭回来，任务还活着。

### 反思

agent 无人值守跑的时候，有些决定没人可问，但不能直接放行。反思是这条审批路径的替代。

以危险操作为例。平时有人的会话里，危险命令会弹审批等人点。没人看的会话里没有人可点，于是操作暂停，起一个嵌套的反思循环：它带着完整的对话上下文，看完危险分级（严重度、后果、更安全的替代方案），然后只能调两个决策工具——确认或取消。确认就继续执行，取消就不执行。

两个细节。反思循环只许调决策工具，别的工具一律拒绝。它判断不了的时候（模型超时、重试耗尽），操作不会执行——失败方向是关死的。人随时可以中止反思、自己拿决定权。

同样的结构用在另外三个地方：计划交付审批前先自查，不过就打回去附修改意见；「务必完成」的任务被改动时，先判断这次修改是否违背了用户真正要求的东西；agent 向你提问而你没在时，可以由摘要模型根据对话内容代答——这个功能默认关闭，需要手动开启，且只在无人值守模式下生效，开启后默认等五分钟，你开始作答倒计时就取消。

任务反思里有过一个真实教训。早期版本的提示词问的是「证据够不够」，结果一次会话卡了一个半小时：3067 个测试全部通过，反思循环连续五次驳回，每次都说还差一点证据。每次驳回单独看都合理，合在一起是死循环，因为那个任务的写法本身就没有可判定的完成条件。现在的提示词改成问意图，不问证据是否完备。

## 四、团队讨论

### 问题是没地方说话

你看着 agent 干了一件事，想跟同事说「这个方案有问题」。说在哪？

说在 agent 对话框里，这句话就变成了给 agent 的指令，它会响应甚至照着改。说在群聊里，脱离了上下文，同事得问你说的哪一步。说在 PR 评论里，那是代码评审，不是过程讨论，而且要等代码写完。

### NarraFork 里怎么做

每个会话旁边有一个讨论室，工具栏上带未读角标的「讨论」按钮打开。人在这里说话，agent 看不到。这不是过滤，是两套数据之间没有通道。

讨论出结论了，选中那几条消息，点「发给叙述者」。转发内容会拼成带作者和时间戳的引用块，进入 agent 的输入框，你发之前还能改。讨论太长可以选「摘要后发送」，先让模型总结，你在确认框里改完再发。

已知的缺口：没有 @提及，讨论不能锚定到时间线的具体某条消息，不进全文搜索；讨论室消息不进站内通知中心，只有未读角标。

## 五、并行开发

### 问题是收拢

十个需求同时跑，让任务并行起来不难。难的是另一半：这十个各自进展到哪了，谁和谁有关系，最后怎么收拢。

### NarraFork 里怎么做

每个需求是一个章节：一个 worktree，一个分支，一个 agent 会话。项目主页是一张图，每个节点对应一个真实 worktree，每条边对应一次真实的 fork 或合并。这张图和 git 状态是同一份数据，不是可视化装饰。

图上可以直接操作：右键节点可以 fork、休眠、唤醒、撤销合并。休眠会移除 worktree、保留分支，活跃 worktree 超阈值时最久没用的自动休眠。套索多选几个节点可以批量合并，遇到冲突会停下来等你决定。

没做完的部分直说：章节之间的依赖关系表达不了（用户拖拽创建 dependency 边的能力已移除）；把多个方案组织成对比实验的「探索组」只有数据库表没有功能；commit 和对话的关联只在 split/fork 路径接通，用户在 git 路径提交时不会自动关联消息。所以这张图现在是历史的自动可视化，还不是组织并行工作的工作台。

## NarraFork 的现状

这份文档讲的是它在用功能，不是宣传。没做完的地方：

- 压缩提示词不能自定义，是内置的。
- 多人同时操作一个会话没有并发保护。是「同看加轮流开」，权限批准先到先得。
- 依赖关系、探索组、commit 关联，上面第五节说了。
- AI 辅助解决合并冲突没有 diff 审核界面。

这些缺口有个共同的模式：声明了，校验器接受了，但没有写入者。

有一个已删掉的例子最能说明问题。曾经有一个 frozen 章节状态，声明了、校验器接受、没有代码路径写它。按它过滤会静默返回全部章节，因为没有一行是 frozen，过滤条件等于没写。这个模式不报错，类型系统满意、测试满意，只有端到端跑一遍真实场景才会发现功能不存在。

一个字段不算完成，直到它有真实的写入者和真实的读取者。只做一半就合并，那半个功能会以「看起来能用」的形态留在代码库里，比完全没有更糟，因为下一个人会以为它能用。
