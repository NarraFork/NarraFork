## 0. 摘要

**问题**
- spec:// 和知识库都以「整篇文档」为粒度：块没有身份，链接到不了段落，写入整篇覆盖，合并整篇三方合并。
- spec 的任务是平铺 JSON，用文本 hash 当身份。知识库的链接只连整个条目，agent 用不上。检索只有正则或 FTS 加手写关键词，没有 embedding，也没有个人记忆。
- 多个 agent 协作时没有持久的共享工作状态：团队只是运行时关系，交接靠消息。

**提案：六个概念**
1. **块**：树形大纲的节点，有稳定 id。页就是根块。
2. **类型**：决定块的属性、状态和系统怎么对待它。内置四种：笔记、断言、任务、视图。
3. **链接**：块与块、块与外部（代码、URL、消息、提交）之间的一切关系，用「角色」区分含义。
4. **空间**：权限与归属的边界。分会话、项目、个人、知识库四种。
5. **提交**：一切改动的单位，带来源。时间机器、撤销、审计都建在提交上。
6. **层**：一组等待某人决定的改动，例如提议、探索路径、待确认的记忆。

**九条规则**
1. 一切关系都是链接，含义由角色决定。
2. 能推导的不存储。新鲜度、「已被取代」都从链接推导。
3. 历史只追加。撤销是补偿提交，fork 是复制，两个会话之间没有共享的可变状态。
4. 块不跨空间。跨空间「移动」是复制加原处删除。
5. 层只为待决定的改动而存在。日常写入直接进空间，不经过层。
6. 注入即视图。agent 拿到的上下文是若干视图的渲染结果。
7. 人看实时，agent 看快照。人之间的并发编辑实时合并；agent 的修改按它读到的版本检查，与别人的修改重叠就拒绝。
8. 图谱是黑板。以后还会被用到的东西都写进图谱，消息怎么发都行。
9. 自由度由计划决定。草稿随情况改；已批准的计划，要改先停下汇报（§9）。

**实时协同和多 agent 协作都不新增概念**
- 实时协同：只有正在编辑的页才有 CRDT，块正文在其中合并；结构和属性由服务端排序；落库后仍然是普通的块版本和提交。编辑器自己写，建在 ProseMirror 的视图层上（§7）。
- 多 agent 协作：委派就是在任务树上建任务并指派，角色由任务推导。只新增一种链接角色「涉及」和一张领取记录表（§8）。
- 计划：计划就是任务子树。人在计划上声明它是草稿还是已批准，由此决定 agent 的自由度（§9）。

**已确认的决策**
- D1：agent 直接写入它有写权限的项目空间；探索 fork 的写入进层。例外情况的处理方式见 §6.1，待确认。
- D2：知识过期默认在读取时复核。批量复核由用户点按钮触发，后台复核默认关闭。
- D3：共享空间的历史永久保留，会话空间的历史随会话走。管理员可以彻底清除。
- D4：时间机器按当前权限显示历史。
- D5：数据库是唯一真相源。永远不以 markdown 文件为真相源，也永远不与 Obsidian vault 双向同步。
- D6：支持多人实时协同编辑同一个块。
- D13：计划分草稿和已批准两档，由写计划的人声明；agent 可以在权限内批准，后果记在它的责任人名下。

## 1. 背景与目标

### 1.1 现状

| | spec:// | 知识库 |
|---|---|---|
| 粒度 | 每个叙述者一个命名空间，里面是平铺的文件 | 一个条目就是一整篇 markdown |
| 结构 | 路径只是字符串；没有链接；没有目录列表 | 集合是平铺的；链接只能连到整个条目，agent 工具用不上 |
| 任务 | `tasks.json`：平铺，最多 100 条，用文本 hash 当身份（`server/services/spec-task-service.ts`） | 无 |
| 检索 | 把全部文件读出来跑正则 | FTS 加关键词触发注入；先截取前 N 条，再做标签和 ACL 过滤（`server/services/knowledge-service.ts` 的 `search()`） |
| 写入 | 整个文件覆盖；Edit 的读-改-写不在锁内 | 整篇覆盖；合并时对全文做三方合并 |
| fork / 回退 | fork 时子会话直接引用父会话的修订行（见 §6.4）；回退会话时 spec 内容不跟着回退 | 不涉及 |
| 实时协同 | 无 | 无 |

- 仓库里目前没有任何 embedding、向量或 rerank 代码，也没有面向 agent 的个人记忆。
- 现在的「团队」是根叙述者加子代理的运行时关系（`server/services/subagent-team.ts`、`TeamStatus` 工具），成员之间靠 `Send` 和广播传话。持久的共享状态只有每个会话各自的 `tasks.json`。

### 1.2 目标
- 无限层级大纲、双向链接、传送门（嵌入），以及拼接视图。
- 用一套模型覆盖全局知识、项目规格、任务、个人知识与偏好、会话工作状态。
- 混合检索：FTS + embedding + rerank，并据此给 agent 自动注入相关内容。
- 时间机器：浏览图谱随时间发生的变更。
- 多人实时协同编辑同一页、同一个块。
- 多个 agent 围绕同一套任务和知识协作，委派、领取、交接、验收都落在图谱上。
- SQLite 和 PostgreSQL 两种方言从第一天起同时支持。

### 1.3 不做

**永远不做**
- 以 markdown 文件为真相源。
- 与 Obsidian vault 双向同步。

**初版不做**
- 长时间离线编辑。短暂断线由 CRDT 补齐。
- 在结构层再造一套分支系统。叙事线已经退役（`docs/NARRATIVE_LINE_REMOVAL_PLAN.md`），这次的分支能力建在现有的会话 fork 和 worktree 上。
- 视图的时间机器。
- 从对话中自动抓取个人记忆，并且不经确认就生效。

## 2. 概念模型

```text
空间 ──包含──▶ 块（树） ──链接（角色）──▶ 块 / 代码 / URL / 消息 / 工具调用 / 提交
  │               └─ 类型：笔记 | 断言 | 任务 | 视图
  ├─ 提交（只追加，带来源）──▶ 时间机器 / 撤销 / 审计
  └─ 层（待决定的改动）──合并──▶ 主线上的一个提交
```

### 2.1 块
- 每个块有两个 id：全局 `id`（`generateId()`），以及空间内唯一的短 id `sid`（`generateShortId()`）。agent 只看到 `sid`（§10.1）。
- 字段：`space_id`、`parent_id`、`order_key`（分数排序键）、`kind`、`content`、`props`（按类型校验的 JSON）、作者、当前版本号。
- `content` 是一段规范化的 markdown 源文本，遵守块内 markdown 方言（§7.7）：一种块体（段落、标题、代码或引用）加上行内语法，不含嵌套列表；要嵌套就用子块。多人实时编辑见 §7。
- 页是 `parent_id` 为空的块，页标题就是根块的正文。页可以带 `aliases`、`tags`、`keywords`。任何块都可以「聚焦」成页来浏览。
- 日志、长代码、文件这类大内容不放进块，走现有的上传和附件，块里只放链接。

### 2.2 类型

| 类型 | 状态 | 系统行为 |
|---|---|---|
| 笔记 `note` | 无 | 默认类型；参与检索 |
| 断言 `assertion` | 立场：假设 `hypothesis` / 采纳 `accepted` / 否定 `refuted`；新鲜度由系统推导 | 参与真值维护（§5）；检索时按状态加权（§11.4） |
| 任务 `task` | 待办 `todo` / 进行中 `doing` / 受阻 `blocked` / 待验收 `submitted` / 完成 `done` / 取消 `cancelled` | 有管理者、执行者和前置任务；计划就是任务子树（§9）；多 agent 协作见 §8，续跑见 §10.4 |
| 视图 `view` | 无 | 正文是说明，`props.query` 是查询，嵌入链接是钉住的块；既可以渲染给人看，也可以注入给 agent（§10.3） |

讨论中提到的其他东西，都不需要单独的类型：
- **决策、坑、事实、偏好**：断言加标签。
- **记忆**：个人空间里的断言。
- **摘要**：带「基于」链接的笔记。它基于的子树变了，摘要就进入存疑，按需重新生成。
- **模板**：被复制的页。实例通过「复制自」链接指回模板。
- **实体**：页加别名。两个实体页合并后，被合并的那页变成「同一」重定向。

### 2.3 链接
所有关系存在同一张链接表里，共九种角色：

| 角色 | 目标 | 含义 | 效果 |
|---|---|---|---|
| 提及 `mention` | 块 | 正文里的 `[[…]]` | 产生反链 |
| 嵌入 `embed` | 块 | 正文里的 `![[…]]`，即传送门 | 渲染时展开目标子树，并按目标的权限就地编辑 |
| 基于 `based_on` | 块 / 代码 / URL | 本块成立所依赖的东西，需要持续盯着 | 目标变化时，本块进入存疑（§5.3） |
| 证据 `evidence` | 消息 / 工具调用 / 提交 / URL / 块 | 本块为什么可信：一次冻结的观察，附摘录 | 断言被采纳、任务由非创建者标完成的前提（§5.4、§8.6） |
| 取代 `supersedes` | 块 | 新块取代旧块 | 来源块为「采纳」时，目标推导为「已被取代」 |
| 前置 `blocked_by` | 任务 | 任务之间的依赖 | 续跑只挑前置都已完成的任务；不能成环 |
| 涉及 `touches` | 代码 / 页 / 子树 | 任务的工作范围 | 重叠提示与变更路由（§8.8） |
| 同一 `same_as` | 页 | 实体合并后的重定向 | 引用自动指向规范页 |
| 复制自 `copied_from` | 块 | 跨空间复制、模板实例化的来源 | 只记录来源，不传播任何状态 |

- 正文里的提及和嵌入，在写入时解析进链接表；其他角色需要显式写入。
- 外部目标的地址格式：
  - `code:<仓库>:<路径>#<符号>`，附符号指纹和验证时所在的提交；
  - `url:…`，附内容 hash 和抓取时间；
  - `msg:<id>`、`tool:<id>`、`commit:<仓库>@<sha>`。
- 「基于」和「证据」的区别：**基于是需要一直盯着的东西，证据是一次冻结的观察。** 一条关于代码的断言通常两者都有：基于那个符号；证据是当时读到这个符号的那次工具调用。
- 父子关系是树结构本身，不算链接。

### 2.4 空间

| 空间 | 数量 | 权限 | 替代什么 |
|---|---|---|---|
| 会话 `session` | 每个叙述者一个，子代理也有自己的 | 跟随叙述者的访问权限 | spec 命名空间 |
| 项目 `project` | 每个项目一个，可以先于仓库存在 | 跟随项目成员与角色 | 新增 |
| 个人 `personal` | 每个用户一个 | 仅本人 | 知识库的个人条目；另外存放偏好与记忆 |
| 知识库 `library` | 多个 | 空间门（级别 + 受控标签）；页可以在此基础上收窄 | 知识库集合 |

- 项目空间与 `projects` 行绑定，但允许先建空间、后绑定：起草阶段还没有仓库也能照常使用，仓库建好后再关联。会话属于哪个项目，仍由 `resolveNarratorProjectId`（`server/services/narrator-project.ts`）决定。
- 块不跨空间。在同一空间内，如果把块移到权限更宽的页，实际做法是复制（带「复制自」链接）并删除原处。显式放宽页或空间的权限属于管理操作，要记审计。

### 2.5 提交
- 每次改动都会产生一个提交，包括：
  - 一次 agent 工具调用；
  - 一次合并、一次撤销、一次导入、一次复核；
  - 人的一段连续编辑：同一个人在同一页上的连续操作，空闲 30 秒以内的合并为一个提交；多人在实时会话里共同编辑的窗口，提交记录全部参与者。
- 字段：空间、层（可为空）、空间内单调递增的 `seq`、种类、作者（类型和 id，可以有多个）、叙述者 id、消息 id、工具调用 id、时间、是否可见。
- 块的每个版本都记录由哪个提交产生、到哪个提交失效（`from_seq` / `to_seq`）。按时间点读取（as-of）时直接按这个区间查询。

### 2.6 层
- 层是一组等待某人决定的改动。它属于一个空间，基线是该空间主线上的某个 `seq`。
- 「主线」指空间里不经过层的那部分状态。
- 层只在以下情况出现：提议（包括直写的两条例外）、对已批准计划的变更请求、探索 fork、agent 写入个人空间、不可信来源写入共享空间（§6.2）。
- 合并时，把层里的改动逐块重放到主线上，压成一个提交。不做 DAG，也不做 rebase。

## 3. 权限

- **读**
  - 先过空间门，再看页级收窄；块继承所在页的权限。
  - 查询前先算出可读的空间和页集合，在 SQL 里过滤，然后才取前 N 条。这样就不会出现知识库那种「先截取再过滤、结果变少」的问题。
- **写**
  - 按当轮驱动者的权限判断。没有直写权限时，写入自动转成提议层（§6.2）。
  - 团队成员在团队任务树里的写范围，由角色决定（§8.4）。
- **会话的读权限 = 所有能驱动这个会话的人的权限交集（D9）**
  - 单人会话就是本人的权限；多人共用的项目会话和 Bot 房间取交集。所以个人空间只在单驱动者的会话里可读。
  - 原因：上下文是跨轮共享的，A 那一轮读进来的内容，B 在下一轮就能问出来。现在知识注入按 `_currentUserId` 逐轮解析权限（`server/services/agent-runtime/orchestrator.ts`），挡不住这条路。
- **链接不是后门**：读不到的目标，提及显示为占位，嵌入不展开，都不暴露目标是否存在。
- **时间机器按当前权限显示历史（D4）。**
- **人写的块受保护**
  - agent 删除或移动团队之外的人或会话写的块，会转成提议，等对方决定（§6.1）。
  - agent 要否定人写的断言时，系统自动把它转成一条带证据的「取代」假设，等人采纳（§5.6）。
  - 已批准的计划，改动先停下汇报，完成由批准人确认（§9）。
- **责任人**：agent 的写入和批准都记在它的责任人（创建它的人）名下（§9.4）。
- **信任基线**：项目空间的信任级别与仓库文件相同，因为 agent 本来就能修改仓库里的 CLAUDE.md。跨项目、跨人的内容（知识库、个人空间）则必须经过人确认。

## 4. 时间机器

### 4.1 体验
大纲视图（P1a）和图谱视图（P5）底部有一条时间轴：
- 变更密度图，用颜色区分人、agent、合并和复核。
- 事件标记：层合并、探索路径选定、断言被取代、批量导入、批量存疑、git tag 和发版。
- 拖到某一点，看那个时刻的样子；框选一段，看这段时间里的变更，增、删、改、移分别高亮。
- 播放、按提交单步前进或后退，以及按人、会话或子树过滤。
- 从任意一处变更跳回产生它的会话和消息。
- 把一个块或一页恢复到某个时间点。恢复本身也是一个补偿提交（§6.4）。
- 层画成旁支泳道，只对能看到该层的人显示；合并点画成汇合。

### 4.2 语义
- 时间机器按的是**系统时间**，回答「当时我们是怎么认为的」。
- **有效时间**回答「这件事对哪个代码版本、哪段故事时间成立」。它由断言的「基于」链接（代码锚点带提交号）或者类型属性表达，和系统时间分开，不混用。
- 派生状态（新鲜度）的变化只作为时间轴上的事件出现，不产生内容版本。

### 4.3 实现
- **按时间点读取**：`outline_block_versions` 按 `(space_id, parent_id, from_seq)` 和 `(block_id, from_seq)` 建索引。按视口分批读取，每批最多 500 块，用户展开时再取。
- **拖动**：首次取视口的完整状态，之后只拉相邻提交的增量。版本里存有前后两态，客户端可以正向或反向应用。提交列表用游标分页。
- **大提交**：超过增量上限（§14）的提交在时间轴上折叠成一个事件，详情按需加载。
- **图谱布局**：对所选时间窗里出现过的全部节点一次性算好布局，节点在原位淡入淡出，拖动时不会乱跳。

### 4.4 保留与清除（D3）
- 共享空间（项目、个人、知识库）的历史永久保留。
- 会话空间的历史跟随会话：会话删除就一起删除，会话归档就保留。
- 被引用的版本不能删，包括层的基线、证据、已归档的探索路径。这为以后做历史粗化留了余地；粗化本身初版不做。
- 管理员可以「彻底清除」：从版本、链接摘录、FTS、向量、层和导出中抹掉内容，只留一条不含内容的审计记录。清除由后台 job 执行。
- 设置页显示每个空间的历史占用。

## 5. 真值维护：知识会过期

### 5.1 范围
只有断言参与。笔记和视图不参与；任务只有状态，没有真假。

### 5.2 立场与新鲜度
- **立场**由写的人设置：假设、采纳或否定。
- **已被取代**不单独存储：只要有一条来自「采纳」块的取代链接指向它，就推导为已被取代。
- **新鲜度**由系统推导，缓存在 `outline_freshness` 里，分三档：
  - 新鲜：没有问题。
  - 存疑：它基于的东西变了，附原因。
  - 过期：它基于的东西已经不存在了，例如符号被删、块被删、URL 失效。
- 新鲜度不产生内容版本，不需要写权限，可以随时重算。

### 5.3 存疑的触发
所有触发都来自「基于」链接。

| 目标 | 触发条件 | 做法 |
|---|---|---|
| 代码符号 | 主干上的提交改变了符号指纹 | 复用 `server/lib/agent/structural/`（tree-sitter 大纲）定位符号，对规范化后的文本取指纹。verified 级语法能精确到符号；generic 级或没有语法的语言，退化为「行范围 + 文本指纹」。文件改名靠 git 的改名检测跟上 |
| 块 | 目标的内容变化、被取代或被删除 | 沿「基于」链接传播，最多 2 跳 |
| URL | 可选的定期复查发现内容 hash 变了 | 默认不复查 |
| 时间 | 到了 `props.review_after` 指定的日期 | 用于天然会变的事实，例如值班人、依赖版本 |

- **代码变更检测**：项目空间绑定的仓库主干前进时，后台 job 取出变更路径（`git diff --name-only`，有条数上限和超时），只重算这些路径上的锚点指纹。
- **批量存疑合并显示**：一次大重构引起的大量存疑，合并成一个事件，例如「提交 abc 让 500 条断言存疑」，并附「立即复核这批」按钮，而不是生成 500 条待办。

### 5.4 证据
- 一条证据链接包含：指针、一段有长度上限的摘录快照、抓取时间。所以即使消息后来被 compact、回退或 fork，证据仍然可读。
- 用户在对话里亲口确认也算证据，用 `msg:` 指向那条用户消息。
- **规则：agent 写的断言没有证据就只能是「假设」，有证据才能是「采纳」。人写的断言默认为「采纳」。**

### 5.5 复核（D2）
- **读时复核（默认）**
  - 存疑的断言被检索注入时附带警告，例如「它基于的 `auth.ts#refresh` 在提交 abc 中改过」。
  - agent 如果要依赖这条断言，就先核实，再调用 `Verify` 写回结论和新证据。
  - 不额外花钱：核实由本来就在运行的 agent 完成。
- **批量复核**：用户在合并显示的事件上点按钮触发，模型由用户选择，用户清楚这一步在花钱。
- **后台自动复核（默认关闭）**
  - 开启前需要选好模型、设定每日预算。
  - 按「被检索次数 × 重要性」排队。
  - 只能做两件事：确认「没变」，或者标出「需要改」。不改写内容，拿不准的保持存疑。

### 5.6 写时提示（不额外调用模型）
- 写入断言或新建页时，系统用 embedding 在同一空间里找高度相似的已采纳断言，以及同名或别名相近的页，把结果放进工具返回，例如「已有相近断言 X、Y」「可能已存在页 Z」。
- 由正在写的 agent 自己判断：重复就合并，矛盾就写一条取代链接，无关就继续。
- 如果 agent 直接去否定一条人写的断言，系统不报错，而是自动转成一条带证据的「假设」加取代链接，并生成一条人的决定（§12）。人采纳这条假设后，旧断言自动变为「已被取代」。

### 5.7 局限
指纹抓得到直接改动，抓不到间接漂移，例如断言讲的是 A 的行为，实际改的是 A 调用的 B。间接漂移只能靠读时复核兜底。

## 6. 写入、层与撤销

### 6.1 默认：直写（D1）
- 人在编辑器里直接写入自己有写权限的空间。agent 直接写入会话空间，以及它有写权限的项目空间。
- 每次写入都是一个带来源的提交，可以在时间机器里看到，也可以撤销。
- 以下例外不直接生效，而是自动转成一个提议层（§6.2）。agent 接着干，它读到的是「主线 + 自己的提议」；人有空时一次看完再决定：
  - 删除或移动团队之外的人或会话写的块。同一团队视为同一个作者组（§8.2）。
  - 单次调用改动超过 50 个块。
- 已批准的计划另有规则：要改先停下汇报（§9.5）。
- 并发规则见 §7.5：人之间实时合并；agent 按读取时的版本检查。

### 6.2 层

| 场景 | 什么写入进层 | 谁来决定 |
|---|---|---|
| 提议 `proposal` | 没有直写权限的人或 agent 的写入；直写的两条例外（§6.1）；知识库空间默认所有人的写入都走这里（D8） | 知识库空间：审核人（沿用审核标签规则）；项目空间：被改内容的作者或项目管理员 |
| 变更请求 `change_request` | 对已批准计划的修改（§9.5） | 计划的批准人，或获授权代批的 agent（§9.4） |
| 探索 `exploration` | 探索会话及其子代理对共享空间的写入 | 发起这次探索的人 |
| 待确认 `pending` | agent 对个人空间的写入 | 本人 |
| 隔离 `quarantine` | Bot 会话对任何共享空间的写入 | Bot 的创建者 |

- **存储**：层只存被改过的块的新状态（`outline_layer_blocks`，块级写时复制），以及改动的提交序列（`outline_commits.layer_id`）。每个改动都带基线版本。
- **读取**：能看到这个层的会话或人，读到的是「主线 + 层」：层里的块覆盖主线上的同一块，层里删除的块不出现。
- **索引**：FTS 和向量的行带 `layer_id`。查询时取主线加上自己可见的层，同一个块优先用层里的版本。
- **状态**：进行中 → 待决定 → 已合并 / 已否决（归档，只读，可以显式检索）/ 已放弃（按保留策略回收）。
- **与现有知识库提交状态的对应**：
  - `pending` → 待决定
  - `approved` → 已合并
  - `rejected` → 已否决
  - `changes_requested` → 进行中（附审核意见）
  - `conflict` → 待决定（有冲突）
  - `withdrawn`、`superseded` → 已放弃
- **部分合并**：可以只合并选中的一部分块，系统自动带上它们依赖的新建父块。
- **层不嵌套**：基线永远是主线。fork 一个持有层的会话时，把层复制一份，基线不变。
- 层里的块同样可以实时编辑（§7）。

### 6.3 合并与冲突
合并由后台 job 执行：把层里的改动逐块重放到主线，最后作为一个提交一次性可见（把 `visible` 置为真）。

| 情况 | 处理 |
|---|---|
| 内容或属性：基线版本 ≠ 主线当前版本 | 冲突。块很小，直接展示三方对比，也可以先让 agent 给出合并方案 |
| 移动：目标父块已在主线删除 | 挂到该页的「孤儿」收容处 |
| 移动：会形成环 | 拒绝这条改动 |
| 只是顺序不同 | 分数排序键自然合并，不算冲突 |
| 层里改了主线上已删除的块 | 冲突 |
| 链接指向已删除的块 | 标为悬空 |

存在时间长的层，界面上持续显示「现在合并会有 N 处冲突」。

### 6.4 撤销与 fork

**撤销 = 补偿提交。** 对目标提交里的每个块：之后没人再改过的，恢复到之前的状态；被别人改过的列为冲突，不覆盖。

**回退会话到消息 M**
- 会话空间里来源晚于 M 的提交，自动补偿。
- 已经写到共享空间的提交，在回退对话框里列出（「这 N 处已写入项目空间，是否一并撤销」），由人选择。
- 层里的提交同理，在层内补偿。
- 现在回退会话并不会回退 spec 内容：`server/services/revert-history-commit.ts` 只把 spec 修订的来源消息置空。新模型补上了这一点。

**fork = 复制**
- 子会话的会话空间复制父会话空间的当前状态，不复制历史。
  - 短 id `sid` 保持不变，所以从父会话继承来的上下文里提到的块地址仍然有效。
  - 子空间记录 `forked_from_space_id` 和 fork 时的 `seq`，时间机器可以从这里跳到父空间的历史。
- 父会话持有的层，复制一份给子会话。
- 共享空间不复制。它的历史只追加、归空间所有，子会话直接共享。
- 对比现在的 spec fork：`forkSpecNamespace`（`server/services/knowledge/sqlite-write-store.ts`）让子会话的文件指针直接引用父会话的修订行，而修订行会随父会话的命名空间级联删除。父会话被硬删后，子会话的指针被置空，文件就悄悄消失了。改成复制以后，这一类问题不再存在。

**子代理**
- 有自己的会话空间，与父会话同属一个团队（§8.2）。
- 写共享空间时和父会话一样直写；如果父会话是探索会话，就写进父会话的探索层。
- 来源记录为子代理自己，需要时可以按来源整批撤销。

### 6.5 探索（多路径）
- **探索 fork** 是 fork 的一个选项：子会话及其子代理对共享空间的写入，都进入一个探索层，基线是 fork 时的主线。
- **探索组**：同一次发起的几条路径组成一个探索组。对比视图用嵌入链接把各条路径的方案、结果、代价并排拼在一起，嵌入链接可以指定读哪个层。
- **选定一条路径时**：
  - 合并它的层；
  - 其余的层标为「已否决」并归档，可以作为负面知识显式检索；
  - 自动生成一条决策断言，链接到选中的和落选的路径。
- **与 git 对齐**：探索层可以绑定该会话 worktree 的分支。分支合入主干时提示合并这个层；worktree 被删除而且没有合入时提示放弃。初版只提示，不自动执行。
- 探索与团队的区别：探索是互相替代的几条路（最后只留一条），团队是同一件事的几个部分（都要完成）。团队成员也可以为自己的任务发起探索。

## 7. 实时协同

### 7.1 目标
- 多人同时编辑同一页、同一个块：字符级合并，看得到彼此的光标和在场。
- agent 的修改实时出现在正在看的人面前。
- 数据库仍是唯一真相源（D5）。实时状态只是暂存，会尽快落回块和提交。

### 7.2 两条通道
新增 WebSocket 端点 `/ws/outline?token=`，承载两条通道：
1. **页订阅**：打开一页就订阅它。服务端推送：
   - 结构操作：插入、移动、删除、改属性；
   - 块正文的节流快照，给只看不编辑的人；
   - 在场信息：谁在看这一页、光标在哪个块、哪个 agent 正在读写这里。
2. **页实时会话**：开始编辑一页时加入。一页一个 Y.Doc，其中每个正在被编辑的块有一个 Y.Text（Yjs 的文本 CRDT）。光标和选区作为在场信息同步，位置用「块 id + Yjs 相对位置」表示，所以选区可以跨块。

- 实时会话按页而不是按块，这样在块之间移动光标、按 Enter 新建块时，都不需要重新加入会话，没有切换延迟；撤销栈和光标也能跨块。
- 每个块只属于一页（它的根块所在的页）。通过传送门或拼接视图编辑别的页里的块时，客户端同时加入那一页的实时会话。

### 7.3 正文：CRDT 只在编辑期间存在
- Y.Text 里存的就是块正文的 markdown 源文本，与 `content` 一致。编辑器负责把它渲染成富文本（§7.7）。
- **静止时**：块就是 `content` 一列加上版本历史，没有 CRDT 状态。
- **开始编辑时**：服务端为这一页建一个 Y.Doc，作为权威参与者转发各方的更新。
  - 已有块的 Y.Text 在第一次被编辑时，由服务端用 `content` 初始化；
  - 新建的块由创建它的一方初始化；
  - 任何一方都不能用已有内容重复初始化同一个 Y.Text，否则会出现重复文本。
- **编辑期间**：
  - 增量更新最迟每秒追加到 `outline_live_updates` 一次，防止崩溃丢失；
  - `content` 按节流同步为当前文本，供读取、检索和其他客户端的快照使用。
- **结束时**：最后一个参与者离开并空闲 60 秒后，服务端写下各块的最终版本，删除增量，丢掉 Y.Doc。下次编辑重新建立，开始一个新的会话纪元，客户端重新同步。
- **服务器重启后**：后台 job 用 `content` 和尚未定稿的增量重建，然后定稿。
- **好处**：
  - CRDT 墓碑不会长期堆积；
  - 关系表里的 `content` 始终是真相；
  - 绝大多数块（agent 写的、没有人同时编辑的）根本不经过 CRDT。
- 链接解析、FTS、embedding、新鲜度传播都只在提交时触发，不跟着每次按键运行。

### 7.4 结构与属性：服务端排序，一个动作一个事务
- 一个用户动作是一个**大纲事务**，由结构操作加上若干块的正文修改组成。例如在块中间按 Enter，就是「截断当前块 + 新建下一块并写入后半段」。
- 大纲事务作为一条消息发给服务端，由服务端原子处理：按空间排序，校验权限、成环和版本，写成提交，再广播。
- 客户端先乐观应用，收到确认后对齐。事务被拒绝时（很少见），客户端丢弃这一页的本地状态，从服务端重新同步。
- 同级并发插入导致分数排序键冲突时，由服务端重新生成。
- 并发移动按服务端顺序，后写为准；会成环的移动直接拒绝。
- 正在编辑的块被别人删除时，编辑器提示「已被删除」，可以一键恢复（一次补偿操作）。

### 7.5 人与 agent 的并发规则

| | 人 | agent |
|---|---|---|
| 看到的状态 | 实时 | 读取时的快照 |
| 正文 | Y.Text 实时合并 | 三方合并：以 agent 读到的文本为基线、它写出的新文本为目标算出补丁，应用到当前文本。和读取之后别人的修改不重叠就合并；重叠就拒绝，并返回当前内容 |
| 结构、属性 | 按服务端顺序，后写为准 | 按读取时的版本检查，不一致就拒绝 |

- **为什么人和 agent 不同**：人看得见别人正在改什么，合并结果不对能马上发现；agent 看的是快照，它的修改如果悄悄和别人的修改混在一起，容易产生没人察觉的错误。
- **合并基线**：agent 读到的文本由服务端按会话做有界缓存，作为三方合并的基线；缓存失效时退化为「读取之后有任何变化就拒绝」。
- **实时会话中的 agent**：块所在的页正处于实时会话时，agent 的合并结果作为一个参与者写进 Y.Doc，正在编辑的人能看到 agent 的光标和修改实时出现。

### 7.6 提交、撤销与权限
- 多人在一个实时会话里共同编辑的窗口，产生的提交记录全部参与者（§2.5）。
- **撤销**：每个用户一个统一的撤销栈，一个大纲事务就是一步。正文部分用 Yjs 的 UndoManager，只撤销自己的修改；结构部分用逆操作。经传送门编辑别的页，也记在同一个栈里。编辑器里的撤销和时间机器的「恢复」（补偿提交）是两回事。
- 加入实时会话需要读权限，发送更新需要写权限。权限被收回时，服务端把该参与者踢出。
- 在场信息只显示给能读这一页的人。
- 实时会话按（层, 页）区分，层里的块也可以实时编辑。
- WebSocket 遵守主线程规则：
  - 更新按 50 ms 合并后广播；
  - 正文快照每块每秒最多 5 次，慢客户端只保留最新一份；
  - CRDT 更新不能丢，客户端积压超过上限时断开、重新同步（上限见 §14）。

### 7.7 大纲编辑器（D11）

**结论：自己写大纲编辑器，建在 ProseMirror 的视图层上。** 既不是每块一个编辑器，也不是直接用 Tiptap 的整页文档模式，更不是从零写 contenteditable。

**为什么不选其他方案**

| 方案 | 问题 |
|---|---|
| 每块一个编辑器（Logseq、Roam 的做法） | 缝隙正好落在最高频的操作上：<br>- 跨块选中文字做不到，只能整块选；<br>- Enter 拆块、Backspace 合并、上下方向键都要在编辑器之间切换焦点，中文输入法和移动端键盘容易出问题；<br>- 撤销要把多个编辑器各自的撤销栈拼起来；<br>- 编辑态和显示态是两套渲染，聚焦时版面会跳 |
| 直接用 Tiptap 的整页文档 | 编辑器文档成了真相，和块级身份、传送门（同一块出现在多处）、按块的版本与协同、agent 的块操作都冲突。Tiptap 的协同扩展（y-prosemirror）还要求整页一个 Y.XmlFragment。最后还是得改造成下面的样子 |
| 从零写 contenteditable 内核 | 输入法、Android、iOS、剪贴板的兼容问题是无底洞。现有的行内输入框设计（`docs/RICH_COMPOSER_DESIGN.md`）也明确不手写裸 contenteditable |
| 整页一个 CodeMirror 6 文档，大纲用缩进列表表示（Obsidian Outliner 插件的路子） | 手感最像 Obsidian，自带视口渲染。但树结构要从文本编辑里反推：删掉一个换行就合并了两个块，粘贴带缩进的文本就改了结构。多人实时编辑、agent 同时写入时太脆弱。列为备选 |

**架构**
- **块模型是真相，编辑器文档只是投影。**
  - 一个编辑视图对应一个编辑面：一页、一个聚焦的子树，或一个拼接视图。
  - 编辑器文档是这个编辑面当前窗口内的块树，每个块节点都带块 id。
- **Schema**：
  - `outline > block+`；`block = body + children?`；
  - 块体类型：段落、标题、代码、引用；
  - 行内：文本加标记（粗体、斜体、代码、删除线、链接），以及引用、嵌入、标签三种行内节点。
- **键位由我们定义**：Enter 拆块，块首 Backspace 合并，Tab / Shift-Tab 缩进和反缩进，Alt+↑↓ 移动，Esc 进入块选择模式（整块选择、拖动、批量缩进），等等。
- **输入 → 大纲事务**：ProseMirror 的事务被翻译成结构操作，加上受影响块的正文修改（§7.4）。正文修改的写法是：把受影响的块序列化成 markdown，与 Y.Text 当前内容做 diff，只写差异。
- **远端修改 → 编辑器**：
  - 重新解析受影响的块并替换其内容，通过「源码偏移 ↔ 编辑器位置」的映射保住本地光标。
  - 本地用户正在用输入法组合某个块时，推迟应用远端对这个块的修改，等组合结束再应用。
- **块内 markdown 方言**：
  - 明确规定支持哪些语法，以及每种语法的规范写法。
  - 服务端写入时把正文规范化成规范写法，保证「解析 → 序列化」往返不变。
  - 方言之外的内容按字面文本保留。
- **传送门**：用 node view 嵌入一个子编辑视图，绑定被嵌入的块。选区不跨越传送门边界，和 Notion 的同步块一样。
- **块的外框**（项目符号、折叠箭头、拖拽柄、状态标记、在场头像）用原生 DOM 的 node view 实现，避免每块一个 React 根。
- **超长页**：
  - 主要靠折叠和聚焦。
  - 单个编辑视图同时展开的块数有上限（初值 2000）。超出部分用占位节点，滚动到附近时再替换成内容。
- **只读场景**（搜索结果、聊天里的引用、悬停预览）继续用现有的 `MarkdownContent` 渲染。
- **依赖**：直接用 ProseMirror（`@tiptap/pm` 已在依赖里），不用 Tiptap 的文档和协同扩展；团队在行内输入框和 spec 编辑器上已经积累了 ProseMirror / Tiptap 的经验。新增的 Yjs（MIT 许可证）按 `docs/LICENSES.md` 登记。

**代价**
- 工作量大，是 P1 里最大的一块。
- 块内 markdown 方言需要定义，并长期维护。
- 虚拟化不如「每块一个编辑器」自然，要靠展开上限和占位节点。

### 7.8 编辑器原型的验收清单（P0）
在真实浏览器里跑，沿用行内输入框的浏览器测试方式。覆盖桌面 Chrome / Safari、iOS Safari、Android Chrome。
1. **中文输入法**：在块中间组合输入时按 Enter、Backspace、方向键；组合期间另一个人修改同一个块。
2. **移动端键盘**：连续按 Enter 新建块、按 Backspace 合并块时，软键盘不收起、不闪烁。
3. **跨块剪贴**：跨块选中文字后复制、剪切、粘贴。复制出来的是 markdown 大纲；粘贴多行 markdown 时拆成多个块。
4. **撤销**：输入 → 拆块 → 缩进 → 输入，四步依次撤销、重做；和别人的并发修改交错时，只撤销自己的。
5. **并发**：两人同时编辑同一个块；一人移动另一人正在编辑的块；agent 同时写入同一页。
6. **传送门**：在嵌入里编辑时，源页实时变化；同一个块在一页里出现两次。
7. **性能**：展开 2000 个块的页面，测输入延迟、滚动和内存。
8. **拼接视图**：来自三页的块混排在一起，就地编辑。

## 8. 多 agent 协作

### 8.1 原则：图谱是黑板
- 凡是以后还会被用到的东西——不管是别的 agent、compact 之后的自己，还是接手的人——都写进图谱：任务、发现、决策、结果。
- 消息（`Send`、团队广播、唤醒）怎么发都行。只是消息里谈定的东西，如果以后还要用，就要落到图谱上。
- 这样做的结果：交接不丢；结果可以检索；时间机器按任务子树过滤，就是团队工作的回放；人随时可以接手。

### 8.2 团队的共享状态
- 新模型里，**团队 = 一棵任务子树 + 参与的会话**。现有的运行时团队关系（根叙述者及其子代理，`teamRootOf`）用来确定成员；任务子树是团队持久的共享状态。
- 团队任务树放在根任务所在的空间：通常是项目空间；没有项目时放在根会话的会话空间，成员按分派获得各自子树的写权限。
- 同一团队视为同一个作者组：队友之间删除、移动彼此的块，不触发 D1 的权限确认，改由角色规则约束（§8.4）。

### 8.3 委派 = 建任务 + 指派
1. 委派方在任务树上建一个任务：
   - 目标和验收写在任务块上；
   - 相关的页和决策用提及、基于链接挂上；
   - 工作范围用「涉及」链接声明（§8.8）。
2. `Agent` 工具可以直接传任务地址。子代理的初始提示由任务子树渲染出来（有预算），所以这份说明是持久的、可以检查的，也可以转交给别人。
3. 执行者把进展、发现和中间结果写在自己的任务下面，完成时附上结果和证据提交。
4. 委派方被唤醒后读任务子树取结果。子代理的最终报告由系统自动挂到任务下面（§9.6）。
5. 子代理中途失败或被替换时，新的执行者领取同一个任务，从子树里接着做。

结果写在任务里并绑定领取代数（§8.5），「把上一轮的报告当成新结果」这类误判（`docs/SUBAGENT_REUSE_ISSUES-DESIGN.md` 问题 1）就更难发生。

### 8.4 角色由任务推导

| 角色 | 是谁 | 能做什么 |
|---|---|---|
| 管理者 | 任务的 `manager`，默认是创建者，子树继承 | 修改任务块本身（目标、验收）；指派、转交；验收或打回；取消、暂停；调整子树结构 |
| 执行者 | 当前的领取者 | 在任务下面写子块、拆子任务；推进状态：开始、受阻、提交 |
| 读者 | 其余能读这个空间的人和会话 | 读；可以向执行者提问（§8.7） |

- 一句话概括：**任务块本身归管理者，任务下面的子树归执行者。**
  - 在草稿计划里，执行者也可以改任务块：写明理由即可，管理者会收到通知，可以撤回。
  - 在已批准的计划里，执行者要先提交变更请求（§9.5）。
- 角色只约束任务的结构和状态。普通知识内容（笔记、断言、页）照常按空间权限写。
- 人按空间权限行事。人建的任务，管理者就是这个人。

### 8.5 领取与租约
- 开始做就算领取，不需要单独的领取动作。
- 领取是原子操作：任务没有执行者，或者原执行者的租约已过期，才能领到。领取记录包括执行会话、代数（epoch）、到期时间，以及领取时任务块的版本。
- 会话运行或续跑期间自动续租。会话结束、崩溃或长时间无响应时，租约到期，任务回到可领取状态（或交还管理者）。子树里的进展原样保留，并自动记一条「上一位执行者租约到期」。
- 结果绑定领取代数和任务版本：
  - 管理者改了任务的目标或验收（任务块的版本变了），执行者会收到通知，已经提交的结果标为「需重新确认」。
  - 租约转给别人之后才到的结果，记为「迟到结果」挂在任务下，不能用来完成任务。
- **可领取池**：没有执行者、前置都已完成、并且标记为可领取的任务。空闲成员是否自动从池里领，由团队设置决定；默认关闭，由管理者指派。

### 8.6 状态与验收
- 状态有：待办、进行中、受阻、待验收 `submitted`、完成、取消。「暂停」是一个独立属性，暂停的任务不进续跑候选。
- 标完成时，系统自动收集依据（§9.6）。执行者不是创建者、又没有依据时，任务照样可以完成，但看板上会标出「无依据」。
- 管理者和执行者不是同一个、并且任务要求验收时，提交后进入待验收：管理者验收则完成；打回则回到待办，附意见，原结果保留在子树里。
- 默认不要求验收，由委派方按需对单个任务打开。已批准的计划，整个计划完成时交批准人确认（§9.3）。
- 受阻时写一句在等什么：前置任务、提问、人，或者外部条件。
- 前置关系不能成环，建立链接时检查。

### 8.7 提问与等待
- **问人**：用现有的异步提问。回答可以作为证据链接进任务。
- **问另一个 agent**：建一个指派给它的小任务，打上「提问」标签，并把它设为自己任务的前置。对方完成任务、在结果里写下回答后，依赖解除，自己被唤醒。这里不需要新概念。

### 8.8 范围声明：涉及
- 「涉及 `touches`」链接从任务指向代码路径或符号、页或子树，表示这个任务的工作范围。
- 用途一：**重叠提示**。领取或开始任务时，如果和其他进行中任务的涉及范围重叠，工具返回里会提示，例如「T12（会话 B）也涉及 `auth/refresh.ts`」。由 agent 自己协调，或者由管理者拆分。
- 用途二：**变更路由**。别人改动了我进行中任务涉及范围里的东西，会进入我下一轮的「团队动态」摘要。
- 涉及范围有两个来源：执行者事先声明的（计划），以及运行时观察到的（现有的团队文件变更记录，`recordTeamFileChange`）。
- 模块页上可以直接列出「涉及这里的进行中任务」，这就是「涉及」链接的反链。

### 8.9 唤醒
- 任务事件经现有的 runtime inbox（`server/services/agent-runtime/inbox.ts`，`team` 通道）投递，按「空闲才唤醒」调度，合并去重。
- 会触发唤醒的事件：
  - 有任务指派给我；
  - 我的前置任务完成或取消；
  - 我的提交被验收或打回；
  - 我管理的任务有人提交；
  - 我的提问有了回答；
  - 我的租约即将到期。
- 「涉及范围里有变化」不单独唤醒，只进下一轮的摘要，避免唤醒风暴。
- 每个会话的唤醒有频率上限，多条事件合并成一条（§14）。

### 8.10 每个成员看到什么
在上下文配方（§10.3）里加入以下内置视图：

| 视图 | 给谁 | 内容 |
|---|---|---|
| 我的任务 | 执行者 | 自己领取的任务：目标、验收、最近的进展，有预算 |
| 团队动态 | 所有成员 | 上一轮之后，别人在团队任务树里、以及我的涉及范围里做的改动 |
| 待处理 | 管理者 | 待验收、长时间受阻、可领取但没人领、租约到期 |
| 相关知识 | 所有成员 | 按我的任务的链接和涉及范围加权检索 |

### 8.11 人在环中
- **团队看板**（一个视图）：按执行者和状态分组。人可以在上面指派、转交、验收、打回。
- **在场信息**：页面上显示哪些 agent 正在读写哪里，agent 的编辑实时出现（§7）。
- **回放**：时间机器按任务子树过滤，可以回放一个团队是怎么完成工作的。
- 人作为管理者时，待验收的任务进入人的决定（§12）。

### 8.12 与 DYNAMIC_SPEC_TEAM_TASKS 的关系
`docs/DYNAMIC_SPEC_TEAM_TASKS.md` 设计了一套团队任务模型。它的任务持久化、写操作和 UI 都还没有实施，可以直接按本模型来实现。对应关系如下：

| 那份设计 | 本模型 |
|---|---|
| 团队任务树、稳定编号 | 空间里的任务子树；块的短 id |
| M / E / R 角色 | 由 `manager` 和领取者推导（§8.4） |
| `todo/doing/blocked/submitted/done/cancelled`、暂停、归档 | 任务的状态与属性（§8.6） |
| contractVersion | 任务块的版本 |
| assignmentVersion / executionRunId | 领取代数（§8.5） |
| origin / event / receipt 记录 | 带来源的提交 |
| 持久事件与派发 | runtime inbox 唤醒（§8.9） |
| protected | 别人建的任务，标完成必须附证据；人建任务的管理者是人 |
| Eval 同步对象 SDK | 可以作为 Outline 工具之外的另一种接口，以后再做 |

### 8.13 让 agent 真正用起来
- **最省事的路就是对的路。** `Agent` 工具接受任务地址；子代理的结果默认写回任务；续跑从任务里挑活；团队状态由视图自动注入。agent 不需要「记得」去用图谱。
- **反馈放在工具返回里。** 写时提示（相近断言、可能已有的页）、重叠提示、「你的任务目标已改」，都出现在 agent 正在看的地方。
- **协议只放在关键处。** 领取防止重复劳动（开始做即领取）；需要验收的任务不能自己验收；租约过期自动交还；已批准的计划要改先停下汇报。其余靠反馈和可见性，不靠拦截。
- **记账交给系统**（§9.6）：状态、证据、结果、compact 前的进展都自动落到图谱上，agent 只补判断。
- **提示词保持短。** 系统提示里只放一段简短的协作约定（放在现在 `getDynamicSpecSystemReminder` 的位置），细节由工具描述和返回值承载。
- **可观测。** 统计有多少委派带了任务说明、多少结果写回了任务、多少提交被打回，用这些数据调整提示词和工具，而不是靠猜。

## 9. 计划、自主性与批准

### 9.1 原则
- **大纲是地图，不是轨道。** 系统要保证地图跟得上实际进展，而不是规定 agent 只能沿着地图走。
- **约束要守，计划看档位，笔记随用。** 行为边界和已采纳的决策是约束；计划按它是草稿还是已批准来对待（§9.3）；笔记只是参考。
- **默认信任，事后可见、可撤销。** 事前拦截只留给已批准的计划和不可逆的事。
- **能转换就不拒绝，能异步就不阻塞。** 需要别人决定的改动转成提议或变更请求，而不是报错或弹窗等人。
- **记账交给系统，agent 只补判断**（§9.6）。
- **协议强度随协作人数增长。** 单人工作几乎没有协议；团队才需要领取；跨人才需要确认。
- **小事不记账。** 一次性的小活不需要建任务，也不会被催着建任务。

### 9.2 计划就是任务子树
- 计划不再是一段 markdown，而是一棵任务子树：
  - **计划根**：目标、验收标准、范围与非目标、约束（链接到行为边界和已采纳的决策）、风险；
  - **步骤**：子任务，每一步有目标和产出，可以带验收、前置和涉及范围；
  - **依据**：调研发现（带证据的断言）、关键决策（连同被否的方案）、开放问题（提问任务）。
- 计划放在工作所属的空间：有项目时放项目空间，否则放会话空间。
- 计划可以分层：里程碑 → 步骤 → 子步骤。批准的单位是子树，所以可以只批准第一个里程碑，后面的保持草稿，边做边细化。
- 项目可以提供计划模板页（P5）。

### 9.3 两档计划（D13）

| | 草稿 | 已批准 |
|---|---|---|
| 谁来定 | 默认就是草稿 | 人，或在权限内的 agent（§9.4） |
| agent 能做什么 | 随情况调整：增删步骤、改顺序、改做法，每处改动留一行理由 | 按计划执行：推进状态、在步骤下写进展、把叶子步骤细化成自己的子任务 |
| 需要改计划时 | 直接改；人会在「计划变更摘要」里看到 | 先停下汇报（§9.5） |
| 完成 | 依据自动收集；没有依据的在看板上标出 | 每一步完成附依据；整个计划完成时交批准人确认 |

- 已批准时冻结的是批准那一刻的计划骨架：
  - **算改**：批准时已有步骤的目标、验收或顺序；删除、跳过或取消步骤；在原本就有子步骤的节点下加新步骤。
  - **不算改**：推进状态（开始、受阻、完成）；在步骤下写进展和结论；把批准时的叶子步骤拆成子任务。这些子任务是草稿。
- 人可以随时把一棵子树从草稿批准为已批准，也可以放开回草稿。档位变化本身是一个提交，在时间轴上可见。
- 两档就够了，不需要中间档：草稿的改动本来就看得见，区别只在于事前问不问。

### 9.4 批准人与责任人
- **责任人**：每个 agent 都有一个责任人，即创建它的人。
  - 子代理沿创建链上溯到根会话的创建人；
  - 例程触发的会话，责任人是例程的创建人；
  - Bot 的责任人是 Bot 的创建人。
- **agent 可以在权限内批准**：
  - 批准计划：比如管理者 agent 把它给下属定的计划批准为已批准，下属的变更请求就报给它，不必惊动人；
  - 批准变更请求：代批别人提交的变更请求。
- **权限 = 三者的交集**：它在任务上的角色、责任人自己的权限，以及人在批准计划时授予的范围。
  - 人批准的计划，目标和验收（也就是契约）只有人能改。
  - 步骤层面的调整，人可以在批准时授权管理者 agent 代批，默认不授权。
  - 不能自批：提出请求的会话和批准它的会话不能是同一个。
- 超出权限就沿链往上：执行者 → 管理者 agent → 人。
- **后果落到责任人头上**：
  - agent 的每次批准都记为「agent X 代 Y 批准」，Y 是责任人。审计和时间机器里显示完整的链条。
  - 责任人会收到「代你批准的变更」摘要，可以一键撤回（补偿提交）。
  - 如果计划原来的批准人是另一个人，他也会收到通知。

### 9.5 已批准的计划要改时：先停下汇报
1. agent 想改已批准的步骤时，工具不报错，而是把这次修改连同理由转成一条变更请求，放进一个层里（§6.2）。工具告诉 agent：请求交给了谁、哪些步骤因此受阻，以及可以先做不受影响的部分。
2. 受影响的步骤，以及依赖它们的步骤，标为受阻，不进续跑。不受影响的步骤照常执行，这本身就是「尽量按计划实施」。如果所有剩余步骤都受影响，agent 结束本轮，等待答复。
3. 请求发给权限内最近的批准人（§9.4）。批准人看到 diff 和理由后，可以：
   - 批准；
   - 驳回，按原计划执行；
   - 驳回并附意见；
   - 把这一部分放开为草稿。

   决定之后唤醒 agent。
4. 提示词里只放一句：「遇到障碍先尽量在计划内解决；确实要改计划，就提交变更请求，并停下相关的工作。」

### 9.6 记账交给系统
- **能推断的由系统直接更新**：开始做就算领取；实际改动的文件计入涉及范围；更新最近活动时间。
- **证据自动收集**：从本轮的工具调用里推断证据和「基于」关系，agent 可以补充或更正。agent 读完 `auth.ts` 写下一条结论，那次读取会自动成为证据，相关符号成为「基于」，结论直接是「采纳」。
- **结果自动挂回**：子代理的最终报告自动挂到委派它的任务下面。
- **compact 不丢进展**：compact 之前，把 compact 摘要里和当前任务相关的部分写回任务进展。
- **在自然节点同步，而不是按固定频率提醒**：
  - 同步时机：回合结束、compact 之前、子代理返回、给用户写总结时；
  - 只在发现明显不一致时才提示一句，比如「测试都过了，T3 还是进行中」；
  - 现在每 15 次工具调用一次的任务提醒、任务列表为空时的催促，都去掉。
- **只注入变化**：团队动态和任务摘要只在有变化时才进上下文。

### 9.7 计划模式（D14）
现在的 `EnterPlanMode` / `ExitPlanMode` 提交的是一段 markdown（或 `.narrafork/plans/` 下的计划文件）。改为围绕计划子树来做：
1. **进入规划**：建立或选定一个计划根，状态为「规划中」。规划阶段的工具限制保留为可选，沿用现在的宽松计划模式选项。
2. **规划**：agent 或 plan 子代理直接在大纲里写计划子树。人可以同时在编辑器里改、加约束、提问，讨论就发生在计划本身上。
3. **提交**：`ExitPlanMode` 改为提交计划根的地址，计划进入待审。
4. **审批**：人看到计划，以及它和上一版的 diff，可以选择：
   - 驳回并附意见，计划回到规划中；
   - 按草稿执行；
   - 批准为已批准，并选择是否授权管理者 agent 代批步骤调整。
5. **执行**：续跑从计划里第一个可以开始的步骤开始。

- 自动反思审查（现在的 plan reflection）改为在计划上留下审查意见。审查通过时最多只能「按草稿执行」；要成为已批准，必须由人或获授权的 agent 来批。
- `.narrafork/plans/` 下的计划文件退役。

## 10. agent 接口

### 10.1 地址
- 块地址写成 `空间/短id`；会话空间可以省略前缀。
- 空间的写法：
  - `s`：本会话；
  - `p`：本会话所属的项目，有多个项目时写 `p:<项目名>`；
  - `me`：驱动者的个人空间，只在单驱动者会话中可用；
  - `kb:<名称>`：知识库空间。
- 例：`7Hq1x9Ka`（本会话）、`p/Ab3dEf9Q`、`kb:arch/Zz81Qw0P`。

### 10.2 工具（名称暂定）

| 工具 | 作用 |
|---|---|
| `OutlineRead` | 按地址读一棵子树。参数：深度、是否展开嵌入、可选的 `as_of` |
| `OutlineSearch` | 混合检索。参数：查询、空间范围、类型、`include`（默认不含已否定和已被取代的断言） |
| `OutlineEdit` | 一组有序的内容操作：插入（可以用一段 markdown 大纲一次插入多块）、更新、移动、删除、增删链接 |
| `Task` | 任务动作：开始（即领取）、受阻、提交、验收、打回、转交、取消、暂停、恢复、批准计划、提交或批准变更请求。动作会检查角色、租约和计划档位（§8、§9） |
| `Verify` | 对一条断言写回复核结论（新鲜 / 需要改 / 否定）和证据 |

- `Agent` 工具新增 `task` 参数（§8.3）。
- `EnterPlanMode` / `ExitPlanMode` 改为围绕计划子树工作（§9.7）。
- `OutlineEdit` 没有隐式删除，要删除必须显式写出来。
- 给 agent 看的渲染格式：

```text
- [p/Ab3dEf9Q] auth 模块
  - [p/7Hq1x9Ka] 坑：token 刷新存在竞态 ‹断言·采纳·存疑：auth.ts#refresh 在 abc 改过›
  - [p/Kd02LmQ1] 补回归测试 ‹任务·进行中·执行：本会话›
```

- 现有 `Read`、`Write`、`Edit`、`Grep` 对 `spec://` 的路由在 P2 移除。

### 10.3 上下文配方 = 视图
- 每个会话空间里有一页「上下文」，内容是若干视图的嵌入链接。每个链接带触发时机和字符预算，触发时机可以是：每轮、每 N 次工具调用、compact 时、按当前消息检索。
- 现在写死的几种注入，改为下面的内置视图；多 agent 协作另有几个视图（§8.10）：

| 现在 | 内置视图 |
|---|---|
| 任务摘要 `living_work_spec`（`server/services/spec-reminder.ts`） | 「当前任务」：进行中、受阻、下一个 |
| 行为边界 `behavior_fence` | 「行为边界」：会话空间和项目空间里标记为 `agent_readonly` 的页 |
| 知识关键词注入（`server/services/knowledge-injection.ts`） | 「相关知识」：按当前消息和工具输出检索（§11） |
| compact 时注入完整任务列表 | 「compact 上下文」：未完成的任务，加上本会话涉及的关键决策 |
| 无 | 「我的偏好」：个人空间里已采纳的偏好，只在单驱动者会话中注入 |

- 插件写入的 SOP 段落和任务，作为块写进对应的页，作者记为插件。
- 项目可以在项目空间里放一个模板页，作为本项目会话的默认配方（P5）。
- 每一段注入都能追溯到某个视图，用户能看出 agent 为什么知道某件事。

### 10.4 任务与续跑
- 续跑候选从数据库查询，和 agent 当前上下文里看到什么无关：
  - 本会话持有领取的任务，以及会话空间里的任务。要求：状态为待办或进行中，前置都已完成，没有暂停；
  - 管理者还会拿到待处理事项：待验收、租约到期、长时间受阻；
  - 执行者是人的任务永远不进候选。
- 没有进行中的任务时，把第一个候选提为进行中。这一条保留现有行为（`server/services/narrator-session.ts`）。
- **人建的任务**（`/goal` 或界面添加）：作者和管理者是人，执行者是本会话。默认是草稿：依据自动收集，没有依据的在看板上标出；人把它批准为已批准之后，完成需要人确认（§9.3）。
  - 这条规则替代现在的「受保护任务」，文本 hash 锁（`spec_protected_tasks`）也就不需要了。
  - 任务反思（`server/lib/agent/tools/task-reflection.ts`）是否保留为可选的证据核查，P2 再决定。

## 11. 检索

### 11.1 流程
1. **确定范围**：按 §3 算出可读空间的集合（包括会话可见的层），在 SQL 里过滤。
2. **召回**：FTS 与向量并行召回。FTS 在 SQLite 上用 FTS5 trigram，在 PG 上用 pg_trgm，沿用 `server/db/fts.ts` 和 `server/db/pg-fts.ts` 的做法。页的 `keywords` 作为高精度触发词，一起合并进来。
3. **扩展**：沿基于、提及、取代链接和父块各扩展 1 跳。
4. **排序**：配置了 rerank 模型就用它，否则用 RRF（倒数排名融合）；最后乘上状态权重（§11.4）。
5. **渲染**：带面包屑（祖先标题）和状态标记，受字符预算约束。

### 11.2 embedding
- **输入**：块正文加上所在页的标题，不含完整的祖先路径。这样祖先改名时，不会触发整棵子树重算；完整的面包屑只在 rerank 时加上。
- **缓存**：以（模型, 内容 hash）为键。相同内容在不同版本、层和合并之间复用，合并时不用重新计算。
- **计算时机**：写入后由后台 job 批量计算。没有配置 embedding 模型时，退化为纯 FTS。
- **模型**：从模型目录里选（`shared/model-catalog` 已有 embedding 类别），支持 API 和 OpenAI 兼容的本地端点（D7）。

### 11.3 向量存储（D10）
- 初版不引入原生扩展：量化后的向量存成 BLOB，在 db-worker（`server/lib/db-worker/`）里先按空间过滤，再暴力扫描。这种做法两种方言通用。
- 单次扫描超过时间预算就降级为纯 FTS，并记一条慢日志。
- 规模上去以后再接 sqlite-vec 或 pgvector，接口提前预留。初定的门槛是单实例超过约 20 万块，以 P0 的基准测试为准。
- 不一开始就用扩展，是因为 bun:sqlite 在 macOS 上默认使用系统自带的 SQLite，要加载扩展就得换一个 SQLite 构建，跨平台打包的成本高。

### 11.4 状态权重与自动注入

| 状态 | 自动注入 | 搜索默认 | 排序 |
|---|---|---|---|
| 笔记 | 按相关度 | 返回 | 正常 |
| 断言：采纳 + 新鲜 | 是 | 返回 | 正常 |
| 断言：采纳 + 存疑 | 带警告注入 | 返回，带标记 | 降权 |
| 断言：假设 | 否（产生它的会话内除外） | 返回，带标记 | 降权 |
| 断言：否定，或已被取代 | 否 | 需要显式 `include` | — |

- 任务和视图不进「相关知识」，它们有各自的专门视图。
- 自动注入受三项约束：相似度阈值、每轮条数上限、字符预算。同一个块在一个 compact 周期内只注入一次，沿用 `knowledge_injection_events` 的语义。

## 12. 人的决定

不新建收件箱，而是在现有的 human attention（`shared/human-attention.ts`，现有 `async_question`、`blocking_question`、`permission`、`plan_approval`、`reflection` 五种）上加两种：

| kind | 内容 |
|---|---|
| `outline_decision` | 待决定的层（提议、对已批准计划的变更请求、探索路径选择、记忆确认、Bot 隔离）；待审的计划（取代现在的 `plan_approval`）；管理者是人的待验收任务 |
| `outline_review` | 需要人看的事件：批量存疑、对人写断言的取代提议、撤销时的冲突、代你批准的变更摘要 |

列表行只带 id 和摘要，不带正文，与现有 human attention 的列表约束一致。

| D5 | 数据库是唯一真相源。永远不以 markdown 文件为真相源，永远不与 Obsidian vault 双向同步 | 已确认 |
| D6 | 支持多人实时协同编辑同一个块。人与人之间：按页建实时会话，块正文是其中的 Y.Text（内容就是 markdown 源文本，只在编辑期间存在）；结构与属性由服务端排序，一个用户动作是一个原子的大纲事务。agent：按读取版本做三方合并，重叠就拒绝 | 需求已确认；Yjs 选型为建议 |
| D7 | embedding 和 rerank 从模型目录配置，支持 API 和 OpenAI 兼容的本地端点；未配置时退化为 FTS | 建议 |
| D8 | 知识库空间默认走审核（层即提议），可以按空间改为直写 | 建议 |
| D9 | 会话读权限 = 所有驱动者权限的交集 | 建议 |
| D10 | 向量初版存为 BLOB，在 db-worker 里暴力扫描，不引入原生扩展 | 建议 |
| D11 | 编辑器：自研大纲编辑器，建在 ProseMirror 视图层上；块模型是真相，编辑器文档只是投影 | 建议 |
| D12 | 多 agent：图谱是黑板；委派即建任务；角色由任务推导；开始做即领取，领取带租约；验收默认关闭、按需打开；同一团队视为同一作者组 | 建议 |
| D13 | 计划分草稿和已批准两档，由写计划的人声明；已批准的计划要改先停下汇报；agent 可以在权限内批准，后果记在责任人名下 | 已确认 |
| D14 | 计划模式重做：计划就是任务子树，审批时选择草稿或已批准，计划文件退役 | 建议 |

**D1 为什么是直写**：讨论时最初的方案是「回合结束时自动合并进主线」，后来改成直写，并已确认。
- 对用户来说一样是自动的，但少了一套每个会话都要维护的层和覆盖读取。
- 原本放在合并关口的检查挪到写入时（§5.6），撤销统一为补偿提交，例外复用现有的权限确认。
- 代价是另一个会话可能读到某一轮进行到一半的修改。影响小，而且在时间机器里可见。

## 18. 待定问题
1. **块内 markdown 方言**：具体支持哪些行内语法和块体类型？规范写法怎么定？
2. **块选择模式与移动端手势**：整块选择、拖拽、批量缩进的交互细节。
3. **超长页**：占位节点按需替换是否够用，还是只靠折叠与聚焦？以 P0 的性能数据为准。
4. **知识库旧修订**：迁移时只迁当前状态，旧修订以只读形式保留多久？
5. **标签**：用属性里的字符串数组，还是像 Obsidian 那样每个标签对应一页？
6. **跨仓库**：一个需求跨多个仓库时，项目空间如何对应多个 `projects` 行？
7. **探索对比**：探索组的对比视图要不要内置模板（方案 / 结果 / 代价三栏）？
8. **任务反思**：是否保留为可选的完成证据核查（§10.4）？
9. **团队任务树的位置**：什么时候放项目空间、什么时候放会话空间，要不要让用户选？
10. **可领取池**：除了「自动领取默认关闭」，是否需要按团队配置更多策略？
11. **agent 在场信息**：在界面上怎么显示才不吵？
12. **代批授权**：只能在批准每个计划时逐个授权，还是允许责任人设一个会话级的默认值？
13. **规划阶段的工具限制**：默认只读（像现在的计划模式），还是默认宽松？

## 19. 主要风险
- **大纲编辑器与实时协同的复杂度**：自研编辑器、块内方言、页实时会话、传送门就地编辑、输入法和移动端，几样叠在一起，是工作量最大的不确定项。P0 按 §7.8 的清单做原型验收。
- **agent 的编辑习惯**：模型更熟悉编辑文件，而不是结构化操作。所以 `OutlineEdit` 允许用 markdown 大纲批量插入，返回值要给足上下文。P0 用真实任务实测。
- **按时间点读取的性能**：历史增长后，这类查询能否保持在视口级别的延迟。P0 先做基准测试。
- **多 agent 的成本与唤醒风暴**：唤醒有频率上限，自动领取默认关闭，「涉及」范围里的变化只进摘要、不单独唤醒。
- **迁移时的 ACL 一致性**：知识库大约 45k 行代码，迁移前必须先有对照用例，再动数据。
