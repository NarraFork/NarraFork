# 大纲：知识、记忆与任务的统一模型

> 决策：D1–D4 已确认；D5–D10 是建议，待确认（§13）。

## 0. 摘要

**问题**
- spec:// 和知识库都以「整篇文档」为粒度：块没有身份，链接到不了段落，写入整篇覆盖，合并整篇三方合并。
- spec 的任务是平铺 JSON，用文本 hash 当身份；知识库的链接只连整个条目，agent 用不上；检索只有正则或 FTS 加手写关键词；没有 embedding，也没有个人记忆。

**提案：六个概念**
1. **块**：树形大纲的节点，有稳定 id。页就是根块。
2. **类型**：决定块的属性、状态和系统怎么对待它。内置四种：笔记、断言、任务、视图。
3. **链接**：块与块、块与外部（代码、URL、消息、提交）之间的一切关系，用「角色」区分含义。
4. **空间**：权限与归属的边界。分会话、项目、个人、知识库四种。
5. **提交**：一切改动的单位，带来源。时间机器、撤销、审计都建在提交上。
6. **层**：一组等待某人决定的改动，例如提议、探索路径、待确认的记忆。

**六条规则**
1. 一切关系都是链接，含义由角色决定。
2. 能推导的不存储。新鲜度、「已被取代」都从链接推导。
3. 历史只追加。撤销是补偿提交，fork 是复制，两个会话之间没有共享的可变状态。
4. 块不跨空间。跨空间「移动」是复制加原处删除。
5. 层只为待决定的改动而存在。日常写入直接进空间，不经过层。
6. 注入即视图。agent 拿到的上下文是若干视图的渲染结果。

**已确认的默认值（D1–D4）**
- agent 直接写入它有写权限的项目空间。以下两种情况走权限确认：删除或移动别人写的块；单次改动超过 50 个块。探索 fork 的写入进层。
- 知识过期默认在读取时复核。批量复核由用户点按钮触发，后台复核默认关闭。
- 共享空间的历史永久保留，会话空间的历史随会话走。管理员可以彻底清除。
- 时间机器按当前权限显示历史。

## 1. 背景与目标

### 1.1 现状

| | spec:// | 知识库 |
|---|---|---|
| 粒度 | 每个叙述者一个命名空间，里面是平铺的文件 | 一个条目就是一整篇 markdown |
| 结构 | 路径只是字符串；没有链接；没有目录列表 | 集合是平铺的；链接只能连到整个条目，agent 工具用不上 |
| 任务 | `tasks.json`：平铺，最多 100 条，用文本 hash 当身份（`server/services/spec-task-service.ts`） | 无 |
| 检索 | 把全部文件读出来跑正则 | FTS 加关键词触发注入；截取前 N 条之后才做标签和 ACL 过滤（`server/services/knowledge-service.ts` 的 `search()`） |
| 写入 | 整个文件覆盖；Edit 的读-改-写在锁外 | 整篇覆盖；合并时对全文做三方合并 |
| fork / 回退 | fork 时子会话直接引用父会话的修订行（见 §6.4）；回退会话不回退 spec 内容 | 不涉及 |

仓库里目前没有任何 embedding、向量或 rerank 代码，也没有面向 agent 的个人记忆。

### 1.2 目标
- 无限层级大纲、双向链接、传送门（嵌入），以及拼接视图。
- 用一套模型覆盖全局知识、项目规格、任务、个人知识与偏好、会话工作状态。
- 混合检索：FTS + embedding + rerank，并据此自动注入给 agent。
- 时间机器：浏览图谱随时间发生的变更。
- SQLite 和 PostgreSQL 两种方言从第一天起同时支持。

### 1.3 非目标（初版）
- 多人实时协同编辑同一个块（CRDT）。
- 以 markdown 文件为真相源，或与 Obsidian vault 双向同步。初版只做只读导出。
- 在结构层再造一套分支系统。叙事线已经退役（`docs/NARRATIVE_LINE_REMOVAL_PLAN.md`），这次的分支能力建在现有的会话 fork 和 worktree 上。
- 视图的时间机器。
- 从对话中自动抓取个人记忆，且不经确认就生效。

## 2. 概念模型

```text
空间 ──包含──▶ 块（树） ──链接（角色）──▶ 块 / 代码 / URL / 消息 / 工具调用 / 提交
  │               └─ 类型：笔记 | 断言 | 任务 | 视图
  ├─ 提交（只追加，带来源）──▶ 时间机器 / 撤销 / 审计
  └─ 层（待决定的改动）──合并──▶ 主线上的一个提交
```

### 2.1 块
- 两个 id：全局 `id`（`generateId()`），以及空间内唯一的短 id `sid`（`generateShortId()`）。agent 只看到 `sid`（§7.1）。
- 字段：`space_id`、`parent_id`、`order_key`（分数排序键）、`kind`、`content`、`props`（按类型校验的 JSON）、作者、当前版本号。
- `content` 是一段行内 markdown，可以包含代码块，但不包含嵌套列表。需要嵌套就用子块。
- 页 = `parent_id` 为空的块，页标题就是根块的正文。页可以带 `aliases`、`tags`、`keywords`。任何块都可以「聚焦」成页来浏览。
- 日志、长代码、文件这类大内容不放进块，走现有的上传和附件，块里只放链接。

### 2.2 类型

| 类型 | 状态 | 系统行为 |
|---|---|---|
| 笔记 `note` | 无 | 默认类型；参与检索 |
| 断言 `assertion` | 立场：假设 `hypothesis` / 采纳 `accepted` / 否定 `refuted`；新鲜度由系统推导 | 参与真值维护（§5）；检索时按状态加权（§8.4） |
| 任务 `task` | 待办 `todo` / 进行中 `doing` / 受阻 `blocked` / 完成 `done` / 取消 `cancelled` | 有负责人和前置任务；续跑从这里挑任务（§7.4） |
| 视图 `view` | 无 | 正文是说明，`props.query` 是查询，嵌入链接是钉住的块；可以渲染给人看，也可以注入给 agent（§7.3） |

讨论中出现过的其他东西都不需要单独的类型：
- **决策、坑、事实、偏好**：断言加标签。
- **记忆**：个人空间里的断言。
- **摘要**：带「基于」链接的笔记。基于的子树变了，摘要就存疑，按需重新生成。
- **模板**：被复制的页。实例通过「复制自」链接回模板。
- **实体**：页加别名。合并两个实体页时，被合并的那页变成「同一」重定向。

### 2.3 链接
所有关系存在一张链接表里，共八种角色：

| 角色 | 目标 | 含义 | 效果 |
|---|---|---|---|
| 提及 `mention` | 块 | 正文里的 `[[…]]` | 产生反链 |
| 嵌入 `embed` | 块 | 正文里的 `![[…]]`，即传送门 | 渲染时展开目标子树，并按目标的权限就地编辑 |
| 基于 `based_on` | 块 / 代码 / URL | 本块成立的前提，需要持续盯着 | 目标变化时本块存疑（§5.3） |
| 证据 `evidence` | 消息 / 工具调用 / 提交 / URL / 块 | 本块为什么可信：一次冻结的观察，附摘录 | 断言被采纳、人建任务被标完成的前提（§5.4、§7.4） |
| 取代 `supersedes` | 块 | 新块取代旧块 | 来源块是「采纳」时，目标推导为「已被取代」 |
| 前置 `blocked_by` | 任务 | 任务之间的依赖 | 续跑只挑前置任务都已完成的任务 |
| 同一 `same_as` | 页 | 实体合并后的重定向 | 引用自动指向规范页 |
| 复制自 `copied_from` | 块 | 跨空间复制或模板实例化的来源 | 只记录来源，不传播任何状态 |

- 正文里的提及和嵌入在写入时解析进链接表；其他角色需要显式写入。
- 外部目标的地址格式：
  - `code:<仓库>:<路径>#<符号>`，附符号指纹和验证时的提交；
  - `url:…`，附内容 hash 和抓取时间；
  - `msg:<id>`、`tool:<id>`、`commit:<仓库>@<sha>`。
- 「基于」和「证据」的区别：**基于的是需要一直盯着的东西，证据是一次冻结的观察。** 一条关于代码的断言通常两者都有：基于那个符号；证据是当时读到这个符号的那次工具调用。
- 父子关系是树结构本身，不算链接。

### 2.4 空间

| 空间 | 数量 | 权限 | 替代什么 |
|---|---|---|---|
| 会话 `session` | 每个叙述者一个，子代理也有自己的 | 跟随叙述者的访问权限 | spec 命名空间 |
| 项目 `project` | 每个项目一个，可以先于仓库存在 | 跟随项目成员与角色 | 新增 |
| 个人 `personal` | 每个用户一个 | 仅本人 | 知识库的个人条目；另外存放偏好与记忆 |
| 知识库 `library` | 多个 | 空间门（级别 + 受控标签）；页可以在此基础上收窄 | 知识库集合 |

- 项目空间与 `projects` 行绑定，但允许先建空间、后绑定：起草阶段还没有仓库时照常使用，仓库建好后再关联。会话归属哪个项目仍由 `resolveNarratorProjectId`（`server/services/narrator-project.ts`）决定。
- 块不跨空间。在同一空间内，如果把块移到权限更宽的页，实际做法是复制（带「复制自」链接）并删除原处的块。显式放宽页或空间的权限属于管理操作，要记审计。

### 2.5 提交
- 每次改动产生一个提交。改动包括：一次 agent 工具调用、一次合并、一次撤销、一次导入、一次复核，以及人的一段连续编辑（同一个人在同一块上，空闲 30 秒以内的编辑合并为一个提交）。
- 字段：空间、层（可空）、空间内单调递增的 `seq`、种类、作者类型（人 / 叙述者 / 系统 / 插件）、作者 id、叙述者 id、消息 id、工具调用 id、时间、是否可见。
- 块的每个版本都记录由哪个提交产生、到哪个提交失效（`from_seq` / `to_seq`）。按时间点读取（as-of）时直接按这个区间查。

### 2.6 层
- 层是一组等待某人决定的改动。它属于一个空间，基线是该空间主线上的某个 `seq`。
- 「主线」指空间里不经过层的那部分状态。
- 层只在四种情况下出现：知识库提议、探索 fork、agent 写入个人空间、不可信来源写入共享空间（§6.2）。
- 合并时，把层里的改动逐块重放到主线上，压成一个提交。不做 DAG，也不做 rebase。

## 3. 权限

- **读。** 判断顺序是空间门，再加页级收窄；块继承所在页的权限。查询前先算出可读的空间和页集合，在 SQL 里过滤，然后才取前 N 条。这样就不会出现知识库那种「先截取再过滤、结果变少」的问题。
- **写。** 按当轮驱动者的权限判断。没有直写权限时，写入自动转成提议层（§6.2）。
- **会话的读权限 = 所有能驱动这个会话的人的权限交集（D9）。**
  - 单人会话就是本人的权限；多人共用的项目会话和 Bot 房间取交集。所以个人空间只在单驱动者的会话里可读。
  - 原因：上下文是跨轮共享的。A 的那一轮读进来的内容，B 在下一轮就能问出来。现在知识注入按 `_currentUserId` 逐轮解析权限（`server/services/agent-runtime/orchestrator.ts`），挡不住这条路。
- **链接不是后门。** 读不到的目标，提及显示为占位，嵌入不展开，都不暴露目标是否存在。
- **时间机器按当前权限显示历史（D4）。**
- **人写的块受保护。**
  - agent 删除或移动别人写的块，要走权限确认（D1）。
  - agent 不能改人写断言的立场，只能写一条带证据的「取代」假设，等人采纳（§5.6）。
  - 人建的任务，agent 要标完成必须附证据（§7.4）。
- **信任基线。** 项目空间的信任级别与仓库文件相同：agent 本来就能修改仓库里的 CLAUDE.md。跨项目、跨人的内容（知识库、个人空间）则必须经过人确认。

## 4. 时间机器

### 4.1 体验
大纲视图（P1）和图谱视图（P5）底部有一条时间轴，提供以下功能：
- 变更密度图，用颜色区分人、agent、合并和复核。
- 事件标记，包括层合并、探索路径选定、断言被取代、批量导入、批量存疑、git tag 和发版。
- 拖到某一点，看那个时刻的样子；框选一段，看这段时间里的变更（增、删、改、移分别高亮）。
- 播放、按提交单步前进或后退，以及按人、会话或子树过滤。
- 从任意一处变更跳回产生它的会话和消息。
- 把一个块或一页恢复到某个时间点。恢复本身也是一个补偿提交（§6.4）。
- 层画成旁支泳道，只对能看到该层的人显示；合并点画成汇合。

### 4.2 语义
- 时间机器按的是**系统时间**，回答「当时我们是怎么认为的」。
- **有效时间**是另一回事，回答「这件事对哪个代码版本、哪段故事时间成立」。它由断言的「基于」链接（代码锚点带提交号）或类型属性来表达，和系统时间不混用。
- 派生状态（新鲜度）的变化只作为时间轴上的事件出现，不产生内容版本。

### 4.3 实现
- **按时间点读取。** `outline_block_versions` 按 `(space_id, parent_id, from_seq)` 和 `(block_id, from_seq)` 建索引。按视口分批读取，每批最多 500 块；用户展开节点时再取下一批。
- **拖动。** 第一次取视口的完整状态，之后只拉相邻提交的增量。版本里存有前后两态，客户端可以正向或反向应用。提交列表用游标分页。
- **大提交。** 超过增量上限（§11）的提交在时间轴上折叠成一个事件，详情按需加载。
- **图谱布局。** 对所选时间窗里出现过的全部节点一次性算好布局，节点在原位淡入淡出，拖动时不会乱跳。

### 4.4 保留与清除（D3）
- 共享空间（项目、个人、知识库）的历史永久保留。
- 会话空间的历史跟随会话：会话删除时一起删除，会话归档时保留。
- 被引用的版本不可删，包括层的基线、证据、已归档的探索路径。这为以后做历史粗化留了余地；粗化本身初版不做。
- 管理员可以「彻底清除」：从版本、链接摘录、FTS、向量、层和导出中抹掉内容，只留一条不含内容的审计记录。清除由后台 job 执行。
- 设置页显示每个空间的历史占用。

## 5. 真值维护：知识会过期

### 5.1 范围
只有断言参与真值维护。笔记和视图不参与；任务只有状态，没有真假。

### 5.2 立场与新鲜度
- **立场**由写的人设置：假设、采纳或否定。
- **已被取代**不单独存储。只要有一条来自「采纳」块的取代链接指向它，就推导为已被取代。
- **新鲜度**由系统推导，缓存在 `outline_freshness` 表里：
  - **新鲜**：没有问题。
  - **存疑**：基于的东西变了，附原因。
  - **过期**：基于的东西已经不存在了（符号被删、块被删、URL 失效）。
- 新鲜度不产生内容版本，不需要写权限，可以随时重算。

### 5.3 存疑的触发
所有触发都来自「基于」链接。

| 目标 | 触发条件 | 做法 |
|---|---|---|
| 代码符号 | 主干上的提交改变了符号指纹 | 复用 `server/lib/agent/structural/`（tree-sitter 大纲）定位符号，对规范化后的文本取指纹。verified 级语法能精确到符号；generic 级或没有语法的语言退化为「行范围 + 文本指纹」。文件改名靠 git 的改名检测跟上 |
| 块 | 目标内容变化、被取代或被删除 | 沿「基于」链接传播，最多 2 跳 |
| URL | 定期复查时发现内容 hash 变了（可选） | 默认不复查 |
| 时间 | 到了 `props.review_after` 指定的日期 | 用于天然会变的事实，例如值班人、依赖版本 |

- **代码变更检测。** 项目空间绑定的仓库主干前进时，后台 job 取出变更路径（`git diff --name-only`，有条数上限和超时），只重算这些路径上的锚点指纹。
- **批量存疑聚合。** 一次大重构引起的大量存疑，聚合成一个事件，例如「提交 abc 让 500 条断言存疑」，并附「立即复核这批」按钮。不会因此生成 500 条待办。

### 5.4 证据
- 证据链接由三部分组成：指针、一段有长度上限的摘录快照、抓取时间。所以即使消息后来被 compact、回退或 fork，证据仍然可读。
- 用户在对话里亲口确认也算证据，用 `msg:` 指向那条用户消息。
- **规则：agent 写的断言没有证据就只能是「假设」，有证据才能是「采纳」。人写的断言默认为「采纳」。**

### 5.5 复核（D2）
- **读时复核（默认）。**
  - 存疑的断言被检索出来注入时，附带警告，例如「它基于的 `auth.ts#refresh` 在提交 abc 中改过」。
  - agent 如果要依赖这条断言，就先核实，再调用 `Verify` 写回结论和新的证据。
  - 不额外花钱：核实由本来就在运行的 agent 完成。
- **批量复核。** 用户在聚合事件上点按钮触发，模型由用户选择，用户清楚自己在花钱。
- **后台自动复核（默认关闭）。**
  - 开启前需要选好模型、设定每日预算。
  - 按「被检索次数 × 重要性」排队。
  - 只能做两件事：确认「没变」，或者标出「需要改」。不改写内容，拿不准的保持存疑。

### 5.6 写时提示（不额外调用模型）
- 写入断言或新建页时，系统用 embedding 在同一空间里查找高度相似的已采纳断言，以及同名或别名相近的页，并把结果放进工具返回，例如「已有相近断言 X、Y」「可能已存在页 Z」。正在写的 agent 自己判断：重复就合并，矛盾就写一条取代链接，无关就继续。
- 如果 agent 认为某条人写的断言已经不成立，它新写一条带证据的「假设」，加上取代链接，并生成一条人的决定（§9）。人采纳这条假设后，旧断言自动变为「已被取代」。

### 5.7 局限
指纹能抓到直接改动，抓不到间接漂移，比如断言讲的是 A 的行为，实际改的是 A 调用的 B。间接漂移只能靠读时复核兜底。

## 6. 写入、层与撤销

### 6.1 默认：直写（D1）
- 人在编辑器里直接写入自己有写权限的空间。agent 直接写入会话空间，以及它有写权限的项目空间。
- 每次写入都是一个带来源的提交，可以在时间机器里看到，也可以撤销。
- 以下例外走现有的工具权限确认，流程和危险命令相同：
  - 删除或移动别人（其他人或其他会话）写的块；
  - 单次调用改动超过 50 个块。
- **并发控制用块级比较交换（D6）。** 服务端按会话记录它读到的每个块的版本，agent 不需要在参数里带版本号。如果块在读取之后被别人改过，写入失败，并返回当前内容。这和「先 Read 再 Edit」的文件保护是同一套直觉。

### 6.2 层

| 场景 | 什么写入进层 | 谁来决定 |
|---|---|---|
| 提议 `proposal` | 没有直写权限的人或 agent 的写入；知识库空间默认所有人都走这里（D8） | 知识库空间：审核人（沿用审核标签规则）；项目空间：项目管理员 |
| 探索 `exploration` | 探索会话及其子代理对共享空间的写入 | 发起这次探索的人 |
| 待确认 `pending` | agent 对个人空间的写入 | 本人 |
| 隔离 `quarantine` | Bot 会话对任何共享空间的写入 | Bot 的创建者 |

- **存储。** 层只存被改过的块的新状态（`outline_layer_blocks`，块级写时复制），以及改动的提交序列（`outline_commits.layer_id`）。每个改动都带基线版本。
- **读取。** 能看到这个层的会话或人，读到的是「主线 + 层」：层里的块覆盖主线上的同一块，层里删除的块不出现。
- **索引。** FTS 和向量的行带 `layer_id`。查询时取主线加上自己可见的层，同一个块优先用层里的版本。
- **状态流转。** 进行中 → 待决定 → 三种结局之一：
  - 已合并；
  - 已否决：归档，只读，可以显式检索；
  - 已放弃：按保留策略回收。
- **现有知识库提交状态的对应关系：**
  - `pending` → 待决定
  - `approved` → 已合并
  - `rejected` → 已否决
  - `changes_requested` → 进行中（附审核意见）
  - `conflict` → 待决定（有冲突）
  - `withdrawn`、`superseded` → 已放弃
- **部分合并。** 可以只合并选中的一部分块，系统会自动带上它们依赖的新建父块。
- **层不嵌套。** 层的基线永远是主线。fork 一个持有层的会话时，把层复制一份，基线不变。

### 6.3 合并与冲突
合并由后台 job 执行：把层里的改动逐块重放到主线上，最后作为一个提交一次性可见（把 `visible` 置为真）。

| 情况 | 处理 |
|---|---|
| 内容或属性：基线版本 ≠ 主线当前版本 | 算冲突。块很小，直接展示三方对比，也可以先让 agent 给出合并方案 |
| 移动：目标父块已在主线上删除 | 挂到该页的「孤儿」收容处 |
| 移动：会形成环 | 拒绝这条改动 |
| 只是顺序不同 | 分数排序键会自然合并，不算冲突 |
| 层里改了主线上已删除的块 | 算冲突 |
| 链接指向已删除的块 | 标为悬空 |

存在时间长的层，界面会持续显示「现在合并会有 N 处冲突」。

### 6.4 撤销与 fork

**撤销 = 补偿提交。** 对目标提交里的每个块，如果之后没人再改过，就恢复到之前的状态；被别人改过的列为冲突，不覆盖。

**回退会话到消息 M：**
- 会话空间里来源晚于 M 的提交，自动补偿。
- 写到共享空间的提交，在回退对话框里列出来（「这 N 处已写入项目空间，是否一并撤销」），由人选择。
- 层里的提交同理，在层内补偿。
- 现在回退会话并不会回退 spec 内容：`server/services/revert-history-commit.ts` 只把 spec 修订的来源消息置空。新模型补上了这一点。

**fork = 复制：**
- 子会话的会话空间复制父会话空间的当前状态，不复制历史。
  - 短 id `sid` 保持不变，所以从父会话继承来的上下文里提到的块地址仍然有效。
  - 子空间记录 `forked_from_space_id` 和 fork 时的 `seq`，时间机器可以从这里跳到父空间的历史。
- 父会话持有的层，复制一份给子会话。
- 共享空间不复制。它的历史只追加，且归空间所有，子会话直接共享即可。
- 对比现在的 spec fork：`forkSpecNamespace`（`server/services/knowledge/sqlite-write-store.ts`）让子会话的文件指针直接引用父会话的修订行，而修订行会随父会话的命名空间级联删除。父会话被硬删后，子会话的指针被置空，文件就悄悄消失了。改成复制之后，这一类问题不再存在。

**子代理：**
- 有自己的会话空间。
- 写共享空间时与父会话一样直写；如果父会话是探索会话，就写进父会话的探索层。
- 来源记录为子代理自己，需要时可以按来源整批撤销。

### 6.5 探索（多路径）
- **探索 fork** 是 fork 的一个选项：子会话及其子代理对共享空间的写入，都进入一个探索层，基线是 fork 时的主线。
- **探索组。** 同一次发起的几条路径组成一个探索组。对比视图用嵌入链接把各路径的方案、结果、代价并排拼在一起（嵌入链接可以指定读哪个层）。
- **选定一条路径时：**
  - 合并它的层；
  - 其余的层标为「已否决」并归档，以后可以作为负面知识显式检索；
  - 自动生成一条决策断言，链接到选中的和落选的路径。
- **与 git 对齐。** 探索层可以绑定该会话 worktree 的分支。分支合入主干时，提示合并这个层；worktree 被删除且没有合入时，提示放弃。初版只提示，不自动执行。

## 7. agent 接口

### 7.1 地址
- 块地址是 `空间/短id`。会话空间里的块可以省略空间前缀。
- 空间的写法：
  - `s`：本会话。
  - `p`：本会话所属的项目；有多个项目时写 `p:<项目名>`。
  - `me`：驱动者的个人空间，只在单驱动者会话中可用。
  - `kb:<名称>`：知识库空间。
- 示例：`7Hq1x9Ka`（本会话）、`p/Ab3dEf9Q`、`kb:arch/Zz81Qw0P`。

### 7.2 工具（名称暂定）

| 工具 | 作用 |
|---|---|
| `OutlineRead` | 按地址读取一棵子树。参数：深度、是否展开嵌入、`as_of`（可选） |
| `OutlineSearch` | 混合检索。参数：查询、空间范围、类型、`include`（默认不包含已否定和已被取代的断言） |
| `OutlineEdit` | 执行一组有序操作：插入（可以用一段 markdown 大纲一次插入多块）、更新、移动、删除、增删链接、改状态 |
| `Verify` | 对一条断言写回复核结论（新鲜 / 需要改 / 否定）和证据 |

- `OutlineEdit` 没有隐式删除，要删除必须显式写出删除操作。
- 给 agent 看的渲染格式：

```text
- [p/Ab3dEf9Q] auth 模块
  - [p/7Hq1x9Ka] 坑：token 刷新存在竞态 ‹断言·采纳·存疑：auth.ts#refresh 在 abc 改过›
  - [p/Kd02LmQ1] 补回归测试 ‹任务·进行中·负责：本会话›
```

- 现在 `Read`、`Write`、`Edit`、`Grep` 对 `spec://` 的路由，在 P2 移除。

### 7.3 上下文配方 = 视图
- 每个会话空间里有一页「上下文」。页里是若干视图的嵌入链接，每个链接带触发时机和字符预算。触发时机可以是：每轮、每 N 次工具调用、compact 时、按当前消息检索。
- 现在写死的几种注入，改为以下内置视图：

| 现在 | 内置视图 |
|---|---|
| 任务摘要 `living_work_spec`（`server/services/spec-reminder.ts`） | 「当前任务」：进行中、受阻、下一个 |
| 行为边界 `behavior_fence` | 「行为边界」：会话空间和项目空间里标记为 `agent_readonly` 的页 |
| 知识关键词注入（`server/services/knowledge-injection.ts`） | 「相关知识」：按当前消息和工具输出检索（§8） |
| compact 时注入完整任务列表 | 「compact 上下文」：未完成的任务，加上本会话涉及的关键决策 |
| 无 | 「我的偏好」：个人空间里已采纳的偏好，只在单驱动者会话中注入 |

- 插件写入的 SOP 段落和任务，作为块写进对应的页，作者记为插件。
- 项目可以在项目空间里放一个模板页，作为本项目会话的默认配方（P5）。
- 这样做的好处：每一段注入都能追溯到某个视图，用户能看出 agent 为什么知道某件事。

### 7.4 任务与续跑
- **续跑候选：**
  - 会话空间里的任务，加上项目空间里负责人是本会话的任务；
  - 状态为待办或进行中，且前置任务都已完成；
  - 负责人是人的任务永远不进候选。
- 没有进行中的任务时，把第一个候选提为进行中。这保留了现在的行为（`server/services/narrator-session.ts`）。
- **人建的任务**（通过 `/goal` 或界面添加，作者是人，负责人可以是本会话）：agent 要把它标为完成，必须附上证据，例如提交、测试结果或工具输出。
  - 这条规则替代现在的「受保护任务」，文本 hash 锁（`spec_protected_tasks`）也就不需要了。
  - 任务反思（`server/lib/agent/tools/task-reflection.ts`）是否保留为可选的证据核查，P2 再决定。

## 8. 检索

### 8.1 流程
1. **确定范围。** 按 §3 算出可读空间的集合（包括会话可见的层），在 SQL 里过滤。
2. **召回。** FTS 和向量并行召回。FTS 在 SQLite 上用 FTS5 trigram，在 PG 上用 pg_trgm，沿用 `server/db/fts.ts` 和 `server/db/pg-fts.ts` 的做法。页的 `keywords` 作为高精度触发词，一并合进召回结果。
3. **扩展。** 沿基于、提及、取代链接和父块，各扩展 1 跳。
4. **排序。** 配置了 rerank 模型就用它；没配置就用 RRF（倒数排名融合）。最后乘上状态权重（§8.4）。
5. **渲染。** 结果带面包屑（祖先标题）和状态标记，受字符预算约束。

### 8.2 embedding
- **embedding 的输入**是块正文加上所在页的标题，不含完整的祖先路径。这样祖先改名时，不会触发整棵子树重新计算；完整面包屑只在 rerank 时才加上。
- **缓存键**是（模型, 内容 hash）。相同内容在不同版本、层和合并之间复用，合并时不需要重新计算。
- 写入后由后台 job 批量计算。没有配置 embedding 模型时，退化为纯 FTS。
- 模型从模型目录中选择（`shared/model-catalog` 已有 embedding 类别），API 和 OpenAI 兼容的本地端点都支持（D7）。

### 8.3 向量存储（D10）
- 初版不引入原生扩展。量化后的向量存成 BLOB，在 db-worker（`server/lib/db-worker/`）里先按空间过滤，再暴力扫描。这种做法在两种方言下通用。
- 单次扫描超过时间预算，就降级为纯 FTS，并记一条慢日志。
- 等规模上去之后（初值：单实例超过约 20 万块，以 P0 基准测试为准），再接入 sqlite-vec 或 pgvector，接口提前预留。
- 不一开始就用扩展的原因：bun:sqlite 在 macOS 上默认使用系统自带的 SQLite，要加载扩展就得换一个 SQLite 构建，跨平台打包的成本高。

### 8.4 状态权重与自动注入

| 状态 | 自动注入 | 搜索默认 | 排序 |
|---|---|---|---|
| 笔记 | 按相关度 | 返回 | 正常 |
| 断言：采纳 + 新鲜 | 是 | 返回 | 正常 |
| 断言：采纳 + 存疑 | 带警告注入 | 返回，带标记 | 降权 |
| 断言：假设 | 否（产生它的会话内除外） | 返回，带标记 | 降权 |
| 断言：否定，或已被取代 | 否 | 需要显式 `include` | — |

- 任务和视图不进「相关知识」，它们有各自的专门视图。
- 自动注入受三项约束：相似度阈值、每轮条数上限、字符预算。同一个块在一个 compact 周期内只注入一次，沿用 `knowledge_injection_events` 的语义。

## 9. 人的决定

不新建收件箱，而是在现有的 human attention（`shared/human-attention.ts`，目前有 `async_question`、`blocking_question`、`permission`、`plan_approval`、`reflection` 五种）上加两种：

| kind | 内容 |
|---|---|
| `outline_decision` | 待决定的层：知识库提议、探索路径选择、记忆确认、Bot 隔离 |
| `outline_review` | 需要人看的知识事件：批量存疑、对人写断言的取代提议、撤销时的冲突 |

列表行只带 id 和摘要，不带正文。这条约束和现在 human attention 的列表行一致。

## 10. 存储

```text
outline_spaces          id, kind(session/project/personal/library), project_id?, narrator_id?,
                        owner_user_id?, gate_json(级别 + 受控标签), forked_from_space_id?,
                        forked_at_seq?, next_seq
outline_blocks          id, space_id, sid, parent_id, order_key, kind, content, props_json,
                        author_kind, author_id, version_seq, deleted          -- 当前态，快速读取路径
                        UNIQUE(space_id, sid)
outline_block_versions  block_id, from_seq, to_seq?, commit_id, parent_id, order_key, kind,

outline_links           id, space_id, layer_id?, from_block_id, role, target_kind, target_ref,
                        target_state_json(指纹 / 提交 / hash / 指定层), excerpt?, from_seq, to_seq?
outline_commits         id, space_id, layer_id?, seq, kind(edit/merge/revert/import/verify/purge),
                        actor_kind, actor_id, narrator_id?, message_id?, tool_call_id?,
                        visible, created_at, summary
outline_layers          id, space_id, base_seq, kind, owner_kind, owner_id, decider_json,
                        status, group_id?, bound_branch?, created_at, decided_at?
outline_layer_blocks    layer_id, block_id, …（与 outline_blocks 同形的层内当前态）
outline_freshness       block_id, state, reasons_json, since_seq, checked_at   -- 派生缓存
outline_embeddings      model_id, content_hash, dims, vector_blob, created_at

```

- 表定义写在 `server/db/schema.ts` 里，按规范流程生成迁移。PG schema 由 `scripts/generate-postgres-schema.ts` 转译，两种方言同时交付。
- 统一使用 `outline_` 前缀，避免和消息块存储的 `narrator_blocks` 混淆。
- 子树查询用递归 CTE，两种方言都支持。每次查询都有深度和条数上限。
- 主线程只做小规模、走索引的读写。合并、导入、清除、批量存疑、embedding 计算和向量扫描，全部放在后台 job 或 db-worker 里执行。

### 12.2 知识库（P4）

| 现在 | 迁移到 |
|---|---|
| 集合 | 知识库空间；空间门 = 集合的级别 + 受控标签 |
| 条目 | 页，正文解析成块；条目自身的级别或受控标签比集合更严时，作为页级收窄 |
| 关键词 | 页的 `keywords` |
| 条目链接 | `related`、`mention`、`custom` → 提及；`expands`、`depends_on` → 基于；`supersedes` → 取代；`parent` → 提及（不改动树结构） |
| 个人的独立条目 | 个人空间里的页 |
| 关联草稿、提交 | 提议层，状态按 §6.2 映射 |
| 审核标签 | 层的决定者规则 |
| 修订历史 | 只迁当前状态；旧修订以只读形式保留到退役为止（保留多久待定，§15） |
| Pack | 机制不变；原本绑定条目的 Pack 改为绑定页 |
| `Knowledge*` 工具、关键词注入 | `OutlineSearch` / `OutlineRead`、「相关知识」视图 |

- 迁移前后用同一套 ACL 用例做对照：链接不是后门、不暴露是否存在、通知只带 id。
- 保留：空间门继续使用现有的级别与标签定义（`knowledge_levels`、`knowledge_tag_types`、`knowledge_tags`）、`acl_grants` 和授权审计（`knowledge_acl_events`），以及 Pack 两张表。
- 迁移完成后退役：集合、条目、修订、草稿、提交、条目链接、注入记录、已弃用的 `knowledge_grants`，以及对应的服务、路由和前端。

**D1 的精炼。** 讨论时的方案是「回合结束时自动合并进主线」，这里改为直写。
- 用户感受相同，都是自动生效。
- 少了一套每个会话都要维护的层和覆盖读取。
- 原本放在合并关口的检查，挪到了写入时（§5.6）。
- 撤销统一为补偿提交。
- 例外情况复用现有的权限确认。
- 代价：另一个会话可能读到某一轮进行到一半的修改。影响小，而且在时间机器里都可见。

## 15. 待定问题
1. **大纲编辑器。** 是在现有 Tiptap（spec 的 `SpecMarkdownEditor` 在用）上实现大纲节点，还是像 Logseq 那样每块一个轻量编辑器？需要同时兼顾超长页的虚拟化和移动端。
2. **知识库旧修订。** 迁移时只迁当前状态，旧修订以只读形式保留多久？
3. **标签。** 用属性里的字符串数组，还是像 Obsidian 那样每个标签对应一页？
4. **跨仓库。** 一个需求跨多个仓库时，项目空间如何对应多个 `projects` 行？
5. **探索对比。** 探索组的对比视图要不要内置模板（方案 / 结果 / 代价三栏）？
6. **任务反思。** 是否保留为可选的完成证据核查（§7.4）？

## 16. 主要风险
- **大纲编辑器的复杂度。** 传送门的就地编辑、超长页、移动端，三者叠在一起，是工作量最大的不确定项。P0 先做原型。
- **agent 的编辑习惯。** 模型更熟悉编辑文件，而不是结构化操作。所以 `OutlineEdit` 允许用 markdown 大纲批量插入，返回值要给出足够的上下文。P1 要用真实任务验证。
- **按时间点读取的性能。** 历史增长后，这类查询能否保持在视口级别的延迟。P0 先做基准测试。
- **迁移时的 ACL 一致性。** 知识库约 45k 行代码，迁移必须先有对照用例，再动数据。
