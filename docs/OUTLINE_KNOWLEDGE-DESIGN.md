## 0. 摘要

**要做什么**：一个像 Obsidian 的大纲笔记网络，把全局知识、个人知识与偏好、工程规格、任务放进同一套东西，替代 spec:// 和知识库。人和 agent 在上面协作；agent 检索用上 embedding 和 rerank。

**六个概念**
1. **块**：大纲的节点，页就是顶层的块。正文是 markdown，`[[…]]` 是链接，`![[…]]` 是嵌入（传送门）。
2. **任务**：带复选框的块。可以指派、有前置、可以锁定。
3. **依据**：一个块凭什么成立。系统从运行记录里自动挂上；正文里写的代码位置成为锚点，代码变了会提示。
4. **空间**：东西放在哪、谁能看：知识库、项目、个人、会话。
5. **历史**：每次改动都留下来。底部的时间轴可以回放，可以撤销。
6. **待确认**：需要别人点头的改动，只有几种（§2.6）。

**两个维度**：页上默认只看到**事实**，也就是现在成立的东西，按「是什么」组织，每一层概括下一层。计划、提问、报告是**过程**；历史和依据是每个块的另外两面。它们都不挂进事实树，只在例外时在事实上露一个标记，比如「进行中」「代码已变」，平时在侧栏和时间轴里。哪些是过程不用标：任务和它下面的块就是（§2.1）。任务完成后，原会话接着把里面站得住的结论放进事实树，原会话不在了才交给单独的整理 agent（§4.7）。

**agent 只需要知道三条**
1. 以后还用得到的写进大纲：结论、决定、坑、计划。写在手头的任务下面就行；任务完成时，工具会给出要整理的内容和做法。
2. 开始做一个任务就把它勾成进行中，做完勾成完成；需要人决定的，提问并附上建议。
3. 工具说「已交给某人确认」时，先做不受影响的部分。

**人只需要知道三条**
1. 计划默认随 agent 调整；要它严格照做，就锁定。
2. 收件箱只放要你决定的事，每条带建议，可以一次回答多条。
3. 一切都能在时间轴上回放、撤销。

**其余都由系统在后台做**：权限、历史、出处、领取与租约、责任链、依据收集、代码锚点检查、检索与注入、关注范围、子代理报告挂回、关口统计、提醒整理和兜底整理。

**和第一版相比**
- 去掉：断言类型和立场、九种链接角色、待验收和受阻两种状态、计划的骨架与契约、层、范围的三个级别和写入关卡、作者 / 代记人 / 责任人三件事、专注 / 协调两种模式。
- 依据：两轮试用里，这些机制要么没用上，要么只是走过场（附录 B）。
- 第二版后来又去掉：决策包的名字（同一个块下的提问就是一件事，§3.3）、结项任务和计划归档（任务完成就整理，§4.7）。

## 1. 需求

### 1.1 需求清单
负责人 2026-10-24 确认，R26、R27 是 2026-10-25 补充的。按功能写，不按名字写：比如「传送门」「泡」是想要的效果，不是要做成叫这个名字的实体。每条对应到设计的位置见附录 A。

**定位**
- **R1** 一个统一平台：全局知识、个人知识和偏好、工程规格、任务放在同一套东西里。
- **R2** 完全替代现在的 spec:// 和知识库。
- **R3** 支撑这些场景：新项目起草、老项目探索并建立完整图谱、新需求开拓、修 bug、多路径探索最后只留一条、coding 之外的项目管理。

**内容怎么组织、怎么看**
- **R4** 像 Obsidian 的大纲笔记：层级不限，内容双向关联。
- **R5** 在一处直接看到、编辑别处的内容（「传送门」）。
- **R6** 把散在各处的内容拼成一个视图（「定制拼接视图」）。
- **R7** 查看时底部有时间轴，快速浏览图谱随时间的变化。
- **R26** 大纲覆盖一个团队乃至整个企业的产品和知识时，每一层都呈现恰好密度的事实：上层看得到全貌，下层看得到细节。
- **R27** 计划、演进、评估、证据放在另一个维度，不干扰人对结构和事实的观察。

**数据与编辑**
- **R8** 数据库是唯一真相源。永远不以 markdown 文件为真相源，永远不和 Obsidian vault 双向同步。
- **R9** 多人实时同时编辑同一个块。
- **R10** 为大纲文档设计的编辑器，可以重写或深度定制，不是每块一个编辑器。
- **R11** agent 直接写入，不经过暂存再合并。

**检索**
- **R12** 接入 embedding 和 rerank，让 agent 检索得更准。

**agent 怎么用**
- **R13** 这套模型真正服务于多 agent 协作。
- **R14** agent 按大纲做事并及时更新大纲，同时保留自由自主，不过度防御。
- **R15** 概念和规则不能多到分散注意力、削弱能力。
- **R16** 能派不受约束的子 agent 专心攻坚，由守规则的 agent 帮它协调；攻坚的 agent 要真的专注，不给它加格式。
- **R17** 支持多语言，不依赖解析自然语言。

**计划与决定**
- **R18** 写计划的人决定严格程度：粗略的草稿随情况改；讨论审批过的严密计划尽量照做，要改先停下来汇报。
- **R19** agent 可以在权限内批准变更，后果最终落到创建人头上。
- **R20** 规划方式重新设计，不再是「一段 md 一个 plan」。
- **R21** 计划完成后滤掉不需要的信息、整理结构，自然成为知识；同时保留当时的计划，供参考和追溯。

**多工作区与关注范围**
- **R22** 一个会话原生管多个工作区、多台设备上的目录，用于多服务器联调、多仓库联合开发。
- **R23** agent 有几块关注区域（「泡」），区域外也能适当查看，保持适配。
- **R24** 主 agent 或人可以批准下级 agent 改变范围。

**做法**
- **R25** 先用 Python 原型承载这次的计划，真实推进，从使用中发现问题。

### 1.2 不做

**永远不做**
- 以 markdown 文件为真相源。
- 与 Obsidian vault 双向同步。

**初版不做**
- 长时间离线编辑。短暂断线由 CRDT 补齐。
- 在结构层再造一套分支系统。多路径探索建在现有的会话 fork 和 worktree 上（§4.5）；叙事线已经退役（`docs/NARRATIVE_LINE_REMOVAL_PLAN.md`）。
- 视图的时间机器。
- 从对话里自动抓个人记忆，并且不经确认就生效。

### 1.3 现状

| | spec:// | 知识库 |
|---|---|---|
| 粒度 | 每个叙述者一个命名空间，里面是平铺的文件 | 一个条目就是一整篇 markdown |
| 结构 | 路径只是字符串；没有链接 | 集合是平铺的；链接只能连整个条目，agent 工具用不上 |
| 任务 | `tasks.json`：平铺，最多 100 条，用文本 hash 当身份（`server/services/spec-task-service.ts`） | 无 |
| 检索 | 把全部文件读出来跑正则 | FTS 加关键词触发注入；先截取前 N 条再做 ACL 过滤（`server/services/knowledge-service.ts` 的 `search()`） |
| 写入 | 整个文件覆盖；Edit 的读-改-写不在锁内 | 整篇覆盖；合并时对全文做三方合并 |
| fork / 回退 | 子会话直接引用父会话的修订行；回退会话时 spec 不跟着回退 | 不涉及 |

- 仓库里没有 embedding、向量或 rerank 代码，也没有面向 agent 的个人记忆。
- 「团队」只是根叙述者加子代理的运行时关系（`server/services/subagent-team.ts`），成员之间靠 `Send` 传话；持久的共享状态只有各自的 `tasks.json`。
- spec 文件在界面上只能用所见即所得编辑器（`SpecMarkdownEditor`）改。它保不住的语法在加载时就被扔掉，保存后才真正丢失：表格整张消失，图片只剩 alt 文字，任务列表丢复选框，JSON、YAML 文件存一次就坏。原型第二轮按锁定的版本复现过。已按 D24 修好（提交 `df821f4d`）：源码优先、所见即所得可选；检测到保不住的语法就不让在所见即所得里保存。

### 1.4 设计原则
1. **概念从需求来。** 每个概念都要能对应到 §1.1 的某条需求；实现需要的东西（版本表、租约、授权链）留在系统内部，不让人和 agent 去理解。
2. **agent 看到的是它早就熟悉的东西**：markdown 列表、复选框、双链、代码位置。
3. **系统能推断的，不让人和 agent 填**：身份、出处、依据、领取、关注范围、事实还是过程。
4. **默认信任，事后可见、可撤销。** 关口只留给别人的东西和不可逆的事（§2.6）。
5. **关口要自证有用。** 每道关口统计「原样通过率」；长期接近 100% 的，改成事后摘要。两轮试用里，范围请求和验收都是 3 次全部原样通过。
6. **不解析自然语言。** 结构来自 markdown 语法、复选框、代码位置和运行记录，不来自标题措辞和关键词（R17）。
7. **页上只看事实。** 过程（计划、提问、报告）、历史和依据在另一个维度，不改变事实树的结构，只在例外时露一个标记（R27）。
8. **指标从需求来，只算边际成本。** 记账只算在本来就要做的事之外多花的；量知识有没有用，就看以后找不找得到、依据对不对；量人的负担，就看每天要决定几件、每件花多久（附录 B）。

## 2. 概念

```text
空间 ──包含──▶ 块（树，页是根块） ──链接 / 嵌入──▶ 块
                 ├─ 任务：复选框、指派、前置、锁定
                 └─ 依据：运行记录、代码锚点、人的确认
每次改动 ──▶ 历史（时间轴、撤销、责任链）
少数改动 ──▶ 待确认 ──确认──▶ 生效
任务和它下面的块是过程，其余是事实（由位置推出，不用标）
完成的任务 ──整理──▶ 事实树（出处指回任务）
```

### 2.1 块
- 大纲的节点，层级不限（R4）。页是顶层的块，任何块都可以「聚焦」成页来浏览。
- 正文是一段 markdown，遵守块内方言（§6.8）：一个块体（段落、标题、代码、引用、表格）加行内语法；要嵌套就用子块。
- **链接**：正文里的 `[[…]]`。系统维护反链，所以关联是双向的（R4）。
- **嵌入**：正文里的 `![[…]]`，就是传送门：在这里展开目标块，按目标的权限就地编辑（R5）。展开受视图的预算约束（§3.1），所以一页嵌入几十个团队的页，也只先显示各自的概括。
- **拼接视图**（R6）：一页里放几个嵌入，或者放一个保存的查询，例如「指派给我的进行中任务」「涉及 `auth/` 的结论」。渲染时就地展开，可以编辑。
- **地址**：每个块有稳定 id 和空间内的短 id。人和 agent 用标题或别名引用，系统存稳定 id，改名不断链。工具的返回值单独给出地址，不让 agent 从渲染文本里抠（原型发现）。
- **不成立**：块可以标为「不成立」，附一句原因，用于试过不行的方案、被推翻的结论。它们默认不进检索、注入和事实视图，但保留下来，作为「试过的方案」。
- **事实与过程**（R26、R27）：
  - 任务和它下面的一切（进展、报告、运行记录、提问和它的选项、回答），以及会话空间里的内容，是**过程**；其余的块是**事实**。不用标，由位置推出来，所以不是新概念，agent 也不用记。
  - 事实树按「是什么」组织：产品 → 领域 → 模块 → 细节，每一层概括下一层。过程不挂进事实树，靠代码位置和链接指向它涉及的事实。
  - 页默认按事实来看（§3.1）；过程在看板、计划树、收件箱里看，或者在事实视图里展开。
  - 事实块下面也可以挂任务或提问，比如「这条要不要改」。它们是过程，在事实视图里收成这个块上的「进行中」。
  - 任务完成后，它下面站得住的结论由原会话接着放进事实树（§4.7）。
- 日志、长代码、文件这类大内容走附件，块里放链接。

### 2.2 任务
- **写法就是复选框**：`[ ]` 待办、`[/]` 进行中、`[x]` 完成、`[-]` 取消；`@名字` 指派给人或 agent。其他属性写成 `键:: 值`，键是固定的英文，例如 `depends:: [[步骤一]]`（前置）、`due:: 2026-11-01`。
- **开始即领取**：把 `[ ]` 改成 `[/]` 就是开始做。系统原子地检查：已经有别人在做，就告诉你是谁。租约、续租、交还都由系统管（§4.5）。
- **等待不单设状态**：前置没完成，系统显示「等前置」；受阻原因写成子块。
- **完成**：勾成 `[x]`。依据由系统自动收集（§2.3），没有依据的在看板上标出。建任务的人会收到通知，不满意可以重开。不设验收关口：试用里需要验收的 3 个任务全部原样通过。完成或取消后，下面写过的东西进入整理（§4.7）。
- **计划就是一棵任务树**：根块写目标和验收，子任务是步骤（§4.3）。
- **锁定**（R18）：写计划的人，或在权限内的 agent，可以锁定一棵任务树。锁定后：
  - 增删任务（把锁定时的叶子任务拆成子任务除外）、改任务的内容或顺序，转成待确认，交给锁定人；
  - 推进状态、在任务下面写进展和发现、把叶子任务拆成子任务，照常直写；
  - 被改的任务在确认前显示「等确认」，agent 先做别的；
  - 整个计划标完成，要锁定人确认；
  - 锁定人可以指定一个 agent 替他确认步骤调整（R19），逐个计划指定，没有默认值（D25）。这类确认记在那个 agent 的责任人名下（§2.5），锁定人会收到通知；agent 不能确认自己提的改动。
- 不锁定的计划，agent 随情况调整。每处改动都在时间轴上，人可以撤销。

### 2.3 依据
依据回答「这个块凭什么成立」。来源有三种，都不需要 agent 手写：
1. **运行记录**：写这个块的会话在这一轮里读过的文件、跑过的命令和结果、引用的消息；如果它是在记子代理的结论，也包括那个子代理的运行记录（§4.4）。
   - 系统按块里提到的代码位置，去找**真的读到过那几行**的调用，读得越窄越优先；只按「碰过同一个文件」去对会挂错（原型第三轮）。
   - 对不上的不硬挂；块在某份报告下面整理出来的，出处指回报告。
   - 每条都带一段摘录快照，所以消息后来被 compact、回退或 fork，依据仍然可读。
2. **正文里的代码位置**：`path:line`、`path#symbol` 是语法，不是自然语言，系统把它们转成代码锚点：用 `server/lib/agent/structural/`（tree-sitter）定位到所在的符号，对规范化后的文本取指纹，记下当时的提交。没有语法的语言退化为「行范围 + 文本指纹」。
3. **人的确认**：人在对话或收件箱里确认的事，确认本身就是依据，用 `msg:` 指向那条消息。

- 整理进事实树的块带着出处，指回任务；它的代码位置照样按那个任务的运行记录去对（§4.7）。出处本身也算依据。
- **评估不另设**：测试、评审、基准的结果就是运行记录，挂成依据。

**代码锚点（轻量保留）**
- 仓库主干前进时，后台 job 只重算变更路径上的锚点（`git diff --name-only`，有条数上限和超时）。
- 指纹变了，块显示「代码已变」：检索降权，注入时附一句提醒，例如「它提到的 `auth.ts#refresh` 在提交 abc 中改过」。
- agent 要依赖这样的块时先核实：仍然成立就点「仍成立」刷新锚点；不成立就改写，或标为不成立。这一步由本来就在运行的 agent 完成，不额外花钱（D2）。
- 一次大重构引起的大量提示合并成一个事件，附「批量核实」按钮，模型和花费由用户选。
- 局限：抓得到直接改动，抓不到间接漂移，例如块讲的是 A 的行为，实际改的是 A 调用的 B。

**显示只标例外**：「无依据」「代码已变」；不成立的块在事实视图里不列。有依据、没变化的块不加任何标记，依据列表在块的侧栏里（§3.1）。

### 2.4 空间

| 空间 | 数量 | 谁能看 | 替代什么 |
|---|---|---|---|
| 知识库 | 多个 | 空间门（级别 + 受控标签），页可以再收窄 | 知识库集合 |
| 项目 | 每个项目一个，可以先于仓库存在 | 项目成员与角色 | 新增 |
| 个人 | 每个用户一个 | 仅本人 | 知识库的个人条目；另外存偏好与记忆 |
| 会话 | 每个叙述者一个，子代理也有 | 跟随叙述者的访问权限 | spec 命名空间 |

- agent 默认写在当前项目或自己的会话空间。会话属于哪个项目，仍由 `resolveNarratorProjectId`（`server/services/narrator-project.ts`）决定。
- 块不跨空间移动，跨空间是复制，系统自动记下出处。
- **读权限**
  - 先过空间门，再看页级收窄；块继承所在页的权限。查询前先算出可读的集合，在 SQL 里过滤，然后才取前 N 条。
  - 会话能读到什么，取所有**能读**这个会话的人的交集（D9）：注入的内容会持久化、广播、每轮重放，只读的人也看得到。公开会话退回匿名基线；项目会话先过项目门，再取成员交集（有人数上限）；个人空间只在单人私有会话里可读。会话的可见范围放宽时，已经注入的内容另外处理。现在的知识注入按 `_currentUserId` 逐轮解析（`server/services/agent-runtime/orchestrator.ts`），挡不住「A 读进上下文、B 下一轮问出来」。
  - 链接不是后门：读不到的目标，链接显示为占位，嵌入不展开，不暴露目标是否存在。
- **写权限**：有直写权限就直接写（D1）；没有的转成待确认（§2.6）。项目空间的信任级别与仓库文件相同，因为 agent 本来就能改仓库里的 CLAUDE.md；知识库和个人空间这类跨项目、跨人的内容要人确认。

### 2.5 历史
- **每次改动都是一个提交**：谁写的（人、会话或子代理）、哪条消息、哪次工具调用、什么时候。人在同一页上空闲 30 秒以内的连续编辑合并成一个提交；多人在实时会话里共同编辑的窗口，提交记下全部参与者。
- **时间机器**（R7）：大纲视图底部有一条时间轴（体验见 §3.2）。块的每个版本记录由哪个提交产生、到哪个提交失效，还冗余记下块那时在哪一页。按时间点读取一页就是一次按页加区间的查询（`page_id = ? AND from_seq <= T AND (to_seq IS NULL OR to_seq > T)`）；页里某棵子树从整页结果在内存里截取。P0 基准：2000 块的页 p95 约 8–10 ms（§7.2）。
- **撤销 = 补偿提交**：之后没人再改过的块恢复原状；被别人改过的列为冲突，不覆盖。
- **回退会话到某条消息**：会话空间里晚于这条消息的改动自动补偿；已经写到共享空间的列出来，由人选择是否一并撤销。现在回退会话不会回退 spec 内容（`server/services/revert-history-commit.ts` 只把修订的来源消息置空），新模型补上了这一点。
- **fork = 复制**：子会话复制父会话空间的当前状态，不复制历史，短 id 不变，所以继承来的上下文里的地址仍然有效。共享空间不复制，直接共享。现在的 `forkSpecNamespace`（`server/services/knowledge/sqlite-write-store.ts`）让子会话的指针引用父会话的修订行，父会话被硬删后文件会悄悄消失；改成复制就没有这个问题。
- **保留**：共享空间的历史永久保留，会话空间的历史随会话；被引用的版本不能删；管理员可以彻底清除，由后台 job 执行，只留一条不含内容的审计记录（D3）。
- **按当前权限显示历史**（D4）。
- **责任链**（R19）：每个提交都能沿创建链追到人：子代理 → 派它的会话 → 会话的发起人；例程触发的会话追到例程的创建人，Bot 追到 Bot 的创建人。agent 的确认、锁定都记在链上那个人的名下，审计和时间轴里可见。这条链由系统维护，不需要谁去理解它。

### 2.6 待确认
直写是默认（D1）。下面这些改动不直接生效，而是转成待确认，交给决定的人；写的一方接着做别的。

| 改动 | 交给谁 |
|---|---|
| 没有直写权限的写入，例如知识库空间默认要审核（D8）、Bot 写共享空间 | 空间的审核人；Bot 的创建者 |
| 锁定计划里增删任务、改任务的内容或顺序；锁定计划的完成 | 锁定人，或他指定的 agent |
| agent 写人的个人空间（偏好、记忆） | 本人 |
| 一次删除或移动大量别人写的内容（团队之外，超过 50 块） | 内容的作者或项目管理员 |
| 给会话加一个工作区的执行权限 | 派它的会话自己有这个工作区时由它给，否则由人；生产设备一律由人 |

- 写的一方在确认前读到的是自己的版本，别人看到的还是原样。
- agent 可以在权限内确认，记在它的责任人名下；不能确认自己提的。
- 人一次可以看完、批量处理（§3.3）。
- 每种待确认都统计原样通过率（§1.4 原则 5）。
- 多路径探索不需要待确认：探索出来的会话默认只写自己的会话空间，选定后再整理进项目，带出处（§4.5、§4.7）。

## 3. 人怎么用

### 3.1 浏览与编辑
- **页默认是事实视图**（R27）：只列事实；任务和它下面的内容收起来，在相关的事实上露一个「进行中」，点开看是哪些任务、提问或待确认的改动。切到「全部」或者打开任务本身，就看到过程。
- **事实上只有三种标记**：「代码已变」「无依据」「进行中」。「进行中」只算三种情况：
  - 挂在这个块下面、还没做完的任务或提问；
  - 笔记碰到同一段代码、还在做，或者做完了还没整理的任务；
  - 这个块等确认的改动。
  只是链接到它的不算：计划引用一条事实，多半是依赖它，不是要改它。这些在侧栏的反链里看。
- **侧栏**：一个块的依据、出处、反链、历史，以及和它相关的过程（包括试过不行的方案）。它们是另一个维度，不进正文。
- **按预算逐层展开**（R26）：先放满一层，再展开下一层，放不下的折成「…还有 N 项」，嵌入也算在预算里。所以顶层总能看到全貌，越往下越细。人看的视图按屏幕定预算，agent 读和注入按块数或字符数（§7.2），规则是同一条。
- **团队或企业的总图**：就是一页拼接视图，嵌入各个空间、各个团队的顶层页，按预算每个只显示它的概括；读不到的显示为占位（§2.4）。每个团队维护自己的子树，总图不需要另一套结构。
- 大纲视图的其余功能：层级、折叠、聚焦；链接和反链；嵌入就地编辑（R5）。
- 拼接视图（R6）：在一页里放嵌入或保存的查询。查询按空间、标题、正文、任务状态、指派、标签、是否有依据、是否代码已变来筛。
- 任务看板是过程这一维的内置视图：按执行人和状态分组，可以指派、转交、重开；完成了还没整理的任务标「待整理」。
- 编辑器见 §6。

### 3.2 时间轴
大纲视图（P1a）和图谱视图（P5）底部有一条时间轴（R7）：
- 变更密度图，用颜色区分人、agent 和系统。
- 事件标记：确认生效、探索路径选定、批量导入、批量「代码已变」、git tag 和发版。
- 拖到某一点看那个时刻的样子；框选一段，看这段时间的增、删、改、移。
- 播放、单步前进后退，按人、会话或子树过滤；从任意一处变更跳回产生它的会话和消息。
- 把一个块或一页恢复到某个时间点，恢复本身是一个补偿提交。
- 实现：读出那个时刻的整页（2000 块以内），在内存里按树序切成每批最多 500 块；拖动时只拉相邻提交的增量，版本行上的变化标记直接给出增、改、移、删；超过增量上限的大提交折叠成一个事件；图谱布局对时间窗内出现过的全部节点一次算好，拖动时不乱跳。
- **跟着视图走**（R27）：事实视图的时间轴只走改到事实的提交，单步和播放都跳过只改过程的提交；每一处变化都能点回造成它的任务（整理的提交带着出处）。过程视图回放的是进展。
- 时间机器按「系统时间」回答「当时我们是怎么认为的」；代码锚点里的提交号回答「这件事对哪个代码版本成立」，两者不混用。

### 3.3 收件箱与决定
- **收件箱只放要你决定的事**：待确认的改动，以及问你的问题。每条都带建议和理由。
- **一次回答多条**：全部采纳建议；不同意的单独回答。
- **一件事**：一条提问连同挂在它下面的细项，或者同一个块下面的几条提问，在收件箱里算一件事，可以一次回答，各个子项带默认值。不另起「决策包」的名字，放在同一个块下面就是一组。原型里 31 条要你回答的提问最后收成了 5 件。
- **可逆的先按建议做**：草稿计划里可逆的决定，agent 先按建议做，标为「暂定」，你随时可以推翻；建在暂定决定上的东西会被标出来。只有不可逆的、关乎你偏好的，才停下来等你。
- **优先在对话里问**：agent 在回合结束时提问并附建议，你在对话里回答，回答作为依据记下来。收件箱是兜底。原型里负责人的全部决定都是在对话里做的。
- **agent 代你确认的事**，每天汇总成一份摘要，可以一键撤回。
- 不另建收件箱，在现有的 human attention（`shared/human-attention.ts`，现有 `async_question`、`blocking_question`、`permission`、`plan_approval`、`reflection` 五种）上加两种：`outline_decision`（待确认、问你的问题）和 `outline_digest`（汇报、代你确认的摘要、批量「代码已变」）。列表行只带 id 和摘要。

### 3.4 汇报
- 从提交 diff 生成一份汇报：今天多了哪些知识（事实树里新增或改写的）、完成了哪些任务、什么在等你，每项带链接，可以点进去看。
- 这是人日常读的东西，不是原始的大纲树。原型里一天长出 550 块，负责人实际读的是 agent 写的汇报。
- agent 给人写总结时，也从这份汇报出发。

## 4. agent 怎么用

### 4.1 工具

| 工具 | 作用 |
|---|---|
| `OutlineRead` | 读一页（默认只列事实）或一个任务（全部列出），渲染成 markdown 大纲，按预算逐层展开；可以按时间点读 |
| `OutlineSearch` | 混合检索（§5） |
| `OutlineEdit` | 用 markdown 大纲写：新增、改写、移动、删除。任务就是复选框，改复选框就是推进状态 |
| `Ask` | 问人：问题、可选项、建议和理由；回答回来时唤醒 |

- 不暴露身份参数、链接角色、空间规则和关注范围。地址用标题、别名或短 id，返回值结构化。
- 写入的结果只有两种，都说清楚：已生效；或者已交给某人确认，以及哪些任务因此要等。
- `OutlineEdit` 一次可以写一整段大纲，所以「把一份报告记成几条结论」是一次调用。没有隐式删除，要删就显式写。
- 锁定和解锁是 `OutlineEdit` 里的显式操作，只有计划的作者、它的管理者，或者人授权的 agent 能做。
- `Agent` 工具新增 `task`、`workspaces`、`focus` 参数（§4.4、§4.6）；`EnterPlanMode` / `ExitPlanMode` 改为围绕计划树（§4.3）。
- 渲染给 agent 的样子。读一页：

```text
- auth 模块 ‹进行中：补回归测试、改刷新逻辑›
  - token 刷新存在竞态 ‹代码已变：auth.ts#refresh›
  - 刷新令牌只存在服务端（`auth/store.ts#saveRefresh`）
（这里只列事实；任务和它们下面的 6 块没列出）
```

读一个任务：

```text
- [ ] 改刷新逻辑 @agent:w-auth ‹等前置：补回归测试›
  depends:: [[补回归测试]]
  - 方案：刷新时带上版本号，旧版本的请求直接拒绝
```

- 现有 `Read`、`Write`、`Edit`、`Grep` 对 `spec://` 的路由在迁移后移除。

### 4.2 上下文注入
- 系统提示里只放 §0 那三条约定，放在现在 `getDynamicSpecSystemReminder` 的位置。细节由工具描述和返回值承载。
- 现在写死的几种注入改为内置视图，每段有字符预算，只在有变化时注入：

| 现在 | 内置视图 |
|---|---|
| 任务摘要 `living_work_spec`（`server/services/spec-reminder.ts`） | 当前任务：进行中、等待中、下一个 |
| 行为边界 `behavior_fence` | 行为边界：标记为 agent 只读的页 |
| 知识关键词注入（`server/services/knowledge-injection.ts`） | 相关知识：按当前消息和工具输出，只从事实里检索（§5） |
| compact 时注入完整任务列表 | compact 上下文：未完成的任务，加上本会话涉及的关键决定 |
| 无 | 团队动态：上一轮之后，别人在团队任务树和我关注的地方做的改动 |
| 无 | 我的偏好：个人空间里的偏好，只在单驱动者会话中注入 |

- 每一段注入都能追溯到视图，用户看得出 agent 为什么知道某件事。
- 过程不进「相关知识」：别的任务下面的内容只在显式检索时出现，自己的任务在「当前任务」里。
- 插件写入的 SOP 段落和任务，作为块写进对应的页。

### 4.3 计划与规划方式
- **计划就是一棵任务树**（R20）：根块写目标和验收，子任务是步骤；调研结论、决定、开放问题挂在下面。可以分层：里程碑 → 步骤 → 子步骤；锁定的单位是子树，所以可以只锁第一个里程碑。
- **规划**：agent 或 plan 子代理直接在大纲里写计划树。人可以同时在编辑器里改、加约束、提问，讨论就发生在计划本身上。规划阶段默认宽松：本来就要写大纲、读代码、跑只读命令；「规划时不改文件」做成可选项（D25）。
- **提交**：`ExitPlanMode` 提交计划根。人看到计划和上一版的 diff，选择：
  - 退回，附意见；
  - 按草稿执行；
  - 锁定后执行，可以指定一个 agent 替自己确认步骤调整（§2.2）。
- **执行**：续跑从第一个能开始的任务开始（§4.8）。
- **完成**：不另设结项步骤。每个任务完成都会整理（§4.7）；计划根完成时，完成它的人在根下写一句结果和目标的对照，这也只是一条普通笔记。
- 现在的自动计划审查（plan reflection）改为在计划上留意见，不阻塞。
- `.narrafork/plans/` 下的计划文件退役。

### 4.4 子代理：专注
- **子代理默认不拿大纲工具**（R16）。它拿到的是一份普通语言的任务说明：目标、真正相关的约束、必要的上下文，由派它的会话从任务树生成。
- 它照常干活、自由写报告，用什么语言、什么格式都可以。不需要知道大纲、地址、规则，也不需要填任何格式。
- **结束时系统自动挂回**：报告原文和运行记录挂到它的任务下。报告只按 markdown 语法转成子块，不解析语义；报告里提到的代码位置同样成为锚点。所以报告本身就能被检索，代码变了也会提示。
- **派它的会话顺手记账，不另开会话**：它本来就要读子代理的回复才能接着干活，记账只是顺手多写几行。只写三样：
  - 一两句摘要，出处自动指回报告；
  - 要人拍板的提问，带建议；
  - 遗留的任务。
- **不把报告抄一遍**：结论已经在挂回的报告里，可以检索；任务完成后由派它的会话接着整理进事实树（§4.7）。它刚读过报告，上下文和提示缓存都在。
- 子代理中途有问题，就问派它的会话；后者替它查大纲，用普通的话回答。
- 「无约束」指不背大纲协议，不是不受安全约束：工具权限、行为边界、工作区照旧由系统强制。
- 需要时也可以给子代理大纲工具，比如让它维护一棵大任务树；默认不给。
- 人自己在主会话里专注写代码时，也可以派一个子代理在后台替团队记账。这只是一种用法，不是一种模式。
- 原型实测：专注 agent 三轮都没有规则负担。第三轮另开一个会话记账，读报告就占了大半成本；这部分派它的会话本来就要做，不该算成记账（附录 B）。

### 4.5 多 agent 协作
- **图谱是黑板**（R13）：交接、结果、决定，凡是以后还会用到的都写进大纲；消息怎么发都行，但谈定的事要落到大纲上。好处是交接不丢、结果可以检索、人随时能接手，时间轴按任务树过滤就是团队工作的回放。
- **委派 = 建任务 + 指派**：`Agent` 工具可以直接传任务地址，子代理的说明由任务树渲染出来（有预算）；结果自动挂回（§4.4）。
- **领取**：勾成进行中即领取。会话运行期间自动续租；会话结束或长时间无响应，租约到期，任务回到可领取，子树里的进展保留，并自动记一条「上一位执行者的租约到期」。结果绑定领取代数，租约转给别人之后才到的结果记为迟到结果，不能用来完成任务（对应 `docs/SUBAGENT_REUSE_ISSUES-DESIGN.md` 问题 1）。
- **完成通知管理者**（建任务的人或会话），不满意就重开。
- **重叠提示**：系统从实际改动的文件推断每个任务的工作区域（现在的 `recordTeamFileChange`）。两个进行中的任务碰到同一处时，在工具返回里提示一句，例如「T12（会话 B）也在改 `auth/refresh.ts`」。
- **唤醒**：经现有的 runtime inbox（`server/services/agent-runtime/inbox.ts`，`team` 通道），按「空闲才唤醒」调度，合并去重。事件：有任务指派给我、我的前置完成或取消、我问的问题有了回答、我管的任务完成、我的租约快到期。关注范围里的变化不单独唤醒，只进下一轮的团队动态。
- **可领取池**：没有执行人、前置都已完成、标为可领取的任务。空闲成员是否自动领，由团队设置决定，默认关闭，由管理者指派。
- **多路径探索**（R3）：从同一个需求 fork 出几个会话，各自有 worktree，默认只写自己的会话空间。对比视图用嵌入把几条路径的方案、结果、代价并排拼起来。选定一条：用 git 合并它的代码，它的任务按 §4.7 整理进项目的事实树；落选的只整理落选原因，写成「不用 X：原因」。选定之前，几条路径都不整理。
- **与 `docs/DYNAMIC_SPEC_TEAM_TASKS.md` 的关系**：那份设计的任务持久化、写操作和 UI 还没实施，直接按本模型实现。

| 那份设计 | 本模型 |
|---|---|
| 团队任务树、稳定编号 | 空间里的任务树；块的短 id |
| M / E / R 角色 | 建任务的人是管理者，领取者是执行者 |
| `todo/doing/blocked/submitted/done/cancelled`、暂停、归档 | 复选框四种状态；等待由前置推导；不设待验收 |
| contractVersion | 任务块的版本 |
| assignmentVersion / executionRunId | 领取代数 |
| origin / event / receipt 记录 | 带来源的提交 |
| 持久事件与派发 | runtime inbox 唤醒 |
| protected | 人建的任务；要严格照做就锁定 |

### 4.6 多工作区与关注范围

**工作区**（R22）
- 会话可以绑定多个工作区：某台设备上的一个目录，可以是 worktree。执行类工具（`Bash`、文件读写、终端）要指明目标工作区；只有一个时可以省略。
- 每个工作区按所在设备的原生路径规则处理，Windows 和 POSIX 不同。每个工作区对应一个项目，会话因此出现在多个项目里。
- 各仓库的 AGENTS.md、CLAUDE.md 不一次全部加载：第一次在某个工作区修改或执行时才加载那个仓库的约定。
- 跨仓库的一次改动在同一个任务下成组记录，每个仓库的提交都作为依据。
- 加工作区：根会话由人加；子代理由派它的会话从自己有的工作区里给，否则转待确认交给人。生产设备一律由人确认，可以带期限，期限从确认时算起（R24）。
- 设备授权在执行路径上检查，不依赖提示词。讨论分支 `discuss/narrator-remote-workspace` 里的「会话 × 设备工作目录绑定」并入这里。
- **归属只认一个主项目，执行按工作区**（D21）：
  - 谁能看会话、trait、routines 只看主项目；执行层（执行策略、设备授权、CLAUDE.md）按每个工作区自己所属的项目算。会话同时属于几个项目不可行：读权限取并集会泄露，取交集几乎没人能看。
  - 主项目创建时定下：从项目页建就是那个项目，否则取第一个工作区推导出的项目，非 git 工作区不能当主项目。可以显式换，换前确认并列出会得到、失去访问的人；切目录、切设备不再悄悄换。
  - 在工作区 W 上执行时，规则是全局 + 主项目的 deny 层 + W 所属项目的全部规则层 + 会话层；allow 只取 W；设备按 W 的项目授权。技能加载所有工作区的根。子代理写明：行为跟归属走，执行跟工作区走。
  - 加工作区 B 要有 B 的 write，私有项目还要是成员；B 的 owner 收通知，不用审批。B 的成员只看到「有会话在这里干过活」：标题、主项目、目录、提交，正文仍按会话的权限。
  - 远端工作区的项目在绑定时由人选，executor 上报的 remote URL 只用来预填。
  - 跨仓库产出的知识默认写主项目空间；写进 B 要有直写权限，否则转待确认。
  - 落地顺序：先修现有的四个缺口（不改表、不等 PG，见「现状：会话与项目归属」页）；改链接表时同时给 PG 建索引；worktree 按「同仓库同相对路径」归回子目录项目，嵌套仓库和子模块维持现状，写进文档。

**关注范围**（R23）
- 会话关注的几块地方：页或子树、代码路径、工作区。存在会话上，不是一页大纲。
- 作用：这些地方的内容优先注入，变化会进它的团队动态。范围之外照样能读、能搜，结果标「范围外」；只在跨边界时提一句，比如「你依赖的 `contracts/api.ts` 改了」。
- 默认由系统推断：它的任务、实际改动的文件、所在的项目。派活时可以指定（`Agent` 工具的 `focus` 参数）。
- **不设写入关卡**：关注范围只管注意力，不管能不能写。能不能写由权限和 §2.6 决定。试用里 3 次「扩大范围」请求全部原样通过，说明关在这里只是摩擦。
- 主 agent 或人可以随时调整下级的关注范围和工作区（R24）。
- 软上限约 5 块，每块注入一段摘要，而不是全部内容。

| 场景 | 怎么配 |
|---|---|
| 多服务器联调 | 根会话绑定 staging-a、staging-b 两个工作区；要上生产服务器排查时，由人给 30 分钟的执行权限 |
| 多仓库联合开发 | 根会话管前端、后端、契约三个仓库。后端子代理只拿到后端工作区，关注后端模块页和契约仓库；要改接口定义时，根会话把契约工作区给它 |
| 只看不碰的调研 | 子代理绑定同一个工作区，但只给读文件和检索的工具（现有的工具权限），报告交给派它的会话 |

### 4.7 整理：过程变成知识
目标（R21、R26）：完成的任务里有长期价值的结论，按主题进入事实树，放在合适的层；过程原样留在任务下，两边可以互相追溯。干活的 agent 不用操心这件事。

**什么时候整理**
- 任务完成或取消、提问被回答之后，马上排队。下面只有复选框、没写过笔记的任务不整理，不花钱。
- 同一组提问（一条提问连同细项，或者同一个块下的几条）一起整理、一起收尾；队列也按组列。
- 子任务各自整理自己下面的笔记；父任务完成时只整理它自己下面的。完成之后又有人补了笔记，只整理新的部分。
- 兜底：一直不完成的长任务，下面一周没再变的笔记也整理；会话空间里不在任务下的笔记，同样一周后整理。
- 多路径探索选定之前不整理（§4.5）。

**谁来整理**（D15）
- **默认由原会话接着整理**：做完这个任务的会话自己整理；专注子代理干的活，由派它的会话整理，子代理不碰大纲（R16）。原会话的上下文里有结论、推理和读过的代码，提示缓存也还热，比另起一个 agent 从头读报告更准，也更省：第三轮另开会话记账，读报告就占了大半成本；单独的整理 agent 每个任务要 14–26 万 token（附录 B）。原会话用的是它自己的模型，单价可能更高，靠缓存和不重读抵消，第五轮量一次。
- **时机**：把任务勾成完成的那次写入，工具返回里就提示有多少笔记要整理、怎么看（原型的 `settle`）。会话在这一轮结束前整理；人正在等回复时，放到回合末尾，不打断。要整理的内容、可能的去处（事实树里讲同一段代码、或者被笔记链接到的块）、事实树的顶层页和整理的做法都在工具返回里，不用背规则。
- **兜底才派单独的整理 agent**：原会话已经结束、相关上下文被 compact 掉了、迁移进来的积压、长期任务一周没变的笔记，以及「下层已变」队列。整理 agent 用便宜的模型，每次一个任务或一组。
- 整理的提交记在任务管理者的责任人名下（§2.5）。写入权限照常：项目空间直写；知识库空间走审核（D8）；写别的项目空间要有那里的直写权限，否则转待确认；跨仓库的结论默认写主项目空间（D21）。

**怎么整理**（`settle` 的工具返回里写着这些，谁来整理都一样）
1. 只挑以后还用得到、站得住的结论；只对这次任务有意义的过程、拿不准的，不搬。
2. 写成脱离这次任务也读得懂的现在时陈述，代码位置照写。决定写成现行规则，带一句理由。
3. 先找它该在的地方：事实树里已经有，就改写那一块，旧说法留在历史里；还没有，就加在最贴近的块下面，和兄弟块一样粗细；没有合适的页，就新建一页，页下第一条写一两句概括。
4. 一个块的直接子块别超过 15 个，多了就加一层归组；改了下层，看一眼上层的概括还对不对。
5. 试过不行、以后还会有人想到的方案，写一条「不用 X：原因」，放在相关的事实下面。被推翻的事实直接改写，事实树里不留「不成立」的块。
6. 没做完的子任务不用管，它们还在看板上。

**维护各层的密度**（R26）
- **下层已变**：一个事实块的直接子块，自它上次改动或核实以来变了 3 处以上，就进整理队列，看它的概括还对不对：对就核实（`recheck ok`），不对就改写。只看直接子块：再往下的变化由中间那层的概括吸收，改了中间层，就算它的父块下面变了一处。
- 收尾时，整理的会话放进内容、挪动或改过的那些块的父块都记为已核实，所以它自己的整理不会再触发一轮。归组时常常先写好组的概括再挪子块，不这样算就会误报。
- 「下层已变」不标给读者：整理很快就会跟上，标出来只是多一个标记。
- 不设密度的硬上限：15 个子块只是整理的指引；读者那边由按预算展开兜底（§3.1）。

**出处与追溯**
- 整理进来的块自动带出处，指回任务；它的代码位置照样按那个任务的运行记录去对依据（§2.3）。从任务那边也能看到它被整理成了什么。
- 过程不删、不改：任务和报告原样保留。完成的任务不进续跑和自动注入（过程本来就不进「相关知识」），显式检索能查到。所以不需要「结项任务」「计划归档」「钉在完成那一刻」这些步骤和状态。
- 统计整理结果的原样保留率：一周内没被人改写、删除或撤销的比例。长期偏低，就换模型，或者让整理先转待确认。

**常见和边缘情况**

| 情况 | 怎么处理 |
|---|---|
| 新项目，事实树还是空的 | 第一次整理就建页，页下第一条写概括 |
| 这条结论事实树里已经有了 | 改写那一块，加上出处，不新建重复的块 |
| 新结论推翻了旧事实 | 改写旧事实，旧说法在历史里；时间轴上看得到是哪个任务改的 |
| 结论涉及好几个模块 | 放在最主要的那处，别处用嵌入或链接，不复制 |
| 结论属于另一个项目（跨仓库） | 按代码位置放进那个项目的空间；没有直写权限就转待确认 |
| 任务取消了 | 照样整理，主要是试过不行的方案 |
| 任务下只有复选框 | 不整理 |
| 一直不完成的长任务 | 下面一周没变的笔记照样整理 |
| 事实块下面挂着待办或提问 | 它们是过程，在这个块上收成「进行中」 |
| 只装着提问的块，比如「待定问题」页 | 它本身是事实，正文就是一行标题；下面的提问收成「进行中」 |
| 有人把事实块勾成了任务 | 它就成了过程，从事实视图里消失；要在事实上挂待办，就挂在它下面 |
| 整理放错了 | 在时间轴上撤销或移走；原样保留率会反映出来 |
| 整理时有人在编辑同一页 | 走正常的并发合并（§6.5），冲突的块留给人，整理结果里列出来 |
| 锁定的计划 | 整理只写事实树，不改计划本身，不触发锁定的确认 |
| 时间机器回看 | 事实还是过程，按那个时刻的树判断 |

### 4.8 续跑与现有机制
- **续跑候选**从数据库查，和 agent 当前上下文里看到什么无关：本会话领取的任务和会话空间里的任务，待办或进行中，前置都已完成；执行人是人的任务不进候选。没有进行中的任务时，把第一个候选提为进行中，保留现有行为（`server/services/narrator-session.ts`）。
- **人建的任务**（`/goal` 或界面添加）：管理者是人，执行者是本会话。现在的「受保护任务」和文本 hash 锁（`spec_protected_tasks`）由锁定替代。`/goal` 建的任务默认锁定（D26）：锁的只是目标和验收，下面的步骤随 agent 调整，整个目标完成要人确认。
- **任务反思**（`server/lib/agent/tools/task-reflection.ts`）：不改成可选，P2 补齐下面四个缺口后，和它的门禁、两个决策工具、`spec_protected_tasks`、human attention 里的 task_reflection 一起删（D26）。理由：只找到它误拦和出故障的记录，没有拦对的案例；它只能读会话历史，不能验证。删之前要补上：取消、删除和完成一样会让任务消失，同样要标出来；依据要带结果，并且晚于最后一次相关改动，能确定性校验的由系统校验。
- **在自然节点同步**：回合结束、compact 之前、子代理返回、给用户写总结时，系统把明显的进展同步到任务上；只在发现明显不一致时提示一句，比如「测试都过了，T3 还是进行中」。现在每 15 次工具调用一次的任务提醒、任务列表为空时的催促，都去掉。
- compact 之前，把摘要里和当前任务相关的部分写回任务进展。

## 5. 检索

### 5.1 流程
1. **确定范围**：按 §2.4 算出可读集合，在 SQL 里过滤。
2. **召回**：FTS 与向量并行。FTS 在 SQLite 上用 FTS5 trigram，在 PG 上用 pg_trgm，沿用 `server/db/fts.ts` 和 `server/db/pg-fts.ts` 的做法；页的关键词作为高精度触发词一并合入。
3. **扩展**：沿链接和父块各扩展 1 跳。
4. **排序**：配置了 rerank 模型就用它，否则用 RRF（倒数排名融合）；最后乘上 §5.4 的权重（R12）。
5. **渲染**：带面包屑（祖先标题）和例外标记，受字符预算约束；过程里的结果标出所在的任务。

### 5.2 embedding
- 输入是块正文加所在页的标题，不含完整的祖先路径，这样祖先改名不会触发整棵子树重算；完整面包屑只在 rerank 时加上。
- 以（模型, 内容 hash）为键缓存，相同内容在不同版本之间复用。
- 写入后由后台 job 批量计算；没有配置 embedding 模型时退化为纯 FTS。
- 模型从模型目录里选（`shared/model-catalog` 已有 embedding 类别），支持 API 和 OpenAI 兼容的本地端点（D7）。

### 5.3 向量存储
- 初版不引入原生扩展：向量量化成 int8，在 db-worker（`server/lib/db-worker/`）里常驻成矩阵，先按空间过滤，再暴力扫描。两种方言通用（D10）。
  - 存储：按 `(model_id, space_id, chunk_no)` 打包存，每行约 512 个向量（带块 id 和缩放系数），worker 启动时分批加载，按（空间, 页）连续存放。分批是因为加载峰值是稳态的两倍。
  - `outline_embeddings`（按内容去重的缓存）不在查询路径上 join：P0 基准里这样做，20 万向量、10% 过滤时 p95 就要 190 ms 左右。
  - 内核用 WebAssembly SIMD（5 KB，`prototypes/outline-bench/vector/kernels.c`），不支持时回退纯 JS（慢 3–4 倍）。
  - 精度：int8 对 float32 的召回 @10 约 0.98；要更高就 int8 先取前 200 再用 float32 重排（合成数据上召回 1.000，真实嵌入要复测）。
- P0 基准（100 万 × 1024 维，常驻 int8 + wasm）：10% 过滤 p95 46–71 ms，不过滤扫全量 268 ms；常驻内存约 1.2 GB；扫描期间主线程事件循环 p99 ≤ 2 ms。
- 单次扫描超过时间预算就降级为纯 FTS，并记慢日志。预算按**候选数**算，不按总向量数。
- **该换扩展的信号**，满足任一：候选数长期超过 50–70 万（没有 wasm 时 10–15 万）；常驻内存超过 1–2 GB 不可接受；不过滤的全库检索超过约 75 万向量；需要在 PG 里直接做库内检索。届时接 pgvector 的 HNSW；sqlite-vec 是否能带来量级提升没有验证。接口提前预留。不一开始就用扩展，是因为 bun:sqlite 在 macOS 上默认用系统自带的 SQLite，要加载扩展就得换构建，跨平台打包成本高。

### 5.4 排序与注入

| 块 | 自动注入 | 搜索默认 | 排序 |
|---|---|---|---|
| 事实 | 按相关度 | 返回 | 正常 |
| 无依据 | 只在写它的会话里 | 返回，带标记 | 降权 |
| 代码已变 | 注入，附提醒 | 返回，带标记 | 降权 |
| 不成立 | 否 | 显式 `include` 才返回 | — |
| 过程（任务和它下面的块、会话空间） | 只进「当前任务」，不进「相关知识」 | 返回，标出所在的任务 | 同样相关时排在事实后面 |

- 同一件事既在任务下、又已经整理进事实树时，检索先给事实，过程里的原文作为出处跟在后面。
- 自动注入受相似度阈值、每轮条数和字符预算约束；同一个块在一个 compact 周期内只注入一次，沿用 `knowledge_injection_events` 的语义。
- **注入的边界**（D22）：
  - 关键词仍是唯一能无条件触发注入的方式；按相关度的注入要过阈值，受 §2.4 的读权限约束，和关键词注入共用每轮的字符预算。
  - 没有执行用户的轮次（例程、系统触发）不注入。
  - 没有项目的会话只看全局空间和个人空间。
  - 知识库里归档的条目迁过来后默认不返回，显式 `include` 才返回，和不成立的块一样。
- **写入时提示**：写入或新建页时，在同一空间里找高度相似的块和同名、别名相近的页，放进工具返回，例如「已有相近的块 X」「可能已经有页 Z」。由正在写的 agent 自己判断是合并、改写旧的，还是无关。不额外调用模型。

## 6. 编辑器与实时协同

### 6.1 目标
- 多人同时编辑同一页、同一个块（R9）：字符级合并，看得到彼此的光标和在场。
- agent 的修改实时出现在正在看的人面前。
- 数据库仍是唯一真相源（R8）：实时状态只是暂存，尽快落回块和提交。

### 6.2 两条通道
新增 WebSocket 端点 `/ws/outline?token=`：
1. **页订阅**：打开一页就订阅它。服务端推送结构操作、块正文的节流快照（给只看不编辑的人）、在场信息（谁在看、光标在哪个块、哪个 agent 正在读写这里）。
2. **页实时会话**：开始编辑一页时加入。一页一个 Y.Doc，其中每个正在被编辑的块有一个 Y.Text。光标和选区用「块 id + Yjs 相对位置」表示，所以选区可以跨块。

- 实时会话按页而不是按块：在块之间移动光标、按 Enter 新建块都不需要重新加入，撤销栈和光标也能跨块。
- 每个块只属于一页。通过嵌入或拼接视图编辑别的页里的块时，客户端同时加入那一页的实时会话。

### 6.3 正文：CRDT 只在编辑期间存在
- Y.Text 里存的就是块正文的 markdown 源文本，与 `content` 一致，编辑器负责渲染成富文本。
- **静止时**：块就是 `content` 加版本历史，没有 CRDT 状态。
- **开始编辑时**：服务端为这一页建一个 Y.Doc，作为权威参与者转发更新，并且当场用各块的 `content` 给整页的块建好 Y.Text（P0 原型：2000 块约 10 ms、213 KB、堆多 0.8 MB）；新建的块由创建方初始化；任何一方都不能用已有内容重复初始化，否则会出现重复文本。不等到第一次编辑才建：初始化到达之前的按键，按 §6.5 的严格合并会被判成冲突而丢字，原型里实际发生过。
- **编辑期间**：增量最迟每秒追加到 `outline_live_updates`，防止崩溃丢失；`content` 按节流同步为当前文本。
- **结束时**：最后一个参与者离开并空闲 60 秒后，服务端写下各块的最终版本，删除增量，丢掉 Y.Doc。服务器重启后由后台 job 用 `content` 和未定稿的增量重建，然后定稿。
- 好处：墓碑不长期堆积；`content` 始终是真相；页不在实时会话时，agent 直接写 `content`，不经过 CRDT。链接解析、FTS、embedding、锚点重算都只在提交时触发。

### 6.4 结构与属性：一个动作一个事务
- 一个用户动作是一个**大纲事务**：结构操作加若干块的正文修改。比如在块中间按 Enter，就是「截断当前块 + 新建下一块并写入后半段」。
- 大纲事务作为一条消息发给服务端，原子处理：按空间排序，校验权限、成环和版本，写成提交，再广播。客户端先乐观应用；被拒绝时（很少见，原型的随机压力里 900 次操作被拒 23 次，都是对方同时删了块）只回滚被拒的那个事务，之后还没确认的本地事务在新状态上重放，不能连同它们一起丢掉。
- 同级并发插入导致排序键冲突时由服务端重新生成；并发移动后写为准，会成环的直接拒绝。
- 正在编辑的块被别人删除时，编辑器提示「已被删除」，可以一键恢复。

### 6.5 人与 agent 的并发

| | 人 | agent |
|---|---|---|
| 看到的状态 | 实时 | 读取时的快照 |
| 正文 | Y.Text 实时合并 | 三方合并：以 agent 读到的文本为基线算补丁，应用到当前文本；和读取之后别人的修改不重叠就合并，重叠就拒绝并返回当前内容 |
| 结构、属性 | 按服务端顺序，后写为准 | 按读取时的版本检查，不一致就拒绝 |

- 人看得见别人正在改什么，合并结果不对能马上发现；agent 看的是快照，它的修改悄悄混进别人的修改里，容易产生没人察觉的错误。
- agent 读到的文本由服务端按会话做有界缓存，作为合并基线；缓存失效时退化为「读取之后有任何变化就拒绝」。
- 块所在的页正处于实时会话时，agent 的合并结果作为一个参与者写进 Y.Doc，正在编辑的人能看到它实时出现。

### 6.6 撤销与权限
- 每个用户一个统一的撤销栈，一个大纲事务就是一步。正文用 Yjs 的 UndoManager，只撤销自己的修改；结构用逆操作。经嵌入编辑别的页，也记在同一个栈里。编辑器里的撤销和时间轴上的「恢复」是两回事。
- 加入实时会话要读权限，发送更新要写权限；权限被收回时，服务端把该参与者踢出。在场信息只显示给能读这一页的人。
- WebSocket 遵守主线程规则：更新按 50 ms 合并后广播；正文快照每块每秒最多 5 次，慢客户端只保留最新一份；CRDT 更新不能丢，客户端积压超过上限就断开重连（§7.2）。

### 6.7 大纲编辑器（D11）
**结论：自己写大纲编辑器，建在 ProseMirror 的视图层上**（R10）。

| 方案 | 为什么不选 |
|---|---|
| 每块一个编辑器（Logseq、Roam） | 缝隙落在最高频的操作上：跨块选文字做不到；Enter 拆块、Backspace 合并、上下方向键都要切换焦点，中文输入法和移动端键盘容易出问题；撤销要拼多个栈；编辑态和显示态两套渲染，聚焦时版面跳动 |
| 直接用 Tiptap 的整页文档 | 编辑器文档成了真相，和块的身份、同一块出现在多处、按块的版本与协同、agent 的块操作都冲突 |
| 从零写 contenteditable | 输入法、Android、iOS、剪贴板的兼容是无底洞；行内输入框的设计（`docs/RICH_COMPOSER_DESIGN.md`）也明确不手写 |
| 整页一个 CodeMirror 文档，缩进表示层级 | 手感最像 Obsidian，但树结构要从文本编辑反推，多人实时编辑和 agent 同时写入时太脆弱。列为备选 |

- **块模型是真相，编辑器文档只是投影**：一个编辑视图对应一个编辑面（一页、一棵聚焦的子树或一个拼接视图），编辑器文档是当前窗口内的块树，每个块节点带块 id。
- **Schema**：`outline > block+`；`block = body + children?`；块体有段落、标题、代码、引用、表格；行内有文本和标记，以及链接、嵌入两种行内节点；任务的复选框是块的属性，画在块的外框上。
- **键位**：Enter 拆块，块首 Backspace 合并，Tab / Shift-Tab 缩进，Alt+↑↓ 移动，Esc 进入块选择模式（整块选择、拖动、批量缩进）。
- **输入 → 大纲事务**：ProseMirror 事务翻译成结构操作加受影响块的正文修改。正文修改是把块序列化成 markdown，和**编辑器上次显示的源码**做 diff，再按这期间收到的远端修改映射到 Y.Text 当前内容上写。直接和 Y.Text 当前内容做 diff，会覆盖还没显示进编辑器的远端修改：原型在输入法组合期间实际丢过对方的字。「编辑器上次显示的是哪一版」要做成显式的状态，单独写单元测试和随机测试。
- **跨页的编辑面**（拼接视图、嵌入）里跨块删除要按页拆开：两端各自截断，中间的块按页删除，不能像 ProseMirror 默认那样合并两端，否则后一页的块会被挂到前一页下。
- **块合并**：被并入的块的 id 不能就此消失，指向它的链接改指向合并后的块（或给旧 id 留重定向），记进提交。
- 结构操作在原型里是全量比较前后两棵块树：2000 块 9–12 ms，在单视图 2000 块的上限内可以接受；更大的页或低端设备上，结构键位要直接产出大纲操作，投影只重建变了的块。
- **远端修改 → 编辑器**：重新解析受影响的块并替换内容，通过「源码偏移 ↔ 编辑器位置」的映射保住本地光标；本地正在用输入法组合的块，推迟应用远端修改。
- **嵌入**用 node view 放一个子编辑视图，选区不跨越嵌入边界。块的外框（项目符号、折叠箭头、拖拽柄、复选框、在场头像）用原生 DOM 的 node view，避免每块一个 React 根。
- **超长页**：主要靠折叠和聚焦；单个编辑视图同时展开的块数有上限，超出部分用占位节点，滚动到附近再替换。
- 只读场景（搜索结果、聊天里的引用、悬停预览）继续用现有的 `MarkdownContent`。
- 依赖：直接用 ProseMirror（`@tiptap/pm` 已在依赖里），不用 Tiptap 的文档和协同扩展；新增的 Yjs（MIT）按 `docs/LICENSES.md` 登记。
- 代价：工作量是 P1 里最大的一块；块内方言要长期维护。

### 6.8 块内方言
- 服务端写入时把正文规范化，保证「解析 → 序列化」往返不变。
- 块体：段落、标题、代码、引用、表格。行内：粗体、斜体、行内代码、删除线、链接、`[[…]]`。嵌入 `![[…]]` 独占一块。任务写成复选框，属性写成 `键:: 值`。
- 分词器用 `shared/` 里已有的 marked@18（`shared/pretext-layout/parse-markdown.ts` 在用），浏览器和服务端共用同一份实现，序列化器自己写。`@tiptap/markdown` 不适合做规范实现：它过度转义（`snake_case` 变成 `snake\_case`），服务端和浏览器结果不同，还会丢表格。
- `[[…]]` 和 `![[…]]` 必须在分词阶段识别；行内代码里的是字面文字。
- 仓库里并存三套解析器（micromark、marked@18、marked@17），方言只取三者行为一致的子集。
- **方言外的写法不能静默丢弃**：要么拆成子块（列表、多段），要么原样保留为文本。现在的 `SpecMarkdownEditor` 就是反例（§1.3）。
- 细项已定（D23）：
  - 表格用 GFM 写法，单元格里不换行；docs 里 12 处 `<br>` 迁移时改成「；」。
  - 正文存 `[[空间/短id]]`，改别名不断链；输入时可以写别名、省略本空间前缀，显示成别名或标题；支持 `[[地址|显示文本]]`，表格里的竖线要转义。会话空间的块存绝对的会话空间 id。
  - 嵌入只能独占一块，放在一行中间的只能是提及。
  - 数学和图片先不进方言，写入时转义；图片以后做成附件块。
  - 块内的换行就是换行，按硬换行显示。
  - agent 写了列表、多段这类方言外的结构，拆成子块，并在工具返回里说拆成了什么；拆不了的按普通文本保留。
  - 最小转义，再做三个解析器的一致性模糊测试，以 marked@18 为准。
  - 标题 1–3 级，h4 及以下迁移时改成粗体段落；分隔线不做，迁移时丢掉。
- P0 原型发现的两条补充（负责人 2026-10-26 确认，D23）：
  - **中文标点紧贴强调**：粗体、斜体的边缘是全角标点、外侧紧跟汉字时（`这是**重点：**内容`、`**「重点」**内容`），CommonMark 解析不出来，12 种常见全角标点全部失败；随机中英混排段落里约 30% 会遇到。序列化后立即读回核对，把边缘的标点挪到标记外面（`这是**重点**：内容`），还不行就去掉这段标记，保证文字不丢。三个解析器上都要确认。
  - **裸网址和提及**：GFM 的裸网址会把紧跟的 `[[…]]` 吞进网址（marked 和 remark-gfm 都这样）。方言里网址就是文字，序列化时在网址和紧跟的 `[[` 之间补一个空格。

### 6.9 编辑器原型的验收清单（P0）
在真实浏览器里跑，覆盖桌面 Chrome / Safari、iOS Safari、Android Chrome。
1. **中文输入法**：在块中间组合输入时按 Enter、Backspace、方向键；组合期间另一个人修改同一个块。
2. **移动端键盘**：连续按 Enter 新建块、按 Backspace 合并块时，软键盘不收起、不闪烁。
3. **跨块剪贴**：跨块选中后复制、剪切、粘贴；复制出来是 markdown 大纲，粘贴多行 markdown 拆成多个块。
4. **撤销**：输入 → 拆块 → 缩进 → 输入，四步依次撤销、重做；和别人的并发修改交错时只撤销自己的。
5. **并发**：两人同时编辑同一个块；一人移动另一人正在编辑的块；agent 同时写入同一页。
6. **嵌入**：在嵌入里编辑时，源页实时变化；同一个块在一页里出现两次。
7. **性能**：展开 2000 个块的页面，测输入延迟、滚动和内存。
8. **拼接视图**：来自三页的块混排在一起，就地编辑。
9. **往返不丢**：方言内的写法往返逐字不变；方言外的写法拆成子块或原样保留。往返测试不依赖 DOM，写成普通单元测试。

**P0 原型的结果**（`prototypes/outline-editor/RESULTS.md`，2026-10-26）：ProseMirror + Yjs，块模型是真相，内存服务端，两个客户端加一个三方合并的 agent。
- 无头 Chromium 上第 1、3–9 项全部通过：180 条浏览器检查、69 个单元测试；方言往返的模糊测试 14,000 个随机块体，文字从不丢。输入法是用 CDP 模拟的。
- 第 2 项和 Safari、iOS、Android、真实输入法没测，留到 P1 真机测。已经看到的风险：组合中收到不经输入法的 Enter（安卓键盘走的就是这条路）会在组合没结束时拆块。
- 2000 块：按键到画完 p50 14–19 ms、p95 23–29 ms；Enter p95 36–59 ms；远端修改到显示 p50 11–18 ms；滚动 149 帧里超过 50 ms 的 0–1 帧；JS 堆约 3.3 KB/块。
- 由此改了 §6.3（会话开始时建整页的 Y.Text）、§6.4（被拒只回滚那一个事务）、§6.7（和编辑器上次显示的源码做 diff；跨页删除按页拆开；块合并保住链接），§6.8 补了两条建议。
- 原型没做：合并广播与背压、增量落库与崩溃恢复、会话关闭、只读订阅、权限、「已被删除」提示、块选择模式、占位节点、HTML 粘贴、三个解析器的一致性模糊测试；服务端和浏览器在同一个线程里，没有真实的 WebSocket。

## 7. 存储与上限

### 7.1 表

```text
outline_spaces          id, kind(library/project/personal/session), project_id?, narrator_id?,
                        owner_user_id?, gate_json(级别 + 受控标签), forked_from_space_id?,
                        forked_at_seq?, next_seq
outline_blocks          id, space_id, sid, parent_id, order_key, content, alias?,
                        task_json?(状态、指派、前置、截止、锁定人、整理到的提交), invalid_reason?(不成立),
                        in_process(派生缓存), reviewed_seq?(上次核实概括),
                        page_id(冗余), author_kind, author_id, version_seq, deleted  -- 当前态，快速读取
                        UNIQUE(space_id, sid)；INDEX(page_id)
outline_block_versions  block_id, from_seq, to_seq?, commit_id, page_id(冗余), parent_id, order_key,
                        content?, task_json?, invalid_reason?, content_hash, change_flags,
                        deleted, redacted                                   -- 只追加
                        PK(block_id, from_seq)；INDEX(page_id, from_seq, to_seq)；INDEX(commit_id)
outline_links           id, space_id, from_block_id, kind(link/embed/depends/basis/source),
                        target_kind, target_ref, snapshot_json?(摘录、指纹、提交), from_seq, to_seq?
outline_commits         id, space_id, seq, kind(edit/confirm/revert/import/purge),
                        actor_kind, actor_id, responsible_user_id, narrator_id?, message_id?,
                        tool_call_id?, visible, created_at, summary
                        UNIQUE(space_id, seq)；INDEX(space_id, narrator_id, seq)
outline_pending         id, space_id, kind, ops_json, base_json, requested_by, decider_json,
                        status, created_at, decided_at?                     -- 待确认
outline_task_claims     task_block_id, holder_narrator_id, epoch, task_version_at_claim,
                        claimed_at, expires_at
outline_live_updates    page_block_id, epoch, seq, update_blob, actor_kind, actor_id, created_at
outline_anchor_state    link_id, state(ok/changed/gone), checked_commit, checked_at  -- 派生缓存
outline_embeddings      model_id, content_hash, dims, vector_blob, created_at   -- 按内容去重的缓存
outline_vector_chunks   model_id, space_id, chunk_no, block_ids, scales, vectors_i8  -- 每行约 512 个向量，worker 加载用
outline_curation        id, kind(settle/stale), block_id, since_seq, status, actor?, created_at,
                        done_seq?                                           -- 整理队列
outline_gate_stats      kind, window, unchanged, edited, rejected             -- 关口和整理的原样通过率
outline_fts             FTS5 / pg_trgm
```

- 链接的 `kind` 是系统内部的区分，不是给人和 agent 的概念：`link`、`embed` 来自正文，`depends` 来自任务属性，`basis` 由系统挂上，`source` 记复制和提炼的来源。
- **版本表的写入不变量**：删除一棵子树，给每个后代都写一条墓碑版本；跨页移动一棵子树，给每个后代都写一条 `page_id` 改变的新版本。这样按页读取不用递归。`to_seq` 用 NULL 表示当前版本，索引里带上结束边界：只按 `(page_id, from_seq)` 建索引时，p95 慢 3 倍（P0 基准）。
- `change_flags` 是这个版本相对上一个变了什么（创建、内容、移动、删除、恢复、任务、换页），时间轴不用临时和上一个版本比较，快 2.5–3.5 倍。
- `order_key` 在 PG 里声明 `COLLATE "C"`，两种方言的排序才一致。
- 事实还是过程不是字段：`in_process` 只是随结构维护的缓存（移动子树、改复选框时批量更新，受子树条数上限约束），给检索和视图过滤用。
- 关注范围和工作区绑定存在会话上，在场信息只放内存。
- 表定义写在 `server/db/schema.ts`，按规范流程生成迁移；PG schema 由 `scripts/generate-postgres-schema.ts` 转译，两种方言同时交付。统一用 `outline_` 前缀，避免和消息块存储的 `narrator_blocks` 混淆。
- 子树查询用递归 CTE，每次都有深度和条数上限。
- 主线程只做小规模、走索引的读写；导入、清除、批量锚点重算、embedding、向量扫描、实时会话的崩溃恢复都放在后台 job 或 db-worker。

| 项 | 上限 |

**D19 的来由**：负责人提出（2026-10-25）：大纲覆盖团队乃至整个企业时，每一层都要呈现恰好密度的事实，计划、演进、评估、证据放在另一个维度，不干扰对结构和事实的观察；并要求每个设计元素都必要，agent 要记的概念和规则尽量少。所以做法上不加概念：过程就是任务和它下面的块，系统据此过滤视图；密度靠按预算展开、整理和「下层已变」维护；干活的 agent 只多知道一句「写在任务下面就行」。

**D18 的来由**：两轮原型试用之后，负责人评估运行时的心智负担，认为概念和规则太多，影响了灵活性和能力；随后整理出需求清单（§1.1），确认按清单重写。

## 12. 风险
- **编辑器与实时协同的复杂度**：自研编辑器、块内方言、页实时会话、嵌入就地编辑、输入法和移动端叠在一起，是工作量最大的不确定项。P0 原型在桌面 Chromium 上按 §6.9 验收通过；剩下最大的风险是真实输入法和移动端软键盘，P1 要真机测。
- **依据挂错**：自动挂接只是候选，块上显示依据来自哪次调用，人和 agent 可以改；第三轮试用量化准确率。
- **暂定决定被推翻的连锁影响**：建在暂定决定上的块都被标出来，推翻时列出受影响的范围。
- **按时间点读取的性能**：P0 基准已验证，每块 30 个版本时仍在视口级延迟内；外推到每块 100 个版本是 25–30 ms，没有实测，到那时再考虑按页做检查点。
- **多 agent 的成本与唤醒风暴**：唤醒有频率上限，自动领取默认关闭，关注范围里的变化只进摘要、不单独唤醒。
- **多工作区的安全**：执行类工具能落到多台设备上，授权检查必须在执行路径上；生产设备默认不绑定，要执行时由人确认，建议带期限。
- **整理放错或改坏事实**：出处双向可查，时间轴上可以撤销；统计原样保留率，偏低就换模型或先转待确认；知识库空间本来就走审核。
- **事实树跟不上过程**：任务完成就排队整理；在这之前，相关的事实上有「进行中」，读的人知道有新东西还没落地。
- **迁移时的 ACL 一致性**：知识库大约 45k 行代码，迁移前必须先有对照用例，再动数据。
