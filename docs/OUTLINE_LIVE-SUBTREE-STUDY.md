# 大纲实时编辑：从「一页」改成「任意子树」（D56 设计研究）

依据：`origin/main`（dd11a53e）的代码；小型原型和测量在 `scratchpad/live-subtree-prototypes/`（不进产品代码）。

## 背景

大纲现在是一棵连着的树（我的空间 → 项目 → 页 → 会话 → 页 → 块），但实时编辑的单位仍然是「一页」：一页一个实时会话、一个撤销栈、一份历史索引、一份折叠状态。所以树里展开的页只能只读，改字要去「聚焦页」；跨页拖动、跨页选择、跨页撤销都做不了。负责人在 D56 决定：实时编辑的单位改成「任意子树」，编辑跟着屏幕上展开的内容走，拖动、选择、撤销要能跨过原来的页边界；可以重做实时协议和服务端，先设计和原型验证再开工。

## 建议（先看这一节）

**采用「一个空间一个会话，文字按块，页只剩下加载单位」**（下文叫方案 B′，是候选 B 的一个具体形态）。

- 服务端本来就把一个空间的所有改动排成一队（`live/lane.ts` 的空间通道，提交序号也是按空间的），跨页移动在写入路径里本来就是一次提交。真正把「页」变成硬边界的只有两处：实时会话按页开，文字的协作文档按页建。把这两处改掉，页边界就从编辑里消失了。
- 文字的协作文档改成**每块一份**。原型证实：一份文档不能只同步其中几块；而每块一份时，块搬到哪里文字都不用动，别人正在这块里打的字不会丢。
- 客户端把屏幕上几个空间的会话合成**一个编辑文档**，只把展开的块放进编辑器。实测输入延迟和「放进编辑器的块数」成正比，而且主要花在浏览器排版上，所以上限从「一页 2000 块」改成「一棵树里同时展开 2000 块」。
- 会话**不跨空间**：权限是按空间给的，跨空间的合成只发生在客户端。跨空间拖动今天没有任何实现，只能做成「复制过去再删掉原处」，建议放在最后单独做（问题 2）。
- 代价：约 9 个 PR、1.5 万行左右非测试代码，前 3 个 PR 读者看不到变化。比「保留按页会话、只在客户端拼起来」（方案 C，约一半工作量）贵，但 C 留下的妥协正是 D56 想去掉的那些（大页不能编辑、搬走的块文字要重建、页数名额）。若第 1 个 PR（文字按块）做不稳，退回 C。

## 1. 做完之后读者看到什么

- **在树里任何展开的地方直接改。**
  - 进入编辑一次（双击文字或点「编辑」，见问题 1），之后这棵树里所有展开的、读者有写权限的内容都可以改，不再是「同时只有一页」。
  - 只读的空间（没有写权限的项目、别人的会话）照常显示，行上标「只读」，光标可以经过、可以选中复制，不能改。
  - 别人和代理的改动实时出现在展开的任何地方；别人的光标也是。
- **跨边界的拖动、选择、撤销。**
  - 把一个块（连同它下面的内容）从一页拖到另一页、拖成一个新的顶层块、把一整页拖到另一页的某个块下面：都是一次移动，一次提交，别人看到的是「移走/移来」，不是「删了又加」。
  - 选区可以从一页的末尾拖到下一页的开头；删除、复制、缩进按选中的块执行。选区跨了两个空间时，可以复制和删除，移动按问题 2 的规则。
  - Ctrl-Z 只有一个撤销栈：按读者自己做的先后顺序撤，不管这一步落在哪一页、哪个空间。只撤自己的改动（现状）。
- **仍然看得见的限制，以及什么时候出现。**

| 限制 | 读者什么时候碰到 | 看到什么 |
|---|---|---|
| 一棵树里同时可编辑的展开块：2000 | 展开很多大页之后再展开一处 | 新展开的那一处显示只读的前若干行和一句「可编辑的内容已到上限，收起别处或单独打开这里」 |
| 单个顶层块（原来的页）超过 10,000 块 | 极少；现在是 2000 就不能编辑 | 只读，说明原因 |
| 一次跨页移动的子树超过 2000 块 | 把一棵很大的子树拖到另一页 | 拒绝并说明；同一页内移动没有这个限制 |
| 一个空间同时的编辑者人数（暂定 50，需压测） | 很多人同时改同一个项目空间 | 第 51 人进入旁观，提示可重试 |
| 跨空间拖动不是「移动」而是「复制后删除」 | 把块从我的空间拖到项目里 | 确认框，说明历史、链接、任务归属不跟过去（问题 2） |
| 手机 | 窄屏 | 仍在聚焦视图里编辑（G 的决定不变） |

- **不变的东西**：聚焦某个块单独看、思维导图、历史视图、待确认改动侧栏、提问的答题表单、输入法和折叠保护的规则。

## 2. 「页」现在是硬边界的三处（已核对代码）

### 2.1 实时协作：一个会话 = 一页

- 常量（`shared/outline-live-protocol.ts` `OUTLINE_LIVE_LIMITS`）：一个 socket 8 个会话（`sessionsPerSocket`）；一页 20 个编辑者、50 个旁观者（`editorsPerPage` / `viewersPerPage`）；全进程 500 个实时页（`livePages`）；可实时编辑的页 ≤ 2000 块、≤ 4 MiB（`maxPageBlocks` / `maxPageBytes`）；一次结构事务 ≤ 200 个操作；客户端文字批量 30 ms（`typingBatchMs`）。
- 服务端（`server/services/outline/live/`）：
  - `session.ts` `LivePage`：一页一个 Yjs 文档，里面每块一个 `Y.Text`，**开会话时把整页所有块一次建好**（`LivePage.open` 用 `listPageBlocks(pageId, 2000)`，超了回 `too_large`）；`mirror.ts` `PageMirror` 是这一页结构的内存副本；操作序号 `opSeq` 每页会话各自从 0 数；续连用的操作日志只留 256 批（`OUTLINE_LIVE_BOUNDS.opLog`）。
  - 结构不是 CRDT：结构事务由服务端排序、对照镜像检查（`planTx`）、经 `writeOutline` 写成一次提交、再用规范形式广播；被拒的事务整页重建再重放。`planTx` 要求操作里的块和新父块都「在这一页里活着」，所以**移到别的页的操作在协议层就发不出去**；父块也不能为空，所以**不能把块变成顶层块**。
  - 时序（`OUTLINE_LIVE_TIMING`）：广播合并 50 ms、光标 100 ms、落日志 500 ms、文字提交在安静 2 秒后、最迟 10 秒、没人之后 60 秒关会话。（代码里没有 30 秒的提交合并；30 是客户端 30 毫秒的打字批量。）
  - 外部写入（代理、回退）走 `live-barrier.ts`：先占住**空间**的通道，让这个空间所有实时页把没提交的字提交，写入，再把提交推回各页会话（`applyCommits` → `applyVersions`）。推回时，**移出这一页的块被当成删除，移进来的块被当成新建并用库里的内容重建文字**（`session.ts` `applyVersions` 的 `inPage` / `created` 分支）；页自己被删或被移到别的块下面，会话直接结束。
  - 崩溃恢复：`outline_live_updates` 表按（页, 会话轮次, 序号）存 Yjs 更新，`replay.ts` 启动时回放。
  - `registry.ts`：按页登记会话，按空间建通道；权限变化时逐个参与者重查（失去读 → 结束，失去写 → 变旁观）。
- 客户端（`frontend/components/outline/editor/`）：
  - `live-client.ts`：一页一个客户端、一个 Yjs 文档、**一个撤销栈**（文字靠 `Y.UndoManager`，结构靠逆操作）；`store.ts` `Store(pageId)` 是这一页的结构。
  - `live-sessions.ts`：按「页 + 模式」共享会话，自己数 8 个名额；`unsaved-texts.ts` 按页存没送达的字（50 条 / 256 KiB）。
  - `view.ts`：一个 ProseMirror 编辑器，根可以是页也可以是页里任何一个块，但底下永远是**整页**的会话；收起的块的子块仍在编辑器文档里，只是用 CSS 藏起来，折叠保护和输入法规则都建立在这一点上。
  - `../edit-surface.ts`：大纲和思维导图共用一页的会话。

### 2.2 历史：按页索引

- `outline_block_versions` 每行带 `page_id`，索引 `idx_outline_versions_page_range (page_id, from_seq, to_seq)`（`server/db/schema.ts`）；「某一页在某个序号时的样子」是这个索引上的一次范围查询（`read.ts` 文件头）。
- 为此，不变式 2（`model.ts`）规定活块的 `page_id` 等于它顶层祖先的 id；**子树换页时给每个后代写一行新版本**（`write.ts` `move` → `liveSubtree`），一次提交最多 2000 行（`OUTLINE_LIMITS.maxRowsTouched`）。
- 时间线 `GET /spaces/:spaceId/pages/:pageId/commits`、会话推回外部提交用的 `listPageVersions(pageId)`、待确认改动（`outline_pending.page_id`，每页最多 100 条未决，换页时跟着走：`write.ts` `checkRepage` / `planPending`）都按页。
- 回退（`revert.ts`）按提交、在空间里做，不按页；「只改了页」的版本不算后来的改动。

### 2.3 读、订阅、视图状态

- 读 `GET /spaces/:spaceId/blocks/:blockId`（`routes/outline.ts`、`read.ts`）：先定位块所在的页，读整页结构，再按预算取内容。预算：默认 800 块、最多 2000 块 / 256 KiB（`OUTLINE_VIEW_LIMITS`）；树里一页 200 块 / 64 KiB（`OUTLINE_TREE_LIMITS`）；`fold=default` 按读者存的折叠裁剪。一页结构最多读 10,000 块（`OUTLINE_LIMITS.maxPageBlocks`），2000 以内在主线程，更大的在读线程。
- 页订阅（`shared/outline-page-events.ts`、`server/websocket/outline-page-ws.ts`）：一个 socket 16 个、一页 50 个；只通知「这一页变了」，客户端再读。树里 12 页带内容、其中 8 页订阅（`tree/tree-open-state.ts` `TREE_OPEN_LIMITS`）。
- 折叠和导图方向：`outline_view_state` 每人每页一行（主键 `user_id, page_block_id`），最多 2000 个 id、每人 500 页（`OUTLINE_VIEW_STATE_LIMITS`）。
- 提问：路由表按空间和收件人，页上的未答提问按页列（`listOpenQuestionBlocksOnPage`，一页摘要最多 200 条）。

### 2.4 另外几件事

- **块今天怎么换页**：只有 `writeOutline` 的 `move`（代理的编辑工具、回退会用到）；人没有入口，因为人的结构改动只走实时协议。实测一次提交的耗时（SQLite，测试库，单次）：

| 子树块数 | 页内移动 | 跨页移动 | 跨页写的版本行 |
|---|---|---|---|
| 1 | 3.6 ms | 3.8 ms | 1 |
| 100 | 1.7 ms | 9.6 ms | 100 |
| 500 | 2.5 ms | 14.6 ms | 500 |
| 1000 | 1.8 ms | 27.1 ms | 1000 |
| 1999 | 1.9 ms | 73.1 ms | 1999 |
| 2001 | 1.4 ms | 拒绝（`OUTLINE_TOO_MANY_ROWS`） | 0 |

- **跨空间移动**：不存在。「每次写入是一个空间里的一次提交」（`model.ts`），序号、短 id、别名、历史都是按空间的；没有任何跨空间的移动或复制接口。
- **锁、计划、权限**：权限只到空间这一级（`access.ts`：项目空间跟项目，个人空间只有本人，会话空间跟会话），没有页级的收窄。锁挂在任务块上、管它的子树、只约束代理（`locks.ts`）。代理另有读范围（`session-scope.ts`）和个别保留页（会话空间的 `behavior`、`tasks` 别名，`model.ts`）——这是按别名的规则，不是页权限。
- **「把一个块当页聚焦」时的 `pageId`**：仍是它顶层祖先的 id（`OutlineResolveResponse` 的 `blockId` / `pageId` / `isPage`）。聚焦只是换了编辑器的根，会话、历史、折叠状态都还是那一整页的。

## 3. 三个候选方案的比较

| | A 一空间一份整文档 | B′ 一空间一个会话、文字按块、按页加载（建议） | C 保留按页会话，客户端拼成一个文档 |
|---|---|---|---|
| 并发结构改动 | 最简单：一份文档一个顺序 | 一个空间一个顺序（通道已有）；跨页移动是普通操作；成环由后到的那个被拒（现有机制） | 跨页移动要同时改两个页会话；写库是一次提交，但两边会话各记各的序号 |
| 搬走的块里别人正在打字 | 不受影响 | 不受影响（文字跟块走） | 文字在目标页重建：那一刻在途的按键丢到「未保存文字」，那一块的撤销历史清空 |
| 撤销 | 一个栈 | 客户端一个栈，文字每块一个撤销器 | 客户端一个栈，每页一个撤销器；跨页移动的逆操作要再走一次跨页事务 |
| 排序/因果 | 一个序号 | 每空间一个序号；客户端每空间记一个 | 每页一个序号，跨页事务要对齐两个 |
| 续连 | 整空间状态向量 | 结构重发（2000 块约 90 KB），文字只对有未确认输入的块做差分 | 现状，每页一次 |
| 内存/CPU 上限 | 随空间大小：5 万块的空间快照 4.5 MB、服务端约 48 MB，客户端应用 109 ms；大空间整体不能编辑 | 随「被人打开的页」；文字文档只为被编辑的块建 | 随「被人打开的页」，每页整页建 Yjs；8/500 的页名额要放大 |
| 「2000 块一页」变成什么 | N 块一空间（更差） | 一棵树展开 2000 块；单个顶层块 10,000 | 不变：2001 块的页哪里都不能编辑 |
| 多人时的分发 | 空间里每个人收到所有改动 | 只发给加载了那一页的人；路由成本可忽略（实测 < 1 微秒/次） | 现状 |
| 权限 | 按空间 | 按空间；会话不跨空间 | 按空间 |
| 历史 | 不用改 | 不用改 | 不用改 |
| 对聚焦页编辑器 | 重写 | 引擎换掉，界面不变；每个 PR 都要过现有全部编辑器测试 | 不动 |
| 工作量（非测试行） | — | 约 15,000 | 约 7,000 |

- **A 不建议**：它等于 B′ 去掉加载边界。空间会一直变大（项目空间、长会话的空间），上限从「一页」变成「一空间」只会让更多内容不能编辑。真实空间有多大没有数据（见第 8 节末尾）。
- **C 是退路，不是目标**：它交付「树里跨页拖动、选择、撤销」最快，客户端那一半工作和 B′ 相同。但它留下：大页不能编辑；搬走的块文字要重建；页名额；把页拖到别的块下面会结束那一页的会话；服务端仍有两套序号要在跨页事务里对齐。这些正是「为了页做的妥协」。
- **还考虑过、没采用的**：
  - 结构也用 CRDT（可移动树）：现在结构由服务端排序并经 `writeOutline` 检查全部不变式（别名唯一、任务认领、锁、待确认），换成 CRDT 等于重写写入路径，得不到新能力。
  - 一份 Yjs 文档里只同步部分块：原型证实不行（客户端缺了同一作者前面的更新，后面的会一直挂起，见第 8 节）。

## 4. 建议的架构

```
浏览器的一棵树（一个标签页里的一个宿主）
┌──────────────────────────────────────────────────────────┐
│ 一个编辑文档（ProseMirror）                                   │
│   空间行/项目行/会话行（不可编辑的行）                          │
│   └ 顶层块 ─ 块 ─ 块 …      只放「展开的」块，≤ 2000            │
│ 一个撤销栈；一个选区                                          │
├──────────────┬───────────────┬───────────────────────────┤
│ 空间会话客户端 │ 空间会话客户端  │ 空间会话客户端               │  每个空间一个：
│ 我的空间      │ 项目 A         │ 会话 a1 的空间（只读）        │  结构副本 + 每块文字 + 序号
└──────┬───────┴───────┬───────┴─────────────┬─────────────┘
       │ 同一条 /ws/narrator，二进制帧，每个空间一个句柄
┌──────┴───────────────┴─────────────────────┴─────────────┐
│ 服务端：每个空间一个实时会话（LiveSpace）                       │
│   空间通道（已有）：这个空间的一切改动排成一队                    │
│   已加载的顶层块（页）：结构镜像；谁加载了哪一页                  │
│   文字：每块一份协作文档，有人编辑时才建；其余是库里的字符串        │
│   一个操作序号；参与者、在场、权限重查                           │
│        │ writeOutline（不变）：一次事务 = 一个空间里的一次提交      │
│   outline_blocks / outline_block_versions（page_id 不变）      │
└──────────────────────────────────────────────────────────┘
```

### 4.1 必须成立的事

1. **一个空间一队**：参与者的帧、会话自己的文字提交、外部写入、把外部提交推回会话，都在空间通道里按到达顺序一个一个做（现状，保留）。
2. **一个空间一个序号**：每批结构改动有一个会话内序号；每个客户端按序号应用；自己的事务被确认时拿到它的序号。
3. **文字跟块走**：一块的协作文档只属于这一块，和它在树里的位置无关。移动从不碰文字。
4. **结构以服务端为准**：通道里两个任务之间，已加载部分的镜像等于库；`writeOutline` 仍是唯一的写入者，所有检查（成环、别名、认领、锁、行数）仍在那里再做一遍。
5. **加载按顶层块整块进出**：客户端要么有一个顶层块的全部活块，要么完全没有。于是「一个操作该不该发给某人」只看它涉及的顶层块：两边都加载了 → 移动；只加载了来源 → 「移走」；只加载了目标 → 「移来」并带上那棵子树（一次提交最多 2000 行，所以有界）。
6. **会话不跨空间**：读写权限在加入时和每次权限变化时按空间查；失去读 → 那个空间的会话结束，树里它的内容换成「无权查看」；失去写 → 那个空间的块在编辑器里变只读，没送达的字进「未保存文字」。别的空间不受影响。
7. **有界**：每个客户端放进编辑器的块 ≤ 2000；每个客户端加载的块 ≤ 20,000；每个顶层块 ≤ 10,000；全进程加载的块有总量上限；超了的那一处退回只读并说明，绝不悄悄截断。
8. **打过的字不会无声丢失**：要么被确认，要么出现在「未保存文字」里（现状，存放处改成按块）。

### 4.2 并发的几种情况

- **跨原来的页边界移动/缩进/删除**：一条结构事务，一次提交。缩进到上一页最后一块下面、反缩进成顶层块、把一页拖到另一页的块下面，都是 `移动(块, 新父, 位置)`，新父为空表示顶层。
- **两人同时移动造成环**（甲把 X 移到 Y 下，乙把 Y 移到 X 下）：通道里先到的写成提交；后到的对照镜像发现成环，回 `conflict`；乙的客户端按现有机制回滚并重放它后面的改动。范围从「重建一页」变成「重建这个空间里已加载的部分」。
- **代理的提交在编辑中到达**：流程不变（先提交脏的文字，再写，再推回）。区别是代理把块搬到别的页时，会话收到的是移动而不是「删了又建」，文字文档原样保留。
- **同一块两人同时打字**：不变（每块自己的 CRDT）。
- **撤销跨子树**：栈里每一步记着它属于哪个空间、哪些块。结构用逆操作（跨页移动的逆操作就是移回去）；文字用那一块自己的撤销器。撤销删除时，把那次删除带走的整棵子树恢复（协议里加一个「恢复这次事务删掉的子树」的操作，服务端按那次提交的版本恢复，不要求客户端记得每个后代）。
- **选区跨两个空间时删除**：拆成每个空间一条事务。两条不是原子的；其中一条被拒时只回滚那个空间。

### 4.3 协议改什么（`shared/outline-live-protocol.ts`，版本 2）

- `join` 的对象从页改成空间；另加 `watch`：增减要加载的顶层块（一帧可列多个）。回答是每个顶层块一帧快照：结构（现有的行格式）+ 每块的文字（没人编辑的块发纯文本，有人编辑的块发那一块的文档状态）。
- `update`、`tx`、`batch` 里的文字更新带块 id（一帧可带几块）。
- 结构操作：`m`/`i` 的父可以为空（顶层）；新增「移来（带子树）」「移走」「恢复子树」。
- 在场：参与者列表按空间；光标只发给加载了那一页的人；每个顶层块上「几个人在编辑」由服务端从加载表直接算出（G3 想要的数字不用再另做）。
- 续连：结构每次重发（有界且小），不再靠 256 批操作日志；文字只对客户端有未确认输入的块做状态向量差分。事务编号和「服务端已应用到哪一笔、已落盘到哪一笔」的规则照旧。
- 限额改名改义：`sessionsPerSocket` 8 → 16（按空间数）；`editorsPerPage`/`viewersPerPage` → 按空间（暂定 50 / 100，要压测）；`livePages` 500 → 活跃空间数 + 全进程已加载块数；`maxPageBlocks` 2000 → 顶层块 10,000 + 客户端两个预算。

### 4.4 服务端改什么（`server/services/outline/live/`）

- `session.ts` `LivePage` → `LiveSpace`：页镜像变成「若干已加载顶层块」的镜像；`planTx` 去掉「必须在这一页」，改成「涉及的块所在的顶层块都已加载」，父可为空；`applyVersions` 把换页识别成移动；文字从「一份文档一张表」改成「每块一份、按需建」。
- 文字提交：仍是安静 2 秒 / 最迟 10 秒，仍是每个作者自己的提交；一次提交可以包含几页的块（提交本来就按空间，`pageIds` 是列表）。
- `registry.ts`：按空间登记；权限重查不变（本来就是按空间判断）；加载/卸载顶层块的引用计数和 60 秒空闲卸载。
- 日志：新表按（空间, 轮次, 序号）存，行里带块 id（现有表的主键和外键都是页）。`replay.ts` 按块三方合并的做法不变。旧表留一个版本，只供启动时把旧日志回放完。
- 写入路径 `write.ts`、历史、回退、待确认、锁、认领：**不改**。
- 主线程规则：加载一个顶层块用现有的按页读（2000 块以内主线程，更大走读线程，`store/sqlite-read.ts`）；快照按顶层块分帧；每个参与者在通道里排队的字节数仍有上限；镜像是内存操作，实测 10 万块的结构副本约 19 MB、订阅 70 人时索引约 16 MB。
- PostgreSQL：实时会话是进程内状态，两种存储都只经 `OutlineStore` 接口；新日志表按规定流程生成 PG 迁移。多进程部署下实时编辑本来就只能单进程，这一点不变。

### 4.5 客户端改什么（`frontend/components/outline/`）

- `editor/live-client.ts`：按空间；结构副本按顶层块分片；文字每块一份文档、每块按需一个撤销器（`Y.UndoManager` 不能跨文档，原型已证实，所以由栈自己记「这一步用哪几块的撤销器」）。
- 新的一层（暂名「编辑森林」）：把几个空间客户端合成一个编辑文档，统一的撤销栈、选区、拖动；空间/项目/会话的行作为不可编辑的行放进同一个文档，这样选区和拖动才能连续。
- `editor/view.ts`：**只把展开的块放进编辑器**。现在收起的块的子块在文档里、用 CSS 藏着；改成不在文档里，预览行和计数从结构副本算。折叠保护的规则不变，实现从「CSS 显隐」改成「放进/拿出文档」。这是客户端风险最大的一处（第 7 节）。
- `tree/OutlineTree.tsx`：编辑模式下展开的页由编辑森林画；只读模式不变（HTTP 读 + 页订阅）。
- `live-sessions.ts`、`unsaved-texts.ts`：按空间计名额；未保存文字按块存，提示出现在那一块所在的位置。
- 聚焦视图、思维导图：是「只看一个根」的同一套东西，界面不变。

### 4.6 存储改什么

- 新增实时日志表（SQLite + PG 各一次生成的迁移）。大纲的表目前都不在数据导入导出里（`data-portability.ts` 没有列它们），所以导入导出不用动。
- `outline_block_versions.page_id`、`outline_blocks.page_id`、`outline_pending.page_id`、`outline_view_state.page_block_id`：**都不改**。
- 折叠状态仍按顶层块存；块被拖到另一页时，客户端把它和它后代的折叠记号从原页那一行搬到新页那一行（两行都在手上）。别的设备上那几个块会回到默认折叠——可以接受的小瑕疵。

## 5. 「页」还在不在

- **读者看得见的地方：作为名字还在，作为边界不在。**
  - 空间里的顶层块仍然叫「页」：树里的页行、快速切换、地址、面包屑、「这一页的历史」、待确认改动和提问的分组，都还按它组织。
  - 它不再限制编辑：光标、选区、拖动、撤销都能穿过它；任何块都可以拖成顶层块，顶层块也可以拖到别的块下面。
  - 唯一还露出来的痕迹是第 1 节表里的两条：单个顶层块 10,000 块的上限，和跨顶层块移动 2000 块的上限。
- **内部还在的地方。**
  - 存储分片键：`page_id` 在块表和版本表上，「某页在某时刻的样子」靠它一次范围查询；所以换顶层块时仍给每个后代写一行版本。
  - 实时加载单位：客户端按顶层块整块加载和卸载。
  - 只读路径：HTTP 读的预算、`fold=default` 裁剪、页订阅、代理的读工具，都不变。
  - 每页的配额：未决的待确认改动 100 条、折叠记号 2000 个。

## 7. 风险（按大小排）

1. **只把展开的块放进编辑器（P4）会碰到折叠保护和输入法的全部规则。** 这些规则是 PR C 花了很多轮才稳定的。退路：P4 关掉，按「整棵放进编辑器」上线，代价是预算按整棵算，大页在树里更容易触顶。
2. **文字按块（P1）的撤销/重做。** 代码注释里记着原型踩过的坑：文字文档晚建会让按键和建文档抢跑，重做时把字反过来。P1 正是把「开会话时全建」改成「按需建」。原型里用「两边从同样的纯文本、同样的固定作者号各自建出同一份文档」的做法，300 轮并发 + 撤销全部收敛，但那不是真编辑器。**若 P1 不能让现有全部编辑器测试和加大轮数的随机收敛稳定通过，就放弃 B′，改走 C**（客户端的 P0、P5、P6 仍然有用）。
3. **一个编辑文档里混着空间行、会话行和块（P5）。** 选区穿过不可编辑的行、拖动落点、读屏顺序都要重新过；延迟随展开的块数线性涨，预算留的余量不大（2000 块时按键到下一帧中位 12–14 ms）。
4. **一个空间一条通道成为热点。** 很多人同时改同一个项目空间时，每条结构事务都是一次库提交，全部排队。今天也是这样，但今天一页最多 20 人；放到按空间之后人数上限要靠压测定，不能照搬。
5. **升级那一刻的版本错位**：没刷新的旧页面打的字会进「未保存文字」而不是自动送达。
6. **跨空间移动的语义损失**（问题 2）。

**什么情况下整体放弃这个方向**：P1 做不稳（转 C）；或 P5 证明单个编辑文档在 2000 块预算下达不到流畅输入（那就退到「每个空间一个编辑器、选区不跨空间、拖动可以跨」）。

## 8. 测量

环境：本容器，Bun 1.4.3，无头 Chromium 146（无 GPU）。数字只能相对比较。

**8.1 真编辑器里，文档大小和输入延迟**（`scale.browser.test.ts`：现有 `OutlinePerf` 的做法，页面每 10 块一个顶层块、其余在它下面，服务端上限临时放开；延迟 = 按键到下一帧；每个规模跑 1 次，2000 跑了 3 次）

| 块数 | DOM 节点 | 打字 中位 / p95 | 回车（拆块）中位 | Tab（缩进）中位 | 全部收起后打字 中位 | 全部收起后回车 | 最后一键到另一人看到 | 页面堆内存 |
|---|---|---|---|---|---|---|---|---|
| 2,000 | 3.9 万 | 12–14 / 26–34 ms | 26–29 ms | 26–31 ms | 8–9 ms | 9 ms | 60–65 ms | 26–28 MB |
| 5,000 | 9.8 万 | 28 / 41 ms | 63 ms | 70 ms | 14 ms | 17 ms | 91 ms | 53 MB |
| 10,000 | 19.6 万 | 57 / 92 ms | 133 ms | 141 ms | 28 ms | 39 ms | 1.2 s | 98 MB |
| 20,000 | 39.2 万 | 115 / 134 ms | 254 ms | 278 ms | 49 ms | 66 ms | 3.5 s | 187 MB |

- 延迟和块数成正比。2000 块大约一帧，5000 块两帧，10,000 块读者能明显感到。
- 10,000 块时对打字做 CPU 采样：63.6% 是浏览器自己的工作（样式、排版、绘制），27% 空闲，编辑器的 JavaScript 合计不到 10%。所以瓶颈是「放在页面里的节点数」，不是编辑器逻辑；收起的块现在仍在页面里，收起只省了一半。这是「只把展开的块放进编辑器」和「预算按展开的块算」的依据。

**8.2 文字协作文档放在哪一级**（`yjs-granularity.test.ts`、`yjs-partial.test.ts`，Yjs 13.6.33）

| | 2,000 块 | 10,000 块 | 50,000 块 |
|---|---|---|---|
| 一份文档：堆内存 / 快照大小 / 客户端应用 | 2.5 MB / 176 KB / 9 ms | 9.6 MB / 887 KB / 23 ms | 48 MB / 4.5 MB / 109 ms |
| 每块一份、全部建好：堆内存 | 6.4 MB | 32 MB | 160 MB（约 3.2 KB/块） |
| 每块一份：加载 2,000 块的快照 / 编码 / 客户端应用 | 152 KB / 9 ms / 25 ms | 同左 | 同左 |
| 2,000 次单字输入：一份文档 / 每块一份 | 32 / 24 ms | 25 / 23 ms | 20 / 25 ms |

- 一份文档里只同步一部分块：**不行**。只把涉及已加载块的更新发给旁观者，更新被挂起、文字不变。
- 一个 `Y.UndoManager` 管两份文档里的文字：**不行**（只撤了第一份）。每块一个撤销器：建 300 个 0.5 ms，按栈顺序撤 2,000 步 22.6 ms，全部复原。
- 每块全部建好要 3.2 KB/块，所以应当「有人编辑时才建」；两边从同样的纯文本各自建文档，300 轮并发编辑加撤销全部收敛。

|---|---|---|---|---|
| 20 × 8 | 0.04 微秒 | 0.18 微秒 | 6 MB | 0.4 ms |

| 500 × 8 | 0.06 微秒 | 0.94 微秒 | 80 MB | 0.3 ms |

- 10 万块的结构副本约 19 MB。分发的 CPU 不是问题；内存随「人数 × 每人加载的块」涨，所以要有全进程的已加载块总量上限。

**8.4 今天跨页移动的代价**：见 2.4 的表（`cross-page-move.test.ts`）。

**没有测的**

- 真实数据里空间和页有多大（本机库是空的测试库）；所以「10,000 块一个顶层块」「20,000 块一个标签页」是按机制定的，不是按分布定的。
- 「只把展开的块放进编辑器」之后的实际延迟（只测了全部收起但仍在页面里的情况）。
- 加载顶层块的库读耗时、PostgreSQL 上的任何数字、多人同时写一个空间时通道的吞吐。
- 真输入法、手机、慢网络；一个文档里混入空间行之后的选区行为。
- `LiveSpace` 的真实内存（只测了结构副本和 Yjs 的量级）。

## 9. 负责人要定的事

**问题 1　树里怎么进入编辑**

背景：D56 说「编辑跟着屏幕上展开的内容走」。G 定过「双击或『编辑』按钮进入，同时只有一页」。只读的树只花 HTTP 读；进入编辑要为每个展开的空间开实时会话，并让别人看到你「在编辑」。

例子：读者展开了项目 A 的三页和会话 a1 的任务页，想改第二页里的一个错字，再把第三页的一个块拖到任务页。

- **A（建议）**：仍然要一次明确的进入（双击文字、点「编辑」、F2）。进入后整棵树里展开的内容都可编辑，直到点「完成」、连按两次 Esc，或 2 分钟没操作且没有未送达的字。例子里：双击错字 → 改 → 直接拖，不用再进入一次。
- B：不要进入动作，树一打开就是可编辑的。最顺手；但每个只是来看的人都会占实时会话、显示成「在编辑」，随手一点就落光标，触屏滚动容易误触。
- C：保留 G 的「一次一页」，拖动时临时把目标页也变成可编辑。实现最接近 G，但撤销栈、选区仍按页切，和 D56 的目标不符。

**问题 2　跨空间拖动做不做、怎么算**

背景：每个空间有自己的提交序号、历史、短 id，权限也按空间给。今天没有任何跨空间移动。能做的只有「在目标空间新建一份，再把原处删掉」：新块是新 id，原来的历史留在原空间，指向原块的 `((链接))`、任务认领、锁、未答提问都不会跟过去；而且把个人空间的内容拖进项目，等于公开给项目里的人。

例子：读者把「我的空间」里一段 30 块的笔记拖到项目 A 的「设计」页下面。

- **A（建议）**：第一版不做拖动跨空间。拖到另一个空间时落点显示「不能直接移到另一个空间」，同时提供「复制到这里」（原处保留）。等 P6 上线后再做 B（P7）。
- B：做，弹确认框：「移到『项目 A』：项目成员都能看到；历史和指向这些块的链接不会跟过去」。确认后复制再删除。有别人认领的任务、锁定的计划、未答提问、或超过一次事务大小（200 块）时拒绝并说明。撤销是「再搬回来」，又是一份新块。
- C：让块真正跨空间移动（保留 id 和历史）。要改历史模型（一个块的版本跨两个空间的序号），所有按空间读历史的地方都要重做。不建议。

**问题 3　展开的内容到了可编辑上限时怎么办**

背景：实测输入延迟和放进编辑器的块数成正比：2000 块约 13 ms，5000 块约 28 ms，10,000 块约 57 ms（回车和缩进是这个的两倍多）。所以一棵树里同时可编辑的展开块要有上限。

例子：读者已经展开了 1,900 块，又展开一个有 400 块子内容的任务。

- **A（建议）**：上限 2000。新展开的这一处先显示只读的前若干行和一句提示（「可编辑的内容已到上限，收起别处或单独打开这里」）；读者收起别处后它自动变成可编辑。已经在编辑的地方不受影响。
- B：上限 2000，但自动把最久没碰的展开处变回只读来腾位置。读者不会被拦住；但他可能回头发现刚才能改的地方不能改了，要再点一下。
- C：上限 5000，不提示得那么早。大多数人碰不到上限；碰到之前输入已经明显发涩（两帧以上），慢机器更糟。

**问题 4　和 G 的先后**

背景：G（树里就地编辑，一次一页）已设计、未开工，3 个 PR 约 3,600 行，其中 G2/G3（约 2,500 行）是「一次一页」的切换逻辑，在本方案的 P6 会被整体替换。本方案约 9 个 PR、1.5 万行，读者要到 P6 才在树里看到变化（P3 之后同一空间的页之间已经实时互通，P4 之后大页在聚焦视图里可编辑）。

例子：现在读者改树里的一个错字要去聚焦页。

- **A（建议）**：只做 G1（两边都需要），跳过 G2/G3，直接做 P1–P6。树里能编辑的时间比做 G 晚，但不写要扔掉的代码，也不让读者先学一套「一次一页」再换。
- B：先把 G 做完上线（3 个 PR），再做本方案。读者最早能在树里改字；G2/G3 的大部分代码和一轮测试之后作废，读者经历两次交互变化。
- C：改走方案 C（约 7,000 行）：保留按页会话，只做客户端合成和跨页事务。大约一半时间交付跨页拖动和撤销；留下第 3 节列的妥协，以后若仍要 B′，服务端那部分照样要做。
