# NarraFork 插件系统：需求与边界

> 文档定位：定义插件系统要解决的问题、允许扩展的能力、明确不做什么，以及插件与 NarraFork 核心之间不可跨越的边界。本文件不定义完整 Manifest 字段、RPC 消息格式、数据库表或 UI Bridge 细节。

## 标记约定

- **[当前事实]**：可由当前仓库代码或现有设计文档直接确认。
- **[设计建议]**：本轮建议采用的目标架构或约束。
- **[假设]**：为了形成可执行设计而暂时采用、但尚未被项目正式确认的前提。
- **[待决策]**：需要主叙述者或后续 ADR 明确选择的事项。

## 1. 问题定义

### 1.1 当前扩展方式

- **[当前事实]** `server/app.ts` 静态导入并挂载 Hono 路由，公共路由与全局 `requireAuth` 门禁顺序由核心代码决定；当前没有供外部代码任意注册 Hono middleware 或 route 的稳定接口。
- **[当前事实]** `ProviderAdapter` 是进程内 TypeScript 接口，包含历史转换、工具格式化、流式聊天、生成、usage、取消信号等较宽的协议面；provider 解析目前由核心设置和 `createProviderByName()` 完成。
- **[当前事实]** Agent 工具体系通过 `ToolDefinition`、`ToolContext` 和 `AbortSignal` 工作。`ToolContext` 含叙述者、项目、用户、权限处理、执行设备等敏感上下文，不适合原样交给第三方代码。
- **[当前事实]** `McpManager` 已具备外部进程/远端连接、工具发现、调用取消、断线重连和工具列表变化通知，但 MCP 只覆盖工具协议，不是通用的 NarraFork 插件生命周期或宿主 API。
- **[当前事实]** 后端主线程同时承担 Bun HTTP/WS、SQLite、序列化和大量事件分发。项目规则明确要求长任务、无界输出和大数据处理不得阻塞该线程。

### 1.2 目标问题

- **[设计建议]** 插件系统应让管理员在不修改 NarraFork 源码、不重新编译核心的前提下安装、检查、启用、禁用、升级和卸载扩展。
- **[设计建议]** 插件应通过稳定、版本化、可审计的公共宿主接口扩展系统，而不是导入 `server/*` 内部模块。
- **[设计建议]** 第三方插件故障、死循环、内存泄漏或协议错误不得直接拖垮 HTTP/WS/SQLite 所在的核心进程。
- **[设计建议]** provider、Agent 工具、事件消费者、后台任务和 UI 面板应能分别声明、授权和激活，避免“安装一个插件即获得全部能力”。
- **[设计建议]** 插件系统应优先服务小团队私有部署：支持离线安装包、本地管理员授权和可诊断的运行状态，不依赖公共插件市场才能工作。

## 2. 核心术语

- **[设计建议] Core Host（核心宿主）**：NarraFork 主进程中唯一可以访问内部服务、数据库、原始 `eventBus`、Hono app、JWT 实现和 Agent 内部对象的代码。
- **[设计建议] Plugin Manager（插件管理器）**：核心宿主中的控制面，负责发现、校验、状态管理、激活决策、进程监管、升级和卸载。
- **[设计建议] Plugin Runtime（插件运行时）**：承载单个插件后端代码的独立进程或隔离容器。
- **[设计建议] Contribution（贡献项）**：插件声明给宿主的可发现能力，例如 provider、tool、command、event subscription、view。
- **[设计建议] Capability（宿主能力）**：插件希望调用的宿主 API 类别，例如只读查询、执行命令、读写插件存储、读取某类 secret。
- **[设计建议] Grant（授权）**：管理员对某一已安装插件实际批准的 capability 子集。
- **[设计建议] Activation Event（激活事件）**：宿主需要某项贡献时触发插件启动的声明式条件。
- **[设计建议] Public Host API（公共宿主 API）**：稳定、版本化、DTO 化的查询、命令、事件、存储、配置、secret 和日志接口。

## 3. 插件能力范围

### 3.1 目标能力

**[设计建议]** 目标能力与边界如下：

| 能力 | 目标支持 | 边界 |
|---|---:|---|
| AI provider | 是 | 由宿主的 `RemoteProviderAdapter` 映射到现有 Agent Loop；插件不直接进入 loop，也不读取核心 settings 对象 |
| Agent 工具 | 是 | Manifest 提供静态描述/schema，执行时由宿主代理 RPC；仍经过核心工具过滤、权限审批、超时和审计 |
| 只读查询 | 是 | 只能调用分页、限量、脱敏的公共 Query API，不得直接查询 SQLite |
| 核心命令 | 是 | 只能调用明确列入公共 API 的业务命令；认证、授权、参数校验和事务由核心服务完成 |
| 公共事件订阅 | 是 | 订阅稳定、脱敏、版本化事件；不得持有原始 `eventBus` 或同步阻塞事件发布者 |
| 后台任务/定时激活 | 是 | 调度权、并发限制、取消和运行记录由宿主持有；插件不能自行创建不受监管的守护进程树 |
| 插件配置与 secret | 是 | 配置与 secret 分离；secret 通过句柄或按请求注入，不向 UI 或日志返回明文 |
| Namespaced storage | 是 | 每个插件独立命名空间、配额和迁移版本；不得创建/修改 NarraFork 核心表 |
| UI 面板 | 是 | 使用受限 iframe/UI Bridge 和固定 contribution point；不得直接注入 React 组件或操作宿主 DOM |
| 状态/诊断 | 是 | 管理员可查看版本、授权、运行状态、崩溃次数、最近错误、资源和队列状态 |

### 3.2 能力组合原则

- **[设计建议]** 后端插件、provider 插件和 UI 插件是可组合但可独立启用的贡献项。一个安装包可以同时包含多类贡献，但宿主必须能分别显示状态并按授权裁剪。
- **[设计建议]** 工具定义、provider 元数据、命令标题、UI 面板入口等“发现信息”应尽可能静态存在于 Manifest，使未激活插件仍可被列出和按需激活。
- **[设计建议]** 插件对外暴露的 ID 必须带插件命名空间，避免覆盖核心或其他插件，例如 `com.example.review/provider/main`。
- **[设计建议]** 插件不得声明与核心同名的保留贡献；显式 override 若未来需要，应是管理员可见的独立高风险能力，而不是默认行为。

## 4. 非目标

- **[设计建议]** 不把插件系统设计成任意 Bun/Node 模块加载器；可安装第三方代码不允许直接 `import` 核心源码。
- **[设计建议]** 不允许插件任意注册 Hono middleware、修改认证顺序、截获全部 HTTP 请求或获得原始 WebSocket 连接。
- **[设计建议]** 不允许插件直接访问 `db`、Drizzle schema、SQLite 文件、原始 `eventBus`、内部 service 单例、JWT secret、用户 Bearer token 或 provider 凭据文件。
- **[设计建议]** 不允许插件自行修改 `server/db/schema.ts`、生成核心迁移或在核心事务中执行插件代码。
- **[设计建议]** 不允许 UI 插件向宿主页面注入任意脚本、React 组件、CSS 全局覆盖或读取宿主 localStorage/JWT。
- **[设计建议]** 不承诺普通本地子进程提供强安全沙箱。无容器/OS sandbox 时，独立进程主要提供故障隔离；不可信代码的文件和网络隔离需要额外运行环境。
- **[设计建议]** 不用插件替代 MCP。MCP 继续作为标准工具集成协议；插件系统负责更广的生命周期、NarraFork 公共 API、provider 和 UI 集成。
- **[设计建议]** 不要求第一阶段提供公共插件市场、自动付费、跨实例分发或任意语言 SDK。协议应语言中立，但首个 SDK 可以只支持 TypeScript。
- **[设计建议]** 不保证插件能参与核心数据库的跨服务原子事务。插件需要通过单个核心命令获得核心侧原子性，跨命令工作流使用 operation ID、幂等和补偿。

## 5. 可信度模型

### 5.1 信任等级

**[设计建议]** 信任等级只影响来源判断和可申请能力，不改变“可安装插件默认进程外运行”的原则：

| 等级 | 定义 | 运行位置 | 能力原则 |
|---|---|---|---|
| T0 核心代码 | 随 NarraFork 编译和发布的实现 | 核心进程 | 可访问内部对象；不属于可安装插件 |
| T1 官方/组织可信插件 | 签名来源受管理员信任的插件 | 独立进程；必须进核心的组件改列为 T0 | 可申请高风险 capability，但仍需显式授权和审计 |
| T2 第三方已批准插件 | 来源可识别、管理员已安装并授权 | 独立进程；高风险场景建议容器 | 只获得 Manifest 请求与管理员 Grant 的交集 |
| T3 未批准/来源未知包 | 仅完成下载或检查，尚未获准 | 不执行 | 只能读取包元数据、签名和静态清单 |

- **[设计建议]** “签名可信”只证明发布者和包完整性，不等同于自动授权。
- **[设计建议]** “官方插件”也默认走公共 Host API，不因发布者身份直接访问数据库或内部服务。这样可以减少核心耦合，并保持可测试的兼容边界。
- **[设计建议]** 只有随核心编译、由 NarraFork 团队维护的 T0 适配层可以进程内运行；用户安装包不能通过配置切换为进程内模式。
- **[设计建议]** 有效权限按下式收敛，而不是只看 Manifest：

```text
effectiveCapabilities =
  manifestRequested
  ∩ installationGrants
  ∩ hostPolicy
  ∩ currentUserAuthority
  ∩ currentInvocationScope
```

### 5.2 威胁与失效假设

- **[假设]** 第三方插件可能有缺陷，也可能恶意构造超大消息、无限流、重复重连、路径穿越、secret 外传或越权命令。
- **[假设]** 管理员可能授予高风险文件/网络能力，因此权限提示必须说明资源范围，而不能只显示抽象权限名。
- **[设计建议]** 宿主不能信任插件返回的身份、路径、资源归属、usage、错误可重试性或 UI 文本；所有影响核心状态的数据都要校验、限量并绑定宿主生成的调用 ID。
- **[设计建议]** 插件进程退出、连接中断和协议错误属于正常可恢复故障，核心功能应继续可用。

## 6. 不可跨越的系统边界

### 6.1 数据边界

- **[设计建议]** 核心数据库只由核心服务访问。插件读取核心数据必须走 Query API，写入必须走 Command API。
- **[设计建议]** Query API 默认返回摘要字段、游标分页和 `LIMIT n + 1` 风格的 `hasMore`；大字段需专用详情/流接口并有字节上限。
- **[设计建议]** 插件私有数据进入独立 namespaced storage；存储 API 负责配额、schema version 和清理策略，不暴露 SQL。
- **[设计建议]** 插件不能把自身数据结构加入 `contentJson` 等核心大字段作为隐式数据库；跨版本可持久化数据必须有插件自己的版本标识。

### 6.2 业务服务边界

- **[设计建议]** 公共命令应表达业务意图，例如“创建章节”“发送叙述者消息”“运行例程”，而不是暴露内部 service 方法或允许任意函数调用。
- **[设计建议]** 核心命令负责 Zod 校验、认证、授权、事务/回滚、审计和事件发布。插件只能收到结果 DTO，不能持有 service 引用。
- **[设计建议]** 插件触发的命令携带 `PluginPrincipal`、可选 `UserPrincipal`、调用原因和 correlation ID，禁止伪造普通用户 JWT。

### 6.3 事件边界

- **[设计建议]** 原始 `eventBus` 保持内部接口。Event Gateway 将内部事件映射为白名单公共事件，执行字段脱敏、版本转换、过滤和节流。
- **[设计建议]** 插件事件处理必须异步解耦；核心发布者不等待插件完成。
- **[设计建议]** 公共事件默认采用 at-most-once 在线投递。需要可靠消费的场景应使用可游标读取的审计/任务资源，而不是假设事件总线永久可靠。

### 6.4 Agent 边界

- **[设计建议]** provider 插件通过远程适配层实现现有 `ProviderAdapter` 语义，不接收 Agent Loop 对象、数据库消息实体或核心 settings。
- **[设计建议]** 工具插件只接收经过 schema 校验和权限批准后的参数，以及收窄后的公开执行上下文；不得获得完整 `ToolContext`。
- **[设计建议]** 工具插件不能宣布自己“无需权限”。是否提示、允许、拒绝或进入 danger reflection 始终由核心权限系统决定。
- **[设计建议]** provider/tool 流必须可由核心 `AbortSignal` 取消，并受首包、空闲、总时长、输出字节和事件频率限制。

### 6.5 HTTP、WebSocket 与 UI 边界

- **[设计建议]** 核心只静态挂载插件管理 API 和统一代理入口；插件不能动态修改 Hono app。
- **[设计建议]** 若未来允许插件 HTTP handler，只能位于固定命名空间，由宿主先完成认证、授权、body 限制、超时和速率限制，再转为 RPC；第一阶段不要求支持该能力。
- **[设计建议]** UI 插件通过 sandboxed iframe 与宿主创建的 `MessageChannel` 通信，不得到 JWT，也不能直接连接内部 WebSocket。
- **[设计建议]** UI Bridge 调用同一 Capability Broker；“来自已登录页面”不自动意味着拥有管理员或当前用户的全部权限。

### 6.6 进程与资源边界

- **[设计建议]** 一个后端插件至少对应一个独立受监管进程；不同插件不共享 JS isolate、全局变量或未受控模块缓存。
- **[设计建议]** 宿主必须限制单帧大小、累计输出、排队字节、并发调用数、启动次数和日志速率。
- **[设计建议]** 插件产生的 stdout 只承载协议，普通日志走 stderr 或显式 log 通知，避免协议帧与日志混杂。
- **[设计建议]** 需要强文件/网络隔离的 T2 插件应支持 Podman profile；本地子进程模式必须在管理界面明确标记“故障隔离，不是安全沙箱”。

## 7. 生命周期与激活需求

### 7.1 生命周期需求

- **[设计建议]** 安装、启用、运行是不同状态：安装只校验和落盘，不执行代码；启用表示允许响应激活事件；激活才创建运行时。
- **[设计建议]** 所有生命周期操作必须幂等，并可在进程崩溃或主机重启后根据持久化期望状态恢复。
- **[设计建议]** 禁用先阻止新调用，再取消或等待在途调用，最后停止运行时并撤销动态贡献。
- **[设计建议]** 插件激活失败不能阻止 NarraFork 启动；该插件进入错误、退避或隔离状态，并向管理员暴露诊断。
- **[设计建议]** 核心优雅退出时对每个插件执行有硬超时的 drain/deactivate/shutdown，超时后终止进程，不能拖住整体退出。

### 7.2 激活事件需求

- **[设计建议]** 激活事件采用白名单、声明式匹配，不允许插件提交宿主内执行的任意表达式。
- **[设计建议]** 目标事件族包括：宿主启动、provider 首次使用、工具首次执行、命令调用、UI 面板打开、公共事件到达和宿主调度触发。
- **[设计建议]** `onStartup` 属于高成本激活事件，默认不授予第三方插件；能够懒激活的贡献不得要求启动即运行。
- **[设计建议]** 对同一插件的并发激活请求必须 single-flight；激活期间的新调用进入有界队列，失败时统一返回结构化错误。
- **[设计建议]** 事件触发激活应支持过滤、去抖和合并，避免高频叙述者流事件造成进程反复启动或队列爆炸。

## 8. 版本兼容需求

- **[设计建议]** 兼容性至少分三层：包清单 schema、Host API、进程 RPC protocol；三者不能只共用一个“插件版本”。
- **[设计建议]** 安装/升级时先做静态兼容检查，不兼容包可以被保留用于检查，但不得激活。
- **[设计建议]** Host API 使用语义化版本范围；RPC 使用可明确拒绝的 major 与可协商 feature/capability 集。
- **[设计建议]** 插件不得依赖核心源码路径或 TypeScript 结构兼容；跨边界数据必须是可序列化 DTO，并带稳定 discriminator/version。
- **[设计建议]** 新宿主应优先保留至少一个旧 API major 的兼容窗口，具体窗口由发布策略决定；移除能力前要有弃用期和诊断。
- **[设计建议]** provider/tool 等贡献可拥有独立 capability version，以避免整个 Host API 因单一能力演进而升 major。
- **[待决策]** NarraFork 0.x 阶段是否承诺跨多少个 minor 版本兼容，以及官方插件是否与核心版本锁步发布。

## 9. 可靠性、取消与背压需求

- **[设计建议]** 所有跨进程请求都必须携带 request ID、deadline 和取消路径；宿主超时后必须忽略迟到结果。
- **[设计建议]** 流式调用必须区分首事件超时、流空闲超时、总时长限制和累计字节限制。
- **[设计建议]** 背压不能只依赖操作系统 pipe 缓冲。RPC 层需要有界发送队列、最大在途请求和流量窗口/确认机制。
- **[设计建议]** 日志、进度、遥测等可降级流量在拥塞时允许采样、合并或丢弃；命令响应、取消、权限结果和最终状态不得静默丢弃。
- **[设计建议]** 插件崩溃后采用带抖动的指数退避和重启预算；超过预算进入 quarantine，必须由管理员或冷却策略恢复。
- **[设计建议]** 宿主不自动重放已经可能产生副作用的命令。只有带幂等键且公共 API 明确声明可重试的操作才允许恢复重试。

## 10. 升级与卸载需求

- **[设计建议]** 升级采用 staging → 静态校验 → 兼容性检查 → 停止旧版本 → 原子切换 → 健康检查 → 提交的两阶段流程。
- **[设计建议]** 新版本激活失败时自动回滚到旧包和旧授权；插件私有数据迁移若不可逆，必须在升级前明确提示并要求备份/确认。
- **[设计建议]** 升级期间阻止新调用，并对在途调用执行 drain 或取消；不能让新旧版本同时写同一插件存储，除非未来显式支持多版本运行。
- **[设计建议]** 卸载先隐式禁用，撤销贡献、secret 和授权，再删除可执行包；namespaced storage 默认保留，只有显式“清除插件数据”才永久删除。
- **[设计建议]** 卸载后 UI 布局、例程或配置中引用的贡献应保留可诊断的缺失占位，而不是静默改写用户数据。
- **[待决策]** 保留插件私有数据的默认期限、旧包回滚保留数量，以及签名密钥撤销后的自动禁用策略。

## 11. 验收级需求清单

### 11.1 功能

- **[设计建议] R-F01** 管理员可以安装、检查、启用、禁用、升级、回滚和卸载插件。
- **[设计建议] R-F02** provider、tool、event、command、background、view 可以独立发现和授权。
- **[设计建议] R-F03** 插件可以通过公共 API 查询和执行允许的 NarraFork 业务操作，但不能导入内部模块。
- **[设计建议] R-F04** 支持按激活事件懒启动，并能报告插件冷启动/运行状态。
- **[设计建议] R-F05** 插件配置、secret、私有存储和日志具有插件命名空间。

### 11.2 安全与边界

- **[设计建议] R-S01** 第三方后端插件不在核心进程执行。
- **[设计建议] R-S02** 插件不接收数据库句柄、内部 service、原始 eventBus、JWT 或完整 `ToolContext`。
- **[设计建议] R-S03** 每次宿主 API 调用都经过 capability、用户权限、调用范围和参数校验。
- **[设计建议] R-S04** UI 插件运行在 sandboxed iframe，并通过宿主代理访问能力。
- **[设计建议] R-S05** 安装不等于信任，签名不等于授权。

### 11.3 可靠性与性能

- **[设计建议] R-R01** 单个插件崩溃不能导致核心进程退出或 API 全局无响应。
- **[设计建议] R-R02** 所有请求/流均有超时、取消、输出上限和背压。
- **[设计建议] R-R03** 插件激活与重连采用 single-flight、有界队列、退避和熔断。
- **[设计建议] R-R04** 插件调用不得在 Bun 主线程执行第三方同步工作或无界 JSON 处理。
- **[设计建议] R-R05** 优雅退出不能被插件无限期阻塞。

### 11.4 兼容性与运维

- **[设计建议] R-O01** 不兼容原因可在不执行插件代码的情况下显示。
- **[设计建议] R-O02** 管理员可以查看贡献、授权、运行时、最近崩溃、超时、队列和版本协商结果。
- **[设计建议] R-O03** 升级失败可回滚，卸载不会默认永久删除私有数据。
- **[设计建议] R-O04** 核心功能在全部插件禁用、损坏或不兼容时仍可启动和使用。

## 12. 假设与待决策汇总

### 12.1 假设

- **[假设]** 第一阶段以后端独立进程 + UI iframe 为主，不实现 WebAssembly 插件运行时。
- **[假设]** 第一阶段只允许一个插件版本处于 active，升级不做蓝绿双运行。
- **[假设]** MCP server 继续由现有 `McpManager` 管理，插件系统只可把 MCP 作为一种贡献来源或依赖，不重写 MCP SDK。
- **[假设]** 管理员是安装与高风险授权主体；普通用户只在调用时提供自身权限上下文。

### 12.2 待决策

- **[待决策]** 第三方插件默认是否必须使用 Podman，还是允许管理员选择“本地子进程（弱隔离）”。
- **[待决策]** 首个版本支持哪些 contribution；建议最小集合为 provider、tool、command、event、storage，UI 后续接入。
- **[待决策]** 是否允许插件提供固定命名空间 HTTP endpoint；建议第一阶段不提供。
- **[待决策]** 官方签名信任根、组织私有签名根和吊销机制如何分发。
- **[待决策]** Host API 兼容窗口、插件数据保留期限、回滚包保留数量和资源配额默认值。
