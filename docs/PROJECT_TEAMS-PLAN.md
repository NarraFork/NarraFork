# 项目里的 Team：协调者 + 子代理树，集成分支与合并账本（设计与实施计划）

依据：`origin/main`（4f5d23ea，2026-11-16）的代码；大纲按 `origin/claude/outline-pageless`（775823d3，A3 合入后）读；删除叙事线的提交 a7e316f6 的父提交里的合并代码。文中 `文件:行号` 都指主干，标了「pageless」的指集成分支。本文只是计划，没有改产品代码，没有跑测试。git 历史是浅的（1,820 条），子代理限制最初是在哪个提交、为什么加的，只能从代码注释读。

## 背景

现在并行开发靠用户自己：开 worktree、派会话、记哪个分支合进了测试分支、合并时自己处理冲突、合完自己删 worktree。测试分支里到底合了什么全凭转述，所以会漏合，冲突解决时会把一侧的代码静默丢掉。你要的是：

- 一个**协调者**（主叙述者）只管全局：项目、当前任务、每个 worktree 的合并情况（有托管时是 PR）、团队里每个人和每个代理在干什么。它自己除了极小的即时改动不做任何占上下文的事，设计、实现、测试、评审都交给子代理。
- 子代理放开以前限制掉的：终端、浏览器、再派子代理（最多两层）。
- 协调者加它的子代理树是一个 **team**。一个仓库可以有多个 team，一个人可以建多个 team，一个 team 可以多人用；team 之间互相独立，靠大纲减少冲突。

我现在手工当协调者的做法就是这个产品要原生支持的：一份短的简报；每个工作单元一个子代理、一个 worktree；由新的子代理独立评审直到没有阻塞问题；推送、开 PR、等 CI、合并、删 worktree 和分支、记进简报；先合进长期集成分支；基线动了就合进在途分支；同一时间只允许一个在途分支加数据库迁移；flaky 的 CI 只重跑一次。

## 这份计划的形状

- **做完是什么样**：项目页像 Cursor：左边项目和 team，中间是协调者的对话，右边是看板（排队 / 进行中 / 待评审 / 完成 / 取消）和「集成」「PR」两个面板。每张卡是一个**工作项**：一个分支、一个 worktree、负责它的子代理、评审轮次、在不在集成分支里、PR 和 CI 状态。所有改 git 状态的动作（建 worktree、合进集成分支、同步基线、开 PR、合并、清理）由服务端执行并记账，协调者只发指令、读结果。
- **不需要大纲也能用**：工作项、集成账本、跨 team 的「同一文件」提醒都从 git 事实来。大纲（pageless 合入主干后）再加上「动手之前的认领和意图」。
- **量**：16 个 PR，约 2.6 万行非测试代码。12 个现在就能在主干上做；2 个大纲相关的等 pageless 合入主干；另有 2 个（托管）可以提前也可以推后。
- **你定下的** 8 件，在第五节，编号 T1–T8（2026-11-16 定）。

文中用到的词：

- **协调者**：team 的主叙述者。**一级子代理**：协调者派的；**二级子代理**：一级子代理派的。「最多两层」我理解成协调者下面最多这两层（T6）。
- **工作项**：一个工作单元，对应一个分支和一个 worktree，可选地连一个大纲任务块。
- **基线**：合回的目标分支，默认项目的 `defaultBranch`（`main`）。
- **集成分支**：team 的长期测试分支（下文叫 dev），用来跑实例体验；实例由协调者自己用终端或长驻服务管理，产品不提供起实例的功能（T8）。
- **账本**：集成分支「里面合了什么」的记录：每一行是「某个工作项的某个提交，以某个合并提交进了 dev」。
- **保全检查**：冲突解决后，对照两侧相对共同祖先新增的内容，确认没有哪一侧的新增被悄悄丢掉。

### 2. 多人对话今天是什么样

- 一个叙述者有两条独立的受众轴：读（private / project / public）和写（owner / project / public），外加按叙述者的显式授权（`acl_grants`）。写权限就是「能驱动」：发消息、批工具调用、回滚、改模型（`narrator-acl.ts` 文件头，`routes/narrators.ts:900-930`）。
- 所以第二个人今天就能和同一个叙述者对话：给他写权限，他在同一个输入框里说话。每条模型可见的消息带 `<sender kind="human" id name>` 标记，模型知道是谁说的（`narrator-prompt.ts:227`）。忙时排队。
- Bot 模式（`docs/BOT_NARRATOR.md`）是另一种形态：每人一间 `bot` 房间，bot 只用 `Send({ user })` 说话，会话记录是监控视图。它有一条和协调者完全同构的规则：**主循环只做协调**，耗时工作交给子代理，代码侧兜底是 bot 的 `Agent` 一律后台运行（`tools/task.ts:432-435`）。群聊（多人一间房）在文档 §5 只写了扩展方向，没有实现。房间种类现在只有 `dm`、`bot`、`narrator`（叙述者旁边的讨论房间）（`shared/chat-room-kinds.ts`）。
- 审批：谁对根叙述者有写权限谁就能批；没有「指定审批人」。

### 3. 能用来约束协调者的机制

- **能力上限 trait**（`server/lib/runtime-policy-trait.ts`）：工具白名单、MCP 级别、只读、`readOnlyGitShell`（Bash 只能跑受限的只读 git，`narrator-permission.ts:4909`、`5042`）、拒绝的能力、续跑上限。多层声明取交集、只收窄。Bot 就是这样存了一层上限（`BOT_RUNTIME_CEILING`，`policy.ts:86-89`）。这是约束协调者的现成骨架。
- **没有的**：按次的改动大小上限、按次或按轮的读取 / 输出上限。现有的只是工具自己的保护值：Read 全文 10 万字符（`tools/read.ts:26`），Bash 内存里 10 MB（`tools/bash.ts:31`），都是为了不爆内存，不是为了省上下文。
- **一次性放行**的先例：行为边界文件由用户这一轮授权一次写入（`tools/behavior-fence-grant.ts`）。
- **按创建预加载工具**的先例：知识管家和设置助手在创建时写 `enabledTools`（`narrator-service.ts:1558-1619`）。
- 上下文用量有快照列（`schema.ts:354` `context_usage_snapshot_json`），可以拿来显示和提醒。

### 4. 大纲（pageless 分支）对 team 有什么

大纲默认关闭（pageless `server/services/outline/feature.ts`），还没合进主干；16 个 PR 合了 10 个，剩下的是实时编辑 L3–L6 和拆除 X1、X2。任务和团队那条线（A1–A3）已经做完。和 team 相关的现成东西：

- **任务与认领**：任务是带 `task_json` 的块（状态、指派、前置、manager、claimable、计划），领取在写入路径里原子完成，有租约和领取代数（`task-json.ts`、`lease-keeper.ts`）。
- **委派即任务**：`Agent({ task })` 把任务交给子代理，认领随之交过去，报告挂回任务下；只接受「任务在大纲里的根会话」（`delegation.ts` 文件头）。子代理没有自己的任务，指派只认根会话（`assignee.ts`，D27c）。
- **团队事件与唤醒**：指派给我、前置完成、我建的任务结束三种事件，每会话限流（`team-events.ts`、`team-wake.ts`）。
- **团队动态**：每次运行开始写一行 `sys`，讲别人在相关任务树和项目任务清单上做了什么，以及「你改过的文件别的会话的进行中任务也改了」（`team-activity.ts`）。
- **重叠提示**（`overlap.ts`）：按（项目、仓库、仓库内路径）索引，同一仓库的不同 worktree 算同一个文件；按**根会话**记，子代理的改动算到它的根；只有 Write/Edit 会在结果末尾提示，Bash 只进索引；只在内存里，重启清空；同一会话的子代理之间不提示；只在大纲开着时工作。
- **开任务会话**（`task-session.ts`）：从看板「为这个任务开新会话」，目录用项目目录或上次的目录，**从不新建 worktree**；PostgreSQL 上会话运行时不跑，直接拒绝。
- **交出、交接、释放**（`hand-out.ts`、`handoff.ts`、`release.ts`）：会话空间的任务复制到项目任务清单；没做完的项目任务在运行结束时退回并写交接块。

对 team 来说缺的：没有「team」这一级（只有会话和项目）；嵌套后的根要改成 ACL 根，否则二级子代理的改动算不到协调者头上；意图（「我打算改这些文件」）没有地方放。另外 pageless 计划定了「分支期间主干上不改大纲相关的文件」（`OUTLINE_PAGELESS-PLAN.md` 三.1），所以碰大纲的 team 工作必须等。

## 二、目标设计

### 1. Team 是什么

- **一个 team 就是一个协调者会话**：建 team 就是建一个带 `team` trait 的主叙述者，team 的名字就是这个叙述者的名字（改名就是改 team 名）。`project_teams` 以协调者的叙述者 id 为主键，只放 team 级的东西：所属项目、基线、集成分支、合回方式、设置。一个项目多个 team，任何对项目有写权限的人都能建；一个人可以建多个。
- **成员和权限不另起一套**：team 的访问就是协调者会话的访问。给某人协调者的写权限，他就是这个 team 的成员（能说话、能批工具调用）；给读权限就是旁观。子代理沿用 `acl_root_narrator_id`，嵌套两层也落到协调者上（创建时沿父链继承，`narrator-service.ts:1981`）。
- **不换协调者**：叙述者本来就能一直用，上下文随时可以压缩或清空。清空或压缩之后，团队状态和简报在下一次运行开始时照常注入（第 2 条），所以协调者不会「忘了 team」。协调者会话归档就是 team 归档（工作项、账本保留，只读）；删除协调者会话前必须先清理或交出 team 的工作项。
- 团队之间没有共享状态，只共享仓库和项目空间：跨 team 的协调靠 git 事实（第 10 条）和大纲（pageless 之后）。

### 2. 协调者：职责与约束

**职责**（写进协调者提示词，`server/lib/prompts/team-lead.ts`）：

- 拆工作、建工作项、派子代理、收报告、安排评审轮次、决定合进 dev、开 PR、合回、清理。
- 保持全局注意力：每个工作项的状态、集成分支里有什么、PR 和 CI、待批的工具调用、团队里的人和代理、其他 team 在改哪些文件。
- 除了极小的即时改动，不读大文件、不跑长命令、不改代码。

**它看到的全局状态不靠它自己记**：每次运行开始和长运行中每 10 分钟，系统写一行「团队状态」`sys`（做法同大纲的团队动态：写进历史，不进系统提示，文本确定、不带相对时间，保住提示缓存）。内容有上限（约 6 KB）：工作项表（最多 30 行，其余计数）、dev 账本摘要和与分支不一致的地方、PR 与 CI、待批工具调用、独占锁、和别的 team 的文件重叠、成员最近一次发言。另有一段「简报」（≤ 4 KB 文本，协调者和成员都能改，`Team({ action: "brief" })`），取代我现在手写的简报文件。

**约束怎么执行**（T4 已定：全软）：不拒绝、不截断，靠提示词、即时提醒和统计。

| 项 | 建议值（暂定，没有测） | 超了怎么办 |
|---|---|---|
| 工具 | 和普通主叙述者相同；提示词要求终端、浏览器、长命令、读大文件交给子代理 | — |
| 单次改动 | Edit/Write 一次 ≤ 30 行（按新旧文本行数取大），新文件 ≤ 60 行 | 照常执行，结果末尾加一行「这次改了 84 行，超出协调者建议的 30 行；这类工作交给子代理」 |
| 一轮改动的文件 | ≤ 3 个 | 同上 |
| 改动位置 | 建议只改 team 自己工作项的 worktree；项目主检出、dev 的 worktree 不直接改 | 同上提醒；直接改 dev 或基线的提交会被账本核对列成「不来自账本的提交」 |
| 单次读取 | Read ≤ 300 行；Grep/Glob ≤ 100 行；Bash 输出 ≤ 8 KB | 照常返回全文，末尾提醒 |
| Agent / Await | 建议后台派、不阻塞等待，让协调者随时听得见人 | 提示词要求，不强制 |
| 上下文 | 用量过 60% 时团队状态里提醒压缩；照常有自动压缩 | — |

每次超出记一笔（种类、大小），团队状态和 team 页显示「本周超出 N 次、最常见是哪类」，你据此决定以后要不要收紧。实现位置：建议值存在 team 设置里；提醒在工具结果投影时追加（确定文本，不影响缓存）；统计进 `team_work_events`。

### 3. 子代理放开的能力和边界

- **工人模板**：team 设置里定义一级子代理的模板（默认 = `general` + Terminal + Browser + 可以再派），评审模板（默认 = `review`，只读、Bash 只读 git、可以开浏览器看页面）。创建时预加载 Terminal、Browser（照知识管家的 `enabledTools` 做）。工人的上限来自 team 的模板，**不**继承协调者自己的预算。
- **嵌套**：创建时记委派深度。一级子代理的上限允许 `spawnAgent`、`awaitAgent`（它要等自己的帮手）；二级子代理一律拒绝 `spawnAgent`。二级子代理的上限 = 它的模板 ∩ 父的上限（只读的父派不出可写的子）。服务端三处兜底的检查加深度判断。
- **要改的「只有一层」的地方**：事件和审批的广播目标改成 ACL 根（协调者），不是父；TeamStatus 给协调者看一棵树（一级下面挂二级）；`teamRootOf` 的使用者里，「团队」语义要的是 ACL 根的（重叠、文件改动统计）换成 ACL 根；前端子代理卡片支持嵌套一层；子代理恢复路径（`narrator-subagent-recovery.ts`）补二级用例。
- **工作目录**：派到工作项 worktree 的 `Agent({ workdir })` 不再要用户批准——这个目录是 team 自己记录的资源；其他目录照旧要批。二级子代理默认用父的目录。
- **终端**：子代理建的终端归它自己；协调者页面能看到整棵树的终端（只读列出，点开要写权限）；子代理归档时关掉它的终端。每个子代理 ≤ 3 个终端。
- **浏览器**：每个子代理 ≤ 2 个会话，每个 team ≤ 6 个，进程全局另设上限；子代理结束时关掉。
- **并发**：每个 team 同时运行的一级子代理 ≤ 6，整棵树 ≤ 16（暂定）。超了 Agent 返回「team 已满，等某个完成」。team 有一个「全部暂停」按钮：停掉整棵树的运行。
- **审批**（T6）：工作项 worktree 内的读写自动允许；命令照项目和用户的执行策略；其余进协调者页面的「待批」列表，任何成员都能批。审批不交给上一级子代理。

### 4. 工作项：任务、worktree、分支、PR 的记录

一张 `team_work_items`，一行一个工作单元：

- 标题、种类、状态（排队 / 进行中 / 待评审 / 可合 / 已合回 / 取消）。
- 分支名、基线、`worktree_resource_id`（现有资源表的行，worktree 由现有 `NarratorWorktreeService.create` 建）、当前头提交。
- 负责的一级子代理、评审轮次（每轮：哪个评审子代理、结论 `blocker / clear`、问题数）。
- PR 编号、地址、状态、CI 状态。
- 改动的路径（相对共同祖先的 name-only，最多 2,000 条，存列，有字节上限），用于跨 team 重叠和独占锁。
- 可选：连一个大纲任务块（空间 id、块 id，pageless 之后用）。
- 一张只追加的 `team_work_events`：每次状态变化、评审结论、合进 dev、同步基线、CI 重跑、清理，各一行，带人或代理。它就是我现在简报里「记一笔」的那部分。

协调者用一个 `Team` 工具操作（服务端执行，协调者只读结果）：`work.create`（建分支和 worktree、写行）、`work.review`（记一轮评审结论）、`work.ready`、`work.sync`（把基线合进这个分支）、`integrate`、`pr.open` / `pr.merge` / `merge.local`、`cleanup`、`instance.start/stop`、`brief`。子代理在自己的 worktree 里照常提交。

看板的列由状态决定：排队、进行中、待评审（有评审在跑或 PR 等 CI）、完成（已合回）、取消。卡片上另有「在 dev 里」「dev 里是旧提交」「有冲突」「独占」几个标记。

**任务是放大纲还是放这张表**（T3）：建议工作项表管 git 事实和看板，大纲任务（pageless 之后）管「做什么、谁认领」，两者用一个可空的连接；连上时状态单向同步（工作项开始 → 任务进行中，合回 → 完成）。

### 5. 集成分支和「里面合了什么」

- 建 team 时可选建 dev：分支 `nf-dev/<team>`，从基线某个提交建，worktree 记成 team 的资源。dev 有自己的 worktree，所以合并、冲突、实例都在那里，不碰用户的主目录。
- **合进 dev**（`integrate`）：工作项必须已提交、干净；先用 merge-tree 预览；没冲突就在 dev 的 worktree 里 `git merge --no-ff`（持 worktree 锁），账本记一行（工作项、源提交、合并提交、时间、谁）。有冲突走第 6 条。
- **基线动了**：dev 落后基线时，`integrate base` 把基线合进 dev，账本记一行。在途工作项落后基线时，`work.sync` 把基线合进它的分支（预览无冲突时服务端直接合；有冲突交给它的子代理，同样过保全检查）。
- **账本自己会核对**（防漏合、防误删）：每行的源提交是不是 dev 的祖先；工作项后来又有新提交时显示「dev 里是旧的，落后 3 个提交」；dev 上有不来自账本的提交（有人手工提交）时列出来；状态是「可合」却不在 dev 里的工作项列出来。都是有上限的 `rev-list`，后台跑，结果缓存。
- **从 dev 撤出一个工作项**：见 T1。建议：平时增量，账本就是配方；要撤出或者 dev 乱了，就从基线按账本顺序重建一个新的 dev（旧的保留到你确认），重建时在 dev 的 worktree 里临时开 `rerere`（`-c rerere.enabled=true`，不改仓库配置）复用以前的冲突解决，结果照样过保全检查。
- **独占路径**（来自「同一时间只允许一个在途分支加迁移」）：项目设置里列独占路径（NarraFork 自己填 `drizzle/**`、`drizzle-postgres/**`、`server/db/schema.ts`）。工作项的改动碰到它们时，在第一次合进 dev 或开 PR 时拿项目级的独占锁（数据库唯一索引保证原子），第二个就被挡住，直到第一个合回基线或放弃；人可以强制放行，记一笔。跨 team 生效。

### 6. 冲突流程：不得静默丢代码

1. 预览列出冲突文件。
2. 服务端在 dev 当前头上开一个临时 worktree（记录在案），在那里 `git merge`。dev 本身不进冲突状态，实例和别的合并不受影响。
3. 派一个解决冲突的子代理到临时 worktree，说明里带两侧的意图（工作项标题、两侧碰这些文件的提交说明）。它解决、跑相关测试、提交合并。
4. **保全检查**（系统做，不是模型）：
   - 对两侧都改过的每个文件，取「共同祖先 → 我方」「共同祖先 → 对方」新增的行（去掉行尾空白，空行和很短的行不算），逐行看结果里有没有，按次数比较；
   - 一侧新增的文件结果里必须在，一侧删掉的文件结果里不能复活；
   - 没有冲突的文件，结果必须和 merge-tree 自动合并的结果完全相同（防止解决冲突时顺手改了别处）；
   - 解决者可以写一份「有意丢弃」清单（文件、哪一侧、哪几行、原因），清单之外的缺失一律算失败。
5. 通过：dev 的 worktree 干净时快进到这个合并提交，账本记一行（标「有冲突」，附检查报告）。不通过：卡片上列出缺失的行，协调者把它退回解决者，或者人确认这些丢弃（记下谁确认的）。检查做不完（超时、Worker 不可用）一律当不通过。
6. 上限：最多 300 个文件、单文件 1 MiB、合计 32 MiB、60 秒；git 输出从子进程限流读，逐行比较在 Worker 里做，Worker 不可用就失败，不回主线程。

已知局限：一侧的代码被搬到别处或重排格式会被报成缺失，要解决者写进丢弃清单说明。

### 7. 合回基线

两种方式（T2），按项目选：配了托管走 PR，没配本地合并：

- **本地合并**：用 merge-tree 算出合并结果，`commit-tree` 生成合并提交；基线分支如果在某个 worktree 里检出且干净，就在那里 `merge --ff-only` 到这个提交；检出的地方不干净就拒绝并说明（绝不在用户有未提交改动的目录里合并）；没有检出就 `update-ref` 带旧值比较交换。
- **托管 PR**：推分支（用宿主机的 git 凭据）、开 PR、轮询 PR 和检查结果、合并。

合回后：账本里这个工作项标「已经在基线里」；dev 下次同步基线时自然包含。

**谁按最后一下**（T7 已定）：满足「CI 绿（本地合并时为评审子代理跑过的测试通过）、最后一轮评审无阻塞、没有持有或等待独占锁」时协调者直接合，不等人；不满足时它不能合。每次合回记一笔（谁、哪个提交、依据的评审和 CI），team 页列出最近的合回，人随时可以叫停（「全部暂停」）或把 team 设成「合回要人点」。

**CI**：开 PR 的工作项由后台任务每 60 秒查一次（ETag，每项目最多 50 个开着的 PR，尊重限流头）。失败时：项目设置里的「已知不稳定」清单（检查名，可选日志尾的正则，日志尾最多取 256 KiB）全部命中就自动重跑失败的作业**一次**，记一笔；再失败或不在清单里就通知协调者（团队事件，照大纲 team-wake 的限流做法）。

### 8. 实例（不做成产品功能，T8）

- 产品不提供「从 dev 起实例」的功能，也没有端口分配、实例表。要体验时协调者自己用子代理的终端或 Bash 长驻服务（`background_kind:"service"`）在 dev 的 worktree 里起，按项目自己的说明来。
- 仍然成立的铁律：NarraFork 开发 NarraFork 时，承载会话的进程永远不由协调者或子代理停、重启或接管；起的实例要用另一个端口和另一个数据目录（`NARRAFORK_HOME`、`PORT`）。这写进协调者提示词和 NarraFork 自己的项目说明，不靠产品代码拦。

### 9. 清理

- 只按记录删：只删 `team_work_items` / `project_teams` 引用的 worktree 资源行对应的目录，经现有删除保护（有会话 cwd 在里面、有终端在用就删不掉）；有未提交改动或未推送且未合回的提交时拒绝。**不列目录、不扫 `.worktrees/`**，旧章节目录永远不会被碰到。
- 分支只用 `git branch -d`（git 自己确认已合并），或者账本证明这个提交已经是基线的祖先；远端分支由托管接口删（可选）。从不 `-D`，除非人在确认框里明确选。
- 清理时归档这个工作项的子代理（它们的终端、浏览器随之关掉），记一笔。
- 默认由协调者或人触发，不自动跑。

### 10. team 之间怎样不打架

先用 git 事实，不依赖大纲：

- **谁在改什么**：每个活跃工作项的改动路径（第 4 条的列）在后台更新（子代理一轮结束时 + 每 2 分钟一批最多 50 项）。项目页有一张「谁在改什么」：同一个文件被两个以上活跃工作项改动时列出来（同 team、跨 team 都列）。比较时每项最多 500 条路径参与，超了按顶层目录比；全项目最多 100 个活跃工作项。这些列在库里，重启不丢（大纲的重叠索引只在内存）。
- **提醒到协调者**：重叠和独占锁进团队状态；新出现的跨 team 重叠作为团队事件告诉两边的协调者（限流）。
- **独占路径**：第 5 条，跨 team 生效。

pageless 合入主干之后再加大纲（O1、O2）：

- 每个 team 在项目空间的任务清单下有一个块，team 的任务在它下面；工作项连任务块，派子代理时走现有的 `Agent({ task })`，认领交给一级子代理，别的 team 在看板上看得到「Team B 的 X 正在做，认领者是谁」。二级子代理不持有认领（现有规则：只有根会话能被指派）。
- **意图**：协调者建工作项时写「预计改动的路径」，写进任务块；开工前和别的 team 的意图、认领、实际改动比对，冲突时提醒，不阻止。
- 大纲的重叠提示和团队动态改用 ACL 根算「根会话」，二级子代理的改动才会算到协调者头上；团队动态里加上「其他 team 的任务变化」。

### 11. 项目页

- 路由 `/projects/$projectId/teams/$teamId`。左栏：项目列表，项目下列 team。中间：协调者的对话（复用叙述者面板）。右栏三个标签：**看板**（五列，卡片见第 4 条）、**集成**（dev 账本、核对结果、独占锁）、**PR**（PR 与 CI、已知不稳定的重跑记录）。顶部：待批数、运行中的代理数、「全部暂停」。
- 项目首页加一个 team 列表和「谁在改什么」。
- 窄屏：三个标签（对话 / 看板 / 集成）切换，360 px 能用；明暗两套。
- 中英文。

### 12. 多人用同一个 team

- 对话形态见 T5。建议先用「共享协调者会话」：成员都在协调者的输入框里说话，发送者标记区分是谁；协调者忙时排队；它的回复所有成员都看得到。协调者提示词要求：不同人的指令冲突时先问，不自己选。
- 审批：协调者页面的「待批」列出整棵树待批的工具调用（只查这个 team 的叙述者，最多 50 条），任何成员都能批，记下是谁批的。需要人的事发通知（现有的注意力通知）。
- 子代理以「触发这一轮的那个人」的身份行事（`tools/task.ts:518`），所以权限按那个人算。

### 13. 跟本仓库规则的对照

- **两种方言**：新表都写在 `schema.ts`，SQLite 用 `bun run db:generate`，PostgreSQL 用 `generate-postgres-schema.ts` + `db:generate:pg`；改一致性测试的表数列数。PostgreSQL 上会话运行时不跑，team 的改动路由和项目一样返回 503，表照样生成。新加迁移的 PR 同一时间只有一个在途。
- **主线程**：所有 git 调用是带超时、带输出上限的子进程；看板和账本的读取是有索引、有上限的小查询，游标分页；核对、改动路径、CI 轮询都是后台任务，有游标和让出；保全检查的比较在 Worker 里，Worker 不可用就失败。
- **数据导入导出**：项目本来就不在导出清单里，team 的表也不进（它们引用的是这台机器上的 git 状态和目录）；`clearData` 清叙述者时 team 的协调者列置空。写进 `docs/DATA_PORTABILITY.md`。
- **不重启**：第 8 条。

### 14. 照 Claude Code 的做法

我现在当协调者用的就是 Claude Code（云端会话 + 子代理 + GitHub 事件）。它好用的地方直接搬过来，下面每条写「它怎么做 → team 里怎么做」，并标出落在哪个 PR。

**派活和收活**

- **派出去就不管，完成时唤醒**：Claude Code 的子代理默认后台跑，跑完把一份报告作为下一条输入送回主对话，主对话从不轮询、不阻塞等待；报告不直接给用户看，由主对话转述要点。→ 协调者派的子代理一律后台；完成、失败、需要人时由系统把报告或状态作为一条输入唤醒协调者（照现有 Await 规则和大纲 team-wake 的限流）；协调者页面把报告折叠显示，协调者负责转述。（S1、P3）
- **一个参数开隔离的 worktree**：Claude Code 的 `Agent({ isolation: "worktree" })` 自动建一个临时 worktree，没改东西就自动清掉。→ `Agent({ isolation: "worktree", title })` 就是「建工作项」：服务端建分支和 worktree、写工作项行、把子代理放进去；子代理结束时 worktree 没有任何提交就自动清理并把工作项标成取消。`Team({ action: "work.create" })` 保留给「先建工作项、以后再派」。（P3）
- **用名字续派，上下文不丢**：Claude Code 用 `SendMessage` 继续一个已完成的子代理，它带着原来的上下文接着干（评审意见回来后让原作者修，而不是新开一个）。→ 工作项记住负责的子代理；评审有阻塞问题时，协调者 `Send` 给原来的子代理续做；子代理已归档就恢复它。（P3）
- **像对同行一样写简报**：Claude Code 要求派活时把目标、已排除的方向、要读的文件、范围写清楚，因为子代理只知道简报里的东西；另有共享的规则文件（我现在的 `briefs/common.md`、`briefs/pageless.md`）。→ team 的简报（≤ 4 KB）是所有子代理的共同规则，自动附在每个子代理的系统提示后面；每个工作项另有一段任务说明。协调者提示词里写明「简报要写到对方不用问就能干」。（P1、P3）
- **新开还是带上下文**：Claude Code 有「全新子代理」和「继承当前上下文的分身」两种。→ 现有的 fork 模式（`fresh` / `compressed` / `full`）直接用；评审一律用全新的，不让评审带着作者的思路。（S1）

**上下文保护**（T4 全软之后，这是真正让协调者「不吃上下文」的机制）

- **大输出落盘、只给摘要**：Claude Code 的大输出自动存成文件，主对话只看到摘要和路径；子代理的完整记录明确禁止主对话去读。→ 协调者的工具结果超过建议值时，全文存成附件，协调者看到头尾和附件链接（这是提醒，不是截断：它要看全文可以再读）；子代理的会话记录不进协调者上下文，只有报告进。（P2）
- **压缩带摘要**：Claude Code 上下文快满时自动压缩成摘要继续。→ 现有压缩照用；压缩后团队状态立刻重新注入一次。（P2）

**外部事件**

- **订阅 PR，事件来了唤醒**：Claude Code 订阅一个 PR 之后，评审、CI 完成、合并、关闭都作为一条结构化事件送进对话，每种事件附一句处理规则（例如「CI 失败：这次唤醒必须以推送修复或在 PR 上说明为止」）；自己发的评论回来的回声、重复事件直接跳过。→ 开 PR 的工作项自动订阅；后台轮询（自托管收不到 webhook，有就用 webhook）把变化转成团队事件唤醒协调者，事件文本固定格式、带种类和处理规则；同一事件只送一次，自己的评论不送。（H1、H2）
- **外部内容是数据不是指令**：Claude Code 把 PR 评论、CI 日志、作者名标成「不可信字段」，里面像指令的话不照做，要做出格的事先问人。→ 事件里的外部文本放在标明「外部内容」的字段里，协调者提示词写明同样的规则。（H2）
- **兜底的自检**：Claude Code 在只等评审或 CI 时给自己定一次「过一会儿回来看看」（第一次约 50 分钟，以后约 4 小时一次，连续 3 次没变化就停，有任何新动静就重新计数）。→ `Team({ action: "checkin", minutes })` 用现有的定时任务给协调者排一次唤醒；团队状态里显示下一次自检时间；同样的退避和停止规则写进提示词。（P3）
- **看守和自动修只针对自己的 PR**：Claude Code 对自己开的 PR 负责到底（冲突、CI、评审意见都要处理），对别人让它看的 PR 只做有把握的小修、其余问人。→ 工作项开的 PR 归 team 负责；别人的 PR 只读、只提醒。（H2）

**把 PR 推到绿**（我现在照做的规则，写进协调者提示词和 H2 的自动处理）

- 顺序：先解合并冲突（把基线合进来，不改写别人分支的历史，不 rebase、不强推），再看 CI，再处理评审意见。
- 「flaky」不是原因：确认和本 PR 无关的失败，在 PR 上说明一次并只重跑一次；再失败就当真问题。永远不跳过、禁用测试，不推空提交、不关了再开来触发 CI。
- 推送前先跑仓库自己的快速检查（lint、类型、相关测试），修 CI 时先复现再修。
- 评审意见：小的直接改；大的（跨文件重构、接口变化）写方案给人定；可选的意见回一句、能顺手改的跟下一次推送。

**权限和人**

- **不能借道**：Claude Code 里一个代理被拒绝的操作，不能让另一个代理去做；被拒就报告给人。→ 子代理被拒的审批，协调者和别的子代理都不能代做；协调者把它列进「待批」并告诉成员。（S1）
- **问人用结构化的选择题**：Claude Code 问用户时给 2–4 个选项、推荐项放第一个并标出、每个问题能单独看懂，还可以带预览。→ 协调者用现有的 `AskUserQuestion`，同样的写法要求进提示词；多人 team 里任一成员可以答，记下是谁答的。（M1）
- **决定替人做了要说**：我替你做的小决定都在汇报里写明，你可以推翻。→ 协调者每次「替人拍板」记一笔，团队状态里列最近的几条。（P2）

**不搬的**：Claude Code 的确定性多代理工作流脚本（一次派几十个代理）——规模和成本都不适合默认开；以后需要再说。

## 四、风险，从大到小

1. **软约束守不住**。T4 定了全软：协调者可能照样读大文件、改大段代码，把上下文吃满。靠即时提醒、超出统计和放弃条件（收紧成混合）兜住；建议值全是估计，没有测。
2. **嵌套放大成本和噪音**。两层 × 每层几个，审批、通知、token 都成倍。靠并发上限、「全部暂停」、工作项目录内自动允许把审批量压下去。
3. **保全检查**：漏报（模型把一侧的逻辑改写了但新增行碰巧都在）抓不住，只能靠评审子代理；误报靠丢弃清单。它是「不静默丢」的底线，不是正确性证明。
4. **人手工动 git**：有人直接在 dev 或基线上提交、重置。账本核对能发现，但不能自动修，要人决定。
5. **令牌安全**：令牌在加密文件里，但能读整个 NarraFork 主目录的人能解。代理的工具结果、环境变量、日志里都不能出现它，要测试守住。
6. **NarraFork 开发 NarraFork**：产品不管实例，协调者自己起的实例和主进程共用一台机器，端口、数据目录、构建产物（`dist/`）都可能撞，承载会话的进程可能被误停。只靠提示词和项目说明约束（第二节第 8 条）。
7. **pageless 推迟**：O1、O2 会跟着推迟；在那之前没有「动手之前的认领」，只有「改了之后的提醒」。
8. **多人对着一个协调者**：指令互相矛盾。靠提示词要求先问、和发言人显示；人多了要考虑 T5 的群聊。
9. **PostgreSQL 部署用不了**：和项目、会话运行时一样。
10. **长期 worktree 占磁盘**：每个工作项一份完整检出加依赖（NarraFork 一份 `node_modules` 不小）。清理不自动跑，要在看板上提示「已合回、可清理」。
