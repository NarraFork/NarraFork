# 流程与 description 优化：逐轮实验记录

> 本页按轮保留历史结果。最新冻结 V6 已完成全六场景、两模型、各两次的资格验证：24/24 业务正确并有效终止（22 次显式交付、2 次正常自然结束）。交互契约已达到本轮满意标准；生产代码尚未实施，按用户要求等待整理工作区及明确继续授权。

## 结论

**已落地单一描述来源、角色/状态动作提示、同次 Eval 验收流程及按错误来源恢复；但尚不能宣称默认 description 已稳定优于基线。**

验收题的误用消失，多个执行场景的 Eval 次数下降。另一方面，Luna 的最终返回形状和 Flash 的“达标后仍继续查询”没有稳定解决。更长、更强的提示并不保证更高通过率；当前 V4 是实验候选，不是生产 SDK 易用性验收通过。

本轮实际执行两轮完整配对测试：**24 条题目轨迹、45 次 Eval、68 次模型请求**。没有替模型修改代码，也没有让评分器在中途达标时提前结束会话。

## 已实施的优化

| 位置 | 变化 |
|---|---|
| `tests/task-call-challenges/contract.ts` | 集中维护方法签名、精简说明、流程和 Eval description；不包含题号、答案或评分条件 |
| [API.md](API.md) | 从契约生成；先区分执行、验收、查询，再介绍同步对象，不默认灌入完整进阶方法表 |
| `runner.ts` | read 合并概要与详情，返回 `workflow: {kind,actions,note}`；动作由角色和状态推导，仅供选择，不赋予权限、不自动执行 |
| `runner.ts` 的 help | 从同一契约生成目录和方法说明；覆盖实际暴露的 16 个方法，包括子集合、分页与模拟工具 |
| `run.ts` | 使用同源 native description；核对真实请求中的 guide/description/code schema、low 和仅 Eval；运行前保存输入/源码快照，结束检查源码漂移 |
| `analyze.ts` | 统计重复调用候选、反馈字符数和 usage；允许新输出路径重算基线，不覆盖旧分析 |
| [统一设计稿](../DYNAMIC_SPEC_TEAM_TASKS.md) | 同步默认流程、同对象/同 Eval 验收、错误分流和提示边界 |

具体流程：

- **自己的工作**：按要求执行、验证后 finish；分派工作是 submitted，不等于负责人已验收。
- **验收他人提交**：同一次 Eval、同一个对象 read 最新提交，核对后 accept。既不把 finish 自动转换成 accept，也不复用上一 Eval 的读取凭据。
- **只查询或列计划**：不额外开始/提交/恢复任务；查询需要完整分页，但取齐目标结果后应结束。
- **合并调用后的错误分流**：真实测试失败才记录执行阻塞；目标变更重读要求，不自动改变生命周期；读取条件不足则在验收的同次 Eval 重读，不能 catch 所有异常后一律 block。

动作提示只在详情展开时返回，列表仍保持概要。错误消息说明本次是否修改，不暗示之前的成功调用已经回滚。

## 必须保留的失败证据

### V3：宽泛 catch 把提交冲突当成测试失败

[Luna 第 5 题](results/2026-09-06T11-40-20-915Z-luna-5.json) 把 Bash 和 finish 包进同一个 try，catch 任意异常后都 block。测试实际通过，finish 因目标变更被拒；模型仍额外把 doing 改成 blocked，然后正确返回了新 acceptance。

这不是“假报完成”。旧评分器的合并断言给出“用旧结果完成了新目标”，实际失败原因是**没有保持约定的生命周期状态**。原题的“等待确认”可能诱发阻塞处理，因此 V4 将“冲突恢复不自动改变生命周期”明确成接口流程，而非指望模型推断。没有放宽评分，也没有让宿主偷偷拒绝本来有权执行的 block。

### V4：错误分流正确，但最终返回形状仍错误

[Luna 第 5 题](results/2026-09-06T11-54-55-805Z-luna-5.json) 已分别处理 TEST_FAILURE 和 CONTRACT_CHANGED，重读后保持 doing，没有再次提交、重跑或 block。

但是返回的是 `{status: "doing", acceptance: "…"}`，不是题目要求的 acceptance 文本。**状态处理已改善，严格评分和既有恢复评分仍不通过**；不把它算作 6/6。

### V4：中途正确结果被过度复核覆盖

[Flash 第 3 题](results/2026-09-06T11-54-55-805Z-flash-3.json) 在第 3 次 Eval 已返回正确 key 数组。之后又查询两次，最后移除了 search 条件，返回包含“历史文档”的对象数组，而非所需 key 数组。5 次响应预算耗尽，未自然结束。

V4 已提醒完整分页后结束，但本次轨迹没有遵循。不能宣称加重停止提示解决了问题，更不能在评分器发现第 3 次 Eval 达标时强制截断，伪装成模型完成。

## 校准与边界

- 原 6 个参考程序、6 个错误反例均按预期通过/拒绝；3 个状态对象返回校准通过。

- 最终七个实验文件的定向 Biome 检查有 86 项历史动态类型等 warning、无 error；新增 contract.ts 单独检查零 warning。未宣称整个实验驱动零警告或生产级可用。
- 没有变更生产工具注册、数据库或运行中的服务。本实验不验证生产 Worker/SAB、安全隔离准入、真实工具审批或恢复。

## 本轮决策

保留已验证的接口机制：同步对象、单一描述来源、上下文动作提示、同次验收和错误分类。**暂不把 V4 作为“易用性稳定通过”的版本。**

本轮按约定止于一次针对性修正后的完整配对复测，不继续重跑挑最好成绩。下一次若继续，应做单变量实验，优先研究“明确最终交付与中间诊断输出的区别、按用户要求约束输出形状”，而不是继续累加禁止句或放宽评分。新机制不能依赖隐藏评分器替模型决定何时结束。

## 后续：显式交付同期对照（V5）

### 假说、实现与约束

为避免 `return` 同时充当观察和交付，本轮只增加实验用 `deliver(value, summary?)`：正文与补充说明分开，成功封存后结束操作阶段，不再由下一轮查询覆盖结果。它不自动 finish/accept，也不校验答案是否正确；停止条件只看模型的显式动作，不能读取隐藏评分。

- `profiles.ts`：A 使用冻结 V4 文本/帮助/schema，B 追加交付方法与最短说明；默认 API.md 和常规运行入口不变。
- `runner.ts`：VM 私有交付状态、不可变值快照、64 KiB UTF-8 正文上限、2000 JS 字符 summary 上限；交付后调用、重入、吞错、重复交付和超时不能伪装为干净交付。
- `run.ts`：传入 profile、记录原生 call ID、只按可信交付回执停止；同一响应里交付后的额外调用标记为未执行/协议冲突。业务评分和交付协议指标分别记录。
- `delivery.test.ts`：33 个测试通过（162 个断言），包括两种协议的三轮 SSE 回放、四条既有模型轨迹对冻结 V4 运行器的逐步差分回放、六题语义保持、交付封存与异常、错误答案也会结束但评分失败的反例。
- 原六题参考/反例、既有权限校准继续通过；本轮模型运行前及收尾全仓 `bunx tsgo --noEmit` 均通过。三个新增文件的定向 Biome 检查零错误、零警告。前面 V4 收尾记录的 tutorial 变更问题未在此轮检查中复现，没有为此修改无关文件。

实验固定为第 3、5 题，两个原模型 low，每组合重复 2 次，按 A-B-B-A 交错。每轨迹仍是 5 次响应 / 6 次 Eval。总计 **16 条轨迹、36 次 Eval、45 次模型请求**；无基础设施错误，未修改评分器、题目或初始数据。

### 失败轨迹与新增摩擦

1. **Luna 第 5 题的两次 B 都未采用交付。** 它重读要求并保持 doing，但继续返回 `{status, acceptance}` 对象，然后用自然语言结束；要求的 acceptance 文本依然没有作为正确形状交付。[B1](results/2026-09-06T13-35-40-408Z-delivery-pilot-luna-5-B-1.json) · [B2](results/2026-09-06T13-35-40-408Z-delivery-pilot-luna-5-B-2.json)
2. **Flash 第 3 题 B1 未采用交付，且再次覆盖正确结果。** 第 4 次 Eval 已返回完整 key 数组，随后把 archived 从 only 改为 include，并返回对象数组，预算耗尽。[完整轨迹](results/2026-09-06T13-35-40-408Z-delivery-pilot-flash-3-B-1.json)
3. **同一轨迹还暴露了 IIFE 的返回歧义。** 第 3 次 Eval 写成 `(() => { …; return allKeys; })()`，没有把值从 Eval 的外层函数 return 出去。运行器因此按既有规则返回最后一次 API 的末页，而不是 allKeys。将这段模型原代码分别在 A/B 中离线重放，结果一致；不是交付扩展引入的差异，也没有把手工改过的代码算成模型成功。
4. **同期 V4 也有波动。** Flash 的两次 A 分别用了 1 和 5 次 Eval；Luna 第 5 题 A 一次返回正确文本、一次返回包装对象。不能只拿历史最差轨迹与新候选比较。

新增方法让“停止后不能覆盖结果”成为可执行约束，但**是否选择这个方法仍依赖模型**。尤其原有恢复流程仍写“重读并返回”，与新交付约定并存；这是下一轮需要验证的说明一致性假说，不是已经证明的失败根因。

### 请求减少并非业务调用减少

A 的 24 次请求由 17 次 Eval 加 7 次自然语言收尾构成；B 为 19 次 Eval 加 2 次自然语言收尾。B 少掉 5 次收尾，却多了 2 次 Eval，净少 3 次请求。因此不能将请求下降解释为更高的业务推理效率。

原始 usage：A 输入/输出 38898 / 6069 token；B 为 34601 / 5057。由于严格成功率不同，不能宣布等质量成本优势；这些仍只是对应网关回报的小样本数据。

### 本轮决策与下一步证据需求

保留可选交付 profile、边界实现与离线测试，但不推广为默认。实验说明“追加一种正确的机制”不等于“模型会稳定采用它”，也不能单独解决返回形状问题。

若继续，应优先独立验证观察/交付语义的一致性，以及外层 return、IIFE 最后表达式与诊断输出之间的明确契约；不要在保留多套返回惯例时再追加一个终态方法。任何新的输出形状约束都应来自用户要求，不能从隐藏评分器读取答案或自动把错误输出修成成功。

## 后续：一致性说明同期对照（V6）

### 本轮改变了什么

这次不新增方法，也不修改 Eval 取值规则。A 直接读取前轮冻结的 V5 profile；B 重新组织 V6 的 guide、native/code description、help、workflow note 和目标变化反馈，不再在 V5 的旧段落末尾继续追加规则。

统一为两个意图：

- 还需要模型理解资料再决定：外层 return 用于观察，之后继续操作。
- 本轮已可答复用户：deliver 用户要求的值，说明另放 summary。完成、真实受阻、等待确认、只读查询都能交付；**业务仍是 doing/submitted，不意味着本轮不能答复。**

目标变更路径也使用这一约定：保持生命周期、重读后交付所需的新信息，不自动 block。代码仍是函数体，IIFE 内层 return 仍不会穿透外层；没有自动提取最后表达式、解包对象、改评分或增加权限。
