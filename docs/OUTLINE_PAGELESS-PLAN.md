# 大纲去掉「页」：实施计划（D56、D57）

依据：`origin/main`（570b2c3e，2026-11-14）的代码；设计分支上的两份研究（`docs/OUTLINE_LIVE-SUBTREE-STUDY.md`、`docs/OUTLINE_TREE-HISTORY-STUDY.md`）、`docs/OUTLINE_KNOWLEDGE-DESIGN.md`（需求 R1–R28）和 `docs/OUTLINE_P2-PLAN.md`；两份研究的基准在草稿目录的 `tree-history-prototypes/` 和 `live-subtree-prototypes/`。本文只是计划，没有改任何产品代码，也没有重跑基准。

## 背景

大纲现在把每个空间的顶层块叫「页」，并且把它当成边界：一页一个实时编辑会话、一个撤销栈、一份历史索引、一份折叠状态、一份订阅，待确认改动、提问、读取预算也都按页算。所以树里展开的内容只能看不能改，跨页不能拖、不能选、不能撤销，子树换页超过 2000 块被拒绝，超过 1 万块的页读不出历史。你在 D56、D57 定了：编辑的单位是任意子树；页这个概念整个不要；一次做到位，不留新旧并存；过去的历史不用保留，只把现在的内容搬过去。

## 这份计划的形状

- **做完是什么样**：空间下面直接是块。存储里没有 `page_id`；历史靠「位置表」和「变动表」按父块一层层读；实时编辑是一个空间一个会话、每块一份文字文档；浏览器里只读的树和可编辑的树是同一个组件的两种模式，聚焦视图是只有一个根的同一个组件。
- **数据怎么过去**：一次由生成器产出的结构变更，加一次性的转换程序。转换只保留现在活着的内容和每块当前版本的出处，旧版本和旧提交删掉，新历史从转换那一刻开始。转换前自动把大纲的表拷到一个单独的文件里，你可以留着。
- **怎么施工**：在一条长期的集成分支上按固定顺序合 16 个可评审的 PR（每个不超过约 2,500 行非测试代码，每个合完分支都能跑、大纲功能齐全），最后**一次**合进主干。主干和你的真实数据只经历一次变化。集成分支上有一段时间 `page_id` 和新表同时在（先加后拆），这段并存只存在于分支，最后一个 PR 把它拆干净并用守卫测试守住。
- **量**：约 3.5 万行非测试代码的新增和修改，删掉约 2 万行。关键路径是实时编辑那 6 个 PR。
- **要你定的**只剩 3 件（第四节末尾）。

文中用到的词：

- **层**：一个父块的全部直接子块。空间的顶层块是「父块为空间」的那一层。
- **提交、序号**：每次写入是一个空间里的一次提交，序号在空间内从 1 递增。
- **版本**：一个块每改一次留一行，带「从哪个序号到哪个序号有效」。
- **位置表**：每个块「在哪个父块下、排第几」的有效区间。**变动表**：每次提交把被改的块的每个祖先记一行。两张都是从版本表派生的。
- **历史起点**：一个空间里历史开始保留的序号（转换那一刻）。
- **森林**：浏览器里一棵树当前加载的所有层，可以跨几个空间。
- **收尾**：删除或恢复大子树之后，后台分批更新后代的「已删除」标记、搜索索引、别名、链接、任务认领。

## 一、目标设计（要求 B）

### 1. 数据模型

**什么是事实，什么是派生**

- 事实只有三样：`outline_blocks`（每块的当前状态）、`outline_block_versions`（只追加的版本，仍带父块和排序键）、`outline_commits`。
- 派生、可随时从版本表重算：位置表 `outline_block_edges`、变动表 `outline_subtree_changes`、块上的 `in_process`（是不是过程）和 `deleted`（是不是已不在活着的树里）。
- 表、列、索引的完整清单在附录 B。两种存储同一套列和主键。

**兄弟顺序**

- 不变：分数排序键 `order_key`，按字节序；PostgreSQL 上声明 `COLLATE "C"`。顶层块在块表里 `parent_id` 为空，在位置表里父键填空间 id，于是空间就是树根，顶层块不再特殊。

**位置区间**

- 位置表只在创建、移动、换顺序、删除、恢复时写一行；改字、改任务不写。「X 的子块在时刻 T 是哪些」是位置表上按父键的一次查找。
- 位置单独成表而不是给版本表加父块索引的原因（研究实测）：改字也产生版本行，10,000 块的页上取前 50 个子块，父块索引要 7.3 ms，位置表 0.6 ms。

**变动标记**

- 一次提交里每个被改的块，它改动前、改动后的每个祖先各记一行（同一提交内去重）。保证：某个块在 (T1, T2] 里既没有自己的版本也没有变动行，它这棵子树在两个时刻完全一样。
- 用处三个：任意块的时间线；比较时跳过没变的子树；订阅「这个块下面有没有变」。
- 实测每次普通提交多写 2.7 行、多花 0.05 ms（0.105 → 0.15 ms）；全部提交平均 5.4–6.7 行。

**按祖先删除**（你默认采纳的第 9 条）

- 删除一个块：给它自己写一行墓碑版本，关掉它的位置。它下面的一切立刻从树上、从时间机器里消失；后代不写版本。
- 后代的 `deleted` 标记、搜索索引、别名、链接、任务认领、提问，由同一个「收尾」函数处理：提交里先做一部分（计入每次提交 2000 行的预算），剩下的进 `outline_detached` 队列由后台任务分批做，每个事务不超过 2000 行，有游标，重启后接着做。小子树在提交里就做完了，大子树几秒内做完；只有这一套做法，没有两种删除。
- 收尾没做完时，凡是从索引直接拿结果的读取（搜索、任务列表、续跑候选、提问、别名查找、反链、待确认）都对结果多查一步「它的祖先是不是在待收尾的根下面」。一个空间没有待收尾的根时这一步不发生。
- 恢复：重新打开根的位置、写一行恢复版本，整棵原样回来；后代的标记由同一个收尾函数反向补。恢复时别名已被别的活块占用的，按现有规则丢掉别名，由收尾写成一次普通的系统提交。
- 「活着」的定义因此变成：顺着未关闭的位置能走到空间。块表的 `deleted` 是它的缓存。

**限额和来源**

| 限额 | 值 | 来自哪里 |
|---|---|---|
| 一棵树里放进编辑器的块 | 2,000，超了自动把最久没碰的展开处变回只读 | 实测输入延迟和编辑器里的块数成正比：2,000 块 12–14 ms，5,000 块 28 ms，10,000 块 57 ms；D57 第 7 条 |
| 一个浏览器标签页实时加载的块 | 20,000 | 按机制定的，没有按真实分布测 |
| 一层的子块数 | 存储上限 10,000（现有）；能就地编辑的层 2,000 | 兄弟要排序；一层要么整层在编辑器里要么不在（待定问题 3） |
| 深度 | 1,000（现有） | 查环、记变动行都沿祖先走 |
| 一次提交写的行 | 2,000（现有；变动行也计入） | 写入是主线程上的一个同步事务 |
| 一次读取 | 默认 800 块，最多 2,000 块 / 256 KiB（现有） | 浏览器排版和响应大小 |
| 只读树里画出来的行 | 3,000，超了收起最久没碰的展开处 | 现在是 12 页 × 200 块；只读行的延迟没有测，随 F1 的性能测试定 |
| 一个 socket 的实时空间数 | 16 | 取代「8 页」 |
| 一个空间同时的编辑者 / 旁观者 | 50 / 100，暂定 | 没有测；L2 的压测定 |
| 全进程已加载的块 | 200,000 | 实测 10 万块的结构副本约 19 MB |
| 订阅的块 | 每个 socket 256 个 | 取代「16 页」 |
| 未决的待确认改动 | 每个空间 500（现有的扫描上限） | 取代「每页 100」 |
| 折叠记号 | 每人 20,000 行，最久没写的先丢 | 取代「每页 2,000 × 每人 500 页」 |
| 跨空间「复制到这里」 | 199 块 / 120 KiB（现有交出任务的上限） | 一次事务的大小 |

移动没有块数上限：移动任意大的子树只写 1 行版本（实测共 6 行、0.2–0.7 ms，和子树大小无关；现在的写法搬 2 万块要 2–6.5 秒）。

### 2. 写入路径和必须成立的事

写入仍是唯一入口 `writeOutline`：先规划（只读需要的行），再在一个同步事务里认领序号并写入，别人抢先提交了就重新规划。每次提交之后成立：

1. 每个块恰好一个未关闭的版本，当前行等于它（现有不变式，保留）。
2. 每个块在任一序号上至多一条有效位置；活块未关闭的那条位置等于它当前行的父块和排序键。
3. 位置表和变动表只凭「历史起点之后」的版本就能重算出同样的结果。重算是修复手段，做成一个管理动作。
4. 一次提交改了块 b，b 改动前后的每个祖先都有一行变动。
5. 活着的兄弟排序键互不相同；不成环；深度不超过上限（现有）。
6. 别名在空间的活块里唯一；短 id 在空间里永远唯一（现有）。
7. 新表的行和版本行在同一个事务里写。
8. 删掉的东西：「活块的 `page_id` 等于顶层祖先」这条不变式、换页时给每个后代写版本、删除时给每个后代写墓碑、「只改了页」的变化标记、跨页 2000 行的拒绝、锁定任务换页时待确认改动跟着走（`checkRepage`、`planPending` 里的 `repage`）。

保留不动的：任务认领与租约、锁定和待确认的分类、三方合并、补偿提交、提问的派生、`in_process` 的维护方式（超过行数预算就标记空间、后台重建，读的人在此期间从树上现算）。

保留别名 `tasks`、`behavior`：它们是带别名的块，系统建在顶层。「代理不能移动、删除、改名任务清单块」「代理只能凭用户当轮授权写行为边界」这两条规则原样保留，判断从「在不在这一页」改成「祖先里有没有那个块」（沿祖先走，有上限）。人把它们拖到别的块下面，规则照样成立。

### 3. 读取

**当前状态**

- 按父块读一层：块表现有的 `(space_id, parent_id, order_key)` 索引。
- 按预算读一屏：从根开始广度优先，到预算为止；`fold=default` 时只往「默认展开或读者自己展开」的块下面走，收起的块只读预览行需要的那一个子块和直接子块数。
- 实测（100 万块的空间）：前 800 块 3–8.5 ms，子树是 2 千块还是 2 万块都一样。整棵读完比现在慢约 3 倍（2,000 块 2.9 → 8.5 ms），所以不再有「整页读结构」这种读法，全部按预算。

**某时刻**

- 同一个接口多一个序号参数：位置表按父键取那一刻的子块，再按块取那一刻的版本。
- 实测：50 块的可见范围 0.3–0.7 ms（现在要先读整页：2,000 块的页 25 ms，10,000 块的页 93 ms）；一屏 800 块带内容 6–12 ms，和子树大小无关。
- 单独按 id 读一个块的某时刻，要沿那一刻的位置往上走到空间，确认它当时在树里。
- 序号早于历史起点的读取直接回答「历史从某日开始」。

**子树下的统计**（未答提问、进行中的任务、待确认、锁）

- 一律「先从空间的部分索引拿候选，再逐个往上确认在不在这棵子树里」，候选最多 500 个，超了标「至少」。这些候选本来就少（一个空间里未答的提问、进行中的任务），所以任何收起的行都能显示它藏着几件事，不用读它下面的内容。
- 研究实测的是「走一遍子树」（2,000 块 4.7 ms，1 万块 42 ms，10 万块 428 ms），所以大子树不能走一遍。候选优先的做法**没有测**，由 H2 的基准测试定。

**预算和线程**

- 一层、一屏都是「小、有索引、有上限」，留在主线程。超过 2,000 行的读取（整棵导出、大子树比较）走现有的读线程池；读线程不可用就明确失败，不回主线程。

**查询计划**

- 研究里 SQLite 有一次把递归查询的连接顺序反过来，慢了 10–20 倍。写法钉住顺序（SQLite 用 `CROSS JOIN`，PostgreSQL 用 `LATERAL`），并有检查查询计划的守卫测试，两种存储各一份。

### 4. 任意块上的历史功能

- **时间线**：变动表按（祖先, 序号）倒序，加这个块自己的版本，归并去重。实测 0.01–0.02 ms。空间的时间线就是提交表。
- **拖动时间轴**：相邻提交只读这次提交写的版本（0.02 ms），只应用到已展开的层；跳得远就重读可见范围。
- **比较两个时刻**：从根往下，只进入有变动行的子块。实测相隔 1000 次提交：2,000 块 1.7–3.8 ms，1 万块 15 ms；10 万块以上改用「取这段提交写的版本逐个往上找」（约 50 ms）。计划的 diff 改用同一套。
- **恢复到某时刻**：比较得到差异，生成反向操作，走普通写入的补偿模式，是一次新提交，不改写历史；超过 2,000 行就分成几次提交。具体恢复哪些见待定问题 2。写入部分**没有测**。
- **撤销一次提交**：规则不变。历史起点之前的提交只作出处显示，不能撤销。
- **每块历史、出处**：不变。

### 5. 实时协议

把两份研究合成一套，冲突这样解决：

| 冲突 | 实时研究的假设 | 历史研究的说法 | 定成 |
|---|---|---|---|
| 加载单位 | 顶层块整块进出 | 按父块整层进出 | **按层**：客户端要么有某个父块的全部活子块，要么没有 |
| 历史 | 不改，`page_id` 留着 | 去掉 `page_id` | 去掉；会话把外部提交推回时按「父块在不在已加载的层里」判断移入移出 |
| 跨页移动 2,000 块、顶层块 10,000 块两条上限 | 保留 | 不需要 | 没有 |
| 移进来的子树 | 整棵带上（所以要 2,000 行上限） | 只带这一块和「下面还有多少」 | 只带这一块；下面的层等读者展开再加载 |
| 折叠状态 | 仍按顶层块存，移动时客户端搬 | 改成按块 | 按块存，移动不用管 |
| 撤销删除 | 协议里加「恢复这次事务删掉的子树」 | 恢复只要重新打开根 | 一个「恢复这个块」的操作，服务端重开根的位置 |
| 只读的树 | HTTP 读 + 页订阅 | — | HTTP 按层读 + 按块订阅 |
| 实时日志表 | 按（空间, 轮次, 序号）新表，旧表留一个版本 | — | 新表；旧表不留（见第二节） |

定下来的协议（二进制帧，仍走 `/ws/narrator`）：

- **会话按空间**：`join` 的对象是空间，按权限是编辑者或旁观者。会话不跨空间；权限按空间查，变化时逐个参与者重查（失去读就结束这个空间的会话，失去写就变旁观）。
- **`watch` 按父块**：增减要加载的层，一帧可列多个。回答是每层一帧快照：结构行，加每块的文字（没人编辑的发纯文本，有人编辑的发那一块的文档状态）。
- **文字每块一份文档**，有人编辑时才建。一份文档不能只同步其中几块（原型证实），每块一份时块搬到哪里文字都不用动。一个 `Y.UndoManager` 管不了两份文档（原型证实），所以每块一个撤销器，由统一的栈记「这一步用哪几块的撤销器」（原型：建 300 个 0.5 ms，按顺序撤 2,000 步 22.6 ms）。
- **结构事务**：由服务端在空间通道里排序、对照镜像检查、经 `writeOutline` 写成一次提交、再按规范形式广播。移动的新父可以是任何已加载的块，也可以为空（顶层）。一个操作发不发给某人，只看它涉及的父块在不在那人已加载的层里：两边都在是移动，只有来源在是移走，只有目标在是移来。两人同时移动成环，后到的被拒，客户端回滚并重放它后面的改动。
- **代理的提交**：流程不变（先占空间通道，把没提交的字提交，写入，再推回会话）。代理搬块时会话收到的是移动，那一块的文字文档原样保留。
- **在场**：参与者按空间；光标只发给加载了那一层的人；代理的在场照旧由服务端代发。
- **续连**：结构重发（有界且小），文字只对客户端有未确认输入的块做差分。
- **崩溃恢复**：`outline_live_log` 按（空间, 轮次, 序号）存，行里带块 id；启动时回放成提交。

这套设计依赖但**没有测**的：真编辑器里「文字文档晚建」不引起重做反转（原型只在 Yjs 层面 300 轮收敛）；一个空间一条通道在几十人同时改时的吞吐；`LiveSpace` 的真实内存。分别由 L1 的随机收敛测试、L2 的压测定。

### 6. 客户端

**一个组件，两种模式**

- 「森林」组件画一棵树：空间行、分组行和块。数据是按父块存的层。
- **读模式**：HTTP 按层读，加按块订阅（服务端在提交后告诉订阅者「这个块下面变了」，客户端重读受影响的层）。时间机器（看某时刻）只有读模式。
- **编辑模式**：同一个组件，数据换成每个空间一个实时会话，展开的块放进一个 ProseMirror 编辑文档。
- **聚焦视图**：只有一个根的同一个组件。思维导图是聚焦视图的另一种画法，共用同一个编辑面。

**进入和离开编辑**（D57 第 5 条）

- 进入：双击文字、点一直可见的「编辑」、或按 F2。之后这棵树里展开的、有写权限的内容都能改；只读的空间照常显示，行上有只读标记（图标，不是文字符号），光标可以经过、可以选中复制。
- 离开：点「完成」、连按两次 Esc、或 2 分钟没操作且没有未送达的字。
- 手机（窄屏）：树里不就地编辑，在聚焦视图里编辑（第 8 条）。

**一个编辑文档盖住展开的森林**

- 只把展开的块放进编辑器。现在收起的块的子块在文档里、用 CSS 藏着；改成不在文档里，预览行和计数从层数据算。折叠保护和输入法的规则不变，实现从「显隐」改成「放进/拿出文档」。实测 10,000 块时 63.6% 的时间是浏览器自己的排版绘制，全部收起但仍在页面里只省一半，所以要拿出去。拿出去之后的实际延迟**没有测**，由 L4 的性能测试定。
- 空间行、分组行作为不可编辑的行放进同一个文档，选区和拖动才能连续。
- 一个撤销栈：按读者自己做的先后顺序撤，不管落在哪个空间；结构用逆操作，文字用那一块的撤销器。离开编辑模式后栈清空，之后要回退用时间轴。
- 选区跨两个空间时删除：拆成每个空间一条事务，不是原子的，一条被拒只回滚那个空间。
- 拖动：同一空间里任意移动，包括拖成顶层块、把顶层块拖到别的块下面，都是一次移动、一次提交。拖到另一个空间时只提供「复制到这里」（第 6 条）：原处保留，复制的规则沿用现有「交出任务」的做法（进行中的任务复制成待办、不带认领、提问复制成普通块、别名和锁不带、第一个子块写明出处），目标空间比来源更公开时在确认里说明谁会看到。

**预算和自动降级**（第 7 条）

- 编辑器里超过 2,000 块时，最久没碰的展开处自动变回只读，不弹提示。光标或选区所在的地方、正在用输入法组字的块、有未确认文字的块不降级。被降级的地方再点一下就回到可编辑。

**打过的字不会无声丢失**

- 要么被确认，要么出现在「未保存文字」里。存放从按页改成按块，提示出现在那一块所在的位置。

### 7. 地址和导航

- 地址形状不变：`/outline`（整棵树）、`/outline/<空间>`（以空间为根的树）、`/outline/<空间>/<块>`（聚焦）、`/outline/ref?…`（按引用或提交解析）。它们本来就不带「页」。
- 空间的落地页：现在是一张页的列表；改成以这个空间为根的树，顶层块默认收起成一行一个，看上去和现在的列表一样，但可以就地展开。
- 按提交解析：现在是「这次提交改的第一页」；改成这次提交改动的块的最近公共祖先（沿那一刻的位置往上走，有上限），找不到就是空间。
- 面包屑：祖先链，不再有「页」这一级。快速切换、最近访问：列的是块。搜索结果的路径是祖先标题，太长时中间省略。
- 浏览器里记的树展开状态（`page:<id>`）换成按块的键；旧的记录直接作废，树回到默认展开。

### 8. agent 的工具

- 参数和返回里不再有「页」。`OutlineRead` 不带地址时列出各空间和它们的顶层块；`key/` 列一个空间的顶层块；读任何块都是「它和它下面的内容，按预算」。`OutlineEdit` 的 `add: key/` 是「加顶层块」，`move … to: key/` 是「移到顶层」。
- 文案里的「task page」「behavior page」改成「任务清单（`session/tasks`、`project/tasks`）」「行为边界（`session/behavior`）」，地址不变，所以模型已经学会的用法不变。
- `OutlineSearch` 的结果路径是祖先标题。`Ask` 不涉及页，不变。
- 行为边界、当前任务、团队动态、任务开场说明这些注入里的「页」换成块；`docs/INJECTION.md` 同步改。

### 9. 权限

- 只到空间这一级，和现在一样；没有块级的收窄。查询先按可读空间在 SQL 里过滤再取前 N 条，不变。位置表和变动表里的 id 都属于一个空间。
- 实时会话不跨空间；跨空间的合成只发生在浏览器里。跨空间复制两边都查：读来源，写目标。
- 这套设计明确不解决「子树级权限」：那要逐条往上查祖先，不能在一条 SQL 里先过滤。

### 10. 主线程和 Worker

- 提交多写的位置行、变动行都是有索引的小插入，在同一个同步事务里。
- 收尾任务、派生表重建、转换都是分批的后台工作：每个事务不超过 2,000 行，事务之间让出，可取消，有进度。
- 实时会话的大块文字规范化继续在后台文字 Worker 上做；读线程、文字 Worker、导图测量 Worker 不可用时一律明确失败或显示占位，不回主线程（现有守卫测试 `tests/worker-main-thread-fallback.guard.test.ts` 继续守着）。
- WebSocket：广播 50 ms 合并，每个参与者排队的字节有上限，超了断开重连；快照按层分帧。

### 11. PostgreSQL

- 同样的表、列、主键；`order_key` 用 `COLLATE "C"`；按时刻读用 `LATERAL`。
- 代价（研究实测，10 万块）：历史占用增加约 49%（SQLite 约 12%），主要是变动表每行约 105 字节。
- 实时会话是进程内状态，多进程部署下实时编辑只能单进程，这一点不变。
- PostgreSQL 上的移动、比较、100 万块规模**没有测**，由 H1、H2 的两种存储契约测试和基准补上。

### 12. 和需求的对照

- R4（层级不限）、R9（多人实时）、R10（一个编辑器不是每块一个）、R28（大纲和导图、快速聚焦）：做法更贴近原意。
- R7（时间轴）：从「页的时间轴」变成任意块的时间轴，另加比较和恢复。
- R5、R6（嵌入、拼接视图就地编辑）：以后做时，一处嵌入就是森林里多一个根，不再需要「同时加入另一页的会话」。
- R26、R27（每层恰好密度、过程在另一维）：按预算逐层展开、事实视图、「进行中」标记都不变，只是不再按页裁。
- 设计文档里要改的条目：§2.1「页是顶层的块」、§2.5 按页读历史、§6.2–§6.7 按页的会话、§7.1 表、§7.2「单页块数」等上限，D6（按页建实时会话）。

## 二、数据迁移（要求 C）

### 1. 结构变更

- 每种存储**一份**由生成器产出的迁移：SQLite 走 `schema.ts` → `bun run db:generate`；PostgreSQL 走 `bun scripts/generate-postgres-schema.ts` → `bun run db:generate:pg --name outline_pageless` → `bun run db:check:pg`，并更新 `scripts/lib/__tests__/check-postgres-schema-parity.test.ts` 里的表数和列数。不手改 `drizzle/`、`drizzle-postgres/` 下任何文件。
- 集成分支上中途会生成过几份迁移（测试是回放迁移文件建库的）。最后一个 PR 把这两个目录还原成主干的样子，再各生成一次，所以合进主干的只有一份。

### 2. 转换保留什么、丢什么

| 东西 | 怎么办 |
|---|---|
| 活着的块：文字、父子结构、顺序、短 id、别名、任务、提问、作者 | 原样保留，id 不变 |
| 每个活块的**当前版本**和产生它的那次提交 | 保留。所以侧栏里「最后是谁、哪个会话、什么时候改的」还在；序号不重排，所有记着版本序号的地方不用改 |
| 已关闭的旧版本 | 删 |
| 没有任何保留版本引用的旧提交 | 删 |
| 已删除的块（连同它们的版本、链接、认领、提问） | 删。以前删掉的东西不能再恢复 |
| 链接、反链 | 当前有效的保留，已关闭的删 |
| 任务认领和租约、领取代数 | 保留 |
| 提问和它的投递状态 | 保留 |
| 未决的待确认改动 | 保留；其中「提出之后目标块又被改过」的那些，合并要用的基线版本已经删了，转换时把它们标成撤回并写明原因（便宜的做法；这种行通常没有或只有几条） |
| 折叠状态、导图方向 | 保留：每页一行的 id 数组展开成每块一行 |
| 位置表 | 为每个活块建一条，从历史起点开始有效 |
| 变动表 | 空 |
| 历史起点 | 每个空间记下转换时的最后一个序号 |
| 汇报（`outline_digests`） | 删。它是派生数据，里面记的旧序号指向已删的提交；汇报任务从历史起点接着做 |
| 浏览器里的树展开状态 | 作废，回到默认 |

转换后，序号早于历史起点的时间轴位置、`/outline/ref?…commit=` 旧链接打开时显示「这次提交在历史开始保留之前」，并带到那个块现在的位置。

没有采用的做法：给每个空间写一个「迁移」提交、所有块的版本从它开始。那样要改写每块的版本序号和所有记着序号的地方（待确认的基线、看板的「新完成」、汇报的范围），还丢掉每块最后一次改动的出处；现在的做法只做删除，更少也更安全。

### 3. 转换怎么跑

启动时数据库的步骤是固定的：迁移 → 补列 → 数据回填 → 建搜索索引。转换分两段插进去：

1. **迁移之前**（新加的一步，只在检测到旧结构时做）：
   - 检查 `outline_live_updates` 是空的。它存的是没提交完的实时输入，正常停机时为空；不为空说明上次是崩溃退出，新版本里没有旧的回放器，所以这时停止启动并提示「先用旧版本启动一次再停机」。
   - 把所有 `outline_*` 表拷到 `~/.narrafork/backups/outline-before-pageless-<日期>.db`（一个单独的 SQLite 文件，逐表拷贝，核对行数）。拷不成就不升级。
2. **迁移之后、建搜索索引之前**（现有的数据回填位置，`server/db/data-backfills.ts`）：一个空间一个空间地转换，每个事务不超过 2,000 行，事务之间让出；每个空间做完就写下它的历史起点，中途停了下次接着做，重复跑不会多做。折叠状态从上一步的拷贝文件里读（迁移已经把旧表改掉了）。

- 这一切发生在服务开始接受请求之前，不占请求路径，和现有迁移、回填同一个位置；转换期间启动状态页显示进度。耗时和大纲的大小成正比，**没有测**；每个试用点在你数据的副本上演练时打印耗时。
- PostgreSQL：转换写成这份未发布迁移里的自定义 SQL（规则允许），做同样的删除和建位置行；折叠状态在 PostgreSQL 上不搬（重置）；备份由运维自己做，文档里写明。

### 4. 对你这一个真实用户怎样才安全

- 升级前自动留下那份拷贝文件。它是完整的旧大纲（包括全部旧历史），也是「万一要回去」的唯一依据：回去需要旧版本的程序加人工把表导回，计划里不做自动回退。
- 我不删除任何数据库文件。拷贝文件留多久由你决定，程序不会自动清。
- 「黄金升级测试」从第一个 PR 起就在：拿一个按主干结构建的、带样例数据的库，跑迁移和转换，断言活块逐块相同、位置表和按版本重放的结果一致、被丢的东西确实丢了。它始终从**主干的结构**出发，所以最终那一份迁移是被它验证过的。
- 每个试用点都在你数据目录的副本上跑（`NARRAFORK_HOME` 指向副本），从不碰真库。

### 5. 引用大纲块的其他功能

| 功能 | 影响 |
|---|---|
| 会话的任务后端（`narrators.task_backend`） | 不变 |
| spec 导入状态（`outline_spec_imports`） | `task_page_id` 改名 `task_block_id`，`pages` 改名 `notes`；转换时按别名 `tasks` 重新填一次，所以不依赖生成器怎么处理改名。「一个文件一页」变成「一个文件一个顶层块」，短 id 的推导不变，所以重复导入仍然幂等；「块太多拆成几页」的逻辑删掉 |
| 丢失内容的发现（`outline_spec_loss_findings.block_id`） | id 不变。它指向的块如果早已被删，转换后是「行不存在」而不是「标着已删除」；现有「块被删后重新挂上」的路径要对这种情况加一个测试 |
| 任务认领 | 活任务的保留；已删任务的随块删掉 |
| 插件的任务命令和旧 spec 兼容命令 | 行为不变；`tasks_read` 的游标内部改成按文档顺序的路径（对插件是不透明的串）；返回里叫 `page…` 的字段见第五节 |
| 工作区布局里的大纲面板、最近标签、聊天里的大纲链接、工具卡片里的地址 | 记的都是空间和块的 id 或地址，不变 |
| 铃铛里的待处理（待确认、提问） | 不变；汇报条目随汇报重做 |
| 数据导入导出 | 大纲的表本来就不在导出清单里，不用动；`clearData` 里按表名清 spec 导入状态的语句不受改名影响 |

## 三、施工顺序（要求 D）

### 1. 两种做法，建议第一种

| | **集成分支，最后合一次（建议）** | 在主干上按固定顺序就地替换 |
|---|---|---|
| 主干和你的数据 | 只变一次；转换在最后，演练过多次 | 第一个 PR 就转换真库，之后几周大纲是残缺的 |
| 能不能评审和验证 | 16 个 PR，每个都小，现有 220 多个大纲测试文件一路当回归线 | 一样小，但很多 PR 合进去时大纲的某些功能暂时没有，测试只能先删后补 |
| 中间状态 | 分支上有一段「`page_id` 还在维护、新表也在写」；主干上没有 | 没有并存的代码，但产品本身处在中间状态 |
| 出了问题 | 分支不合就是了，主干无事 | 真库已经转换，回不去 |
| 代价 | 分支要定期跟主干同步；迁移文件每次同步后重新生成 | — |

为什么分支上「先加后拆」而不是「先拆后建」：去掉 `page_id` 会同时打断 40 多个服务端文件和整个前端，一个 PR 装不下；先把新表和新读法加进来，消费者一组一组换过去，最后拆，这样每个 PR 都不用写任何用完就扔的适配代码，分支始终是能用的完整大纲。它和两份研究里作废的那套安排的区别：没有补建（位置行由转换一次建好）、没有新旧结果对照、没有开关、没有回退安排、没有哪个读取同时保留新旧两条路——每个消费者在自己的 PR 里整个换掉。

分支上的规矩：

- 分支期间主干上不改大纲相关的文件（修 bug 除外，修了同步到分支）。
- `schema.ts` 和两个迁移目录只由「存储」这条线改，别的线提需求。
- 最后一个 PR 之前有一个守卫测试列出还在用 `page` 的文件清单，清单只许变短；最后一个 PR 把它换成「大纲代码里不许出现页」的守卫（允许分页意义上的 `nextPage` 之类）。分支合进主干的条件是这份清单为空。

## 四、风险和待定（要求 E）

### 风险，从大到小

1. **按祖先删除改变了「活着」的定义**（X1）。所有从索引直接拿结果的地方都要在收尾期间多查一步；进行中的任务随子树被删时认领的释放、恢复后任务回到谁手里、别名冲突，都要重新过一遍。这是改动面最大的一步，放在倒数第二。
2. **文字按块之后的撤销和重做**（L1）。原型只在 Yjs 层面验证过，不是真编辑器。它在关键路径的第一步，所以最先知道结果。
3. **只把展开的块放进编辑器，再把几个空间放进一个文档**（L4、L5）。折叠保护和输入法的规则当初花了很多轮才稳定；2,000 块时按键到下一帧中位 12–14 ms，余量不大；真输入法和手机只能人工测。
4. **转换是单向的**。靠转换前的拷贝、黄金升级测试和四次副本演练兜住；崩溃后没回放完的实时输入靠「启动前检查日志表为空」兜住。
5. **派生表和版本表对不上，历史悄悄读错**。产品里不再有旧读法可对照，所以靠对照器测试、性质测试，以及「从版本重建派生表」这个修复动作。
6. **查询计划被换**。见上表。
7. **长期分支**：16 个 PR 期间主干在动；迁移文件每次同步后要重新生成；四条线共用的几个文件容易冲突。
8. **一个空间一条通道成为热点**。今天也是按空间排队，但今天一页最多 20 人；按空间之后的人数上限没有数据。
9. **插件**：源码不在仓库里，`tasks_read` 等返回里带 `page` 字样的字段改不改只能按宿主一侧的契约测试判断。
10. **提示词改字**：工具说明里「page」换成「top-level block」「task list」，模型行为可能有细微变化；地址和用法没变，风险小。

### 还要你定的 3 件事

**问题 1　聚焦视图要不要也先「进入编辑」**

背景：你定了树里要一次明确的动作才进入编辑。聚焦视图（单独打开一个块）今天一打开就是可编辑的，没有写权限的人打开它也能逐字看到别人正在打的字。做完之后树和聚焦视图是同一个组件，要定聚焦视图用哪种规矩。进入编辑意味着为这个空间开实时会话，别人会看到你「在编辑」。

例子：你从搜索结果点开一个任务块，想改里面的一个错字。

- **A（建议）**：和树里一样，先读模式，双击文字（同时落下光标）、点「编辑」或按 F2 才进入；2 分钟不动自动退出。只来看的人不占实时会话，也不显示成在编辑；没有写权限的人看到的更新是别人每次提交之后的（停手约 2 秒），不是逐字的。手机上「编辑」按钮放在显眼处。
- B：聚焦视图一打开就是编辑模式（现状），只有树里需要进入。改错字少一步；但每个打开聚焦视图的人都占会话、显示成在编辑，两处规矩不一样。
- C：A，另外让没有写权限的人可以点「实时跟随」以旁观者身份加入，逐字看别人输入。多一个按钮和一种状态。

**问题 2　「恢复到某时刻」到底恢复哪些东西**

背景：做完之后任何块都可以「恢复成某个时刻的样子」，它是一次新的提交，可以再撤销。那个时刻之后，这棵子树里可能新加了块、移走了块、移进来了块，要定这些怎么算。

例子：周一「设计」下面有 30 块。周二有人加了 5 块、把其中 3 块拖到了「归档」下面、又从别处拖进来 2 块。周三你把「设计」恢复到周一。

- **A（建议）**：恢复成周一的样子，但只动当时就在这下面的东西：周二新加的 5 块删掉，拖进来的 2 块移回它们原来的地方，文字和顺序改回周一；拖走的那 3 块**不拉回来**，在结果里列出「这 3 块现在在归档下面」，可以一键移回。确认前先给你看要改的清单。
- B：完全恢复：拖走的 3 块也拉回来。最符合「恢复」的字面意思；但会改动你没在看的地方（「归档」下面少了 3 块）。
- C：只恢复还在这下面、周一就存在的块的文字和顺序；新加的不删，拖进来的不动。最保守，但恢复完并不等于周一的样子。

**问题 3　一个块的直接子块超过 2,000 个时怎么办**

背景：编辑时，一层要么整层在编辑器里，要么不在（否则「插在第几个兄弟后面」对不上）。编辑器的预算是 2,000 块。所以直接子块超过 2,000 个的那一层放不进编辑器。存储允许一层最多 10,000 个。空间的顶层也是一层。

例子：一次导入在某个块下面平铺了 3,000 个子块。

- **A（建议）**：这一层只读，分批显示；每个子块可以单独聚焦进去编辑，agent 和导入照常能写这一层；行上说明「这一层有 3,000 个子块，不能就地编辑，可以分组后再编辑」。整理的指引本来就是一层不超过 15 个。
- B：协议支持一层只加载一个窗口，窗口里可编辑。没有这条限制；但协议和编辑器都要处理「看不见的兄弟」，是一块不小的新复杂度，放在关键路径上。
- C：把存储上限也降到 2,000，写入时就拒绝。规则最简单；但导入和 agent 的大批量写入会开始被拒。

## 五、没能确定的（要求 F）

- **你的真实数据有多大**：空间数、块数、版本数、树多深、有没有未决的待确认改动、实时日志表是不是空的。我没有读 `~/.narrafork`。转换耗时、变动表大小、20,000 和 200,000 这些上限都因此是按机制定的。
- **生成器会把这次变更写成什么 SQL**：drizzle-kit 0.31.10 对 SQLite 删非空列是 `ALTER TABLE … DROP COLUMN` 还是整表重建、改名时怎么提问，要到生成时才知道。转换程序设计成不依赖这一点。
- **位置表、变动表能不能建成 `WITHOUT ROWID`**：研究的大小数字（每行 67+59 和 34 字节）是按 `WITHOUT ROWID` 测的；drizzle-orm 0.45.2 的类型定义里没找到这个选项。建成普通表时的大小没有测。
- **PostgreSQL 上有没有带大纲数据的部署**；`db:generate:pg` 里写自定义转换 SQL 的具体步骤我只读了规则，没有走一遍。
- **仓库外的插件**是否依赖 `tasks_read` 等返回里带 `page` 的字段名（`pageId`、`onTasksPage`）和游标的形状。
- **汇报任务在某人没有任何旧汇报行时的行为**：只读了文件头的说明，没有跟到每个分支。
- **你平时是不是每天用产品里的大纲**：这决定长期分支期间主干上的大纲冻结对你有没有影响。

## 附录 C　提交之后通知什么
